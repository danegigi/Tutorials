Datastar combines reactive signals (client-side state in data-* attributes) with server-sent events (the server streams HTML fragments and signal updates back). It's a hypermedia framework like HTMX, but with a reactive front-end layer baked in — one small script, no build step.

Setup

<script type="module"
  src="https://cdn.jsdelivr.net/gh/starfederation/datastar@v1.0.0/bundles/datastar.js">
</script>

Signals and reactivity

Beginner Declare signals with data-signals, bind inputs with data-bind, and show reactive values with data-text. Everything updates automatically.

<div data-signals="{count: 0}">
  <button data-on:click="$count++">+</button>
  <span data-text="$count"></span>
  <button data-on:click="$count--">-</button>
</div>

<input data-bind:value="$name">
<p data-show="$name != ''">Hello, <span data-text="$name"></span></p>
Syntax matters (v1): use the colon form — data-on:click, data-bind:value, data-attr:disabled — not the hyphenated data-on-click. An unknown/malformed data-* attribute throws during Datastar init and halts processing of the entire page, silently killing all reactivity. Symptom: a button "does nothing" while the endpoint works fine via curl.

Server-sent events: the fragment model

Intermediate A data-on action can call the backend; the server responds with an SSE stream that merges HTML fragments into the page and patches signals:

<div data-signals="{q: ''}">
  <input data-bind:value="$q"
         data-on:input__debounce.300ms="@get('/search')">
  <ul id="results"></ul>
</div>
# Server (SSE) streams a fragment that merges into #results:
event: datastar-merge-fragments
data: fragments <ul id="results"><li>…</li></ul>

# …and can patch signals:
event: datastar-merge-signals
data: signals {count: 5}

Expressions must be single expressions

A recurring trap: a data-on:* handler body is wrapped as return (() => { YOUR_CODE })(), so a statement block like if(!confirm(x)){event.preventDefault()} produces invalid JS and throws at init — again halting all page reactivity. Handlers MUST be single expressions. Proven patterns:
<!-- confirm-then-post with the && short-circuit -->
<button data-on:click="confirm('Delete?') && @delete('/items/42')">Delete</button>

<!-- gate via a global helper returning a bool, comma operator runs both -->
<button data-on:click="window.ok($id) && (@post('/do'), close())">Go</button>

<!-- for a NATIVE form submit confirm, use plain HTML (not Datastar) -->
<form onsubmit="return confirm('Submit?')">…</form>

No client-side list rendering

Datastar has no client list-rendering (<template data-for> does not exist). Render repeated/dynamic rows server-side and stream them via SSE fragment merges. For a fixed small set of toggleable rows, pre-render a pool in HTML and show/hide with data-show="idx < $n".

Bound selects need a seeded signal

A data-bind on a <select> drives the value from the signal, not the option's selected attribute. If the signal disagrees with the current value (or the value isn't in the option list) the select renders blank. Fix: re-seed the signal on the fragment (data-signals:field="'value'") and always include the current value as an option.

Datastar vs HTMX

Both are hypermedia frameworks that swap server-rendered HTML. HTMX is attribute-driven requests with no client state model; Datastar adds reactive signals and leans on SSE for streaming updates. Choose Datastar when you want fine-grained client reactivity (live-bound inputs, computed UI) alongside server-rendered fragments; choose HTMX when request→swap is all you need.

Exercises

  • Build a counter and a live "Hello, {name}" using data-signals, data-bind, data-text, data-show.
  • Deliberately write data-on-click (hyphenated) and observe that it breaks ALL reactivity — then fix it to data-on:click.
  • Add a confirm-before-delete using the && single-expression pattern.

Mini-project: a reactive search with SSE

Build a debounced search box bound to a $q signal that calls @get('/search'); have the server stream a datastar-merge-fragments event replacing a results list rendered server-side. Add a confirm-gated delete on each row using a single-expression handler. You'll hit (and now avoid) the init-halting syntax traps above.
