Once you know ref, reactive, and computed, the next step is organising a real app: running effects at the right moment, extracting reusable logic, routing between pages, and sharing state cleanly. This lesson covers the Composition API patterns that hold a growing Vue 3 app together.

Lifecycle hooks

Intermediate In <script setup> you register lifecycle work with functions called during setup. The common three: onMounted (DOM is ready — fetch, measure, attach listeners), onUnmounted (tear down — the single most forgotten step), and onUpdated (after a reactive re-render flushed to the DOM).

<script setup>
import { ref, onMounted, onUnmounted, onUpdated } from "vue";

const width = ref(window.innerWidth);
const onResize = () => (width.value = window.innerWidth);

onMounted(() => {
  // DOM exists now — safe to read layout or attach listeners
  window.addEventListener("resize", onResize);
});

onUnmounted(() => {
  // ALWAYS mirror an addEventListener with a removeEventListener
  window.removeEventListener("resize", onResize);
});

onUpdated(() => {
  // Runs after every re-render — keep it cheap, never mutate state here
});
</script>

<template><p>Window is {{ width }}px wide</p></template>
Every subscription you create in onMounted must be cancelled in onUnmounted — event listeners, intervals, WebSockets, observers. Forgetting this is the classic Vue memory leak: navigate away and back a few times and you have five resize handlers firing at once.

watch vs watchEffect

Both run a side effect when reactive data changes. They differ in how you declare the dependencies.

watchwatchEffect
DependenciesExplicit — you name the sourceAutomatic — whatever it reads
Runs immediately?No (opt in with { immediate: true })Yes, once on setup
Gives old value?Yes — (newVal, oldVal)No
Best forReacting to a specific changeKeeping something in sync with several sources
 
<script setup>
import { ref, watch, watchEffect } from "vue";

const query = ref("");
const results = ref([]);

// watch: react to ONE source, with debounce + the previous value available
watch(query, (next, prev) => {
  console.log(`query changed from "${prev}" to "${next}"`);
});

// watchEffect: auto-tracks `query`; re-runs whenever it changes.
// The cleanup callback runs BEFORE the next run and on unmount —
// use it to abort the in-flight request so stale responses can't land.
watchEffect(async (onCleanup) => {
  const controller = new AbortController();
  onCleanup(() => controller.abort());
  if (!query.value) { results.value = []; return; }
  const res = await fetch(`/api/search?q=${query.value}`, { signal: controller.signal });
  results.value = await res.json();
});
</script>
Rule of thumb: reach for watchEffect when the effect simply reads some reactive values and you'd otherwise list them all by hand. Reach for watch when you need the old value, want to run only on change (not immediately), or are watching a single precise source.

Composables — reusable stateful logic

Advanced A composable is a plain function named useXxx that uses the Composition API internally and returns reactive state. It's how you extract and share logic without mixins or wrapper components. Each call gets its own isolated state.

// composables/useMouse.js
import { ref, onMounted, onUnmounted } from "vue";

export function useMouse() {
  const x = ref(0);
  const y = ref(0);
  const update = (e) => { x.value = e.pageX; y.value = e.pageY; };

  onMounted(() => window.addEventListener("mousemove", update));
  onUnmounted(() => window.removeEventListener("mousemove", update));

  return { x, y };               // caller gets live refs
}

A more realistic one — a reusable fetch with loading/error state and refetch:

// composables/useFetch.js
import { ref, watchEffect, toValue } from "vue";

// `url` may be a ref/getter — toValue() unwraps it, so the fetch
// re-runs automatically when the url changes.
export function useFetch(url) {
  const data = ref(null);
  const error = ref(null);
  const loading = ref(false);

  async function load() {
    loading.value = true;
    error.value = null;
    try {
      const res = await fetch(toValue(url));
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      data.value = await res.json();
    } catch (e) {
      error.value = e;
    } finally {
      loading.value = false;
    }
  }

  watchEffect(load);             // re-fetch whenever toValue(url) changes
  return { data, error, loading, refetch: load };
}
<script setup>
import { ref } from "vue";
import { useMouse } from "@/composables/useMouse";
import { useFetch } from "@/composables/useFetch";

const { x, y } = useMouse();
const id = ref(1);
// pass a getter so useFetch re-runs when `id` changes
const { data: user, loading, error, refetch } = useFetch(() => `/api/users/${id.value}`);
</script>

<template>
  <p>Mouse: {{ x }}, {{ y }}</p>
  <p v-if="loading">Loading…</p>
  <p v-else-if="error">Error: {{ error.message }}</p>
  <pre v-else>{{ user }}</pre>
  <button @click="id++">Next user</button>
  <button @click="refetch">Reload</button>
</template>
Composables are Vue's answer to React hooks. The naming convention useXxx is a signal to readers (and tooling) that the function uses reactive state and lifecycle, so it must be called synchronously inside setup — not inside a conditional or an async callback.

provide / inject

For passing data down a deep tree without threading props through every level, an ancestor provides a value and any descendant injects it. Provide a ref to keep it reactive.

// Ancestor (e.g. App.vue)
<script setup>
import { ref, provide } from "vue";
const theme = ref("dark");
provide("theme", theme);                 // descendants read it reactively
provide("toggleTheme", () => (theme.value = theme.value === "dark" ? "light" : "dark"));
</script>

// Deep descendant — no props threaded through the middle
<script setup>
import { inject } from "vue";
const theme = inject("theme");           // live ref
const toggle = inject("toggleTheme", () => {});  // 2nd arg = default fallback
</script>
Prefer a Symbol key over a string in a real app to avoid name collisions, and keep the right to mutate with the provider: expose an updater function (as above) rather than letting children write the injected ref directly, or the data flow becomes impossible to trace.

Vue Router

Intermediate The official router maps URLs to components. Define routes (with dynamic params and lazy loading), render the match with <RouterView>, and link with <RouterLink>.

// router/index.js
import { createRouter, createWebHistory } from "vue-router";

const routes = [
  { path: "/", component: () => import("@/views/Home.vue") },     // lazy-loaded chunk
  { path: "/users/:id", name: "user", component: () => import("@/views/User.vue"), props: true },
  { path: "/admin", component: () => import("@/views/Admin.vue"), meta: { requiresAuth: true } },
  { path: "/:pathMatch(.*)*", component: () => import("@/views/NotFound.vue") }, // 404
];

const router = createRouter({ history: createWebHistory(), routes });

// Global navigation guard — e.g. protect authenticated routes
router.beforeEach((to) => {
  const loggedIn = !!localStorage.getItem("token");
  if (to.meta.requiresAuth && !loggedIn) {
    return { path: "/login", query: { redirect: to.fullPath } };  // redirect
  }
});

export default router;
<!-- App.vue -->
<template>
  <nav>
    <RouterLink to="/">Home</RouterLink>
    <RouterLink :to="{ name: 'user', params: { id: 42 } }">User 42</RouterLink>
  </nav>
  <RouterView />        <!-- the matched component renders here -->
</template>

<!-- User.vue: read the dynamic param -->
<script setup>
import { useRoute } from "vue-router";
const route = useRoute();
// route.params.id — or declare `props: true` on the route and accept it as a prop
</script>
Lazy-loading routes with () => import(...) is the single biggest router performance win: each view becomes its own JS chunk fetched on demand, so the initial bundle only contains the first screen. <RouterLink> also sets the active class and handles the back/forward buttons for you — never build navigation with raw <a href> inside an SPA.

Pinia — the official store

Advanced Pinia is Vue's state-management library: a store has state (the data), getters (computed derivations), and actions (methods that mutate state, sync or async).

// stores/cart.js
import { defineStore } from "pinia";

export const useCartStore = defineStore("cart", {
  state: () => ({ items: [] }),
  getters: {
    count: (s) => s.items.reduce((n, i) => n + i.qty, 0),
    total: (s) => s.items.reduce((sum, i) => sum + i.price * i.qty, 0),
  },
  actions: {
    add(product) {
      const line = this.items.find((i) => i.id === product.id);
      line ? line.qty++ : this.items.push({ ...product, qty: 1 });
    },
    async checkout() {
      await fetch("/api/checkout", { method: "POST", body: JSON.stringify(this.items) });
      this.items = [];                         // mutate state directly — it's reactive
    },
  },
});
<script setup>
import { storeToRefs } from "pinia";
import { useCartStore } from "@/stores/cart";

const cart = useCartStore();
// Destructuring state/getters loses reactivity — use storeToRefs for those.
const { count, total } = storeToRefs(cart);
// Actions can be destructured directly (they're bound methods).
const { add, checkout } = cart;
</script>

<template>
  <button @click="add(product)">Add</button>
  <p>{{ count }} items — ${{ total }}</p>
</template>
Why Pinia over a bare reactive({}) object? You can share a global reactive object, but Pinia adds: devtools time-travel and inspection, SSR safety (no cross-request state leaks), hot-module-reload that preserves state, typed stores, and a clear state/getter/action structure the whole team recognises. A bare object has none of that and tends to grow into an untestable blob.

Async components & <Suspense>

<script setup>
import { defineAsyncComponent } from "vue";
// Code-split a heavy component; it loads only when rendered
const Chart = defineAsyncComponent(() => import("@/components/HeavyChart.vue"));
</script>

<template>
  <!-- Suspense shows a fallback while an async component (or a
       component with a top-level await in setup) is resolving -->
  <Suspense>
    <template #default><Chart /></template>
    <template #fallback><p>Loading chart…</p></template>
  </Suspense>
</template>

Performance

Vue's reactivity is cheap, but you can still do needless work. The main levers:

ToolUse when
v-onceContent renders once and never changes — skip it forever
v-memoA list row only needs re-render when specific values change
shallowRefA large object whose identity changes but whose deep fields you don't track (e.g. a chart instance)
computedA derived value read many times — caches until deps change
 
<!-- v-once: static block, never diffed again -->
<footer v-once>© 2026 Acme — all rights reserved</footer>

<!-- v-memo: this row skips re-render unless id or selected changes -->
<div v-for="item in list" :key="item.id" v-memo="[item.id, item.id === selectedId]">
  {{ item.name }}
</div>
import { shallowRef, computed } from "vue";
// Don't deep-track a huge structure you only ever replace wholesale:
const dataset = shallowRef(bigArray);     // reactivity on .value reassignment only
// Prefer computed (cached) over a method (re-runs every render):
const expensive = computed(() => list.value.filter(heavyPredicate));
computed vs method: a computed caches its result and only recomputes when a reactive dependency changes; a method called in the template ({{ compute() }}) runs on every render. For derived values, prefer computed — it's the difference between computing once and computing on every unrelated re-render.

Common mistakes

Side effects inside computed. A computed must be a pure derivation — no fetching, no mutating other state, no DOM writes. Side effects there run unpredictably (or get cached away) and corrupt the dependency graph. Put side effects in a watch/watchEffect or an action.

Forgetting to clean up. A listener, interval, or subscription created in onMounted (or a watchEffect) that isn't cancelled leaks on unmount and fires on a dead component.

Overusing watch where computed fits. If you're watching a value only to assign another value, that's a derived value — use computed. Reserve watch for genuine side effects (fetching, logging, imperative DOM work).

Reactivity loss. Destructuring a reactive object or a Pinia store breaks the reactive link — const { count } = store gives a plain number frozen in time. Use storeToRefs(store) for state/getters, or keep the store object and access store.count.

Exercises

  • Write a useLocalStorage(key, initial) composable that reads/writes localStorage and stays reactive across tabs (hint: a storage event listener cleaned up in onUnmounted).
  • Convert a component that uses watch to derive a value into one that uses computed, and explain why it's better.
  • Add a beforeEach navigation guard that blocks /admin unless a token exists, redirecting to /login?redirect=….
  • Build a Pinia store for a to-do list (state: todos; getters: remaining count; actions: add/toggle/clear-done) and wire it to two components.
  • Lazy-load a heavy component with defineAsyncComponent + <Suspense> and confirm in the Network tab that its chunk loads only when shown.

Mini-project: a small router + Pinia app

Build a two-page product browser. Route / lists products (fetched through a useFetch composable); route /products/:id shows one product, reading the dynamic param. A Pinia cart store holds line items with count/total getters and add/checkout actions; a header component shows the live cart badge via storeToRefs. Lazy-load both route views, protect a /checkout route with a beforeEach guard, and use computed (not a method) for the filtered list. The point is the architecture: URL in the router, shared state in Pinia, reusable fetching in a composable.
