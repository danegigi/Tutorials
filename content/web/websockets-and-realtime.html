HTTP request/response can't push: the server can only answer when asked. Real-time features — chat, live dashboards, notifications, collaborative editing — need the server to send data to the browser whenever it has some. This lesson covers the two tools for that, WebSockets and Server-Sent Events, when each fits, and the production concerns (reconnection, heartbeats, scaling) that tutorials usually skip.

Default to SSE when the client only needs to receive. It's plain HTTP (works through proxies/firewalls, no special infra), reconnects itself, and is simpler. Reach for WebSockets when the client must also send frequently and with low latency.

Server-Sent Events

// client
const es = new EventSource("/api/stream");
es.onmessage = (e) => console.log("tick:", e.data);
es.addEventListener("price", (e) => update(JSON.parse(e.data)));  // named event
es.onerror = () => { /* EventSource auto-reconnects; this just notifies */ };
// server (Bun.serve) — the wire format is dead simple text
return new Response(
  new ReadableStream({
    start(controller) {
      const send = (data, event) =>
        controller.enqueue(`${event ? `event: ${event}\n` : ""}data: ${data}\n\n`);
      const id = setInterval(() => send(new Date().toISOString()), 1000);
      // clean up when the client disconnects:
      // (store id; clear it on stream cancel)
    },
  }),
  { headers: { "Content-Type": "text/event-stream", "Cache-Control": "no-cache" } }
);
The SSE wire format is exact: each message is data: <payload>\n\n (blank line terminates). Miss the double newline and the browser buffers forever. The browser auto-reconnects and sends Last-Event-ID — honor it server-side to resume without gaps.

WebSockets

// client
const ws = new WebSocket(`wss://${location.host}/chat`);
ws.onopen = () => ws.send(JSON.stringify({ type: "join", room: "general" }));
ws.onmessage = (e) => render(JSON.parse(e.data));
ws.onclose = (e) => scheduleReconnect(e.code);   // YOU must reconnect
// server (Bun has first-class WS with pub/sub built in)
Bun.serve({
  fetch(req, server) {
    if (server.upgrade(req)) return;             // upgrade HTTP → WS
    return new Response("expected a websocket", { status: 426 });
  },
  websocket: {
    open(ws) { ws.subscribe("general"); },        // topic-based broadcast
    message(ws, msg) { ws.publish("general", msg); }, // send to everyone in the topic
    close(ws) { ws.unsubscribe("general"); },
  },
});

Reconnection: the thing tutorials skip

Advanced Networks drop. A WebSocket client MUST reconnect, and naively reconnecting in a tight loop hammers the server when it's already struggling. Use exponential backoff with jitter:

let delay = 1000;
function connect() {
  const ws = new WebSocket(url);
  ws.onopen = () => { delay = 1000; };            // reset on success
  ws.onclose = () => {
    const wait = Math.min(delay, 30000) * (0.5 + Math.random());  // cap + jitter
    setTimeout(connect, wait);
    delay *= 2;
  };
}
Jitter is not optional. If every client reconnects on the exact same backoff schedule after an outage, they all hit the recovering server simultaneously — a thundering herd that knocks it back down. Randomizing the delay spreads the reconnections out.

Heartbeats: detect dead connections

A TCP connection can be silently dead (a NAT timed out, Wi-Fi dropped) while both ends think it's open. A periodic ping/pong detects it: the client sends a ping every N seconds; if the server misses several, it closes the socket and frees resources. Without heartbeats you accumulate zombie connections.

Scaling across servers

One server holds its own connections in memory — fine until you run two. When a user on server A sends a message, users connected to server B must receive it. The standard fix is a pub/sub backplane (Redis pub/sub, NATS): each server publishes incoming messages to the backplane and forwards backplane messages to its local sockets. Also configure sticky sessions / proper WS support on your load balancer, since the connection is long-lived.

Security

  • Always wss:// (TLS) in production — ws:// is plaintext.
  • Authenticate on connect (a token in the upgrade request / first message) — the WS handshake isn't automatically authed.
  • Validate and rate-limit incoming messages; a socket is an open door for abuse.
  • Check the Origin header to prevent cross-site WebSocket hijacking.

Common mistakes

  • Reaching for WebSockets when SSE would do — if it's server→client only, SSE is simpler and auto-reconnects.
  • No reconnection logic on a WebSocket, or reconnecting with no backoff/jitter → thundering herd.
  • Malformed SSE frames (missing the blank line) so the browser never fires onmessage.
  • No heartbeat, so dead connections pile up and consume memory.
  • In-memory state with multiple servers and no pub/sub backplane — messages don't cross instances.
  • No auth/origin check on the upgrade, leaving the socket open to hijacking and abuse.

Exercises

  • Build an SSE endpoint that streams a server clock and consume it with EventSource; kill the server and watch the browser auto-reconnect.
  • Add a named SSE event (event: price) and handle it separately on the client.
  • Build a WebSocket echo server with Bun's pub/sub and a two-tab chat that broadcasts between them.
  • Add exponential-backoff-with-jitter reconnection to the WS client and simulate drops.
  • Add a ping/pong heartbeat and prove a silently-dropped connection is detected and cleaned up.
