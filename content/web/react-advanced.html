Once you know useState and useEffect, "advanced" React is mostly about three things: putting complex state in a reducer, sharing it through Context without re-rendering the world, and memoizing only where it actually earns its keep. The hooks below are the toolkit; knowing when not to use them matters just as much.

useReducer for complex state

Intermediate When state updates depend on the previous state, several fields change together, or the "next state" logic is branchy, a reducer is clearer than a pile of useState calls. The reducer is a pure function (state, action) => newState; the component only dispatches actions.

function cartReducer(state, action) {
  switch (action.type) {
    case "add": {
      const existing = state.items.find(i => i.id === action.item.id);
      const items = existing
        ? state.items.map(i => i.id === action.item.id ? { ...i, qty: i.qty + 1 } : i)
        : [...state.items, { ...action.item, qty: 1 }];
      return { ...state, items };
    }
    case "remove":
      return { ...state, items: state.items.filter(i => i.id !== action.id) };
    case "clear":
      return { ...state, items: [] };
    default:
      throw new Error(`unknown action: ${action.type}`);
  }
}

function Cart() {
  const [state, dispatch] = useReducer(cartReducer, { items: [] });
  const total = state.items.reduce((s, i) => s + i.price * i.qty, 0);
  return (
    <>
      {state.items.map(i => (
        <li key={i.id}>{i.name} ×{i.qty}
          <button onClick={() => dispatch({ type: "remove", id: i.id })}>✕</button>
        </li>
      ))}
      <p>Total: ${total.toFixed(2)}</p>
    </>
  );
}
PreferWhen
useStateOne or two independent values; updates are simple assignments.
useReducerMany fields that change together, next-state depends on prev-state, or the transition logic is worth testing in isolation.
A reducer is a plain, pure function — you can unit-test it with no React at all: expect(cartReducer(state, {type:"add", item})).toEqual(...). That testability is a big reason to reach for it.

Context API: sharing state without prop-drilling

Passing a value through five layers of components as props ("prop-drilling") is tedious and brittle. Context lets a far-away descendant read a value directly.

import { createContext, useContext, useReducer } from "react";

const CartContext = createContext(null);

export function CartProvider({ children }) {
  const [state, dispatch] = useReducer(cartReducer, { items: [] });
  // value is an object — see the re-render pitfall below about stabilizing it
  return (
    <CartContext.Provider value={{ state, dispatch }}>
      {children}
    </CartContext.Provider>
  );
}

// A custom hook that also guards against using it outside the provider:
export function useCart() {
  const ctx = useContext(CartContext);
  if (!ctx) throw new Error("useCart must be used inside <CartProvider>");
  return ctx;
}

Any component inside <CartProvider> now calls const { state, dispatch } = useCart() — no props threaded through the tree. Combining Context + useReducer like this is the idiomatic way to hold app-wide state (auth, theme, cart) without a third-party library.

The Context re-render pitfall: every consumer re-renders whenever the Provider's value changes by identity. Writing value={{ state, dispatch }} creates a brand-new object on every Provider render, so all consumers re-render even if they only use dispatch (which never changes). Fixes: wrap the value in useMemo, or split into two contexts — a stable dispatch context and a changing state context — so dispatch-only components don't re-render on state changes.

Performance: useMemo, useCallback, React.memo

Advanced These three memoize different things. They trade memory + a dependency comparison for skipped work — useful only when the skipped work is actually expensive or breaks referential equality downstream.

// useMemo — caches a computed VALUE; recomputes only when deps change.
const sorted = useMemo(
  () => products.slice().sort((a, b) => a.price - b.price), // expensive on big lists
  [products]
);

// useCallback — caches a FUNCTION identity; same function across renders.
const handleAdd = useCallback(
  (item) => dispatch({ type: "add", item }),
  [dispatch] // dispatch is stable, so this handler is stable
);

// React.memo — skips re-rendering a component when its props are shallow-equal.
const Row = React.memo(function Row({ item, onAdd }) {
  return <li>{item.name} <button onClick={() => onAdd(item)}>add</button></li>;
});

React.memo only helps if the props are stable — which is why you'd pass handleAdd from useCallback: an inline onAdd={() => ...} is a new function every render, so React.memo would see "props changed" and re-render anyway. The three tools work as a set.

Don't over-optimize. Memoization is not free: it stores the value and runs a dependency comparison every render. For cheap computations and small lists it costs more than it saves and clutters the code. Reach for it when you've measured a real problem — a genuinely expensive calculation, or a stable prop needed by a React.memo'd child in a long list. Default to not memoizing. (React 19's compiler can auto-memoize, further reducing the need to do it by hand.)

useRef: DOM access and mutable values

useRef gives you a mutable box (ref.current) that persists across renders and — crucially — does not trigger a re-render when you change it. Two distinct uses:

function SearchBox() {
  const inputRef = useRef(null);     // 1) a DOM reference
  const renderCount = useRef(0);     // 2) a mutable value, no re-render

  useEffect(() => { inputRef.current.focus(); }, []); // focus on mount
  renderCount.current += 1;          // mutate freely; UI does NOT update

  return <input ref={inputRef} placeholder="Search…" />;
}
Common mistake: mutating ref.current and expecting the screen to update. It won't — refs are explicitly the escape hatch for values that should not cause renders (timers, previous values, instance-like data, the latest value inside a stale closure). If a change should show on screen, it belongs in state, not a ref.

Custom hooks: extract and reuse logic

A custom hook is just a function named use* that calls other hooks. It's how you share stateful logic between components without copy-paste. Two workhorses:

// useLocalStorage — state that persists across reloads
function useLocalStorage(key, initial) {
  const [value, setValue] = useState(() => {
    const raw = localStorage.getItem(key);
    return raw ? JSON.parse(raw) : initial;        // lazy init: read once
  });
  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);
  return [value, setValue];
}

// Usage reads just like useState, but survives a refresh:
const [theme, setTheme] = useLocalStorage("theme", "light");
// useFetch — data fetching with loading/error state AND a race-condition fix
function useFetch(url) {
  const [state, setState] = useState({ data: null, loading: true, error: null });
  useEffect(() => {
    const controller = new AbortController();
    setState({ data: null, loading: true, error: null });
    fetch(url, { signal: controller.signal })
      .then(r => { if (!r.ok) throw new Error(r.status); return r.json(); })
      .then(data => setState({ data, loading: false, error: null }))
      .catch(err => {
        if (err.name !== "AbortError")                 // ignore the cancel
          setState({ data: null, loading: false, error: err });
      });
    return () => controller.abort();                    // cleanup on url change/unmount
  }, [url]);
  return state;
}

Data fetching in useEffect: the race condition

Advanced When url changes quickly (user types in a search box, or navigates), several requests are in flight at once. They can resolve out of order — the response for an old query arrives after the new one and overwrites it. The useFetch above already fixes this with AbortController; the manual pattern:

useEffect(() => {
  let active = true;                      // flag approach (if you can't abort)
  fetch(`/api/search?q=${query}`)
    .then(r => r.json())
    .then(data => { if (active) setResults(data); }); // ignore if superseded
  return () => { active = false; };        // cleanup marks this run stale
}, [query]);
The classic bug: no cleanup, so an in-flight request for "re" resolves after "react" and the UI flashes stale results — or you call setState after the component unmounted. Always either abort (AbortController) or guard with an active flag in the effect's cleanup. For anything beyond trivial fetching, a cache library (TanStack Query, SWR) handles this and more for you.

React Router basics

Client-side routing maps the URL to components without a full page reload. The essentials: declaring routes, reading URL params, nesting layouts, and navigating programmatically.

import { BrowserRouter, Routes, Route, Link, useParams, useNavigate, Outlet } from "react-router-dom";

function App() {
  return (
    <BrowserRouter>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/products" element={<ProductsLayout />}>   {/* nested */}
          <Route index element={<ProductList />} />
          <Route path=":id" element={<ProductDetail />} />        {/* URL param */}
        </Route>
        <Route path="*" element={<NotFound />} />                 {/* catch-all */}
      </Routes>
    </BrowserRouter>
  );
}

function ProductsLayout() {
  return <section><h2>Products</h2><Outlet /></section>; // child route renders here
}

function ProductDetail() {
  const { id } = useParams();            // "/products/42" -> id === "42"
  const navigate = useNavigate();
  return (
    <article>
      <p>Product {id}</p>
      <button onClick={() => navigate("/products")}>← Back</button>
    </article>
  );
}

<Link> replaces <a> for in-app navigation (no reload), :id declares a param read via useParams(), an <Outlet /> is where nested child routes render inside a shared layout, and useNavigate() navigates from code (e.g. after a form submit).

Common mistakes

  • Unstable context values. value={{ ... }} or an inline function/object in context re-renders every consumer each render. Memoize the value, or split state and dispatch into separate contexts.
  • Wrong or omitted dependency arrays. An empty [] on an effect that reads query captures a stale value; omitting the array entirely runs the effect every render. List every reactive value the effect/callback uses — trust the react-hooks/exhaustive-deps lint rule.
  • Premature memoization. Wrapping cheap computations in useMemo/useCallback everywhere adds overhead and noise without measurable benefit. Memoize measured hot spots, not reflexively.
  • Mutating ref.current expecting a re-render. Refs intentionally don't trigger renders. Visible changes belong in state.
  • Fetch race conditions. An effect that fetches without cleanup lets a stale response overwrite a newer one. Abort or guard with an active flag in the cleanup.

Exercises

  • Rewrite a component that juggles 4+ related useState values as a single useReducer, and unit-test the reducer with no React.
  • Build a ThemeContext combining Context + useReducer; then fix the re-render pitfall by memoizing the provider value (or splitting state/dispatch) and confirm fewer renders with the React DevTools profiler.
  • Write useLocalStorage and useDebounce custom hooks and use them in a settings panel.
  • Reproduce a fetch race condition in a search box (type fast), then fix it with an AbortController in the effect cleanup.
  • Add React Router with a nested layout, a :id detail route read via useParams, and a programmatic useNavigate redirect after an action.
