A real app is a frontend talking to a backend, built and deployed somewhere. Learn how the two connect across environments, how configuration and secrets flow in, and how to ship a static site or an app to production.

How the pieces connect

Beginner The frontend (HTML/CSS/JS, possibly built from a framework) runs in the browser; the backend (an HTTP API) runs on a server. They talk over HTTP/JSON. Two common topologies:

TopologyShapeCORS?
Same originBackend serves the frontend's files and the API under one domainNo (same origin)
Split originStatic frontend on a CDN; API on api.example.comYes — API must send CORS headers
Same-origin is simplest: no CORS, cookies "just work". A reverse proxy (Nginx/Traefik — see the DevOps section) can serve / from the static files and proxy /api/* to the backend, giving you one origin even with separate services.

Environment configuration

The frontend and backend each need per-environment config (API URL, feature flags, keys). The twelve-factor rule: config comes from the environment, not hard-coded.

# Backend reads from env
DATABASE_URL=postgres://…
JWT_SECRET=…
PORT=8080

# Frontend build-time config (bundlers inline these at build)
VITE_API_URL=https://api.example.com
# → import.meta.env.VITE_API_URL in code
Frontend "secrets" are not secret. Anything a bundler inlines (VITE_*, NEXT_PUBLIC_*) ships to the browser and is fully visible. Never put API secrets, DB credentials, or private keys in frontend env — only public config (API URLs, publishable keys). Real secrets live on the backend.

A dev proxy avoids CORS locally

// vite.config.js — proxy /api to the backend during development
export default {
  server: {
    proxy: { "/api": "http://localhost:8080" },
  },
};
// Frontend calls fetch("/api/users") → proxied to the backend, same-origin, no CORS

Build output

Intermediate A build step turns source into static assets a server/CDN can serve:

# Typical commands
bun run build        # → dist/ with hashed filenames (app.4f3a.js)
# Hashed names enable long cache headers: the name changes when content does

For this very tutorial, the "build" is bun run scripts/build-site.js, producing a static docs/ folder with the app shell, lesson pages, manifest, and service worker — nothing to run server-side.

Deploying a static site

# GitHub Pages: push docs/ (with a .nojekyll file) → Settings → Pages → /docs
# Or any static host: Netlify, Cloudflare Pages, S3+CloudFront, nginx
#   just copy the built folder to the web root.
Set caching headers right: hashed assets (app.4f3a.js) get a long Cache-Control: max-age=31536000, immutable; HTML and the service worker get no-cache so updates are picked up. A stale cached sw.js can pin users to an old build.

Deploying an app with a backend

# Containerize the backend, put a reverse proxy in front, serve the frontend as static.
# docker-compose (conceptual):
services:
  api:   { build: ./api, environment: [DATABASE_URL, JWT_SECRET] }
  web:   { image: nginx, volumes: ["./dist:/usr/share/nginx/html"] }
  proxy: { image: traefik, ... }   # routes / → web, /api → api, terminates TLS

The DevOps section covers Docker, Compose, reverse proxies, and TLS in depth — this is the frontend/backend view of the same picture.

Pre-deploy checklist

  • Production build runs clean; type-check and tests pass.
  • No secrets in frontend bundles or committed .env files.
  • CORS configured for the real frontend origin (if split).
  • HTTPS everywhere; secure cookie flags set.
  • Correct cache headers; service worker version bumped.

Exercises

  • Set up a Vite dev proxy so fetch("/api/...") reaches a local backend with no CORS.
  • Move a hard-coded API URL into an env var and read it via import.meta.env.
  • Build a static site and deploy it to GitHub Pages (or Netlify) with correct cache headers.

Mini-project: ship a full-stack app

Take a frontend (your choice) and a backend from the Go or Bun section. Wire them with a dev proxy locally, move all config to env vars (secrets backend-only), build the frontend to static assets, and deploy: frontend to a static host and backend as a container behind a reverse proxy that serves both under one origin with TLS.
