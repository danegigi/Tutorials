Web Components are the browser's own answer to reusable UI: a set of standards — Custom Elements, Shadow DOM, and <template> — that let you define new HTML tags with encapsulated markup, style, and behavior, with no framework. The payoff is a component that drops into React, Vue, plain HTML, or nothing at all, and whose styles can't leak in or out.

The three standards

Intermediate

StandardGives you

A custom element

class CounterButton extends HTMLElement {
  #count = 0;
  connectedCallback() {        // runs when inserted into the DOM
    this.render();
    this.addEventListener("click", () => { this.#count++; this.render(); });
  }
  render() { this.textContent = `Clicked ${this.#count}×`; }
}
customElements.define("counter-button", CounterButton);  // name MUST contain a hyphen
<counter-button></counter-button>   <!-- now a real element -->
The tag name must contain a hyphen (counter-button, not counter). That's the spec's rule to guarantee custom elements never collide with current or future built-in HTML tags. A one-word name silently fails to register.

The lifecycle callbacks

CallbackWhen
constructor()element created — set up state, but DON'T touch attributes/children yet
connectedCallback()inserted into the DOM — render, add listeners, start work here
disconnectedCallback()removed — clean up listeners, timers, subscriptions
attributeChangedCallback(name, old, new)a watched attribute changed
static observedAttributes = ["label"];   // only these fire attributeChangedCallback
attributeChangedCallback(name, _old, value) {
  if (name === "label") this.render();
}
Clean up in disconnectedCallback. A listener on window, a setInterval, or an observer started in connectedCallback but never torn down keeps the (removed) element alive — a memory leak. Elements can be connected and disconnected multiple times, so the two callbacks must balance.

Shadow DOM: real encapsulation

class UserCard extends HTMLElement {
  connectedCallback() {
    const shadow = this.attachShadow({ mode: "open" });
    shadow.innerHTML = `
      <style>
        /* scoped to THIS component — can't leak out, page CSS can't leak in */
        .name { font-weight: 700; color: var(--card-fg, #111); }
        :host { display: block; padding: 12px; border: 1px solid #ddd; }
      </style>
      <div class="name"><slot name="name">Anonymous</slot></div>
      <slot></slot>
    `;
  }
}
customElements.define("user-card", UserCard);
<user-card>
  <span slot="name">Ada Lovelace</span>
  <p>First programmer.</p>   <!-- lands in the default <slot> -->
</user-card>

:host styles the element itself; <slot> projects the user's light-DOM content into the shadow tree. A page-wide .name { color: red } cannot reach inside — that's the encapsulation.

Styling across the boundary is deliberate and limited: expose CSS custom properties (--card-fg above) and ::part() for the hooks you want themeable, and everything else stays private. This is the opposite of normal cascade — isolation by default, opt-in theming.

Attributes vs properties

Advanced HTML attributes are always strings (<x-el count="5"> → "5"); JS properties can be any type (el.count = 5 → number). A robust component reflects between them: parse attributes into typed state, and optionally write state back to attributes so the DOM reflects it. Pass rich data (objects, arrays) as properties, not attributes.

Framework interop

Because a custom element is just a DOM element, it works anywhere HTML does. In React, pass primitives as attributes and listen via refs (React's attribute handling improved in React 19); in Vue, custom elements are first-class. This is why design systems (Shoelace, Material Web, Adobe Spectrum) ship as Web Components — one implementation, every framework.

Common mistakes

  • A tag name without a hyphen — registration silently fails.
  • Touching attributes/children in the constructor — they aren't ready; do it in connectedCallback.
  • No cleanup in disconnectedCallback — leaked listeners/timers keep removed elements alive.
  • Expecting page CSS to style shadow content — it can't; expose custom properties / ::part() instead.
  • Passing objects as attributes — attributes are strings; use properties for non-string data.
  • Forgetting observedAttributes — attributeChangedCallback never fires for an unwatched attribute.

Exercises

  • Build a <counter-button> with click state and confirm it works dropped into plain HTML.
  • Add an observedAttributes + attributeChangedCallback so <counter-button start="10"> initializes the count.
  • Create a <user-card> with Shadow DOM, a named slot, and scoped styles; prove page CSS can't restyle its internals.
  • Expose a --card-fg custom property and theme two instances differently from page CSS.
  • Add disconnectedCallback cleanup for a setInterval and prove (via devtools) the element is GC'd after removal.

Mini-project

Build a small framework-free component library: a <star-rating> (attribute-driven value, emits a change event, keyboard-accessible), a <toast-stack> (a method to push dismissable toasts with timers cleaned up on disconnect), and a <tab-group> using slots for panels. Each uses Shadow DOM with scoped styles, exposes CSS custom properties + ::part() for theming, reflects attributes↔properties correctly, and emits custom events. Then drop the same components, unchanged, into both a plain HTML page and a React or Vue app to prove the interop promise.
