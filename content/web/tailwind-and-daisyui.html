Tailwind CSS 4 is a ground-up rewrite: a new Rust-powered engine, a Vite plugin that replaces the old PostCSS pipeline, and CSS-first configuration — your theme lives in your stylesheet, not a tailwind.config.js. daisyUI 5 then sits on top as a plugin, adding semantic component classes like btn and card so you write far less markup. This lesson covers both, basic to advanced.

What changed in v4

Beginner If you've used Tailwind 3, the big shifts are:

  • One import, no directives. @import "tailwindcss"; replaces the old @tailwind base/components/utilities trio.
  • CSS-first config. Design tokens are declared with @theme in CSS. The tailwind.config.js file is optional (and mostly gone).
  • Automatic content detection. Tailwind scans your project for class names on its own — no content: [...] globs to maintain.
  • A dedicated engine + Vite plugin. No PostCSS/autoprefixer config needed; vendor prefixing and nesting are built in.

Install with Vite

The recommended setup for a Vite app (React, Vue, Svelte, vanilla — all the same) is the official plugin:

npm install tailwindcss @tailwindcss/vite
// vite.config.ts
import { defineConfig } from "vite";
import tailwindcss from "@tailwindcss/vite";

export default defineConfig({
  plugins: [tailwindcss()],
});

Then add a single import to your main CSS file and import that CSS from your entry point:

/* src/style.css */
@import "tailwindcss";
// src/main.ts(x)
import "./style.css";

That's the whole install — no init, no PostCSS file, no content array. Start using utilities immediately:

<h1 class="text-3xl font-bold text-indigo-600">It works</h1>
Not using Vite? There's also @tailwindcss/postcss (for a PostCSS pipeline) and a standalone CLI (npx @tailwindcss/cli -i in.css -o out.css --watch). The Vite plugin is the fastest and simplest when you have a bundler.

CSS-first theming with @theme

Intermediate Instead of editing a JS config, you declare design tokens in CSS with @theme. Each token becomes both a CSS variable and a utility class:

/* style.css */
@import "tailwindcss";

@theme {
  --color-brand: oklch(0.62 0.19 260);  /* → bg-brand, text-brand, border-brand */
  --font-display: "Inter", sans-serif;   /* → font-display */
  --spacing-18: 4.5rem;                   /* → p-18, m-18, gap-18 */
  --breakpoint-3xl: 120rem;               /* → 3xl: variant */
}
<button class="bg-brand font-display px-18">Branded</button>
/* and the raw variable is available too: */
.custom { color: var(--color-brand); }
v4 uses the modern oklch() color space for its default palette — colors stay vivid and perceptually consistent. You can mix in hex/rgb freely; oklch just gives nicer gradients and opacity math.

Custom utilities and variants

Advanced v4 adds directives to extend the engine from CSS. @utility defines a reusable utility; @variant applies a variant inside custom CSS; @custom-variant defines your own variant:

/* a reusable utility */
@utility content-auto {
  content-visibility: auto;
}

/* your own variant — e.g. a theme toggle driven by a data attribute */
@custom-variant dark (&:where([data-theme="dark"] *));

/* apply an existing variant inside a rule */
.card {
  background: white;
  @variant dark {
    background: black;
  }
}

Arbitrary values and the @apply directive still work for extracting repeated utility runs into a component class:

.btn-legacy { @apply inline-flex items-center rounded-lg px-4 py-2 font-medium; }
/* arbitrary value, no config needed: */
<div class="top-[117px] grid-cols-[1fr_500px_2fr]">…</div>

daisyUI 5 — semantic components on top

Tailwind utilities are low-level: a button is a dozen classes you repeat everywhere. daisyUI adds semantic component classes — btn, card, modal, tabs — so you write one class and still customize with utilities. daisyUI 5 is built for Tailwind 4, has zero dependencies, and installs as a plugin in your CSS:

npm install -D daisyui@latest
/* style.css */
@import "tailwindcss";
@plugin "daisyui";

Now the semantic classes exist. Compare the two styles — same button, far less markup:

<!-- pure Tailwind -->
<button class="inline-flex items-center rounded-lg bg-indigo-600 px-4 py-2
               font-medium text-white hover:bg-indigo-700">Save</button>

<!-- daisyUI -->
<button class="btn btn-primary">Save</button>
<!-- still fully customizable with utilities: -->
<button class="btn btn-primary btn-sm rounded-full">Save</button>
<div class="card bg-base-100 w-80 shadow-md">
  <div class="card-body">
    <h2 class="card-title">Plan</h2>
    <p>Semantic markup, Tailwind underneath.</p>
    <div class="card-actions justify-end">
      <button class="btn btn-primary">Buy</button>
    </div>
  </div>
</div>

Themes

daisyUI's killer feature is its theme system. Semantic color names (primary, base-100, accent, error) are driven by CSS variables, so switching themes is one attribute. Enable the built-in themes you want in the plugin config, then set data-theme:

@plugin "daisyui" {
  themes: light --default, dark --prefersdark, cupcake, synthwave;
}
<html data-theme="dark">  <!-- flip the whole app's palette -->
<!-- or per-section -->
<div data-theme="cupcake">…scoped theme…</div>

A theme toggle is just swapping that attribute (persist the choice in localStorage):

const t = localStorage.theme ?? "light";
document.documentElement.dataset.theme = t;
toggle.onclick = () => {
  const next = document.documentElement.dataset.theme === "dark" ? "light" : "dark";
  document.documentElement.dataset.theme = next;
  localStorage.theme = next;
};
Define your own theme with the @plugin "daisyui/theme" block (or the theme generator on daisyui.com), setting the semantic variables to your brand colors. Because components reference the semantic names, your whole UI re-skins at once.

Tailwind vs daisyUI — when to reach for each

UseFor
Tailwind utilitiesLayout (fl/grid/gap), spacing, one-off styling, anything bespoke.
daisyUI classesCommon components (buttons, cards, modals, form controls, alerts) and app-wide theming.

They compose: use daisyUI for the component, Tailwind utilities to adjust it (class="btn btn-primary w-full md:w-auto"). daisyUI is pure CSS — it styles elements; it does not manage behavior, so your framework (React/Vue) still owns state, events, and accessibility wiring.

Common mistakes

  • Carrying v3 habits into v4. No @tailwind base; directives, no content array, no PostCSS config — just @import "tailwindcss"; and the Vite plugin.
  • Still writing tailwind.config.js for theme values. Put tokens in @theme in CSS. A JS config is only needed for a few advanced cases.
  • Classes built from string concatenation. `text-${color}-500` isn't detected by the scanner and won't be generated. Map to full class names.
  • Expecting daisyUI to add behavior. modal styles a dialog; opening/closing and focus trapping are still your job (or use the native <dialog> element).
  • Hard-coding colors instead of semantic ones. Use bg-primary/text-base-content so themes work; bg-indigo-600 ignores the theme.
  • Forgetting to enable a theme. Setting data-theme="synthwave" does nothing unless that theme is listed in the plugin config.

Exercises

  • Create a Vite app, install Tailwind 4 via the plugin, and style a heading — confirm it works with zero config files.
  • Add an @theme block defining --color-brand and a custom spacing token; use both a utility (bg-brand) and the raw variable.
  • Define a custom utility with @utility and use it on an element.
  • Add daisyUI and rebuild a card + button with semantic classes; then tweak them with Tailwind utilities.
  • Enable the light and dark themes and wire a toggle that persists the choice in localStorage.

Mini-project: a themeable dashboard shell

Build a small dashboard layout combining both tools:

  • Layout (sidebar + topbar + content grid) built with Tailwind utilities and responsive variants.
  • Components (navbar, cards, stat tiles, a modal, form inputs) built with daisyUI semantic classes.
  • An @theme block defining your brand color, plus a custom daisyUI theme that uses it as --color-primary.
  • A working theme switcher (light / dark / your custom theme) persisted across reloads, flipping the entire palette via data-theme.
  • Everything styled with semantic colors (bg-base-100, text-base-content, btn-primary) so a theme change re-skins the whole shell at once.

You'll have internalized the v4 model (import + CSS-first theme), custom utilities/variants, and the daisyUI component + theming layer that sits on top.
