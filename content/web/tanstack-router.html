TanStack Router is a client-side router built for type safety first. Every route path, path param, and search param is known to TypeScript, so a typo in a link or a missing param is a compile error, not a runtime 404. It also has first-class data loading and preloading, which makes it a natural partner for TanStack Query.

Why a type-safe router

Beginner In most routers, <Link to="/users/42"> is a plain string — nothing checks that the route exists or that 42 is the right shape. TanStack Router infers a full type graph from your route tree, so:

  • to autocompletes every real route and rejects paths that don't exist.
  • params and search are typed per route — reading useParams() gives you exactly the params that route defines.
  • Required params/search are enforced: you cannot link to a route without supplying them.
npm install @tanstack/react-router
npm install -D @tanstack/router-plugin   # enables file-based routing + codegen

Two ways to define routes

You can define routes in code or via the file system. File-based is the recommended default — the plugin generates a typed route tree from your files. Enable it in Vite:

// vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import { tanstackRouter } from "@tanstack/router-plugin/vite";

export default defineConfig({
  plugins: [
    tanstackRouter({ target: "react", autoCodeSplitting: true }), // must come BEFORE react()
    react(),
  ],
});
The router plugin must be listed before @vitejs/plugin-react in the plugins array, or code-splitting transforms won't apply correctly.

The root route and file layout

Files in src/routes/ map to URLs. __root.tsx is the always-rendered shell; index.tsx is the path's own page; a filename maps to a path segment; $id is a dynamic param:

src/routes/
  __root.tsx          → the app shell (nav + <Outlet />)
  index.tsx           → /
  about.tsx           → /about
  posts/
    index.tsx         → /posts
    $postId.tsx       → /posts/:postId
    $postId.edit.tsx  → /posts/:postId/edit
// src/routes/__root.tsx
import { createRootRoute, Link, Outlet } from "@tanstack/react-router";
import { TanStackRouterDevtools } from "@tanstack/react-router-devtools";

export const Route = createRootRoute({
  component: () => (
    <>
      <nav>
        <Link to="/">Home</Link> <Link to="/posts">Posts</Link>
      </nav>
      <Outlet />        {/* child route renders here */}
      <TanStackRouterDevtools />
    </>
  ),
});

Each route file exports a Route created with createFileRoute. The plugin fills in the path string argument for you (shown here explicitly):

// src/routes/posts/$postId.tsx
import { createFileRoute } from "@tanstack/react-router";

export const Route = createFileRoute("/posts/$postId")({
  component: PostPage,
});

function PostPage() {
  const { postId } = Route.useParams(); // typed as { postId: string }
  return <h1>Post {postId}</h1>;
}

Wiring the router

The plugin generates routeTree.gen.ts. Create the router from it and register its type so all the global helpers are typed:

// src/main.tsx
import { RouterProvider, createRouter } from "@tanstack/react-router";
import { routeTree } from "./routeTree.gen";
import { createRoot } from "react-dom/client";

const router = createRouter({ routeTree });

// make Link/useParams/etc. aware of your routes app-wide
declare module "@tanstack/react-router" {
  interface Register { router: typeof router; }
}

createRoot(document.getElementById("root")!).render(
  <RouterProvider router={router} />,
);

Typed links and navigation

Now links are checked at compile time. A dynamic route requires its params:

<Link to="/posts/$postId" params={{ postId: "42" }}>Read</Link>
<Link to="/postz">…</Link>   // ❌ compile error: no such route

// imperative:
const navigate = Route.useNavigate();
navigate({ to: "/posts/$postId", params: { postId: "42" } });
Add activeProps to style the current link, and preload="intent" on <Link> (or router-wide via defaultPreload: "intent") to prefetch a route's data on hover — navigations then feel instant.

Typed search params with validation

Intermediate Search params (?page=2&sort=asc) are first-class and validated. You declare their shape with validateSearch (a Zod schema works great), and reading them is fully typed — no manual URLSearchParams parsing:

import { createFileRoute } from "@tanstack/react-router";
import { z } from "zod";

const searchSchema = z.object({
  page: z.number().catch(1),
  sort: z.enum(["asc", "desc"]).catch("asc"),
});

export const Route = createFileRoute("/posts/")({
  validateSearch: searchSchema,
  component: Posts,
});

function Posts() {
  const { page, sort } = Route.useSearch();       // { page: number; sort: "asc"|"desc" }
  const navigate = Route.useNavigate();
  return (
    <button onClick={() => navigate({ search: (s) => ({ ...s, page: s.page + 1 }) })}>
      Next (page {page})
    </button>
  );
}
The .catch() on each field means a garbage URL (?page=banana) falls back to a valid default instead of crashing — the router never renders with invalid search state.

Loaders: data before render

A route can declare a loader that fetches data before the component renders. Combined with preloading, the data is often already there by the time you navigate:

export const Route = createFileRoute("/posts/$postId")({
  loader: ({ params }) => fetchPost(params.postId),
  component: () => {
    const post = Route.useLoaderData(); // typed from the loader's return
    return <article>{post.title}</article>;
  },
});

Router context and the Query integration

Advanced The router context is a typed object passed to every loader — the clean way to inject your QueryClient. The best-practice pattern lets the loader prefetch a query and the component read it with useQuery, so you get Query's caching plus the router's preload-on-hover:

// router with context
const router = createRouter({
  routeTree,
  context: { queryClient }, // injected into every loader
  defaultPreload: "intent",
});

// a route that prefetches via the loader, reads via the component
export const Route = createFileRoute("/posts/$postId")({
  loader: ({ context: { queryClient }, params }) =>
    queryClient.ensureQueryData(postQueries.detail(params.postId)),
  component: () => {
    const { postId } = Route.useParams();
    const { data } = useSuspenseQuery(postQueries.detail(postId)); // already warm
    return <article>{data.title}</article>;
  },
});

Why both? The loader guarantees the data is fetched (and preloaded on hover); useSuspenseQuery reads from the same cache and keeps the data live afterward (background refetch, invalidation). Router owns when to navigate; Query owns the cache lifecycle.

Shared example: the Issues Tracker (routing & preload)

Advanced This continues the Issues Tracker begun in the TanStack Query lesson. We import the same issueQueries module — the router doesn't define its own fetching, it drives when to load the queries you already wrote. The route tree:

src/routes/
  __root.tsx              → shell: nav + <Outlet />, QueryClient in context
  issues/
    index.tsx             → /issues        (list, with ?status filter)
    $issueId.tsx          → /issues/:id     (one issue)

The list route validates its ?status filter as typed search, then preloads the matching query in its loader — so by the time the component renders, the data the Query lesson defined is already warm:

// src/routes/issues/index.tsx
import { createFileRoute } from "@tanstack/react-router";
import { useSuspenseQuery } from "@tanstack/react-query";
import { z } from "zod";
import { issueQueries } from "../../issues/queries"; // ← from the Query lesson

const search = z.object({ status: z.enum(["open", "closed"]).optional() });

export const Route = createFileRoute("/issues/")({
  validateSearch: search,
  // the filter from the URL feeds the SAME query key the Query lesson used
  loaderDeps: ({ search }) => ({ status: search.status }),
  loader: ({ context: { queryClient }, deps }) =>
    queryClient.ensureQueryData(issueQueries.list({ status: deps.status })),
  component: IssuesList,
});

function IssuesList() {
  const { status } = Route.useSearch();
  const navigate = Route.useNavigate();
  const { data: issues } = useSuspenseQuery(issueQueries.list({ status }));
  return (
    <>
      <select
        value={status ?? ""}
        onChange={(e) =>
          navigate({ search: { status: e.target.value || undefined } })
        }
      >
        <option value="">All</option>
        <option value="open">Open</option>
        <option value="closed">Closed</option>
      </select>
      <ul>
        {issues.map((i) => (
          <li key={i.id}>
            <Link to="/issues/$issueId" params={{ issueId: String(i.id) }}>
              {i.title}
            </Link>
          </li>
        ))}
      </ul>
    </>
  );
}

The detail route preloads one issue by id — and because defaultPreload: "intent" is on, hovering a list link prefetches the detail before the click:

// src/routes/issues/$issueId.tsx
export const Route = createFileRoute("/issues/$issueId")({
  loader: ({ context: { queryClient }, params }) =>
    queryClient.ensureQueryData(issueQueries.detail(Number(params.issueId))),
  component: () => {
    const { issueId } = Route.useParams();
    const { data: issue } = useSuspenseQuery(issueQueries.detail(Number(issueId)));
    return <article><h1>{issue.title}</h1><p>Status: {issue.status}</p></article>;
  },
});
Notice the division of labour: the URL owns the filter (?status=open is shareable and survives refresh), the loader guarantees the data is fetched and preloaded on hover, and Query owns the cache afterward. Common mistakes

  • Plugin order. Put tanstackRouter(...) before react() in Vite, or codegen/splitting misbehaves.
  • Forgetting the declare module registration. Without registering the router type, Link/useParams/useSearch lose their type safety and fall back to loose strings.
  • Hand-parsing search params. Don't reach for URLSearchParams — declare validateSearch and read typed values.
  • Doing all data loading in useEffect. That reintroduces waterfalls and loses preloading. Use the loader (optionally feeding Query).
  • Editing routeTree.gen.ts. It's generated — your edits are overwritten. Change the route files instead.
  • Deep relative to strings. Prefer absolute typed paths with params; the compiler then catches mistakes.

Mini-project: a type-safe blog browser

Build a small blog UI with file-based routes: / (intro), /posts (list with ?page & ?tag typed search), and /posts/$postId (detail). Requirements:

  • The list route validates its search params with Zod and reflects page/tag changes in the URL — refresh and the state is restored from the URL.
  • Links to detail pages use typed params; a deliberately wrong to must fail to compile.
  • Inject a QueryClient through router context; each route's loader calls ensureQueryData and the component reads with useSuspenseQuery.
  • Turn on defaultPreload: "intent" and confirm in the network panel that hovering a post link prefetches it.
  • Add a not-found route and a route-level error component.

You'll end with navigation, dynamic params, validated search, loaders, preloading, and the Router×Query integration — the full type-safe routing stack.
