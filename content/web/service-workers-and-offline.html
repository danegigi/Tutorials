A service worker is a script the browser runs in the background, separate from any page, that can intercept every network request. It's the engine behind offline support, caching strategies, and background sync. Get its lifecycle and caching right and your app works with no network at all.

The lifecycle

Beginner A worker goes through install → activate → fetch. Understanding each stage is the whole game.

const CACHE = "app-v1";
const SHELL = ["/", "/index.html", "/app.css", "/app.js", "/offline.html"];

self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(CACHE).then((c) => c.addAll(SHELL))
      .then(() => self.skipWaiting())   // activate immediately
  );
});

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(keys.filter((k) => k !== CACHE).map((k) => caches.delete(k)))
    ).then(() => self.clients.claim())   // control open pages now
  );
});
Common mistake: expecting a new worker to take over instantly. By default a new worker waits until every tab using the old one closes. skipWaiting() + clients.claim() override that, but then you must handle the version change on the page side (see "Updates" below) or users get a half-old, half-new app.

Caching strategies

Intermediate The fetch handler decides, per request, where the response comes from. The main strategies:

StrategyBehaviorUse for
Cache-firstServe cache; fetch only on missVersioned static assets
Network-firstTry network; fall back to cacheHTML pages, fresh-ish data
Stale-while-revalidateServe cache now, update it in backgroundAssets that change occasionally
Network-only / Cache-onlyNo fallbackAnalytics / precached shell

Network-first for navigations, with offline fallback

self.addEventListener("fetch", (event) => {
  const req = event.request;
  if (req.method !== "GET") return;

  if (req.mode === "navigate") {
    event.respondWith(
      fetch(req)
        .then((res) => {
          const copy = res.clone();
          caches.open(CACHE).then((c) => c.put(req, copy));  // keep cache warm
          return res;
        })
        .catch(() => caches.match(req).then((hit) => hit || caches.match("/offline.html")))
    );
    return;
  }

  // Stale-while-revalidate for assets
  event.respondWith(
    caches.match(req).then((hit) => {
      const net = fetch(req).then((res) => {
        if (res.ok) caches.open(CACHE).then((c) => c.put(req, res.clone()));
        return res;
      }).catch(() => hit);
      return hit || net;
    })
  );
});

This is close to the exact service worker running this tutorial: navigations are network-first (fresh pages when online, cached pages or the offline fallback when not), and assets are stale-while-revalidate.

Updating the active worker

// Page side: detect a new worker waiting, prompt to reload
navigator.serviceWorker.register("/sw.js").then((reg) => {
  reg.addEventListener("updatefound", () => {
    const sw = reg.installing;
    sw.addEventListener("statechange", () => {
      if (sw.state === "installed" && navigator.serviceWorker.controller) {
        showUpdateBanner(() => reg.waiting.postMessage({ type: "SKIP_WAITING" }));
      }
    });
  });
});
navigator.serviceWorker.addEventListener("controllerchange", () => location.reload());

// Worker side:
self.addEventListener("message", (e) => {
  if (e.data.type === "SKIP_WAITING") self.skipWaiting();
});
Cache versioning: change the cache name (app-v2) whenever assets change; the activate handler deletes old caches. This tutorial's build stamps the version into sw.js on every build, so a redeploy invalidates stale caches automatically.

Background sync (brief)

Advanced Defer failed writes until connectivity returns:

// Page: queue a sync
const reg = await navigator.serviceWorker.ready;
await reg.sync.register("send-outbox");
// Worker:
self.addEventListener("sync", (e) => {
  if (e.tag === "send-outbox") e.waitUntil(flushOutbox());
});

Debugging

  • DevTools → Application → Service Workers: see state, "Update on reload", "Offline" toggle, unregister.
  • DevTools → Application → Cache Storage: inspect exactly what's cached.
  • Hard-reset during development: unregister + "Clear site data" — stale workers cause the most confusing bugs.

Exercises

  • Pre-cache an app shell in install, then toggle "Offline" in DevTools and confirm the page still loads.
  • Serve a page network-first with an offline.html fallback; verify both online and offline paths.
  • Bump the cache version and confirm the old cache is deleted on activate.
