Forms are how the web collects input. The browser gives you a lot for free — typed inputs, required fields, pattern matching, and the Constraint Validation API — but client checks are a convenience, never a security boundary. Always validate on the server too.

Native constraints

Beginner Attributes on inputs declare rules the browser enforces before submit, with no JavaScript:

<form>
  <label for="email">Email</label>
  <input id="email" name="email" type="email" required>

  <label for="age">Age</label>
  <input id="age" name="age" type="number" min="18" max="120">

  <label for="user">Username</label>
  <input id="user" name="user" pattern="[a-z0-9_]{3,16}" required
         title="3–16 lowercase letters, digits, or underscores">

  <input name="pw" type="password" minlength="8" required>
  <button>Sign up</button>
</form>
AttributeEffect
requiredField must not be empty.
type="email"/"url"/"number"/"tel"Format check + the right mobile keyboard.
min/max/stepNumeric/date range.
minlength/maxlengthText length bounds.
patternA regex the value must match.

The Constraint Validation API

Intermediate Script can read validity state and set custom messages — useful for cross-field rules the attributes can't express:

const form = document.querySelector("form");
const pw = form.pw, confirm = form.confirm;

confirm.addEventListener("input", () => {
  // Custom cross-field rule: passwords must match
  confirm.setCustomValidity(
    confirm.value !== pw.value ? "Passwords do not match" : ""
  );
});

form.addEventListener("submit", (e) => {
  if (!form.checkValidity()) {   // triggers the browser's bubbles
    e.preventDefault();
    form.reportValidity();        // show messages
  }
});

// Per-field state
emailInput.validity.valueMissing;   // true if required & empty
emailInput.validity.typeMismatch;   // true if not a valid email
Style invalid fields with the :invalid and :user-invalid pseudo-classes. :user-invalid (newer) only matches after the user has interacted, so you don't flag empty fields the moment the page loads.

Reading form data in JS

form.addEventListener("submit", async (e) => {
  e.preventDefault();
  const data = Object.fromEntries(new FormData(form));   // {email, age, ...}
  const res = await fetch("/signup", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(data),
  });
  // handle res.ok / validation errors from the server
});

Server-side validation is the real one

Intermediate Client validation improves UX; it does not protect your data. Anyone can bypass it with curl or devtools.

The cardinal rule: never trust client input. Re-validate everything on the server — presence, type, length, format, and business rules — and treat the browser checks purely as a fast feedback loop. A form that only validates in JS is an open door.
// Server (pseudo): return field-level errors as JSON
// 422 Unprocessable Entity
{ "errors": { "email": "already registered", "age": "must be 18+" } }
// → the client maps these back onto the fields

Exercises

  • Build a signup form using only native attributes; confirm the browser blocks a bad email with no JS.
  • Add a "confirm password" field with setCustomValidity cross-field matching.
  • Style :user-invalid fields red and show the native message on submit.

Mini-project: a resilient signup form

Build a signup form that (1) uses native constraints for instant feedback, (2) adds a cross-field password-match rule, (3) submits as JSON via fetch, and (4) maps a server 422 error payload back onto the matching fields. Then prove the server rejects a request sent via curl that skipped the client checks — demonstrating why both layers exist.
