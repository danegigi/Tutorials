"State" is any data your UI remembers between renders — a form's contents, the logged-in user, the current filter. Managing it well is mostly about putting each piece of state in the right place and not reaching for a heavy library before you need one.

Four kinds of state

KindExampleLives in
Local UIIs this dropdown open?The component / a local variable
Shared appTheme, logged-in user, cartA shared store
ServerThe list of products from the APIA cache (it's a copy of server truth)
URLCurrent page, search query, filtersThe address bar (query/path)
The most common architecture mistake is treating all four as one blob in a single global store. Server state is a cache (it can go stale, needs refetching) — not the same as client state. URL state belongs in the URL so links are shareable and the back button works. Keeping them separate simplifies everything.

Local state: just use a variable

// Vanilla: state is a variable; a render function reads it
let open = false;
function toggle() { open = !open; render(); }
function render() { menu.hidden = !open; }
// Don't reach for a library to track whether a menu is open.

URL as state

Beginner Filters, pagination, search, and the active tab should live in the URL — then the page is bookmarkable, shareable, and the back button works:

// Read current state from the URL
const params = new URLSearchParams(location.search);
const page = Number(params.get("page") || 1);

// Update it WITHOUT a reload or a new history entry per keystroke
function setParam(key, val) {
  const p = new URLSearchParams(location.search);
  val ? p.set(key, val) : p.delete(key);
  history.replaceState(null, "", location.pathname + "?" + p);  // replace, not push
}
Common mistake: keeping the current filter/search only in a JS variable. The user filters a list, clicks a result, hits back — and lands on the unfiltered page because the state was never in the URL. Store list state in the query string (replaceState so you don't spam history) and re-seed the UI from it on load. (This exact bug and fix recur in real Datastar/SPA list views.)

The observable store pattern

Intermediate For shared client state without a framework, a tiny subscribable store is often all you need:

function createStore(initial) {
  let state = initial;
  const subs = new Set();
  return {
    get: () => state,
    set: (patch) => { state = { ...state, ...patch }; subs.forEach(f => f(state)); },
    subscribe: (f) => { subs.add(f); return () => subs.delete(f); },
  };
}

const cart = createStore({ items: [], total: 0 });
cart.subscribe(s => renderBadge(s.items.length));   // UI reacts to changes
cart.set({ items: [...cart.get().items, product] });

This is the core of every state library (Redux, Zustand, signals): a single source of truth + subscriptions. Persist it by writing to localStorage in set and seeding initial from it.

Avoid over-engineering

Reaching for a global state library on day one is a common mistake. Start with local variables and URL state; add a small store when two distant components genuinely need the same data; add a server-cache library when you're hand-writing fetch+cache+invalidate logic repeatedly. Each step should be justified by pain you actually feel.
