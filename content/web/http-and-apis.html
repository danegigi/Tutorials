HTTP is the protocol every web app speaks. Understand the request/response cycle, methods and status codes, headers, REST conventions, and how to call APIs from the browser with fetch — including the CORS rules that trip everyone up.

The request/response model

Beginner A client sends a request; a server returns a response. Both have a start line, headers, and an optional body.

GET /api/users/42 HTTP/1.1        ← request line (method, path, version)
Host: example.com                  ← headers
Accept: application/json

HTTP/1.1 200 OK                    ← status line
Content-Type: application/json     ← headers
Content-Length: 48

{"id":42,"name":"Ada"}             ← body

Methods

MethodUseSafe?Idempotent?
GETRead a resourceYesYes
POSTCreate / trigger an actionNoNo
PUTReplace a resourceNoYes
PATCHPartially updateNoNo
DELETERemove a resourceNoYes

Safe = no side effects. Idempotent = repeating it has the same effect as doing it once (matters for retries).

Status codes

RangeMeaningCommon
2xxSuccess200 OK, 201 Created, 204 No Content
3xxRedirect301 Moved, 304 Not Modified
4xxClient error400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests
5xxServer error500 Internal, 502 Bad Gateway, 503 Unavailable
401 vs 403: 401 means "I don't know who you are" (authenticate). 403 means "I know who you are, and you can't do this" (authorized but forbidden). Mixing them up is a classic API bug.

REST conventions

GET    /articles         → list
POST   /articles         → create
GET    /articles/42      → read one
PUT    /articles/42      → replace
PATCH  /articles/42      → update fields
DELETE /articles/42      → delete
GET    /articles/42/comments   → nested collection

Nouns, not verbs, in paths; the method is the verb. Use query strings for filtering/paging: /articles?tag=go&page=2&limit=20.

Calling APIs with fetch

// GET + JSON
const res = await fetch("/api/users/42", { headers: { Accept: "application/json" } });
if (!res.ok) throw new Error(`HTTP ${res.status}`);   // fetch does NOT throw on 4xx/5xx
const user = await res.json();

// POST JSON
const created = await fetch("/api/users", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "Bo" }),
});

// Form upload (multipart) — do NOT set Content-Type; the browser adds the boundary
const fd = new FormData();
fd.append("file", fileInput.files[0]);
await fetch("/api/upload", { method: "POST", body: fd });
Common mistake: assuming fetch rejects on a 404 or 500. It only rejects on network failure. You must check res.ok (or res.status) yourself — forgetting this means error responses get parsed as if they were success.

CORS

Intermediate By default, a page can't read responses from a different origin. The server must opt in with headers; the browser enforces it.

// Server response that allows a cross-origin page to read it:
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true   // needed to send cookies
A "CORS error" in the console is almost never fixable in the frontend — it's a missing/incorrect header on the server. Non-simple requests also trigger a preflight OPTIONS call the server must answer. Don't chase it in client code.

Exercises

  • Use curl -i to inspect the status line and headers of three different sites.
  • Write a fetch wrapper that throws on !res.ok with the status and response body in the message.
  • Explain when you'd return 400 vs 401 vs 403 vs 404 for a failed "update article" request.

Mini-project: a REST client module

Build a small http.js with get/post/put/del helpers that set JSON headers, check res.ok, parse the body, and surface errors uniformly. Point it at a public API (e.g. JSONPlaceholder), list posts, create one, and handle a deliberately-wrong URL's 404.
