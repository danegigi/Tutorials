TanStack also ships a family of headless libraries — Table, Form, Store, Virtual, and the newer DB. "Headless" means they give you the logic and state (sorting, filtering, validation, reactivity) but render nothing: you supply the markup. You get full control over the HTML and styling while the hard state management is handled for you.

What "headless" means and why it wins

Beginner A traditional data-grid component renders its own <table>, its own styles, its own sort arrows — and the moment your design doesn't match, you fight it. A headless table hands you a model (rows, header groups, sort state) and lets you render a plain <table> (or a <div> grid, or cards). The payoff: your markup, your CSS, zero override battles — the library only owns the behavior.

TanStack Table

Install the React adapter. The core is framework-agnostic; adapters exist for React, Vue, Solid, Svelte:

npm install @tanstack/react-table

You define column definitions, pass your data and columns to useReactTable with the row model(s) you want, and then render from the returned table instance:

import {
  createColumnHelper,
  flexRender,
  getCoreRowModel,
  getSortedRowModel,
  useReactTable,
} from "@tanstack/react-table";
import { useState } from "react";

type Person = { id: number; name: string; age: number; email: string };
const col = createColumnHelper<Person>();

const columns = [
  col.accessor("name", { header: "Name" }),
  col.accessor("age", { header: "Age" }),
  col.accessor("email", {
    header: "Email",
    cell: (info) => <a href={`mailto:${info.getValue()}`}>{info.getValue()}</a>,
  }),
];

function PeopleTable({ data }: { data: Person[] }) {
  const [sorting, setSorting] = useState([]);
  const table = useReactTable({
    data,
    columns,
    state: { sorting },
    onSortingChange: setSorting,
    getCoreRowModel: getCoreRowModel(),
    getSortedRowModel: getSortedRowModel(), // opt in to sorting
  });

  return (
    <table>
      <thead>
        {table.getHeaderGroups().map((hg) => (
          <tr key={hg.id}>
            {hg.headers.map((h) => (
              <th key={h.id} onClick={h.column.getToggleSortingHandler()}>
                {flexRender(h.column.columnDef.header, h.getContext())}
                {{ asc: " ▲", desc: " ▼" }[h.column.getIsSorted() as string] ?? ""}
              </th>
            ))}
          </tr>
        ))}
      </thead>
      <tbody>
        {table.getRowModel().rows.map((row) => (
          <tr key={row.id}>
            {row.getVisibleCells().map((cell) => (
              <td key={cell.id}>{flexRender(cell.column.columnDef.cell, cell.getContext())}</td>
            ))}
          </tr>
        ))}
      </tbody>
    </table>
  );
}
Row models are opt-in. Sorting does nothing unless you pass getSortedRowModel(); filtering needs getFilteredRowModel(); pagination needs getPaginationRowModel(). Forgetting the model is the #1 "my sort button doesn't work" cause.
Always render cells and headers through flexRender — it handles both plain strings and JSX cell renderers. Reading cell.getValue() directly skips your custom cell renderer.

Filtering, pagination, and controlled vs uncontrolled state

Intermediate Add the row models and the matching state to opt into more features. You choose where the state lives — let the table manage it internally, or control it yourself (needed if the URL or a server drives it):

const table = useReactTable({
  data,
  columns,
  state: { sorting, columnFilters, pagination },
  onSortingChange: setSorting,
  onColumnFiltersChange: setColumnFilters,
  onPaginationChange: setPagination,
  getCoreRowModel: getCoreRowModel(),
  getSortedRowModel: getSortedRowModel(),
  getFilteredRowModel: getFilteredRowModel(),
  getPaginationRowModel: getPaginationRowModel(),
});

// controls:
table.getColumn("name")?.setFilterValue("ada");
table.nextPage(); table.previousPage();
table.getState().pagination.pageIndex;

For server-side data (the server sorts/filters/paginates), set manualSorting, manualFiltering, manualPagination to true, give rowCount, and refetch when the state changes — the table then stops doing the work client-side and just reflects the state.

Virtualization for huge tables

Advanced Rendering 50,000 <tr> elements kills the browser. Pair Table with TanStack Virtual to render only the rows in view:

import { useVirtualizer } from "@tanstack/react-virtual";

const rows = table.getRowModel().rows;
const parentRef = useRef<HTMLDivElement>(null);
const rowVirtualizer = useVirtualizer({
  count: rows.length,
  getScrollElement: () => parentRef.current,
  estimateSize: () => 36,     // row height in px
  overscan: 10,
});
// render only rowVirtualizer.getVirtualItems(), offset with a translateY

TanStack Form

TanStack Form is a headless, type-safe form library. State and validation live in a form instance; each field is a render-prop component that gives you the value, change handler, and errors — you render the input:

npm install @tanstack/react-form
import { useForm } from "@tanstack/react-form";
import { z } from "zod";

function SignupForm() {
  const form = useForm({
    defaultValues: { email: "", password: "" },
    onSubmit: async ({ value }) => { await api.signup(value); },
  });

  return (
    <form onSubmit={(e) => { e.preventDefault(); form.handleSubmit(); }}>
      <form.Field
        name="email"
        validators={{ onChange: z.string().email("Invalid email") }}
      >
        {(field) => (
          <>
            <input
              value={field.state.value}
              onBlur={field.handleBlur}
              onChange={(e) => field.handleChange(e.target.value)}
            />
            {field.state.meta.errors.length > 0 && (
              <em>{String(field.state.meta.errors[0])}</em>
            )}
          </>
        )}
      </form.Field>

      <form.Subscribe selector={(s) => [s.canSubmit, s.isSubmitting]}>
        {([canSubmit, isSubmitting]) => (
          <button type="submit" disabled={!canSubmit}>
            {isSubmitting ? "…" : "Sign up"}
          </button>
        )}
      </form.Subscribe>
    </form>
  );
}
Form is schema-agnostic: validators accept a Zod/Valibot/ArkType schema or a plain function. Use onChange for live validation and onSubmit/onBlur validators for less noisy UX. form.Subscribe re-renders only the button when submit-ability changes, not the whole form.

TanStack Store

Store is the tiny reactive core the other libraries use internally — a framework-agnostic signal store. Reach for it when you need shared client state without pulling in Redux/Zustand:

npm install @tanstack/react-store
import { Store, useStore } from "@tanstack/react-store";

const cartStore = new Store({ items: [] as string[] });
const addItem = (name: string) =>
  cartStore.setState((s) => ({ ...s, items: [...s.items, name] }));

function CartCount() {
  // selector → re-renders only when the count changes
  const count = useStore(cartStore, (s) => s.items.length);
  return <span>{count}</span>;
}

TanStack DB — where it's headed

TanStack DB is the newest member: a reactive client store built on collections and live queries that stay in sync, designed to sit on top of TanStack Query for sync. You define collections, write differential queries against them, and the UI updates incrementally as data changes — with optimistic mutations built in. It's younger than the others, so pin versions and read the current docs before adopting it in production; the collection + live-query model is the thing to understand.

Common mistakes

  • Forgetting a row model. No getSortedRowModel() → sorting silently does nothing. Each feature needs its model.
  • Unstable columns/data references. Defining columns inline in render (new array each time) causes churn — hoist them to module scope or memoize.
  • Bypassing flexRender. Reading getValue() directly skips custom cell renderers and loses JSX cells.
  • Mixing manual and automatic models. If the server paginates, set manualPagination; otherwise the table paginates the partial data it already has.
  • Subscribing to the whole store. In Store, always pass a selector to useStore so a component re-renders only on the slice it reads.
  • Rendering 10k rows without virtualization. Headless makes it possible; it doesn't make it fast. Add TanStack Virtual for large sets.

Exercises

  • Render a sortable table of 20 people with a custom email cell; confirm clicking a header toggles asc/desc/none.
  • Add a global text filter and client-side pagination with prev/next and a page indicator.
  • Build a signup form with TanStack Form validated by a Zod schema, showing per-field errors and a submit button disabled until valid.
  • Create a TanStack Store for a shopping cart and two components that read different selectors; verify each re-renders only when its slice changes.
  • Virtualize a 10,000-row table with TanStack Virtual and confirm the DOM holds only the visible rows.

Mini-project: a headless admin data grid

Build a users admin screen that combines the family:

  • Table with sortable columns, a text filter, and pagination, rendered as your own styled <table> (no component library markup).
  • Form in a side panel to add/edit a user, validated with Zod, disabling submit until valid.
  • Store holding UI state (which row is selected, panel open/closed) with selector-scoped subscriptions.
  • Load the user list with TanStack Query (from the Query lesson); on add/edit, mutate and invalidate so the table refreshes.
  • If the dataset is large, drop in TanStack Virtual and confirm scrolling stays smooth.

This shows the headless philosophy in one app: TanStack owns the behavior and state across table/form/store/query, while every pixel of markup and style is yours.
