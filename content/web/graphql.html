GraphQL is a query language for APIs: instead of many fixed REST endpoints each returning a fixed shape, you expose one endpoint and a typed schema, and the client asks for exactly the fields it needs in one request. This lesson covers queries, mutations, variables and fragments from the frontend's view, the trade-offs against REST, client-side caching, and the N+1 trap that bites on the server.

One endpoint, you choose the shape

Intermediate With REST, GET /users/1 returns whatever the server decided — maybe too much (over-fetching) or not enough, forcing a second call to /users/1/posts (under-fetching). GraphQL inverts this: there's one URL (/graphql), and the query declares the fields and relationships you want, delivered in a single round trip.

# a query — ask for exactly these fields, including nested relations
query {
  user(id: "1") {
    name
    email
    posts(last: 3) {
      title
      comments { author }
    }
  }
}
# the response mirrors the query's shape, nothing more:
# { "data": { "user": { "name": "Ada", "posts": [ ... ] } } }

The schema is the contract

type User {
  id: ID!          # ! means non-nullable
  name: String!
  posts: [Post!]!  # a non-null list of non-null Posts
}
type Query    { user(id: ID!): User }       # read entry points
type Mutation { createPost(input: PostInput!): Post }  # write entry points

The schema is strongly typed and introspectable — which is why GraphQL tooling (autocomplete, the GraphiQL explorer, codegen) is so good: the client can discover the whole API from the server.

Variables and mutations

# parameterize with variables — never string-interpolate user input into the query
query GetUser($id: ID!) {
  user(id: $id) { name email }
}
# variables (sent as JSON alongside):  { "id": "1" }

# a mutation writes and returns the fields you want back
mutation AddPost($input: PostInput!) {
  createPost(input: $input) { id title }
}
// a plain fetch — GraphQL is "just" a POST
const res = await fetch("/graphql", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ query: GET_USER, variables: { id: "1" } }),
});
const { data, errors } = await res.json();   // note: errors is a SIBLING of data
GraphQL returns HTTP 200 even on errors. A failed field shows up in the errors array while data may be partially populated — you must check errors, not just the status code. This trips up anyone treating it like REST where non-2xx signals failure.

Fragments: reusable field sets

fragment UserCard on User { id name avatarUrl }

query {
  me       { ...UserCard }
  friends  { ...UserCard }   # same fields, declared once
}

Fragments keep queries DRY and are the unit most client codegen tools build typed hooks around.

Client-side caching: the real reason to use a client

Advanced You can use fetch, but a GraphQL client (Apollo Client, urql, Relay) earns its place with a normalized cache: it stores each object by its ID, so a user fetched in one query is reused everywhere, and a mutation that returns the updated object updates every view automatically. That's hard to replicate with ad-hoc fetching.

// urql example
const [{ data, fetching, error }] = useQuery({ query: GET_USER, variables: { id } });
// the cache dedupes identical queries and updates views when a mutation returns changed objects.

The N+1 trap (server side)

GraphQL's nested queries make a classic performance bug easy to hit: resolving users { posts } naively runs one query for the users, then one query per user for their posts — N+1 database round trips. The standard fix is a DataLoader: it batches and dedupes the per-item fetches within a tick into a single WHERE id IN (...) query.

If a GraphQL API feels slow, suspect N+1 first. The query looks innocent to the client, but a resolver without batching turns one request into hundreds of DB calls. DataLoader (or your ORM's batching) is essential, not optional, for any list-of-things-with-relations.

It's not all-or-nothing: plenty of systems expose REST for simple resources and GraphQL for the complex, relational, client-driven surface.

Common mistakes

  • Checking only the HTTP status — GraphQL returns 200 with an errors array; inspect it.
  • String-interpolating input into the query instead of using $variables — brittle and unsafe.
  • N+1 resolvers with no DataLoader/batching — the top GraphQL performance killer.
  • Over-asking because you can — request only the fields the view renders; huge nested queries are expensive to resolve.
  • Expecting URL-based HTTP caching — one POST endpoint means you rely on the client cache (or persisted queries) instead.
  • No query depth/complexity limits on the server — a malicious deeply-nested query can DoS you.

Exercises

  • Write a query that fetches a user with two levels of nested relations and only the fields you need, via a plain fetch POST.
  • Convert it to use $variables, and handle the errors array explicitly.
  • Extract a repeated field set into a fragment and use it in two places.
  • Write a mutation that creates an object and returns the new id, then update the UI from the result.
  • On a tiny server (any GraphQL lib), demonstrate the N+1 problem by logging DB calls, then fix it with a DataLoader and show the call count drop.

Mini-project

Build a small blog explorer against a GraphQL API: a schema with User, Post, and Comment types and nested relations; a frontend that fetches a user with their recent posts and each post's comment count in a single query (using variables and a shared fragment), creates a post via a mutation and updates the view from the returned object, and handles the errors array properly. On the server, implement the resolvers with a DataLoader to eliminate N+1 and add a query-depth limit. Finish with a short write-up comparing the GraphQL version to the equivalent REST endpoints you'd have needed.
