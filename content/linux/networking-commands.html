When a service is unreachable, the question is always “where in the chain does it break?” — the interface, the route, DNS, the port, or the application. Linux gives you a focused tool for each link. This lesson covers checking your own addresses (ip), reachability (ping, traceroute), DNS resolution (dig, nslookup, host, /etc/hosts), what is listening locally (ss, netstat), and making HTTP requests from the command line (curl, wget).

Your own addresses and routes

Beginner The modern tool is ip (from the iproute2 suite); the older ifconfig still appears on many systems but is deprecated.

ip addr                   # every interface and its IP(s); 'ip a' for short
# -> 1: lo: <LOOPBACK,UP> inet 127.0.0.1/8 scope host lo
# -> 2: eth0: <BROADCAST,UP> inet 203.0.113.10/24 scope global eth0

ip route                  # the routing table — where does traffic go?
# -> default via 203.0.113.1 dev eth0        (the gateway)
# -> 203.0.113.0/24 dev eth0 proto kernel scope link

ip -br addr               # brief, one line per interface
# -> lo    UNKNOWN  127.0.0.1/8
# -> eth0  UP       203.0.113.10/24

# The old equivalents, for reference:
ifconfig                  # ip addr
route -n                  # ip route

Reachability: ping and traceroute

Beginner ping sends ICMP echo requests — the simplest “is this host alive and reachable?” test. traceroute shows every router (hop) the packets pass through, revealing where a path breaks.

ping -c 4 example.com     # -c 4 = send 4 packets then stop
# -> 64 bytes from 93.184.216.34: icmp_seq=1 ttl=56 time=11.4 ms
# -> ...
# -> 4 packets transmitted, 4 received, 0% packet loss

traceroute example.com    # the hop-by-hop path (mtr is a nicer live version)
# -> 1  203.0.113.1   0.4 ms      (your gateway)
# -> 2  10.0.0.1      4.1 ms
# -> ...
# -> 9  93.184.216.34 11.5 ms     (destination)
Many servers and firewalls block ICMP, so a failing ping does not always mean the host is down — the HTTP port may be perfectly reachable. Treat ping as one signal, not a verdict; confirm with a port check or a curl.

DNS: turning names into addresses

Intermediate Before any connection, the name (example.com) must resolve to an IP. dig is the detailed tool; host and nslookup are quicker.

dig example.com +short            # just the answer
# -> 93.184.216.34

dig example.com A                 # full A-record query with timing
# -> ;; ANSWER SECTION:
# -> example.com.  3600  IN  A  93.184.216.34

dig MX example.com +short         # mail servers
dig @1.1.1.1 example.com +short   # ask a SPECIFIC resolver (Cloudflare)

host example.com
# -> example.com has address 93.184.216.34

nslookup example.com              # interactive-style lookup

Resolution order is set in /etc/nsswitch.conf, but the key file to know is /etc/hosts, which is checked before DNS — a local override:

cat /etc/hosts
# -> 127.0.0.1   localhost
# -> 203.0.113.10 web-01

# Point a name at a specific IP locally (needs sudo), e.g. for testing
echo "127.0.0.1 myapp.local" | sudo tee -a /etc/hosts
ping -c1 myapp.local
# -> 64 bytes from 127.0.0.1 ...
Common mistake: blaming the application for a “site not loading” when the real problem is DNS — a stale cache, a wrong record, or a leftover /etc/hosts entry pointing a production hostname at 127.0.0.1 from an old test. Always resolve the name first (dig +short) and confirm it is the IP you expect before touching anything else.

What is listening locally

Intermediate ss (socket statistics) is the modern replacement for netstat. The flag combination you want is -tulpn: tcp, udp, listening, process (needs sudo), numeric (no name lookups).

sudo ss -tulpn
# -> Netid State  Local Address:Port  Process
# -> tcp   LISTEN 0.0.0.0:22          users:(("sshd",pid=812))
# -> tcp   LISTEN 0.0.0.0:80          users:(("nginx",pid=814))
# -> tcp   LISTEN 127.0.0.1:5432      users:(("postgres",pid=901))

# Is anything on port 8080?
sudo ss -tulpn | grep :8080
# -> (empty = nothing is listening there)

# Established connections (not just listeners)
ss -tn state established

# The old equivalent:
sudo netstat -tulpn
Note the bind address: 0.0.0.0:80 listens on every interface (reachable from outside), while 127.0.0.1:5432 listens only on loopback (local-only — the safe default for a database). An app that “works locally but not remotely” is very often bound to 127.0.0.1 when it needs 0.0.0.0.

Making HTTP requests: curl and wget

Beginner curl is the Swiss-army knife for talking to HTTP APIs; wget shines at downloading files (and recursive mirroring).

curl https://api.example.com/health        # GET, print the body
curl -I https://example.com                # headers only (HEAD)
# -> HTTP/2 200
# -> content-type: text/html

curl -fsSL https://example.com/script.sh   # fail on error, silent, follow redirects
curl -s -o /dev/null -w "%{http_code}\n" https://example.com   # just the status
# -> 200

# POST JSON to an API
curl -X POST https://api.example.com/users \
  -H "Content-Type: application/json" \
  -d '{"name":"ada"}'

# Download a file
wget https://example.com/release.tar.gz
wget -qO- https://example.com/health       # print to stdout, quiet (like curl)
curl flagMeaning
-IHEAD request — headers only.
-fFail (non-zero exit) on an HTTP error instead of printing the error page.
-s / -SSilent (no progress meter) / but still show errors.
-LFollow redirects.
-HAdd a request header.
-dSend a request body (implies POST).
-w "%{http_code}"Print selected response info (here, the status code).

Exercises

  • Find your machine's primary IP address and default gateway using only ip.
  • Resolve a domain with dig +short, then resolve it again against a specific public resolver (@1.1.1.1) and confirm the answers match.
  • List every listening TCP port on your machine with the owning process, and identify which are bound to loopback only.
  • Use a single curl command that prints only the HTTP status code of a URL.

Mini-project: a connectivity probe script

Write a script that walks the chain — DNS, reachability, port, HTTP — for a host and port, printing a clear verdict at each step. This is the manual version of a health check and is invaluable when debugging a down service.

#!/usr/bin/env bash
set -uo pipefail
host="${1:?usage: probe.sh HOST [PORT]}"
port="${2:-443}"

echo "== DNS =="
ip=$(dig +short "$host" | head -1)
[ -n "$ip" ] && echo "resolves to $ip" || { echo "DNS FAILED"; exit 1; }

echo "== Reachability =="
ping -c1 -W2 "$host" >/dev/null 2>&1 && echo "ping ok" || echo "ping blocked/failed (may be fine)"

echo "== Port $port =="
if command -v nc >/dev/null; then
  nc -z -w3 "$host" "$port" && echo "port $port open" || echo "port $port CLOSED"
fi

echo "== HTTP =="
code=$(curl -s -o /dev/null -w "%{http_code}" "https://$host" || echo "000")
echo "HTTPS status: $code"
./probe.sh example.com 443
# -> == DNS ==
# -> resolves to 93.184.216.34
# -> == Reachability ==
# -> ping ok
# -> == Port 443 ==
# -> port 443 open
# -> == HTTP ==
# -> HTTPS status: 200

Run against a broken host and the script tells you exactly which link failed — DNS, routing, the port, or the app — which is the whole discipline of network troubleshooting condensed into one pass.
