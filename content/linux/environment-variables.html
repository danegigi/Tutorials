Environment variables are the key-value settings every process inherits from its parent — they are how you tell a program where to find things, which mode to run in, and what credentials to use, without hard-coding anything. This lesson covers setting and exporting variables, the all-important PATH, inspecting the current environment, and the shell startup files that decide which settings survive a new login.

Setting variables

Beginner A plain assignment creates a shell variable visible only to the current shell. Prefixing a command sets a variable for that one command only. export promotes a variable to an environment variable that child processes inherit.

GREETING="hello"          # shell variable, this shell only
echo "$GREETING"
# -> hello

bash -c 'echo "$GREETING"'   # a child shell does NOT see it
# -> (empty line)

export GREETING           # now promote it
bash -c 'echo "$GREETING"'
# -> hello

# Set a variable for a single command only
DEBUG=1 ./app             # ./app sees DEBUG=1; your shell does not keep it
NODE_ENV=production node server.js
Always quote expansions as "$VAR". Unquoted $VAR is split on whitespace and glob-expanded, so a value with spaces (or a *) breaks in surprising ways. The quotes are not optional cosmetics — they are correctness.

Inspecting the environment

printenv                  # print every exported variable
printenv HOME             # print just one
# -> /home/ada

env                       # same list (and can run a command in a modified env)
echo "$HOME $USER $SHELL" # expand several at once
# -> /home/ada ada /bin/bash

env -i bash -c 'printenv' # run with an EMPTY environment (for debugging)
VariableWhat it holds
PATHColon-separated list of directories searched for commands.
HOMEYour home directory; ~ expands to it.
USER / LOGNAMEYour username.
SHELLYour login shell's path.
PWD / OLDPWDCurrent and previous working directory.
LANG / LC_*Locale: language, date format, sort order.
EDITORWhich editor tools like git and crontab -e open.

PATH: how the shell finds commands

Beginner When you type git, the shell searches each directory in PATH, left to right, and runs the first git it finds. This is why installing a tool is not enough — its directory must be on PATH.

echo "$PATH"
# -> /home/ada/.local/bin:/usr/local/bin:/usr/bin:/bin

which git                 # which git would actually run?
# -> /usr/bin/git

type -a python3           # ALL matches on PATH, in search order
# -> python3 is /usr/local/bin/python3
# -> python3 is /usr/bin/python3

# Add a directory to the FRONT of PATH (takes priority)
export PATH="$HOME/bin:$PATH"
# Add to the END (fallback, lower priority)
export PATH="$PATH:/opt/tools/bin"
Common mistake: writing export PATH="$HOME/bin" without appending the old $PATH — this replaces the entire search path, and suddenly ls, cd, and everything else “command not found” because /usr/bin is no longer on it. Always include :$PATH. If it happens in a live shell, you can still run commands by full path (/usr/bin/ls) or just open a new terminal.

Where to persist settings: the startup files

Intermediate A variable set at the prompt vanishes when the terminal closes. To make it permanent you add the export line to a shell startup file — but which file depends on whether the shell is a login shell or an interactive non-login shell.

FileRead whenPut here
~/.bash_profile (or ~/.profile)At login (SSH session, console login).Things that should be set once per login: PATH, EDITOR, environment for all programs.
~/.bashrcEach interactive non-login shell (new terminal tab in a desktop).Aliases, prompt (PS1), shell options, interactive niceties.
/etc/profile, /etc/environmentSystem-wide, for every user.Machine-wide defaults (needs root).

Most setups make ~/.bash_profile source ~/.bashrc so you only maintain one file in practice:

# in ~/.bash_profile
[ -f ~/.bashrc ] && source ~/.bashrc

# in ~/.bashrc — persist a PATH addition and an editor choice
export PATH="$HOME/.local/bin:$PATH"
export EDITOR=vim
alias ll='ls -la'

# Apply changes without logging out
source ~/.bashrc
After editing a startup file, run source ~/.bashrc (or open a new terminal) to apply it — editing the file does not change your current shell. If a tool's installer told you to “restart your shell,” this is why.

App config via environment: the twelve-factor way

Intermediate Modern apps read their configuration from the environment rather than from code, which keeps secrets out of the repo and lets the same build run in dev, staging, and prod with different values. A .env file is the common local pattern — and it must be gitignored.

# .env  (NEVER commit this — add it to .gitignore)
DATABASE_URL=postgres://localhost/myapp
PORT=8080
LOG_LEVEL=debug

# Load it into the current shell before running the app
set -a; source .env; set +a    # -a auto-exports every variable sourced
echo "$PORT"
# -> 8080
./app                           # now sees DATABASE_URL, PORT, LOG_LEVEL
Never commit a .env that contains real credentials, and never echo a secret value into a log or a chat. If a secret is ever committed or printed, treat it as compromised and rotate it — scrubbing it from history is slower and less reliable than issuing a new one.

Exercises

  • Set a variable without exporting it, confirm a child shell cannot see it, then export it and confirm it can.
  • Print your PATH, then use which and type -a to find every python or python3 on it.
  • Add $HOME/bin to the front of your PATH in ~/.bashrc, create a trivial script there, make it executable, and run it by name alone.
  • Create a .env with two variables, load it with set -a; source .env; set +a, and confirm both are exported with printenv.

Mini-project: a project .envrc loader

Build a small, safe loader so that entering a project directory sets its environment and leaving it unsets it — the manual version of what tools like direnv automate.

# In the project: .env (gitignored) holds the values
cat > .env <<'EOF'
APP_ENV=development
API_BASE=http://localhost:8080
EOF
echo ".env" >> .gitignore

# A loader function in ~/.bashrc
cat >> ~/.bashrc <<'EOF'
loadenv() {
  if [ -f .env ]; then
    set -a; source ./.env; set +a
    echo "loaded $(grep -c = .env) vars from $(pwd)/.env"
  else
    echo "no .env here"
  fi
}
EOF
source ~/.bashrc

cd myproject && loadenv
# -> loaded 2 vars from /home/ada/myproject/.env
echo "$API_BASE"
# -> http://localhost:8080

You now have a repeatable way to pull per-project config out of a gitignored file into the environment, keeping secrets out of both the code and your global shell profile — the foundation every deployment pipeline builds on.
