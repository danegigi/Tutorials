A fresh Linux server is reachable, running services, and trusting defaults — which is exactly what an attacker counts on. Hardening is the disciplined reduction of that attack surface: lock down SSH, close ports with a firewall, enforce mandatory access control, catch brute-force attempts, keep patched, and audit what happened. This lesson is a practical, ordered checklist with the commands.

The principle: reduce attack surface

Beginner Every open port, running service, privileged account, and default credential is surface. Hardening asks three questions of each: is it needed? (if not, remove it), is it exposed? (if not necessary, firewall it), and is it least-privilege? (drop root, drop capabilities). Defense in depth means no single control is your only line.

Harden SSH first — it's the front door

# /etc/ssh/sshd_config  (or a drop-in in /etc/ssh/sshd_config.d/)
PermitRootLogin no               # never log in as root directly
PasswordAuthentication no        # keys only — kills password brute-force
PubkeyAuthentication yes
AllowUsers deploy admin          # explicit allowlist
MaxAuthTries 3
X11Forwarding no
# then: sshd -t  (test config)  &&  systemctl reload ssh
Never disable password auth before you've confirmed key login works — open a SECOND SSH session, verify your key logs in, and only then reload ssh. Keep that second session open until you've reconnected fresh. Locking yourself out of a remote box with no console is the single most common hardening disaster.

Close ports with a firewall

# Ubuntu (ufw) — simplest correct default
ufw default deny incoming
ufw default allow outgoing
ufw limit 22/tcp                 # 'limit' rate-limits SSH (anti-brute-force)
ufw allow 80,443/tcp
ufw enable
ufw status verbose

Deny-by-default inbound is the goal: only the ports you explicitly allow are reachable. ufw limit throttles repeated SSH connections automatically. (firewalld's equivalent is zones + firewall-cmd.)

Keep it patched — automatically

# Debian/Ubuntu: unattended security upgrades
apt install unattended-upgrades
dpkg-reconfigure -plow unattended-upgrades
# RHEL/Fedora:
dnf install dnf-automatic && systemctl enable --now dnf-automatic.timer
Most breaches exploit known vulnerabilities with available patches. Automatic security updates close that window with near-zero effort — the highest return-on-effort hardening step after SSH keys. Reserve manual control for kernel/reboot-requiring updates.

Mandatory Access Control: SELinux vs AppArmor

Advanced Beyond file permissions, MAC confines what a process can do even if compromised — a hacked web server can't read /etc/shadow if policy forbids it.

Diagnoseausearch -m avc, audit2whydmesg | grep DENIED
getenforce                       # Enforcing | Permissive | Disabled
setenforce 0                     # TEMP permissive to test (not a fix!)
# SELinux: when something is "mysteriously" denied, check AVC denials:
ausearch -m avc -ts recent
# AppArmor:
aa-status; aa-complain /etc/apparmor.d/usr.sbin.myapp
Do NOT "fix" an SELinux/AppArmor problem by disabling it. A permanent setenforce 0 or SELINUX=disabled throws away a whole security layer. The right move is to read the denial (ausearch/audit2why or dmesg) and either set the correct label/boolean or adjust the profile. Disabling MAC is the hardening equivalent of unplugging the smoke detector.

Catch brute-force with fail2ban

apt install fail2ban
# /etc/fail2ban/jail.local
[sshd]
enabled = true
maxretry = 4
bantime = 1h
findtime = 10m
# fail2ban watches logs and bans IPs via the firewall after N failures.
fail2ban-client status sshd       # banned IPs, counts

Audit what happens: auditd

apt install auditd
# watch a sensitive file for any access:
auditctl -w /etc/shadow -p rwa -k shadow-watch
ausearch -k shadow-watch          # who touched it, when
# auditd gives you a tamper-evident record for forensics & compliance.

Accounts, sudo, and least privilege

  • No shared accounts — one login per person, so auth.log attributes actions.
  • Grant specific sudo rights, not blanket ALL; use visudo and prefer group-based rules.
  • Disable or lock unused system accounts; set nologin shells for service accounts.
  • Enforce password/key policy; consider MFA (e.g. pam_google_authenticator) for SSH.

Measure yourself

# Lynis — a free hardening auditor that scores the host and lists fixes
apt install lynis && lynis audit system
# Or map against the CIS Benchmark for your distro.

Common mistakes

  • Disabling password auth or enabling the firewall before verifying your way back in — lockout. Always keep a second verified session open.
  • Disabling SELinux/AppArmor to make an error go away instead of reading and fixing the denial.
  • Leaving default-allow inbound — a firewall that permits everything protects nothing.
  • Running services as root and skipping MAC, so one bug is total compromise.
  • No automatic patching, leaving known CVEs open for weeks.
  • Treating hardening as one-time — new services add surface; re-audit (Lynis/CIS) periodically.

Exercises

  • Harden sshd (no root, keys only, allowlist) safely using a second session, and confirm password login is refused.
  • Set a deny-by-default ufw/firewalld policy allowing only SSH + HTTP(S), with SSH rate-limited, and verify with a port scan from another host.
  • Trigger an SELinux or AppArmor denial on purpose (e.g. a service reading an unlabeled path), then diagnose it with ausearch/dmesg and fix it without disabling MAC.
  • Install fail2ban, fail several SSH logins from a test IP, and confirm the ban with fail2ban-client status sshd.
  • Run lynis audit system, pick the three highest-value suggestions, apply them, and re-run to see the score move.

Mini-project

Take a fresh VM from default to hardened and document every step as a repeatable runbook: key-only SSH (no root, allowlist, rate-limited) verified without lockout, deny-by-default firewall with only required ports, unattended security updates, MAC left enforcing with one real denial diagnosed and fixed properly, fail2ban on SSH, auditd watching /etc/shadow and /etc/passwd, and least-privilege sudo. Finish by running Lynis before and after, recording the score improvement, and listing which CIS Benchmark items you satisfied.
