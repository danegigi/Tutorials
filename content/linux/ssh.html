SSH is how you reach every remote machine — the shell on a cloud server, the Git push over an encrypted channel, the file copy to a droplet. It is built on public-key cryptography, so once you understand key pairs the rest (config files, agents, tunnels, file copy) falls into place. This lesson takes you from generating a key to forwarding a port through an encrypted tunnel, with the security pitfalls called out as you go.

Key pairs, not passwords

Beginner An SSH key pair is two files: a private key that never leaves your machine, and a public key you freely hand out. The server stores your public key; when you connect, SSH proves you hold the matching private key without ever sending it. This is far stronger than a password and the only sane option for servers.

# Generate a modern ed25519 key pair
ssh-keygen -t ed25519 -C "ada@laptop"
# -> Enter file in which to save the key (/home/ada/.ssh/id_ed25519):
# -> Enter passphrase (empty for no passphrase):      <- set one!
# -> Your identification has been saved in /home/ada/.ssh/id_ed25519
# -> Your public key has been saved in /home/ada/.ssh/id_ed25519.pub

ls -l ~/.ssh/id_ed25519*
# -> -rw------- 1 ada ada 411 id_ed25519        (private: 600, owner only)
# -> -rw-r--r-- 1 ada ada  97 id_ed25519.pub    (public: safe to share)
Prefer ed25519 over RSA: the keys are tiny, fast, and at least as secure. Only fall back to ssh-keygen -t rsa -b 4096 for an old server that does not support ed25519. Always set a passphrase on the private key — it encrypts the key at rest, so a stolen laptop does not immediately hand over your servers.

authorized_keys: granting access

To let your key log into a server, append its public half to ~/.ssh/authorized_keys on that server. ssh-copy-id does this for you:

ssh-copy-id -i ~/.ssh/id_ed25519.pub ada@203.0.113.10
# -> Number of key(s) added: 1

# ...or by hand, which is what ssh-copy-id does under the hood:
cat ~/.ssh/id_ed25519.pub | ssh ada@203.0.113.10 \
  'mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys'

# Now connect with no password
ssh ada@203.0.113.10
# -> Welcome to Ubuntu 24.04 LTS
Common mistake: copying the private key to the server, or pasting it anywhere. The private key must never leave your machine — only the .pub file goes on servers. If you ever leak a private key, delete its line from every authorized_keys and generate a new pair. Also: SSH refuses keys and authorized_keys files with loose permissions, so keep ~/.ssh at 700 and the files at 600.

~/.ssh/config: stop retyping

Intermediate Instead of long ssh -i ~/.ssh/key -p 2222 user@host commands, declare each host once in ~/.ssh/config and connect by a short alias.

# ~/.ssh/config
Host web
    HostName 203.0.113.10
    User ada
    IdentityFile ~/.ssh/id_ed25519
    Port 22

Host db
    HostName 10.0.0.5
    User postgres
    ProxyJump web          # reach db THROUGH web (a bastion host)

Host *
    ServerAliveInterval 60 # keep idle connections from dropping
ssh web                   # expands to ssh -i ~/.ssh/id_ed25519 ada@203.0.113.10
ssh db                    # transparently hops through 'web' first
scp report.csv web:/tmp/  # the alias works everywhere ssh does

ssh-agent and forwarding

Intermediate If your key has a passphrase (it should), ssh-agent holds the decrypted key in memory so you type the passphrase once per session instead of once per connection.

eval "$(ssh-agent -s)"            # start the agent
# -> Agent pid 4821
ssh-add ~/.ssh/id_ed25519        # add the key (prompts for passphrase once)
# -> Identity added: /home/ada/.ssh/id_ed25519 (ada@laptop)
ssh-add -l                       # list keys the agent holds

# Agent forwarding: use your LOCAL keys from a remote host (e.g. to git clone there)
ssh -A web
# on 'web', your laptop's key is used for the next hop — no key stored on the server
Agent forwarding (-A) is convenient but means anyone with root on the remote host can use your agent to authenticate as you while you are connected. Only forward to hosts you fully trust, and prefer ProxyJump (which does not expose your agent on the intermediate host) for simple bastion hops.

Tunnels: forwarding ports

Advanced SSH can carry arbitrary TCP connections through its encrypted channel. This is how you reach a database bound to 127.0.0.1 on a remote server, or expose a local dev server to a remote box.

FlagDirectionMeaning
-LLocal → remoteOpen a port on your machine that forwards to a host:port reachable from the server.
-RRemote → localOpen a port on the server that forwards back to a host:port reachable from you.
-DDynamicA local SOCKS proxy that tunnels everything through the server.
 
# -L: reach the remote Postgres (bound to localhost on the server) from your laptop
ssh -L 5433:localhost:5432 web
# now 'psql -h localhost -p 5433' on your laptop hits the server's Postgres

# -R: expose your local dev server (port 3000) on the remote box's port 8000
ssh -R 8000:localhost:3000 web
# now something on 'web' hitting localhost:8000 reaches your laptop's :3000

# -L without a login shell (-N = no command, -f = background)
ssh -fN -L 5433:localhost:5432 web

Copying files: scp and rsync

Beginner scp copies files over SSH with scp-like syntax; rsync is smarter — it transfers only the differences, resumes, and preserves attributes, making it the right choice for directories and repeated syncs.

# scp: single files, simple cases
scp app.tar.gz web:/opt/app/              # local -> remote
scp web:/var/log/app.log ./               # remote -> local
scp -r ./dist web:/var/www/site           # a directory (-r)

# rsync: directories, incremental, resumable — prefer for anything non-trivial
rsync -avz ./dist/ web:/var/www/site/     # archive, verbose, compress
rsync -avz --delete ./dist/ web:/var/www/site/   # mirror: delete extras on the far side
# -> sending incremental file list
# -> index.html
# -> sent 2,041 bytes  received 35 bytes  speedup is 118.6
rsync --delete removes files on the destination that are not in the source — it is a true mirror. Run it once without --delete (or add --dry-run) to preview what it would do before letting it delete anything. And mind the trailing slash: rsync src/ dst/ copies the contents of src, while rsync src dst/ copies the src directory itself into dst.

Mini-project: passwordless deploy over an SSH tunnel

Set up key-based access to a server, alias it in your config, then use an rsync over SSH to deploy a static site — the exact flow a simple CI deploy uses.

# 1. Key + config
ssh-keygen -t ed25519 -f ~/.ssh/deploy -C "deploy@ci" -N "ci-passphrase"
ssh-copy-id -i ~/.ssh/deploy.pub ada@203.0.113.10
cat >> ~/.ssh/config <<'EOF'
Host prod
    HostName 203.0.113.10
    User ada
    IdentityFile ~/.ssh/deploy
EOF

# 2. Preview the deploy (dry run — changes nothing)
rsync -avz --delete --dry-run ./public/ prod:/var/www/site/
# -> (lists exactly what WOULD be sent/deleted)

# 3. Deploy for real
rsync -avz --delete ./public/ prod:/var/www/site/
# -> sent 48,112 bytes  received 212 bytes

# 4. Verify over the same SSH connection
ssh prod 'ls /var/www/site | head'
# -> index.html  assets  about.html

You now have a one-command deploy that authenticates with a dedicated key, previews before it destroys, and runs entirely over an encrypted channel — the backbone of every push-to-deploy pipeline.
