Scheduled work — nightly backups, hourly cleanups, a report every Monday — is handled two ways on Linux. The classic tool is cron, dead simple and everywhere. The modern alternative is a systemd timer, which pairs a .service with a .timer and gives you logging, dependencies, and catch-up for missed runs. This lesson teaches both and when to reach for each.

cron: the classic scheduler

Beginner Each user has a crontab — a table of jobs. You edit it with crontab -e, list it with crontab -l. Every line is five time fields followed by the command.

crontab -e        # edit your crontab (opens $EDITOR)
crontab -l        # list current jobs
crontab -r        # remove ALL your jobs (careful — no confirmation)

The five fields, left to right:

# ┌───────── minute        (0-59)
# │ ┌─────── hour          (0-23)
# │ │ ┌───── day of month  (1-31)
# │ │ │ ┌─── month         (1-12)
# │ │ │ │ ┌─ day of week   (0-7, 0 and 7 both = Sunday)
# │ │ │ │ │
# * * * * *  command to run
ScheduleMeaning
0 2 * * *Every day at 02:00.
*/15 * * * *Every 15 minutes.
0 9 * * 1-509:00 on weekdays (Mon–Fri).
30 3 1 * *03:30 on the 1st of every month.
0 */6 * * *Every 6 hours (00:00, 06:00, 12:00, 18:00).
@rebootOnce, when the machine boots.
@daily / @hourlyShorthand for 0 0 * * * / 0 * * * *.
 
# An example crontab
# Nightly backup at 02:15, log output
15 2 * * * /opt/scripts/backup.sh >> /var/log/backup.log 2>&1

# Clear the temp cache every 6 hours
0 */6 * * * find /var/cache/myapp -type f -mtime +1 -delete

# Warm the cache at boot
@reboot /opt/scripts/warm-cache.sh
Common mistakes with cron: (1) cron runs with a minimal environment — no ~/.bashrc, a bare PATH of usually just /usr/bin:/bin. A script that works at your prompt fails under cron because it cannot find a command. Fix: use absolute paths (/usr/local/bin/node) or set PATH= at the top of the crontab. (2) Jobs run silently — if you do not redirect output to a file, a failing job disappears. Always append >> /var/log/job.log 2>&1. (3) A % in a cron command is special (it means newline) and must be escaped as \%.

systemd timers: the modern alternative

Intermediate A systemd timer is two unit files that share a name: a .service describing what to run, and a .timer describing when. Compared to cron you gain: output captured in the journal automatically, the ability to depend on other units, a Persistent= catch-up for runs missed while the machine was off, and randomised start delays to avoid thundering herds.

# /etc/systemd/system/backup.service  — WHAT to run
[Unit]
Description=Nightly backup

[Service]
Type=oneshot
ExecStart=/opt/scripts/backup.sh
User=backup
# /etc/systemd/system/backup.timer  — WHEN to run it
[Unit]
Description=Run backup nightly

[Timer]
OnCalendar=*-*-* 02:15:00     # every day at 02:15
Persistent=true               # if the machine was off at 02:15, run on next boot
RandomizedDelaySec=300        # spread the start over a 5-minute window

[Install]
WantedBy=timers.target

Enable and inspect it:

sudo systemctl daemon-reload
sudo systemctl enable --now backup.timer     # start the timer (not the service)
systemctl list-timers backup.timer
# -> NEXT                        LEFT     UNIT          ACTIVATES
# -> Fri 2026-10-09 02:15:00 UTC 15h left backup.timer  backup.service

systemctl status backup.timer                # is the timer armed?
sudo systemctl start backup.service          # run the job NOW, on demand
journalctl -u backup.service --since today   # its output is in the journal

OnCalendar syntax

The OnCalendar= value is more readable than cron's five fields. Test any expression with systemd-analyze calendar:

OnCalendarMeaning
dailyEvery day at 00:00.
hourlyTop of every hour.
Mon *-*-* 09:00:0009:00 every Monday.
*-*-* 02:15:0002:15 every day.
*-*-01 03:00:0003:00 on the 1st of each month.
*:0/15Every 15 minutes.
 
systemd-analyze calendar "Mon *-*-* 09:00:00"
# -> Normalized form: Mon *-*-* 09:00:00
# -> Next elapse: Mon 2026-10-12 09:00:00 UTC

cron vs timer — which to use

Considerationcronsystemd timer
Setup effortOne line.Two unit files + enable.
Output / loggingYou must redirect to a file.Captured in the journal automatically.
Missed runs (machine off)Skipped.Persistent=true catches up.
Dependencies / orderingNone.Full After=/Requires=.
Run on demandAwkward.systemctl start x.service.
Rule of thumb: for a quick personal job on your own machine, cron is fine and faster to write. For anything on a managed server — especially if you want logging, catch-up, or to run it manually too — a systemd timer is worth the extra file.

Exercises

  • Write cron lines for: every 5 minutes; 06:30 every weekday; the 1st of each quarter (Jan/Apr/Jul/Oct) at midnight.
  • Add a crontab entry that appends the date to a log file every minute, watch it with tail -f, then remove it.
  • Convert that same “append the date” job into a .service + .timer pair and confirm it with systemctl list-timers.
  • Use systemd-analyze calendar to find the next run time of *-*-* 00/4:00:00 and say in words what it means.

Mini-project: a nightly backup, done both ways

Schedule the same backup job with cron and with a systemd timer, so you can compare them directly.

# The job itself: /opt/scripts/backup.sh
#!/usr/bin/env bash
set -euo pipefail
dest=/var/backups
mkdir -p "$dest"
tar czf "$dest/site-$(date +%F).tar.gz" -C /var/www site
find "$dest" -name 'site-*.tar.gz' -mtime +7 -delete   # keep a week
echo "backup complete $(date -Iseconds)"
# Option A — cron (one line, remember to redirect output)
( crontab -l 2>/dev/null; echo "15 2 * * * /opt/scripts/backup.sh >> /var/log/backup.log 2>&1" ) | crontab -
crontab -l | tail -1
# -> 15 2 * * * /opt/scripts/backup.sh >> /var/log/backup.log 2>&1

# Option B — systemd timer (the .service + .timer from above)
sudo systemctl daemon-reload
sudo systemctl enable --now backup.timer
systemctl list-timers backup.timer
# -> NEXT ... backup.timer backup.service

# Prove the systemd version runs on demand and logs itself
sudo systemctl start backup.service
journalctl -u backup.service -n 2
# -> backup complete 2026-10-08T10:30:00+00:00

The cron version is one line but silent unless you wired up the redirect; the systemd version took two files but gives you on-demand runs, journald logging, and catch-up for free. That trade-off is the whole decision.
