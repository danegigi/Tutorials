A container isn't a lightweight VM — it's just a normal Linux process with a restricted view of the system. That view is built from three kernel features: namespaces (what it can see), cgroups (what it can use), and chroot/pivot_root (what filesystem it has). Understanding them demystifies Docker entirely.

A container is a process

Beginner Run a container, then look from the host — it's a plain process in the host's process list:

docker run -d --name web nginx
ps aux | grep nginx          # the nginx process is RIGHT THERE on the host
# There's no VM, no guest kernel — the container shares the host kernel.
# "Isolation" is the kernel showing that process a limited view of itself.

Namespaces: what a process can see

Intermediate Each namespace type isolates one kind of resource. A container gets its own set, so it sees its own PIDs, network, mounts, and hostname — unaware of the host or its neighbors.

NamespaceIsolates
pidProcess IDs — the container's first process is PID 1.
netNetwork interfaces, IPs, ports, routing.
mntMount points / filesystem view.
utsHostname & domain.
ipcShared memory, semaphores.
userUID/GID mapping — root in the container ≠ root on the host.
 
# Create a new UTS + PID + mount namespace by hand — a mini "container":
sudo unshare --fork --pid --mount-proc --uts bash
# inside:
hostname container-demo      # changing it does NOT affect the host
ps aux                       # you only see processes in THIS pid namespace
echo $$                      # your shell is PID 1 here
This unshare demo is the core of what Docker does — Docker just automates creating all the namespaces, setting up networking, and layering a root filesystem. "Container" is a packaging word for "a process in its own namespaces with resource limits."

cgroups: what a process can use

Control groups cap and account resources — CPU, memory, I/O — so one container can't starve the host or its neighbors:

docker run --memory=256m --cpus=0.5 nginx     # hard limits via cgroups
# Under the hood (cgroup v2):
cat /sys/fs/cgroup/.../memory.max             # the byte limit
cat /sys/fs/cgroup/.../cpu.max                # the CPU quota
This is why a container OOM-kills: when a process exceeds its cgroup memory.max, the kernel kills it (exit code 137) — the host is fine, just that container's limit was hit. Set container memory limits deliberately (echoing the Kubernetes resource lesson); no limit means one container can consume all host RAM.

The root filesystem: images & layers

# A container's filesystem is a chroot-like isolated root, built from image layers.
# chroot is the ancestor of this idea:
sudo chroot /path/to/rootfs /bin/sh    # that process now sees rootfs as /
# Docker uses overlayfs to stack read-only image layers + a writable top layer,
# and pivot_root (not plain chroot) for stronger isolation.

Why this matters

  • Security: containers share the host kernel — a kernel exploit can escape. That's why you drop capabilities, run non-root (user namespaces), and don't treat containers as a hard security boundary like a VM.
  • Debugging: nsenter lets you enter a running container's namespaces from the host to inspect it; a "container" process shows up in host tools like any other.
  • Resource bugs: "it works locally but OOMs in prod" is almost always a cgroup memory limit — now you know where to look.
Common misconception: "containers are mini-VMs." They are not — there's no guest kernel and no hardware virtualization. That's why they start in milliseconds and are lightweight, but also why isolation is weaker than a VM's. Know the trade-off when you choose containers vs VMs for untrusted workloads.

Exercises

  • Use unshare --fork --pid --mount-proc to get a shell that's PID 1 and can't see host processes.
  • Run a container with --memory=100m, stress it past the limit, and observe the OOM kill (exit 137).
  • Find a running container's main process in the host ps output and enter its namespaces with nsenter.

Mini-project: build a container by hand

Without Docker, assemble a minimal "container": download a small rootfs (e.g. Alpine's mini root fs tarball), unshare new PID/mount/UTS/net namespaces, chroot into the rootfs, mount /proc, set a hostname, and run a shell — then apply a cgroup memory limit to it. You'll have reproduced, by hand, what docker run does for you, which makes the DevOps Docker lesson click.
