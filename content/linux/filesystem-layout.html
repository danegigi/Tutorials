On Linux there are no drive letters — every file, every disk, every device hangs off one single tree that starts at /. The Filesystem Hierarchy Standard (FHS) is the shared agreement about what lives where, so that /etc means configuration on Ubuntu, Fedora, and Alpine alike. Knowing the map means you can land on an unfamiliar server and immediately know where to look for config, logs, and data.

Everything hangs off root

Beginner / is the root of the tree. Additional disks, USB sticks, and network shares are mounted onto directories inside it rather than appearing as separate letters. df -h shows what is mounted where:

df -h
# -> Filesystem      Size  Used Avail Use% Mounted on
# -> /dev/root        39G   12G   26G  32% /
# -> /dev/sdb1       100G   8G    87G   9% /data
# -> tmpfs           2.0G     0  2.0G   0% /dev/shm

Read it as: the main disk is mounted at /, a second disk at /data, and a RAM-backed filesystem at /dev/shm. From inside the shell it is all one seamless tree.

The top-level directories

PathWhat lives there
/The root. Everything else is somewhere beneath it.
/etcSystem-wide configuration — text files. /etc/ssh/sshd_config, /etc/hosts, /etc/nginx/.
/varVariable data that changes while the system runs: logs (/var/log), caches, spools, databases.
/usrInstalled programs and libraries — /usr/bin, /usr/lib, /usr/share. Read-only in normal use.
/homeEach regular user's personal directory: /home/ada. Root's home is /root, not here.
/tmpScratch space anyone can write to. Wiped on reboot (or periodically) — never store anything you want to keep.
/procA virtual filesystem exposing the kernel and running processes as files. Not on disk.
/devDevice nodes: disks (/dev/sda), terminals, and special files (/dev/null, /dev/random).
/optSelf-contained third-party software that does not follow the usual split, e.g. /opt/app.
/bin, /sbin, /libCore commands and libraries; on modern distros these are symlinks into /usr.

/etc — where configuration lives

Beginner When something is misconfigured, /etc is almost always where the fix is. The files are plain text you can read and edit (with sudo).

ls /etc | head
# -> apt  cron.d  fstab  hosts  hostname  nginx  passwd  ssh  systemd

cat /etc/hostname
# -> web-01

grep -v '^#' /etc/ssh/sshd_config | grep -v '^$' | head -3
# -> Port 22
# -> PermitRootLogin no
# -> PasswordAuthentication no
/etc/fstab declares which filesystems mount at boot, and /etc/hosts maps names to IPs locally (checked before DNS). Both are first stops when a disk or a hostname misbehaves.

/var — data that grows

Anything that accumulates while the machine runs lives under /var. The one you will visit most is /var/log:

ls /var/log
# -> auth.log  nginx  syslog  journal  dpkg.log

du -sh /var/log/*
# -> 12M   /var/log/nginx
# -> 48M   /var/log/journal
# ->  3M   /var/log/syslog
Common mistake: a disk that fills to 100% is very often /var/log or /var/lib/docker growing unchecked — the system then fails in confusing ways (cannot write sessions, cannot start services). Diagnose with df -h to find the full filesystem, then du -sh /var/* | sort -h to find the offender. The fix is logrotate or pruning images, never deleting files blindly.

/proc — the kernel as files

Advanced /proc is not stored on any disk; the kernel generates it on the fly. Reading these files is how tools like ps and top actually work:

cat /proc/cpuinfo | grep -c ^processor
# -> 4                      (number of CPU cores)

cat /proc/meminfo | head -2
# -> MemTotal:        4030152 kB
# -> MemFree:          812400 kB

cat /proc/loadavg
# -> 0.14 0.09 0.05 1/312 20481    (1/5/15-min load averages)

ls /proc/self/   # the directory for the process reading it right now
# -> cmdline  cwd  environ  fd  limits  status

/dev — devices and the useful special files

command 2>/dev/null        # /dev/null swallows output you do not want
head -c 16 /dev/urandom | base64   # a source of random bytes
# -> 3Qx9pLm2vTkY8sRa1bZc==

ls -l /dev/sda*            # the first disk and its partitions
# -> brw-rw---- 1 root disk 8, 0 Oct  8 /dev/sda
# -> brw-rw---- 1 root disk 8, 1 Oct  8 /dev/sda1

Where should YOUR app go?

A deployed application typically splits across the tree the FHS way:

ThingConventional location
The binary / code/opt/myapp or /usr/local/bin
Config/etc/myapp/config.yaml
Logs/var/log/myapp/ (or just use journald)
Mutable data (uploads, DB)/var/lib/myapp/
Runtime files (PID, sockets)/run/myapp/

Exercises

  • Run df -h and identify which filesystem your home directory lives on.
  • Find your machine's total RAM and free RAM from /proc/meminfo without using free.
  • Use du -sh /var/* 2>/dev/null | sort -h to find the largest consumer under /var.
  • Read /etc/hosts and add an entry (with sudo) mapping myapp.local to 127.0.0.1, then ping myapp.local.

Mini-project: lay out a deployment the FHS way

Place a fictional app widgetd across the tree following the conventions above, then confirm each piece landed where it belongs.

sudo mkdir -p /opt/widgetd /etc/widgetd /var/log/widgetd /var/lib/widgetd
sudo tee /etc/widgetd/config.yaml >/dev/null <<'EOF'
port: 8080
data_dir: /var/lib/widgetd
EOF
echo '#!/bin/sh\necho widgetd stub' | sudo tee /opt/widgetd/widgetd >/dev/null
sudo chmod +x /opt/widgetd/widgetd

# Verify the layout
find /opt/widgetd /etc/widgetd /var/log/widgetd /var/lib/widgetd
# -> /opt/widgetd
# -> /opt/widgetd/widgetd
# -> /etc/widgetd
# -> /etc/widgetd/config.yaml
# -> /var/log/widgetd
# -> /var/lib/widgetd

Now any colleague — or any monitoring tool — can find this app's config, data, and logs on the first guess, because it follows the same map every other service does.
