You almost never install software on Linux by downloading an installer — you ask a package manager, which fetches signed packages from configured repositories, resolves their dependencies, and tracks exactly what is installed so you can cleanly remove it later. Which tool you use depends on the distro family: apt on Debian/Ubuntu, dnf/yum on Fedora/RHEL, and pacman on Arch. This lesson covers the everyday commands for all three and when each applies.

Why a package manager at all

Beginner A package manager solves three problems at once: it resolves dependencies (installing a web server pulls in the libraries it needs), it verifies authenticity (packages are signed by the repository's key), and it tracks ownership (every file knows which package put it there, so uninstalling is clean). Downloading a tarball by hand gives up all three.

apt — Debian and Ubuntu

Beginner apt works in two steps you must not confuse: update refreshes the list of available packages from the repositories; upgrade actually installs newer versions. Run update before installing anything.

sudo apt update                 # refresh the package index (does NOT install)
# -> Hit:1 http://archive.ubuntu.com/ubuntu noble InRelease
# -> ... 12 packages can be upgraded. Run 'apt list --upgradable'

sudo apt upgrade                # install newer versions of installed packages
sudo apt install nginx          # install a package + its dependencies
sudo apt install -y htop curl   # -y to skip the confirmation prompt
sudo apt remove nginx           # remove the package, keep its config files
sudo apt purge nginx            # remove the package AND its config
sudo apt autoremove             # clean up dependencies nothing needs anymore
apt search json                 # find packages mentioning 'json'
apt show nginx                  # version, size, dependencies, description
dpkg -l | grep nginx            # what's installed (dpkg is the low-level tool)
Common mistake: running sudo apt install <pkg> immediately after the machine has been up for weeks, hitting a 404 on an old package version. The cached index is stale and points at files the mirror has since replaced. Always sudo apt update first — it is cheap and fixes the vast majority of “package not found” and “hash sum mismatch” errors.

dnf / yum — Fedora, RHEL, CentOS, Rocky, Alma

Beginner dnf is the modern tool; yum is its predecessor and still works as an alias on many systems. Unlike apt, there is no separate “update the index” step — dnf refreshes metadata automatically.

sudo dnf install nginx          # install (metadata refreshed automatically)
sudo dnf upgrade                # upgrade everything (equivalent to apt upgrade)
sudo dnf remove nginx           # remove a package
sudo dnf search json            # find packages
dnf info nginx                  # details about a package
sudo dnf check-update           # list available updates without installing
dnf list installed | grep nginx # what's installed
sudo dnf autoremove             # drop now-unneeded dependencies
On RHEL-family systems, extra software often lives in the EPEL repository (Extra Packages for Enterprise Linux). If dnf install cannot find a common tool like htop, enable EPEL first: sudo dnf install epel-release.

pacman — Arch and Manjaro

Intermediate Arch's pacman uses terse single-letter flags that reward memorising a handful. The golden rule on Arch is to always update the whole system together (-Syu) rather than installing one package against a stale index — partial upgrades are unsupported and can break things.

sudo pacman -Syu                # sync + refresh + upgrade EVERYTHING (do this often)
sudo pacman -S nginx            # install a package
sudo pacman -R nginx            # remove the package
sudo pacman -Rns nginx          # remove it + unused dependencies + config
pacman -Ss json                 # search the repositories
pacman -Si nginx                # info about a package
pacman -Q | grep nginx          # query what's installed
pacman -Qdt                     # list orphaned dependencies to clean up
On Arch, never run pacman -Sy <pkg> (refresh index then install a single package) on its own — that is a partial upgrade, mixing new package metadata with old installed libraries, and is a known way to break a system. Always do a full pacman -Syu.

Repositories: where packages come from

Intermediate A package manager only installs from repositories it has been told to trust. For apt, those are declared under /etc/apt/sources.list.d/ with the signing keys in /etc/apt/keyrings/. Adding a vendor's repo (Docker, for example) means importing their key and pointing apt at their server:

# The modern, keyring-scoped way to add Docker's apt repo (Ubuntu)
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/ubuntu noble stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt update && sudo apt install docker-ce
Adding a repository means trusting whoever controls it to run code as root on your machine on every apt install. Only add repositories from vendors you trust, always pin the signing key (signed-by=), and prefer the distro's own packages when a recent-enough version exists there.

Mini-project: a reproducible provisioning snippet

Write the first-boot commands that bring a fresh Ubuntu server up to a known baseline — the kind of block that goes at the top of a cloud-init script or a Dockerfile. It must be non-interactive (no prompts) and idempotent enough to re-run.

#!/usr/bin/env bash
set -euo pipefail
export DEBIAN_FRONTEND=noninteractive     # no "configure this?" prompts

sudo apt update
sudo apt upgrade -y
sudo apt install -y --no-install-recommends \
  curl ca-certificates git htop ufw fail2ban

sudo apt autoremove -y                     # drop leftovers
sudo apt clean                             # free the downloaded-package cache

# Record exactly what we ended up with, for an audit trail
dpkg -l | awk '/^ii/ {print $2"="$3}' > /tmp/installed-packages.txt
wc -l /tmp/installed-packages.txt
# -> 612 /tmp/installed-packages.txt

Because every package came through apt, the /tmp/installed-packages.txt manifest is a complete, versioned record of the machine's software — the thing that makes a server reproducible instead of a one-off snowflake.
