Sooner or later you hit "address already in use", a server that feels slow, or a service you don't remember starting. The routine is always the same four steps: find what is listening, identify the process, stop it the right way, and verify it is gone. This lesson covers that routine on Linux servers and on macOS (zsh), including the cases where a plain kill doesn't work because systemd, Docker or launchd restarts the process.

Step 1: see what is listening

Beginner On Linux, ss is the modern replacement for netstat:

$ sudo ss -ltnp
State   Recv-Q  Send-Q  Local Address:Port   Peer Address:Port  Process
LISTEN  0       4096          0.0.0.0:22          0.0.0.0:*      users:(("sshd",pid=812,fd=3))
LISTEN  0       511           0.0.0.0:80          0.0.0.0:*      users:(("nginx",pid=1204,fd=6))
LISTEN  0       4096        127.0.0.1:5432        0.0.0.0:*      users:(("postgres",pid=990,fd=5))
LISTEN  0       128                 *:3000              *:*      users:(("node",pid=20311,fd=19))

The flags: -l listening sockets only, -t TCP, -n numeric ports (no name lookup), -p show the owning process. Use -u for UDP and drop -l to see established connections.

Without sudo, ss -p only shows processes owned by your user. A port that appears to have no owner is usually owned by root or another user. Re-run with sudo before concluding nothing is there.

One specific port

$ sudo ss -ltnp 'sport = :3000'
$ sudo lsof -nP -iTCP:3000 -sTCP:LISTEN
COMMAND   PID  USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
node    20311  gina   19u  IPv6 0x1234      0t0  TCP *:3000 (LISTEN)
$ sudo fuser -n tcp 3000
3000/tcp:            20311

All three answer the same question. ss is installed everywhere, lsof is the one that works the same on Linux and macOS, and fuser is the shortest.

macOS

macOS has no ss and its netstat does not show process IDs. Use lsof:

# Everything listening on TCP
lsof -nP -iTCP -sTCP:LISTEN

# One port
lsof -nP -iTCP:3000 -sTCP:LISTEN

# Just the PID (handy in scripts)
lsof -ti tcp:3000

-n skips DNS lookups and -P skips port-name lookups. Both make the command much faster and keep the output numeric.

Step 2: identify the process

Beginner A PID tells you little. Find out what it is, how long it has been running, and who its parent is:

$ ps -p 20311 -o pid,ppid,user,etime,cmd
    PID    PPID USER         ELAPSED CMD
  20311   20290 gina         02:14:37 node server.js --port 3000

# What started it? Follow the parent
$ ps -p 20290 -o pid,ppid,user,cmd
    PID    PPID USER     CMD
  20290       1 gina     npm run dev

A parent PID of 1 means systemd (or launchd on macOS) owns the process. That is your signal that a plain kill may be undone by a supervisor. More ways to look:

ls -l /proc/20311/cwd        # Linux: which directory it was started from
ls -l /proc/20311/exe        # Linux: the real binary
pstree -ps 20311             # the parent chain, if pstree is installed
systemctl status 20311       # Linux: is this PID part of a systemd service?
lsof -p 20311                # every file and socket it has open
Read the full command line before you kill anything. Two processes called node or python can be a throwaway dev server and your production worker.

Step 3: stop it

Beginner Always ask politely first. kill with no flag sends SIGTERM (15), which lets the process close connections, flush buffers and remove lock files:

kill 20311            # SIGTERM: graceful
sleep 3
kill -0 20311 && echo "still running"   # signal 0 only tests that the PID exists
kill -9 20311         # SIGKILL: cannot be caught, no cleanup. Last resort.
SignalNumberUse
SIGTERM15Default. Request a clean shutdown.
SIGINT2Same as Ctrl+C.
SIGHUP1Many daemons reload their config on this. Not a stop.
SIGKILL9Forced. Kernel removes the process. Data in flight is lost.
SIGSTOP / SIGCONT19 / 18Pause and resume without killing.

Shortcuts

# Kill whatever owns port 3000 (gracefully)
kill $(lsof -ti tcp:3000)

# Linux: fuser can do it directly
sudo fuser -k -TERM -n tcp 3000

# By name (matches the process name)
pkill node
pkill -f "server.js --port 3000"     # match the full command line, much safer than a bare name

# See what pkill would hit first
pgrep -af "server.js"
pkill node kills every node process you own, including the ones you forgot about. Run pgrep -af with the same pattern first, and prefer -f with a specific command line or a PID.

Step 4: verify the port is free

Beginner

$ lsof -nP -iTCP:3000 -sTCP:LISTEN
$ echo $?
1

No output and exit code 1 means nothing is listening, so the port is free. Exit code 0 with output means something still holds it. This is the opposite of what many people expect, because for lsof "success" means "found a match". On Linux, ss -ltn 'sport = :3000' printing only the header line means the same thing.

When kill doesn't stick

Intermediate If the process returns a few seconds after you kill it, something is supervising it. Stop it at the source, not the PID.

systemd (Linux servers)

# What services are running?
systemctl list-units --type=service --state=running

# Which unit owns this PID?
systemctl status 1204
# nginx.service - A high performance web server
#    Active: active (running) since Mon 2026-11-02 09:12:44 UTC; 2h ago
#  Main PID: 1204 (nginx)

# Stop it now (it will come back at reboot)
sudo systemctl stop nginx

# Stop it now AND keep it from starting at boot
sudo systemctl disable --now nginx

# Prove it is gone
systemctl is-active nginx          # inactive
sudo ss -ltnp 'sport = :80'        # no rows
Services can also be started on demand by a socket unit. If a port keeps reopening after you stop the service, check systemctl list-sockets and stop the .socket unit too.

Docker

$ docker ps --format 'table {{.ID}}\t{{.Names}}\t{{.Ports}}'
CONTAINER ID   NAMES     PORTS
a1b2c3d4e5f6   web       0.0.0.0:3000->3000/tcp
$ docker stop web
$ docker ps --filter publish=3000      # empty means nothing publishes that port

Killing the docker-proxy process directly does not stop the container and can leave Docker in an odd state. Always stop the container.

Homebrew and launchd (macOS)

brew services list                 # what brew is running
brew services stop postgresql@16

launchctl list | grep -i myapp     # loaded jobs
launchctl bootout gui/$(id -u)/com.example.myapp

A full inventory of a server

Intermediate When you land on an unfamiliar server, build the picture in this order:

# 1. Everything listening, with owners
sudo ss -ltnup

# 2. What systemd is running
systemctl list-units --type=service --state=running --no-pager

# 3. Containers
docker ps 2>/dev/null

# 4. The heaviest processes
ps aux --sort=-%mem | head -10
ps aux --sort=-%cpu | head -10

# 5. Who is connected right now
ss -tn state established | head
who

# 6. What changed recently
journalctl --since "1 hour ago" -p warning --no-pager | tail -30

Anything listening on 0.0.0.0 or * is reachable from the network. Anything on 127.0.0.1 is local only. A database or cache bound to 0.0.0.0 that you did not expect is a finding worth acting on.

Common port problems

Intermediate

"Address already in use" (EADDRINUSE)

Error: listen EADDRINUSE: address already in use :::3000

Run the four-step routine on that port. If nothing is listening but the error persists, the port may be in TIME_WAIT after a recent shutdown. Wait about a minute, or have the server set SO_REUSEADDR (most frameworks do by default).

Permission denied on port 80 or 443

Ports below 1024 are privileged. Run behind a reverse proxy on a high port, or grant the binary the capability instead of running as root:

sudo setcap 'cap_net_bind_service=+ep' /usr/local/bin/myserver

Bound to the wrong interface

If ss shows 127.0.0.1:3000 you cannot reach it from another machine, and if it shows 0.0.0.0:3000 everyone can. Check the app's host setting rather than the firewall first.

Zombie and uninterruptible processes

A process in state Z (zombie) is already dead and waiting for its parent to collect it. You cannot kill it, but killing the parent clears it. A process in state D (uninterruptible sleep, usually stuck on disk or NFS) ignores even kill -9 until the I/O returns.

ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^[ZD]/'

Scripting it safely

Advanced A small helper that frees a port, tries SIGTERM, waits, then escalates, and refuses to touch root-owned processes:

#!/usr/bin/env bash
# freeport.sh PORT  : stop whatever is listening on PORT
set -euo pipefail
port="${1:?usage: freeport.sh PORT}"

pids=$(lsof -ti "tcp:${port}" -sTCP:LISTEN || true)
[ -z "$pids" ] && { echo "port ${port} is already free"; exit 0; }

for pid in $pids; do
  owner=$(ps -o user= -p "$pid" | tr -d ' ')
  cmd=$(ps -o command= -p "$pid")
  if [ "$owner" = "root" ] && [ "$(id -u)" -ne 0 ]; then
    echo "pid ${pid} is owned by root, skipping: ${cmd}" >&2
    continue
  fi
  echo "stopping ${pid} (${owner}): ${cmd}"
  kill "$pid"
done

for _ in 1 2 3 4 5; do
  sleep 1
  lsof -ti "tcp:${port}" -sTCP:LISTEN >/dev/null || { echo "port ${port} is free"; exit 0; }
done

echo "still listening after 5s, sending SIGKILL" >&2
kill -9 $(lsof -ti "tcp:${port}" -sTCP:LISTEN) 2>/dev/null || true

Waiting for a port to open

# Block until something listens on 5432, or fail after 30 seconds
timeout 30 bash -c 'until (echo > /dev/tcp/127.0.0.1/5432) 2>/dev/null; do sleep 1; done' \
  && echo up || echo "timed out"

Check from the outside

ss and lsof tell you what the machine thinks. To test what a remote client sees, use nc -zv host 3000 or curl -v telnet://host:3000. If the local check passes and the remote one fails, look at the bind address, the firewall and the cloud security group, in that order.

Common mistakes

  • Jumping to kill -9. SIGKILL skips cleanup, so you can end up with corrupted files, stale lock files and dropped in-flight requests. Start with plain kill.
  • Killing by name. pkill node or killall python hits every match. Use the PID, or pkill -f with a full command line after checking it with pgrep -af.
  • Forgetting sudo when looking. A port with no visible owner usually belongs to another user. Look with sudo before deciding it is a ghost.
  • Fighting the supervisor. If it comes back after kill, stop the systemd unit, container, brew service or PM2 app instead.
  • Reading exit codes backwards. For lsof and grep, exit 0 means "found something". An empty result with exit 1 is the good outcome when you are freeing a port.
  • Stopping a service that is only disabled-at-boot. systemctl disable does not stop it now, and stop does not stop it at the next boot. Use disable --now for both.
  • Not checking what you are about to kill. Run ps -p PID -o cmd first, especially on a shared or production host.

Exercises

  1. Start a throwaway server with python3 -m http.server 8123. Find its PID three different ways (ss or lsof, fuser, pgrep -af), then stop it with SIGTERM and verify the port is free.
  2. Start the same server twice and read the "address already in use" error. Use the four-step routine to fix it without restarting your shell.
  3. Run sudo ss -ltnp on a machine you manage and write down every listening port, its owner, and whether it binds to 0.0.0.0 or 127.0.0.1. Pick one that surprises you and trace it to its unit or container.
  4. Create a systemd service that runs a simple server (see the Processes & Services lesson). Kill its PID and watch Restart=always bring it back, then stop it properly with systemctl stop.
  5. Start a container with a published port (docker run -d -p 8124:80 nginx), find it from the host with both ss and docker ps, and stop it.

Mini-project: a port doctor script

Write portdoctor.sh PORT that diagnoses one port in a single command. Requirements:

  • Print who is listening: PID, user, full command line, how long it has been running, and the bind address.
  • Say what supervises it: a systemd unit (with systemctl status summary), a Docker container (name and image), a brew service, or "none (plain process)".
  • Print the recommended stop command for that case, but do not run it unless --stop is passed.
  • With --stop, send SIGTERM, wait up to 5 seconds, then offer SIGKILL only after an explicit confirmation prompt.
  • Refuse to touch PID 1, root-owned processes (unless run with sudo), or sshd.
  • Work on both Linux (ss) and macOS (lsof) by detecting uname, and exit non-zero if the port is still in use at the end.
