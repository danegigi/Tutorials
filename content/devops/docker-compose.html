Docker Compose describes a multi-container application in a single declarative file and manages it as one unit — build images, start services on a shared network, wire up volumes, and gate startup on health, all with one command. This lesson uses modern conventions throughout: the docker compose v2 plugin (a subcommand, not the legacy docker-compose binary) and a compose file with no obsolete top-level version: key.

The compose file

Beginner Compose reads a declarative file (conventionally compose.yaml) and turns it into a running set of containers, a private network, and named volumes. You describe the desired state; Compose makes it so.

The key building blocks:

  • services — each container in your app.
  • build / image — build from a Dockerfile, or pull a prebuilt image.
  • ports — publish ports to the host ("HOST:CONTAINER").
  • env_file / environment — inject configuration.
  • depends_on with condition: service_healthy — start order plus readiness gating.
  • healthcheck — how Compose decides a service is actually ready, not just started.
  • volumes / networks — persistence and isolation, declared once and referenced by services.
Modern conventions: filename compose.yaml, command docker compose (space, not hyphen), and no top-level version: key — it is obsolete, and Compose uses the latest Compose Specification automatically.

Services

Intermediate Each entry under services becomes one container. A service either builds its own image or pulls one, publishes ports, and reaches other services by their service name over the project's private network.

# compose.yaml — a web service that builds from the local Dockerfile
name: shop-demo

services:
  web:
    build:
      context: .
      dockerfile: Dockerfile
    image: example/shop-web:local   # name the built image
    ports:
      - "8080:3000"                 # host 8080 -> container 3000
    environment:
      NODE_ENV: production
      DATABASE_URL: mysql://app:app@db:3306/shop
    restart: unless-stopped

Notice db inside DATABASE_URL: it is the name of the other service, resolved by Compose's built-in DNS. You never hard-code an IP.

Networks & volumes

Intermediate By default Compose creates one network for the project and attaches every service to it, so services reach each other by name out of the box. Declaring networks explicitly lets you keep a database off the public-facing network entirely. Named volumes keep data alive across docker compose down and container recreation.

services:
  web:
    # ...
    networks:
      - internal

  db:
    image: mysql:8.4
    volumes:
      - db_data:/var/lib/mysql     # persist the database
    networks:
      - internal                   # private: never published to the host

volumes:
  db_data:

networks:
  internal:
    driver: bridge

The database's port is never published — web reaches it as db:3306 over the private internal network. Expose the edge, keep data private.

Environment & profiles

Intermediate Configuration comes from environment (inline key/values) or env_file (a .env file loaded into the service). Compose also auto-reads a .env file in the project directory for variable interpolation inside the compose file itself.

services:
  web:
    env_file:
      - .env                 # loaded INTO the container
    environment:
      LOG_LEVEL: ${LOG_LEVEL:-info}   # interpolated from the project .env, default "info"

Profiles let you keep optional services in the same file but only start them when asked — a debug tool, a seed job, a local-only mail catcher:

services:
  mailhog:
    image: mailhog/mailhog:latest
    ports: ["8025:8025"]
    profiles: ["dev"]        # only starts when the "dev" profile is active
docker compose up -d                 # mailhog does NOT start
docker compose --profile dev up -d   # now it does
# -> [+] Running 3/3  ✔ web  ✔ db  ✔ mailhog

depends_on & healthchecks

Intermediate A bare depends_on only controls start order — it starts db before web, but does not wait for the database to be ready to accept connections. Combine it with a healthcheck and condition: service_healthy so web waits for a database that actually answers.

# compose.yaml — full web + MySQL stack, no top-level version field
name: shop-demo

services:
  web:
    build: .
    image: example/shop-web:local
    ports:
      - "8080:3000"
    environment:
      NODE_ENV: production
      DATABASE_URL: mysql://app:app@db:3306/shop
    depends_on:
      db:
        condition: service_healthy   # wait for HEALTHY, not merely "started"
    restart: unless-stopped
    networks:
      - internal

  db:
    image: mysql:8.4
    environment:
      MYSQL_DATABASE: shop
      MYSQL_USER: app
      MYSQL_PASSWORD: app
      MYSQL_RANDOM_ROOT_PASSWORD: "1"
    volumes:
      - db_data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uapp", "-papp"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s           # grace window before failures count
    restart: unless-stopped
    networks:
      - internal

volumes:
  db_data:

networks:
  internal:
    driver: bridge

The web service launches only once db reports healthy. The database keeps its data in db_data, and its port is never published.

start_period is the grace window during which a failing healthcheck does not count against retries — essential for databases and JVM apps that take tens of seconds to warm up. Without it, a slow starter is marked unhealthy before it ever finishes booting.

Compose v2 commands

Beginner The everyday verbs. All are docker compose (space), run from the directory containing compose.yaml.

CommandWhat it does
docker compose configValidate and render the final merged config.
docker compose up -d --buildBuild images and start everything detached.
docker compose up -d --force-recreateRecreate containers even if config is unchanged.
docker compose psWhat is running in this project.
docker compose logs -f webFollow one service's logs.
docker compose exec web shShell into a running service.
docker compose run --rm web npm testOne-off command in a fresh container.
docker compose downStop and remove containers + networks.
docker compose down -vALSO delete named volumes (destroys DB data).
 
docker compose up -d --build
# -> [+] Running 3/3
# ->  ✔ Network shop-demo_internal   Created
# ->  ✔ Container shop-demo-db-1      Healthy
# ->  ✔ Container shop-demo-web-1     Started

docker compose ps
# -> NAME                IMAGE                   STATUS                 PORTS
# -> shop-demo-web-1     example/shop-web:local  Up 20s                 0.0.0.0:8080->3000/tcp
# -> shop-demo-db-1      mysql:8.4               Up 25s (healthy)
Destructive: docker compose down -v deletes the project's named volumes — that wipes your database. Back it up (a volume snapshot or a mysqldump) before running it anywhere you care about.

Why --force-recreate matters

A plain docker compose up -d only recreates a container when its config changed. If you edit a file that Compose cannot see as a change (for example a mounted config the container reads at startup), the container keeps running stale. --force-recreate forces fresh containers; restart only restarts the process inside the existing container and does not re-read the compose file.

Log rotation for long-running services

The default json-file log driver grows without bound. Cap it on anything that runs for weeks:

services:
  api:
    image: example/api:1.0
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
    restart: unless-stopped

Common mistakes

Common mistakes
  • Expecting bare depends_on to wait for readiness. It only orders startup. Add a healthcheck + condition: service_healthy, or the app races the database and crashes on connect.
  • Connecting via localhost between services. Inside a container localhost is the container itself. Use the service name (db, api) — Compose DNS resolves it.
  • Keeping a top-level version: key. It is obsolete and emits a warning; delete it.
  • Running restart after editing the compose file. That only restarts processes. Use up -d (or --force-recreate) to apply config changes.
  • Reflexively running down -v. The -v wipes named volumes and your database with them.
  • Publishing the database port. A "3306:3306" on the DB exposes it to the host network — leave it unpublished and reach it over the private network.

Exercises

  • Write a two-service stack (app + Postgres) where the app waits for the database via healthcheck + condition: service_healthy, and confirm the ordering in docker compose logs.
  • Run docker compose config on a file with a deliberate typo (bad indent, unescaped $) and read how it fails.
  • Put the database on a private network with no published port and prove the app still reaches it by service name while the host cannot.
  • Add an optional adminer or mailhog service behind a dev profile and show it only starts with --profile dev.
  • Add json-file log rotation to a service and verify the cap with docker inspect.

Mini-project: a full local dev stack

Build a compose.yaml for a web app, a Postgres database, and a Redis cache. The web service builds from a local Dockerfile and waits on both backends via healthchecks; Postgres and Redis live on a private network with unpublished ports and named volumes for persistence. Load app config from a .env file, put a database-admin tool (Adminer) behind a dev profile, and cap every service's logs. Bring it up with one docker compose up -d --build, verify all services report healthy, write a row through the app, run docker compose down (without -v), bring it back up, and prove the data survived.
