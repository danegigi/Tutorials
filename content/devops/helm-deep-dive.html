Writing the same Kubernetes YAML with slightly different values for dev, staging, and prod gets unmaintainable fast. Helm is the package manager for Kubernetes: it templates your manifests, parameterizes them with values, bundles them as a versioned chart, and installs/upgrades/rolls back the whole set as one release.

Charts, releases, and values — the three nouns

Beginner

TermWhat it is
Charta package: templates + default values + metadata. The "class."
Releaseone installed instance of a chart in a cluster, with a name & revision history. The "object."
Valuesthe parameters that fill the templates — defaults in values.yaml, overridden per release.

Using an existing chart first

helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm search repo postgresql

# install with overrides
helm install mydb bitnami/postgresql \
  --set auth.database=app \
  --namespace data --create-namespace

helm list -n data
# NAME   NAMESPACE  REVISION  STATUS    CHART
# mydb   data       1         deployed  postgresql-15.x

helm upgrade mydb bitnami/postgresql --set primary.resources.requests.memory=512Mi
helm rollback mydb 1          # back to revision 1
helm uninstall mydb -n data
helm upgrade --install (idempotent: install if absent, upgrade if present) is the command you'll actually use in CI/CD — it works whether or not the release exists yet.

Authoring your own chart

helm create myapp
# myapp/
#   Chart.yaml          metadata (name, version, appVersion)
#   values.yaml         default values
#   templates/          the templated manifests
#     deployment.yaml
#     service.yaml
#     _helpers.tpl       reusable template snippets
#   charts/             subchart dependencies
# Chart.yaml
apiVersion: v2
name: myapp
version: 0.1.0        # the CHART version (bump on template changes)
appVersion: "1.4.0"   # the version of the app it deploys

The template engine

Intermediate Templates are YAML with Go template directives. Values come from .Values, chart metadata from .Chart, and release info from .Release.

# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          {{- with .Values.resources }}
          resources:
            {{- toYaml . | nindent 12 }}
          {{- end }}
# values.yaml
replicaCount: 2
image:
  repository: ghcr.io/me/myapp
  tag: ""           # falls back to .Chart.AppVersion
resources:
  requests: { cpu: 100m, memory: 128Mi }
Whitespace is the Helm beginner's nemesis. {{- trims the preceding newline, -}} the following one. Use nindent N (newline + indent) when injecting a block, and indent N when you're already on a fresh line. Get it wrong and you produce invalid YAML that fails at install, not at template time.

_helpers.tpl: don't repeat yourself

# templates/_helpers.tpl
{{- define "myapp.fullname" -}}
{{ .Release.Name }}-{{ .Chart.Name }}
{{- end -}}

{{- define "myapp.labels" -}}
app.kubernetes.io/name: {{ .Chart.Name }}
app.kubernetes.io/instance: {{ .Release.Name }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
{{- end -}}

Then reuse them: {{ include "myapp.labels" . | nindent 4 }}. include (not template) is preferred because its output can be piped into functions like nindent.

Render before you install

# See the final YAML WITHOUT touching the cluster — your fastest feedback loop
helm template myapp ./myapp --values prod-values.yaml

# Dry-run against the real API (validates against the cluster)
helm install myapp ./myapp --dry-run --debug

# Lint for structural problems
helm lint ./myapp
helm template is the single most useful command while authoring: it shows exactly what Kubernetes will receive, so you debug templates in seconds instead of install→fail→read-error cycles.

Flow control and functions

{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
# ...
{{- end }}

{{- range .Values.extraEnv }}
- name: {{ .name }}
  value: {{ .value | quote }}
{{- end }}

# required: fail the render if a value is missing
host: {{ required "ingress.host is required!" .Values.ingress.host }}

Useful functions: default, quote, toYaml, nindent, required, b64enc (for Secret data), and sha256sum (hash a ConfigMap into a pod annotation so changing config triggers a rollout).

Dependencies and subcharts

# Chart.yaml
dependencies:
  - name: postgresql
    version: "15.x.x"
    repository: https://charts.bitnami.com/bitnami
    condition: postgresql.enabled
helm dependency update ./myapp     # fetches subcharts into charts/
# parent values override subchart values under the subchart's key:
# values.yaml → postgresql: { auth: { database: app } }

Hooks: lifecycle actions

Advanced Annotate a resource to run it at a point in the release lifecycle — e.g. a Job that runs database migrations before the new pods come up.

metadata:
  annotations:
    "helm.sh/hook": pre-upgrade,pre-install
    "helm.sh/hook-weight": "0"
    "helm.sh/hook-delete-policy": hook-succeeded
Hooks are NOT reconciled like normal resources — a failed pre-upgrade hook aborts the upgrade, which is usually what you want for migrations. But because they're outside the release's managed set, a hook resource can linger if its delete policy is wrong.

When a chart beats raw YAML (and when it doesn't)

Reach for Helm when you deploy the same app across environments, publish software for others to install, or need rollback-as-a-command. Prefer plain YAML + Kustomize overlays when you have a handful of near-static manifests and the templating overhead isn't paying for itself. Many teams use both: Helm charts for third-party software, Kustomize for their own app (and Flux can drive either — see the GitOps lessons).

Common mistakes

  • Whitespace/indent errors from misusing indent/nindent/{{- — render with helm template to catch them instantly.
  • Confusing version (chart) with appVersion (your app) and never bumping the chart version, so helm upgrade doesn't see a change.
  • Putting secrets in values.yaml in Git. Use a secrets manager, SOPS, or Sealed Secrets, not plaintext values.
  • Not pinning dependency versions, so a subchart changes under you.
  • Using template instead of include when you need to pipe the result into nindent.
  • Forgetting a config-hash annotation, so changing a ConfigMap doesn't restart the pods that consume it.

Exercises

  • Install a public chart (e.g. nginx) with --set overrides, upgrade it with a changed value, then helm rollback and confirm the revision count with helm history.
  • Run helm create, then use helm template to see the rendered output; change replicaCount in values and confirm the diff.
  • Add a named template to _helpers.tpl for common labels and include it in both the Deployment and the Service.
  • Wrap a block of the Deployment in {{- if .Values.ingress.enabled }} and prove it appears/disappears based on the value.
  • Add a pre-install hook Job and watch it run before the main resources with helm install --debug.

Mini-project

Author a production-quality chart for a web app with a database: templated Deployment, Service, optional Ingress (gated behind ingress.enabled), a ConfigMap whose checksum annotation triggers rollouts, a Secret sourced from values (documented as "use SOPS in real life"), reusable labels in _helpers.tpl, a PostgreSQL subchart dependency behind a condition, and a pre-upgrade migration-Job hook. Ship values.yaml defaults plus dev-values.yaml and prod-values.yaml overrides, lint it, render both with helm template, and install it into a local cluster with helm upgrade --install.
