How you roll a new version out determines how much risk each release carries and how fast you can recover. The main strategies — rolling, blue/green, canary — trade off resource cost, blast radius, and rollback speed. Feature flags decouple deploy from release entirely.

Recreate (the naive one)

Beginner Stop all old instances, start all new ones. Simple, but there's downtime during the gap, and if the new version is broken you're down until you roll back.

Only acceptable where brief downtime is fine (internal tools, maintenance windows). For anything user-facing, use one of the zero-downtime strategies below.

Rolling update

Replace instances a few at a time: new ones come up healthy, old ones drain, repeat until done. No downtime, no extra capacity beyond a small surge. This is the Kubernetes default.

# Kubernetes rolling update knobs
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0     # never go below desired count
    maxSurge: 1           # at most one extra pod during the roll
# A readiness probe gates traffic: a pod gets requests only once it reports ready.
Common mistake: rolling updates with no readiness/health probe. Kubernetes then routes traffic to pods that are still starting (or crash-looping), causing errors mid-deploy. The probe is what makes "rolling" actually zero-downtime.

Blue/green

Intermediate Run two full environments: blue (current) and green (new). Deploy to green, test it in isolation, then flip the load balancer/router from blue to green instantly. Rollback is flipping back.

  LB → blue (v1)   [live]        LB → green (v2)  [live]
       green (v2)  [warming]  ⇒       blue (v1)   [standby, instant rollback]
ProCon
Instant switch & instant rollbackDouble the resources during the overlap
Full testing of green before any trafficDatabase migrations must work for both versions

Canary

Intermediate Release the new version to a small slice of traffic (1% → 10% → 50% → 100%), watching error rates and latency at each step. If metrics degrade, roll back having exposed only a few users.

# Progressive shift, gated on metrics (via a service mesh / ingress / Argo Rollouts)
1%  → observe 5m → errors ok? → 10% → observe → 50% → observe → 100%
                           ↳ metrics bad at any step → automatic rollback
Canary is the safest for high-traffic services because the blast radius of a bad release is a few percent of users for a few minutes. It requires good observability — you need real-time error/latency metrics to make the promote-or-rollback decision (see the Monitoring lesson).

Database migrations: the hard part

Any zero-downtime strategy means old and new code run simultaneously against the same database. Schema changes must be backward-compatible:

# The expand/contract (parallel-change) pattern:
1. EXPAND:   add the new column (nullable) — old code ignores it
2. MIGRATE:  deploy new code that writes BOTH old and new; backfill
3. CONTRACT: once all code uses the new column, drop the old one (later deploy)
Never rename or drop a column in the same deploy that ships the code depending on the change — during the roll, the other version breaks. Split it across deploys with expand/contract.

Feature flags: decouple deploy from release

Advanced Ship code to production dark (behind a flag that's off), then turn the feature on independently — for everyone, or a cohort — without a deploy. Deploying becomes low-risk (the code path is inert) and "releasing" becomes a config toggle you can instantly reverse.
