Once your workloads run on Kubernetes, the next step is making them reliable and efficient: health probes that gate traffic, resource requests/limits that keep the scheduler honest, autoscaling, pod placement control, and operators that encode operational knowledge.

Health probes

Intermediate Three probes tell Kubernetes whether a container is alive, ready for traffic, and done starting:

spec:
  containers:
    - name: api
      livenessProbe:        # restart the container if this fails
        httpGet: { path: /healthz, port: 8080 }
        initialDelaySeconds: 10
        periodSeconds: 10
      readinessProbe:       # remove from Service endpoints if this fails
        httpGet: { path: /ready, port: 8080 }
        periodSeconds: 5
      startupProbe:         # give slow starters time before liveness kicks in
        httpGet: { path: /healthz, port: 8080 }
        failureThreshold: 30
        periodSeconds: 2
The classic mistakes: (1) pointing livenessProbe at a check that depends on the database — a DB blip then restarts every pod, turning a small outage into a cascading one. Liveness should test only "is this process wedged?". (2) No readinessProbe, so a rolling update sends traffic to pods still warming up. (3) A slow-booting app with no startupProbe, so liveness kills it mid-startup in a crash loop.

Resource requests and limits

      resources:
        requests: { cpu: "100m", memory: "128Mi" }   # scheduler reserves this
        limits:   { cpu: "500m", memory: "256Mi" }    # hard ceiling

Requests drive scheduling (the node must have this much free) and define the pod's share under contention. Limits cap usage. Memory over the limit → the container is OOM-killed; CPU over the limit → it's throttled (not killed).

Common mistake: no requests at all, so the scheduler packs nodes blindly and pods fight for CPU/memory; or a memory limit far above the request, so a leak balloons until the pod is OOM-killed with no warning. Set requests from observed usage; keep memory limit = request to make the pod's footprint predictable (CPU limits are more debatable — many teams omit them to avoid throttling).

Horizontal Pod Autoscaler

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
# kubectl get hpa  →  watch replicas scale with load

The HPA needs the metrics-server installed and requests set (utilization is a % of the request). For cluster-level scaling of nodes, pair it with the Cluster Autoscaler or Karpenter.

Placement: affinity, taints, and spreading

Advanced

# Keep replicas on different nodes (survive a node loss)
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    labelSelector: { matchLabels: { app: api } }

# Taint a GPU node; only pods that tolerate it land there
# node:  kubectl taint nodes gpu-1 gpu=true:NoSchedule
tolerations:
  - { key: "gpu", operator: "Equal", value: "true", effect: "NoSchedule" }

PodDisruptionBudget

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: api }
spec:
  minAvailable: 2
  selector: { matchLabels: { app: api } }
# Node drains / upgrades won't take you below 2 ready pods.

Operators

An operator extends Kubernetes with a Custom Resource + a controller that reconciles it — encoding "how to run this software" (back up a database, fail over, upgrade) as code. You install operators (Postgres, Prometheus, cert-manager) far more often than you write them, but the pattern is why "the cluster runs itself".

Exercises

  • Add liveness/readiness/startup probes to a Deployment and watch a rolling update keep zero-downtime.
  • Set requests/limits, then load-test with an HPA at 70% CPU and watch replicas scale 2→N.
  • Add a PodDisruptionBudget and a topology spread, then kubectl drain a node and observe the constraints hold.

Mini-project: production-harden a Deployment

Take the app you deployed in Kubernetes Basics and make it production-grade: correct three-probe health checks (liveness independent of the DB), resource requests/limits from measured usage, an HPA, a PDB of minAvailable: 2, and a topology spread across nodes. Prove resilience by draining a node and load-testing to trigger a scale-up — with zero dropped requests.
