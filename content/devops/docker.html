Docker packages an application together with everything it needs to run — code, runtime, system libraries, and configuration — into a single portable unit called a container. This lesson takes you from "what even is a container?" to production-grade multi-stage builds, image registries, volumes, and networks. Everything targets modern Docker: BuildKit as the default builder and the docker CLI as you will actually use it.

Images vs containers

Beginner A container is a process (or a small group of processes) running on your machine, isolated so it sees its own filesystem, network interface, and process table — but sharing the host's Linux kernel instead of booting one of its own. That last part is the whole trick, and it is what makes a container start in milliseconds and weigh megabytes where a virtual machine takes a minute and gigabytes.

Virtual machines vs containers

A virtual machine emulates an entire computer: a hypervisor hands each VM virtual hardware, and each VM boots a full guest OS with its own kernel. A container shares the host kernel and isolates processes using Linux primitives — namespaces (what a process can see) and cgroups (how much it can use). There is no guest OS to boot.

AspectVirtual machineContainer
Isolation boundaryVirtual hardware + full guest OSKernel namespaces + cgroups
KernelIts own guest kernelShares the host kernel
Startup timeSeconds to minutesMilliseconds
Size on diskGigabytesMegabytes to hundreds of MB
Density per hostTensHundreds to thousands

The two words beginners confuse

  • An image is a read-only, layered template — a filesystem snapshot plus metadata (which command to run, which port it exposes). It is inert, like a class definition or an installer.
  • A container is a running (or stopped) instance of an image, with a thin writable layer on top — like an object instantiated from that class.

One image can spawn many containers. Delete a container and its writable layer disappears; the image is untouched. This is why containers are called ephemeral: never store data you care about inside a container's writable layer — use volumes for that.

The supply chain: a Dockerfile is the recipe, docker build bakes it into an image, you push that image to a registry, and on any machine docker run pulls the image and starts a container. Because the image carries its own dependencies, "works on my machine" becomes "works on every machine."

The core Docker CLI

Beginner Almost all day-to-day work runs through a handful of verbs.

CommandWhat it does
docker pull nginx:alpineDownload an image from a registry.
docker imagesList images stored locally.
docker ps / docker ps -aList running / all containers (incl. stopped).
docker run --rm -it ubuntu:24.04 bashRun a temporary interactive container.

The flags you will use constantly

  • -d / --detach — run in the background and return your prompt.
  • -it — -i keeps stdin open, -t allocates a TTY; together they give an interactive shell.
  • -p HOST:CONTAINER — publish a container port to the host. Left side is the host port.
  • --name — a stable name instead of a random one like vibrant_swartz.
  • -e KEY=value — set an environment variable inside the container.
  • --rm — delete the container automatically when it stops.
# Start a detached nginx and hit it
docker run -d --name web -p 8080:80 nginx:alpine
curl -s http://localhost:8080 | head -n 1
# -> <!DOCTYPE html>

docker ps
# -> CONTAINER ID   IMAGE          ...   PORTS                  NAMES
# -> a1b2c3d4e5f6   nginx:alpine   ...   0.0.0.0:8080->80/tcp   web

docker stop web && docker rm web
# -> web
# -> web
docker run = docker create + docker start. When something behaves oddly, splitting them apart (create, inspect, then start) can make the problem obvious.

Writing a Dockerfile

Intermediate A Dockerfile is a plain-text recipe. Each instruction produces a filesystem layer; layers are cached and reused, so the order of instructions directly controls your build speed. The core instructions:

  • FROM — the base image you build on.
  • WORKDIR — set (and create) the working directory for later instructions.
  • COPY — copy files from the build context into the image.
  • RUN — execute a command at build time and commit the result as a layer.
  • EXPOSE — document the port the app listens on (metadata only).
  • ENV — set an environment variable baked into the image.
  • CMD — the default command when a container starts (overridable on the CLI).
  • ENTRYPOINT — the fixed executable; CMD supplies its default arguments.

CMD vs ENTRYPOINT

Use CMD alone when the whole command should be easy to override. Use ENTRYPOINT for the fixed program and CMD for its default args when the image should behave like a single executable. Always prefer the exec form (a JSON array) so signals like SIGTERM reach your process directly:

ENTRYPOINT ["node"]
CMD ["dist/server.js"]
# docker run img            -> node dist/server.js
# docker run img other.js   -> node other.js

Layer caching — get the order right

Docker rebuilds a layer only if that instruction or a file it copies changed; every later layer is then rebuilt too. So copy the files that change rarely (dependency manifests), install dependencies, and only then copy fast-changing source — a code edit does not bust the dependency-install cache.

# Dockerfile — Node app
FROM node:22-alpine
WORKDIR /app

# 1) Copy only manifests first, install deps — cached while package*.json is unchanged
COPY package*.json ./
RUN npm ci

# 2) Now copy the rest; editing app code only invalidates from here down
COPY . .

EXPOSE 3000
CMD ["node", "server.js"]
docker build -t myapp:dev .
# -> [+] Building 12.4s (10/10) FINISHED
# ->  => naming to docker.io/library/myapp:dev

Always add a .dockerignore

The build context (everything sent to the builder) should exclude junk. Without this, COPY . . can drag in node_modules, secrets, and .git history — bloating the image and busting the cache constantly.

# .dockerignore
.git
node_modules
dist
*.log
.env
Dockerfile
docker-compose*.yml

Multi-stage builds & BuildKit

Advanced A single-stage image bakes in the whole build toolchain — hundreds of MB you never need at runtime. A multi-stage build compiles in a fat "builder" stage, then copies just the finished artifact into a tiny final stage.

Start advanced Dockerfiles with a syntax directive so BuildKit fetches the latest frontend, unlocking --mount, secrets, and heredocs:

# syntax=docker/dockerfile:1
FROM golang:1.23-alpine AS build
WORKDIR /src

# Cache modules and the build cache across builds with --mount=type=cache
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download

COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /bin/app ./cmd/app

# Final stage: nothing but the static binary and CA certs
FROM scratch
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /bin/app /app
EXPOSE 8080
USER 65534:65534
ENTRYPOINT ["/app"]

Setting CGO_ENABLED=0 produces a fully static binary with no libc dependency, so it runs in scratch — a completely empty image. The result is often a few MB versus hundreds.

BuildKit secrets mount a file only for the duration of one RUN, leaving no trace in any layer. A token passed as a build ARG or set in ENV, by contrast, is permanently visible in docker history.
# syntax=docker/dockerfile:1
FROM alpine
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
docker build --secret id=npmrc,src="$HOME/.npmrc" -t myapp .
# the .npmrc file is never copied into any layer

Multi-architecture images

# One image manifest that works on amd64 and arm64
docker buildx build --platform linux/amd64,linux/arm64 -t youruser/app:1.0 --push .

Images, tags, and registries

Intermediate An image reference is registry/namespace/repository:tag. Omit the registry and Docker assumes Docker Hub; omit the tag and it assumes :latest — which is just a mutable tag, not a promise of newness.

# Log in once
docker login

# Build with a meaningful version, also tag :latest
docker build -t youruser/myapp:1.4.0 .
docker tag youruser/myapp:1.4.0 youruser/myapp:latest

# Push both tags
docker push youruser/myapp:1.4.0
docker push youruser/myapp:latest
# -> 1.4.0: digest: sha256:9c1f... size: 1986
docker history youruser/myapp:1.4.0   # each layer and its size
docker image inspect youruser/myapp:1.4.0 \
  --format '{{.Config.Entrypoint}} {{.Config.Cmd}}'
# -> [node] [dist/server.js]

Images are content-addressed stacks of layers: if ten images share the same node:22-alpine base, that base is stored once and reused. Pushing a new app version only uploads layers that actually changed.

Never deploy production off a floating :latest tag. Pin an exact version (or a digest, myapp@sha256:…) so a redeploy is reproducible and cannot silently pull a different image.

Volumes, bind mounts, and networks

Intermediate A container's writable layer is thrown away when the container is removed. To keep data, and to let containers talk by name, you use volumes and user-defined networks.

  • Named volume — storage managed by Docker in its own area. Best for database data; survives container removal.
  • Bind mount — a specific host path mapped into the container. Best for local development with live source edits.
# Named volume: Postgres data persists across recreation
docker volume create pgdata
docker run -d --name db \
  -e POSTGRES_PASSWORD=secret \
  -v pgdata:/var/lib/postgresql/data \
  postgres:17-alpine

# Bind mount: edit ./site on the host, see it live (read-only in the container)
docker run -d --name web -p 8080:80 \
  -v "$PWD/site":/usr/share/nginx/html:ro \
  nginx:alpine

The default bridge network gives no name resolution. Create a user-defined bridge and containers on it reach each other by container name via Docker's embedded DNS:

docker network create appnet

docker run -d --name db  --network appnet \
  -e POSTGRES_PASSWORD=secret -e POSTGRES_DB=app postgres:17-alpine

docker run -d --name api --network appnet -p 3000:3000 \
  -e DATABASE_URL=postgres://postgres:secret@db:5432/app \
  youruser/api:1.0

The api container connects to host db — that name resolves over appnet. Notice the database port is not published to the host; it is reachable only inside the network. That is the production pattern: expose the edge, keep data private.

Best practices

Intermediate The habits that separate a demo from a maintainable setup.

  • Small base images. Prefer -alpine, -slim, distroless, or scratch — faster pulls, smaller attack surface.
  • Multi-stage builds. Keep compilers out of the runtime image.
  • Run as non-root. Add a USER instruction so a container breakout does not hand over root.
  • Pin versions. Exact tags or digests so redeploys are reproducible.
  • Healthchecks everywhere. Let Docker gate readiness and restart the genuinely unhealthy.
  • Keep databases private. Do not publish DB ports; reach them over an internal network by name.

Reclaiming disk

docker system df                 # what is using space
docker system prune              # stopped containers, unused nets, dangling images, cache
docker builder prune             # build cache only
Destructive: docker system prune -a --volumes also deletes unused images AND volumes — that can wipe data you meant to keep. Prune reads like a broom; on a shared or production host it can be a wrecking ball. Read the confirmation prompt before answering "y".

Common mistakes

Common mistakes
  • Storing data in the writable layer. It vanishes when the container is removed. Use a named volume.
  • No .dockerignore. COPY . . drags in node_modules, .git, and .env — bloating the image and leaking secrets.
  • Binding to 127.0.0.1 inside the container. The app must listen on 0.0.0.0 or the published port reaches nothing.
  • Expecting EXPOSE to publish a port. It is documentation only — you still need -p HOST:CONTAINER.
  • Copying source before installing deps. Every code edit then reinstalls everything, because the cache busts too early.
  • Shipping secrets in a build ARG or ENV. They live forever in docker history. Use a BuildKit secret mount.

Exercises

  • Run docker run -d --name web -p 8080:80 nginx:alpine, hit it with curl, then exec into it and read nginx -v.
  • Write a two-stage Dockerfile for any compiled language and compare the final image size to a single-stage build with docker images.
  • Create a named volume, run Postgres on it, write a row, remove and recreate the container, and prove the row survived.
  • Create a user-defined network, run an app plus a database on it with the DB port unpublished, and connect the app to the DB by container name.
  • Deliberately break your layer caching by copying source before npm ci, then fix the ordering and watch the rebuild time drop.

Mini-project: containerize a small web app

Take any small HTTP service (Node, Go, or Python). Write a multi-stage Dockerfile that builds in a full base image and ships a minimal runtime image running as a non-root user with a HEALTHCHECK. Add a .dockerignore. Build it, tag it 1.0.0 and latest, run it on a user-defined network alongside a Postgres container (DB port unpublished, reached by name), and confirm the app serves traffic on a published port while the database stays private. Finish by pruning dangling images and comparing your final image size to the base.
