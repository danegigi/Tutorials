A reverse proxy sits at the edge of your network, accepts every incoming request, and forwards it to the right backend behind it — spreading load across a pool of servers, terminating TLS, and routing by hostname or path. This lesson covers why you need one, the Layer 4 vs Layer 7 split that decides everything, and three production tools: Nginx, HAProxy, and Traefik v3 with automatic Let's Encrypt certificates.

Why a reverse proxy

Beginner A forward proxy sits in front of clients and hides them from the internet. A reverse proxy sits in front of servers and hides them from clients: the client only ever talks to the proxy, which decides which backend fulfils the request. One stable public address, many servers coming and going behind it.

What a reverse proxy buys you:

  • Scale — one server handles only so many connections. Add more behind the proxy and capacity grows horizontally.
  • High availability — if a backend dies, the proxy stops sending it traffic and the site stays up.
  • Zero-downtime deploys — drain one backend, update it, return it to the pool, repeat.
  • TLS termination — decrypt HTTPS once at the edge instead of on every backend.
  • Routing — send /api to one service and /blog to another; serve many hostnames from one address.

Layer 4 vs Layer 7

Beginner This is the central distinction and it decides which tool and mode you pick.

  • Layer 4 (transport / TCP-UDP) — the proxy forwards raw packets. It knows IP addresses and ports, not URLs. Extremely fast and protocol-agnostic (works for MySQL, Redis, gRPC, game servers). It cannot route on the HTTP path because it never parses HTTP.
  • Layer 7 (application / HTTP) — the proxy terminates the connection, parses the HTTP request, and can route on hostname, path, headers, cookies, and method. Slower and HTTP-specific, but far smarter.

Two more concepts you will meet in every tool:

  • Health checks — the proxy periodically probes each backend; only healthy ones receive traffic. L7 checks hit a path like /healthz and require a 200; L4 checks just open a TCP connection.
  • Algorithms — round-robin (each request to the next server in turn), least-connections (to whichever server has the fewest active connections — better when request durations vary), and weighted (bigger servers get proportionally more).
Sticky sessions (pinning a client to one backend via a cookie or source IP) exist for apps that keep per-user state in memory. The better long-term fix is to make servers stateless — store session state in Redis or a database — so any server can handle any request.

Nginx as a reverse proxy

Intermediate Nginx is a web server that doubles as an L7 reverse proxy and load balancer — the common front door to an app. You define a backend pool with an upstream block and forward to it with proxy_pass.

Algorithms: default is round-robin; least_conn; sends to the fewest active connections; ip_hash; pins a client IP to one server; server … weight=3; weights distribution.

# /etc/nginx/conf.d/example.conf

upstream app_servers {
    least_conn;                                            # fewest-connections
    server 10.0.1.10:8080 max_fails=3 fail_timeout=30s;    # passive health check
    server 10.0.1.11:8080 max_fails=3 fail_timeout=30s;
    server 10.0.1.12:8080 backup;                          # only if the others are down
    keepalive 32;                                          # reuse upstream connections
}

# Redirect all HTTP to HTTPS
server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$host$request_uri;
}

# HTTPS: terminate TLS, proxy to the upstream
server {
    listen 443 ssl;
    http2 on;
    server_name example.com www.example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    location /blog/ {
        proxy_pass http://blog_servers;      # path routing to a different pool
    }

    location / {
        proxy_pass http://app_servers;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_http_version 1.1;              # required for upstream keepalive
        proxy_set_header Connection "";
    }
}
nginx -t             # test the config for syntax errors
# -> nginx: configuration file /etc/nginx/nginx.conf test is successful
nginx -s reload      # apply with zero downtime (graceful reload)
Open-source Nginx does passive health checks only (max_fails/fail_timeout — it marks a server down after real requests fail). Active health checks (proactively probing /healthz) are an Nginx Plus feature; HAProxy does active checks for free.

HAProxy

Advanced HAProxy (High Availability Proxy) is the industry-standard software load balancer. It does both L4 (mode tcp) and L7 (mode http), with first-class active health checks. A config has four section types: global (process settings), defaults (inherited by all), frontend (where it accepts connections), and backend (the server pool plus algorithm and checks).

# haproxy.cfg — L7 HTTP with path routing
global
    maxconn 4000
    log /dev/log local0

defaults
    mode    http                 # Layer 7 — parse HTTP
    log     global
    option  httplog
    option  redispatch           # if a server dies mid-request, retry elsewhere
    retries 3
    timeout connect 5s
    timeout client  50s
    timeout server  50s

frontend http_in
    bind *:80
    # ACL = Access Control List: tests a condition, like an ALB listener rule
    acl url_blog path_beg /blog   # true when path starts with /blog
    acl url_api  path_beg /api
    use_backend blog_servers if url_blog
    use_backend api_servers  if url_api
    default_backend web_servers

backend web_servers
    balance roundrobin
    option httpchk GET /healthz   # active L7 health check
    http-check expect status 200
    server web1 10.0.1.10:8080 check
    server web2 10.0.1.11:8080 check

backend api_servers
    balance roundrobin
    server api1 10.0.1.20:7070 check weight 2   # gets 2x the traffic
    server api2 10.0.1.21:7071 check weight 1

For non-HTTP protocols switch to mode tcp and HAProxy balances raw connections — here a MySQL pool with a MySQL-aware health check:

frontend mysql_frontend
    mode tcp
    bind *:3306
    default_backend mysql_backend

backend mysql_backend
    mode tcp
    balance roundrobin
    option mysql-check user haproxy_user     # MySQL-aware probe
    server mysql1 10.0.1.30:3306 check inter 2s
    server mysql2 10.0.1.31:3306 check inter 2s
Destructive if skipped: always run haproxy -c -f haproxy.cfg before deploying. A single typo in a live config can take your whole entry point down — the syntax check is your safety net and belongs in CI.
haproxy -c -f /etc/haproxy/haproxy.cfg
# -> Configuration file is valid

Traefik v3 with automatic TLS

Advanced Traefik sits at the edge, owns ports 80 and 443, and routes each request to the right container by reading the container's Docker labels — no static backend list to maintain. It also obtains and renews Let's Encrypt certificates automatically. Every request flows EntryPoint &rarr; Router &rarr; (Middleware) &rarr; Service &rarr; Container.

# traefik/compose.yaml — the edge
name: edge

services:
  traefik:
    image: traefik:v3.4
    command:
      - --providers.docker=true
      - --providers.docker.exposedbydefault=false     # only labeled containers routed
      - --entrypoints.web.address=:80
      - --entrypoints.websecure.address=:443
      # Redirect every HTTP request to HTTPS
      - --entrypoints.web.http.redirections.entrypoint.to=websecure
      - --entrypoints.web.http.redirections.entrypoint.scheme=https
      # Let's Encrypt via TLS-ALPN-01 challenge
      - --certificatesresolvers.le.acme.email=admin@example.com
      - --certificatesresolvers.le.acme.storage=/letsencrypt/acme.json
      - --certificatesresolvers.le.acme.tlschallenge=true
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro   # read-only!
      - letsencrypt:/letsencrypt
    networks:
      - web
    restart: unless-stopped

volumes:
  letsencrypt:

networks:
  web:
    name: web
    driver: bridge

An application declares its routing entirely through labels and joins the shared web network so Traefik can reach it:

# app/compose.yaml
services:
  app:
    image: example/app:1.0
    networks:
      - web
      - internal
    labels:
      - traefik.enable=true
      - traefik.docker.network=web
      # Route app.example.com over HTTPS with a Let's Encrypt cert
      - traefik.http.routers.myapp.rule=Host(`app.example.com`)
      - traefik.http.routers.myapp.entrypoints=websecure
      - traefik.http.routers.myapp.tls.certresolver=le
      - traefik.http.services.myapp.loadbalancer.server.port=3000

  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD: change-me
    networks:
      - internal        # private only: no traefik.enable, no web network

networks:
  web:
    external: true      # created by the edge stack; shared across projects
  internal:
    driver: bridge
docker network create web                         # one-time shared network
docker compose -f traefik/compose.yaml up -d
docker compose -f app/compose.yaml up -d
docker compose -f traefik/compose.yaml logs -f traefik
# -> ... Serving certificate for domain "app.example.com"
Mount the Docker socket read-only (:ro), never expose the Traefik dashboard on the public internet without auth and TLS, and in production prefer a Docker-socket proxy so Traefik cannot control the daemon directly. In a compose file a literal $ (e.g. in a bcrypt auth hash) must be escaped as $$ or Compose tries to interpolate it.

Choosing between the three

Intermediate They overlap, but each has a sweet spot.

ToolLayersConfig modelReach for it when
NginxL7 (L4 via stream)Static files, reloadLightest front door for HTTP; TLS termination; serving static assets too.
HAProxyL4 & L7Static file, reloadBest free active health checks; TCP/MySQL balancing; total control on VMs/on-prem.
Traefik v3L7 (L4 via TCP routers)Dynamic — reads labels/CRDsContainer & Kubernetes environments where backends churn; automatic Let's Encrypt.
Rule of thumb: static VMs and raw TCP &rarr; HAProxy. Lightweight HTTP front door &rarr; Nginx. Containers/Kubernetes with churning backends and auto-TLS &rarr; Traefik. Inside Kubernetes, all three can run as an Ingress controller — the same job, driven by Ingress objects instead of a static file.

Common mistakes

Common mistakes
  • Deploying without a syntax check. nginx -t, haproxy -c -f …, and docker compose config each catch the typo that would otherwise take your edge down.
  • Picking L7 for raw TCP. An HTTP proxy cannot forward MySQL or Redis — use mode tcp (HAProxy) or an NLB/stream block.
  • Forgetting X-Forwarded-For/X-Forwarded-Proto. After TLS termination the backend sees the proxy's IP and plain HTTP unless you forward these headers.
  • Mounting the Docker socket read-write for Traefik. That hands container-escape-to-root. Mount :ro and prefer a socket proxy.
  • Unescaped $ in a compose-embedded Traefik auth hash. Compose interpolates it; double every dollar sign ($$).
  • Relying on sticky sessions forever. It papers over in-memory state; move the state to Redis so any backend can serve any request.

Exercises

  • Run two tiny backend containers and put Nginx in front with least_conn; stop one backend and confirm traffic shifts to the survivor.
  • Write an HAProxy config that routes /api and /blog to separate backends via ACLs, then validate it with haproxy -c -f.
  • Bring up the Traefik v3 edge plus one labeled app on a local machine (use a fake hostname in /etc/hosts) and watch the router appear in the logs.
  • Add an HTTP&rarr;HTTPS 301 redirect in all three tools and confirm it with curl -I http://….
  • Switch an HAProxy backend from roundrobin to leastconn and reason about which workload each suits.

Mini-project: one site, three proxies

Stand up two identical backend web containers that print which instance served the request. Front them in turn with (1) Nginx terminating TLS with a self-signed cert and load-balancing least_conn, (2) HAProxy with an active /healthz check and path routing, and (3) Traefik v3 discovering the backends by Docker labels with an HTTP&rarr;HTTPS redirect. For each, verify load spreads across both backends, a stopped backend is removed from rotation, and HTTP redirects to HTTPS. Write a short comparison of the config model and operational feel of each.
