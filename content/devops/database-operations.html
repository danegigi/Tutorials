The database is usually the hardest part of production to operate — it's stateful, so you can't just redeploy it. This lesson covers the operational concerns: safe schema migrations, backups you've actually tested, replication and failover, connection pooling, and the tuning that keeps it fast.

Schema migrations

Intermediate Migrations are versioned, ordered changes to the schema, applied automatically and reproducibly — never by hand on a prod console.

# A migration tool (golang-migrate, Flyway, Drizzle Kit, Prisma Migrate…) applies
# ordered files and records which have run:
migrate -path ./migrations -database "$DATABASE_URL" up
# 001_create_users.up.sql, 002_add_email_index.up.sql, …
Zero-downtime migrations use expand/contract (from the Deployment Strategies lesson): never rename/drop a column in the same release that ships the code depending on it — during a rolling deploy both old and new code run at once. Also beware migrations that lock a big table: adding an index on a large Postgres table should use CREATE INDEX CONCURRENTLY (outside a transaction) or it blocks writes for the duration. Test every migration on a prod-sized copy first.

Backups — and restores

# Logical backup (portable, slower):
pg_dump "$DATABASE_URL" | gzip > backup-$(date +%F).sql.gz
# Physical + Point-In-Time Recovery (fast, lets you restore to a timestamp):
#   base backup + continuous WAL archiving → restore to any moment before a mistake
A backup you have never restored is not a backup — it's a hope. The classic disaster: nightly dumps "succeed" for a year, then on the day you need them the restore fails (wrong version, corrupt file, missing extension, or it takes 9 hours you don't have). Regularly rehearse the restore into a scratch environment and time it — your Recovery Time Objective is only real if you've measured it.
TermMeaning
RPO (Recovery Point Objective)How much data you can afford to lose (→ backup frequency / WAL archiving).
RTO (Recovery Time Objective)How long a restore may take (→ backup method + rehearsal).

Replication & failover

Advanced A single DB node is a single point of failure. Replication keeps standby copies; failover promotes one when the primary dies.

# Primary → one or more replicas (streaming WAL)
#   - Read replicas: offload read traffic (but mind replication LAG — reads can be stale)
#   - Sync vs async: sync = no data loss on failover but slower writes; async = fast but
#     a failover may lose the last few unreplicated transactions
# Automated failover: Patroni / cloud-managed (RDS Multi-AZ) promotes a standby + repoints.
Managed databases (RDS, Cloud SQL, etc.) handle replication, failover, backups, and patching for you — for most teams that's the right call. Self-manage only when you have a strong reason and the expertise, because getting failover and backups right by hand is a deep specialty.

Connection pooling

# Each DB connection costs memory on the server; thousands of app instances each
# opening their own exhausts max_connections → "too many connections" errors.
# A pooler (PgBouncer) multiplexes many client connections onto few server ones:
#   app → PgBouncer (transaction pooling) → Postgres
#   10,000 clients → 50 real server connections
Common production failure: an app (or serverless functions) opening a fresh connection per request and never pooling, then crashing the database with connection exhaustion under load — not CPU, not disk, just too many connections. Set a sane pool size in the app (the Go SetMaxOpenConns / Bun pool from those lessons) and front the DB with PgBouncer for high-fanout or serverless workloads.

Tuning & observing

  • Indexes — the single biggest performance lever; find slow queries with the DB's slow-query log and EXPLAIN ANALYZE, add the missing index.
  • Key settings — shared_buffers, work_mem, max_connections sized to the box, not left at tiny defaults.
  • Maintenance — autovacuum (Postgres) must keep up, or tables bloat and slow down.
  • Monitor — connections in use, replication lag, cache hit ratio, slow queries (ties to the Observability lesson).

Exercises

  • Write a forward + rollback migration pair and apply/revert it with a migration tool.
  • Take a pg_dump backup and actually restore it into a fresh database; time the restore.
  • Find a slow query with EXPLAIN ANALYZE and fix it by adding the right index.

Mini-project: production-ready database setup

For the app's database (from the Go/Bun database lessons), build the operational layer: a migration workflow run in CI, an automated backup with WAL archiving plus a tested, timed restore into a scratch env, a read replica with lag monitoring, PgBouncer in front with a sized pool, and a dashboard tracking connections/lag/slow-queries. Document your RPO/RTO and prove the restore meets the RTO.
