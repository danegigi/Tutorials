The Security Basics lesson said "never put secrets in Git or images." This lesson is the how: real secret stores, getting secrets into Kubernetes safely, replacing long-lived keys with short-lived identity, and rotating credentials without downtime.

Why the obvious options fail

ApproachProblem
Secret in .env in GitPermanent in history; leaks to everyone with repo access.
Baked into a Docker imagePersists in image layers forever, even if a later layer "deletes" it.
Plain Kubernetes SecretOnly base64-encoded, not encrypted — anyone with get secret or etcd access reads it.
CI/CD stored keyLong-lived; if leaked, valid until someone notices and rotates.
base64 is not encryption. kubectl get secret x -o jsonpath='{.data.password}' | base64 -d prints the plaintext. A Kubernetes Secret keeps credentials out of your manifests, but it is not a vault. Enable encryption at rest for etcd and lock down RBAC on secrets at minimum.

A real secret store: Vault

Intermediate HashiCorp Vault (or a cloud equivalent — AWS Secrets Manager, GCP Secret Manager, Azure Key Vault) centralizes secrets with access policies, audit logs, dynamic secrets, and rotation.

vault kv put secret/myapp/db password=s3cr3t
vault kv get -field=password secret/myapp/db
# App authenticates (via a role/token/OIDC) and reads at runtime — nothing on disk.

# Dynamic secrets: Vault generates a short-lived DB credential on demand
vault read database/creds/myapp-role     # username+password valid for 1h, then revoked
Dynamic secrets are the gold standard: instead of one shared long-lived DB password, each app instance gets a unique credential that auto-expires. A leak is contained to an hour, and you can trace exactly which lease did what.

Getting secrets into Kubernetes

Two popular GitOps-friendly patterns that keep plaintext out of Git:

# 1) External Secrets Operator — syncs from Vault/cloud into a K8s Secret
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: db-creds }
spec:
  secretStoreRef: { name: vault-backend, kind: ClusterSecretStore }
  target: { name: db-creds }           # the K8s Secret it creates
  data:
    - secretKey: password
      remoteRef: { key: secret/myapp/db, property: password }
# 2) Sealed Secrets — encrypt a secret so the CIPHERTEXT is safe to commit
kubeseal --format yaml < secret.yaml > sealed-secret.yaml   # commit this
# Only the in-cluster controller's private key can decrypt it → a real Secret.

Kill long-lived keys: OIDC federation

Advanced The best cloud credential is one that doesn't exist at rest. OIDC lets your CI job or workload prove its identity to the cloud and receive a short-lived token — no stored access keys:

# GitHub Actions assuming an AWS role via OIDC (no AWS keys in secrets!)
permissions: { id-token: write, contents: read }
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123:role/github-deploy
      aws-region: us-east-1
# The role trusts GitHub's OIDC issuer scoped to your repo/branch.
Common mistake: storing a long-lived AWS_SECRET_ACCESS_KEY as a CI secret "because it's easy". If that CI secret leaks, the key is valid until manually rotated. OIDC-issued tokens live minutes and are scoped to the exact workflow — adopt it everywhere the cloud supports it.

Rotation

Every static secret needs a rotation plan: a schedule, dual-credential support (accept old and new during the overlap, like the expand/contract DB pattern), and automation so rotation isn't a scary manual event. Dynamic secrets make this automatic; for static ones, Vault/cloud rotation lambdas handle it.

Exercises

  • Decode a plain Kubernetes Secret to prove base64 ≠ encryption, then enable RBAC that denies get secret to a test ServiceAccount.
  • Seal a secret with kubeseal and confirm the committed ciphertext reveals nothing.
  • Convert a CI job from a stored cloud key to OIDC role assumption.

Mini-project: zero-plaintext-secrets pipeline

Take the app + pipeline from earlier lessons and remove every stored secret: deploy a secret store (Vault dev server or a cloud manager), use External Secrets or Sealed Secrets to deliver the DB credential into the cluster with nothing sensitive in Git, switch CI cloud auth to OIDC, and document a rotation procedure. Prove it by grepping the repo and image history for the secret — zero hits.
