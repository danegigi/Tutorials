Infrastructure as Code means defining your cloud — networks, servers, buckets, databases, DNS — in version-controlled files instead of clicking around a console. Terraform is the most widely used IaC tool: you write declarative HCL, and it figures out the API calls to create, change, or destroy resources. This lesson covers providers, the init/plan/apply loop, a real VPC and S3 example, remote state with locking, modules, and workspaces.

Why Infrastructure as Code

Intermediate Clicking in a console is fast the first time and a disaster the tenth: unrepeatable, undocumented, un-reviewable. IaC turns infrastructure into text you can diff, review in a pull request, and roll back. It is the foundation layer of GitOps — Terraform manages the cloud around your cluster (VPCs, IAM, DNS), while a tool like Flux manages what runs inside it.

Terraform is declarative: you describe the end state ("a VPC with these subnets, this instance"), not the steps to reach it. Terraform reads your files, compares them to what it recorded in state, and computes the minimal set of changes to converge.

Providers

Intermediate A provider is a plugin that teaches Terraform how to talk to a platform (AWS, GCP, Azure, Kubernetes, GitHub). You declare which providers and versions you need; pinning versions keeps a plan reproducible.

# versions.tf
terraform {
  required_version = ">= 1.6.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.aws_region
}

The core workflow: init / plan / apply

Intermediate Terraform's day-to-day loop is four commands.

# 1. Download providers & set up the working dir (run once per new/changed config)
terraform init
# -> Terraform has been successfully initialized!

# 2. Preview what Terraform WOULD do — no changes made. Read this every time.
terraform plan
# -> Plan: 7 to add, 0 to change, 0 to destroy.

# 3. Apply the plan — actually create/modify/delete resources
terraform apply
# -> Apply complete! Resources: 7 added, 0 changed, 0 destroyed.

# 4. Tear everything in this state down
terraform destroy
Destructive: terraform apply and especially terraform destroy change or delete real, billable, sometimes irreplaceable infrastructure. Always read the plan first, and never run destroy against production without being certain what is in that state file.

A first example: VPC + EC2

Intermediate A concrete, minimal stack — a VPC, a public subnet, an internet gateway, routing, a security group, and an EC2 instance. Resources reference each other by type.name.attribute, and Terraform works out the dependency order itself.

# main.tf
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  tags = { Name = "demo-vpc" }
}

resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.0.1.0/24"
  map_public_ip_on_launch = true
  availability_zone       = "${var.aws_region}a"
  tags = { Name = "demo-public" }
}

resource "aws_internet_gateway" "gw" {
  vpc_id = aws_vpc.main.id
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.gw.id
  }
}

resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}

resource "aws_security_group" "web" {
  name   = "demo-web"
  vpc_id = aws_vpc.main.id

  ingress {
    description = "HTTP"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
  ingress {
    description = "SSH"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = [var.ssh_cidr]   # lock to your IP, not the world
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_instance" "web" {
  ami                    = var.ami_id
  instance_type          = var.instance_type
  subnet_id              = aws_subnet.public.id
  vpc_security_group_ids = [aws_security_group.web.id]
  tags = { Name = "demo-web" }
}

Variables, outputs, and tfvars

Hard-coding values is a smell. Declare inputs in variables.tf, supply values in a .tfvars file, and expose useful results via outputs.tf.

# variables.tf
variable "aws_region"    { type = string, default = "us-east-1" }
variable "instance_type" { type = string, default = "t3.micro" }
variable "ami_id"        { type = string }
variable "ssh_cidr"      { type = string, default = "0.0.0.0/0" }

# outputs.tf
output "instance_public_ip" {
  value = aws_instance.web.public_ip
}

# terraform.tfvars  (git-ignore if it holds anything sensitive)
aws_region    = "us-east-1"
instance_type = "t3.small"
ami_id        = "ami-0abcdef1234567890"
ssh_cidr      = "203.0.113.10/32"

Terraform auto-loads terraform.tfvars and *.auto.tfvars; for a specific file use terraform apply -var-file="prod.tfvars".

A smaller example: an S3 bucket

# s3.tf
resource "aws_s3_bucket" "assets" {
  bucket = "demo-assets-${var.env}"
  tags   = { ManagedBy = "terraform" }
}

resource "aws_s3_bucket_versioning" "assets" {
  bucket = aws_s3_bucket.assets.id
  versioning_configuration { status = "Enabled" }
}

resource "aws_s3_bucket_public_access_block" "assets" {
  bucket                  = aws_s3_bucket.assets.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

Remote state with S3 + DynamoDB locking

Advanced Terraform records what it created in a state file (terraform.tfstate) mapping your HCL to real resource IDs. It must never live only on one laptop and must never be committed to Git — it can contain secrets in plaintext. The standard AWS solution is a remote backend: store state in S3, and use a DynamoDB table for a state lock so two people cannot apply at once.

# backend.tf
terraform {
  backend "s3" {
    bucket         = "my-org-terraform-state"
    key            = "demo/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

The backing bucket and lock table are created once by a small bootstrap config (with a local backend), then everything else uses them:

# bootstrap/main.tf — run first, local backend
resource "aws_s3_bucket" "tf_state" {
  bucket = "my-org-terraform-state"
}
resource "aws_s3_bucket_versioning" "tf_state" {
  bucket = aws_s3_bucket.tf_state.id
  versioning_configuration { status = "Enabled" }
}
resource "aws_dynamodb_table" "tf_locks" {
  name         = "terraform-locks"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"
  attribute {
    name = "LockID"
    type = "S"
  }
}
Never commit terraform.tfstate or a .tfvars containing secrets to Git. State files hold resource attributes — sometimes passwords and keys — in plaintext. Remote state in S3 with encrypt = true plus a locked DynamoDB table is the baseline for any team.

Modules

Advanced A module is a reusable, parameterized bundle of resources — the function of the Terraform world. You call a module and pass inputs; it returns outputs. Modules can be local directories or come from the public Terraform Registry.

# Calling a local module
module "network" {
  source     = "./modules/network"
  cidr_block = "10.0.0.0/16"
  env        = var.env
}

# Calling a registry module
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"
  name    = "demo"
  cidr    = "10.0.0.0/16"
  azs             = ["us-east-1a", "us-east-1b"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24"]
  enable_nat_gateway = true
}

Inside modules/network/ you keep the same main.tf / variables.tf / outputs.tf structure; the outputs become the module's return values (e.g. module.network.subnet_id).

fmt & validate

Wire both into CI so a pull request runs them before any human reviews the plan.

terraform fmt -recursive    # rewrite to canonical HCL style
terraform fmt -check         # fail if anything is unformatted (CI)
terraform validate           # syntax, types, references are consistent
# -> Success! The configuration is valid.

Workspaces

Advanced Workspaces let one configuration manage multiple independent state files — a lightweight way to run the same code for dev, staging, and prod.

terraform workspace new dev
terraform workspace new prod
terraform workspace select prod
terraform workspace list      # * marks the current one
# ->   dev
# -> * prod
resource "aws_instance" "web" {
  instance_type = terraform.workspace == "prod" ? "t3.large" : "t3.micro"
  # ...
}
Workspaces suit small differences. For genuinely different environments many teams prefer separate directories or separate .tfvars + backend keys, so a prod mistake cannot silently land in the dev workspace. Pick one convention and stick to it.

Common mistakes

Common mistakes
  • Applying without reading the plan. The plan is your last chance to catch a destroy you did not intend — read the "N to destroy" line every time.
  • Committing state or secret tfvars. State holds plaintext secrets; once in Git history, rotate the credential rather than scrubbing.
  • Local state on a team. Two people applying at once corrupts state. Use remote state with DynamoDB locking.
  • Editing resources by hand in the console. That creates drift; the next apply may revert or conflict. Change infrastructure through code.
  • Unpinned provider versions. A new major provider release can change plan output under you. Pin with ~>.
  • Open SSH in a managed SG. Defaulting ssh_cidr to 0.0.0.0/0 ships a world-open SSH port — require a real CIDR.

Exercises

  • Write a minimal config that creates one S3 bucket, run init / plan / apply, then destroy it — reading each plan.
  • Extract the VPC example into a local modules/network module with input variables and outputs, and call it from the root.
  • Configure an S3 + DynamoDB remote backend (bootstrap it with a local backend first) and migrate an existing local state to it.
  • Add terraform fmt -check and terraform validate as steps and deliberately introduce an unformatted file to see them fail.
  • Use terraform.workspace to size an instance differently in dev vs prod, and switch between the two with workspace select.

Mini-project: a reusable, remote-state VPC stack

Build a Terraform project that provisions a two-subnet VPC (public + private), an internet gateway and routing, a web security group locked to your IP for SSH, and an S3 bucket for assets — all behind variables with no hard-coded values. Factor the networking into a local module. Configure an S3 + DynamoDB remote backend with a one-time bootstrap config, and wire fmt -check and validate as pre-apply checks. Run the full init/plan/apply loop reading each plan, prove the lock works by starting a second apply in another terminal, then destroy cleanly.
