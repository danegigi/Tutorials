Kubernetes is the control system for running containers across a fleet of machines. You describe the desired state of your application in YAML, hand it to the cluster, and Kubernetes works continuously to make reality match — restarting crashed containers, rescheduling them when a node dies, and rolling out new versions without downtime. This lesson takes you from "what even is a cluster?" through Pods, Deployments, Services, Ingress, config, storage, RBAC, Helm, and autoscaling.

The mental model: desired state

Beginner The single most important idea in Kubernetes is declarative desired state. You never tell the cluster "start this container" as a one-off command. You submit a document that says "I want 3 replicas of nginx:1.27 running on port 80" and Kubernetes stores that as the desired state, then takes responsibility for achieving and maintaining it.

Think of a thermostat. You set the target temperature (desired state). It continuously measures the room (observed state) and acts to close the gap. You never toggle the heater manually — you declare intent and the control loop does the rest.

Behind the scenes dozens of controllers run an endless reconciliation loop: observe the actual state, diff it against the declared desired state, and act to reduce the difference. If a node crashes and takes 2 of your 3 replicas, the Deployment controller sees the gap (desired 3, observed 1) and schedules 2 replacements — no human involved. That self-healing is why Kubernetes is declarative rather than imperative.

Every object shares the same shape:

apiVersion: apps/v1        # which API group/version defines this object
kind: Deployment           # what type of object
metadata:
  name: web                # unique within a namespace
  labels:
    app: web               # arbitrary key/value tags used for selection
spec:                      # the DESIRED state — what YOU want
  replicas: 3
# status:                  # the OBSERVED state — written BY Kubernetes, never by you

You write spec. Kubernetes writes status. The gap between them is exactly what the control loop is closing.

Cluster anatomy

Beginner A cluster splits into the control plane (the brain) and worker nodes (the muscle that runs your containers).

  • kube-apiserver — the front door. Every read and write goes through its REST API; it is the only component that talks to etcd.
  • etcd — a distributed key-value store holding the entire cluster state. The source of truth; back it up.
  • kube-scheduler — assigns each unscheduled Pod to the best node, considering resource requests, affinity, and taints.
  • kube-controller-manager — runs the reconciliation loops (Deployment, ReplicaSet, Node, Job controllers).
  • kubelet (on every node) — makes sure the containers described in each Pod spec are running and healthy.
  • kube-proxy — programs the network rules that implement Services.
  • container runtime — containerd or CRI-O, which actually pulls images and runs containers.
Flow of one deploy: kubectl apply &rarr; apiserver validates & writes to etcd &rarr; Deployment controller creates a ReplicaSet &rarr; ReplicaSet controller creates Pods &rarr; scheduler assigns each Pod to a node &rarr; that node's kubelet tells the runtime to pull the image and start the container &rarr; kube-proxy wires up Service networking.

A local cluster to practice on

# kind = Kubernetes IN Docker (needs Docker running)
kind create cluster --name dev
kubectl cluster-info --context kind-dev
kubectl get nodes
# -> NAME                STATUS   ROLES           AGE   VERSION
# -> dev-control-plane   Ready    control-plane   40s   v1.31.0

Pods & kubectl essentials

Beginner A Pod is the smallest deployable unit — a wrapper around one (or a few tightly-coupled) containers that share a network namespace and can share storage. You rarely create Pods directly in production (a Deployment manages them), but understanding the Pod is the foundation.

# pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80

Almost everything you do is a verb against an object type:

CommandWhat it does
kubectl apply -f <file>Create or update objects from a manifest.
kubectl get pods -o wideList pods with node and IP columns.
kubectl describe pod <name>Full detail + recent events (the gold at the bottom).
kubectl logs -f <pod>Stream a container's logs.
kubectl logs --previous <pod>Logs from the PREVIOUS crashed container.
kubectl exec -it <pod> -- shShell into a running container.
kubectl get events --sort-by=.lastTimestampThe single best triage command.
kubectl delete -f <file>Delete everything defined in a manifest.
 
kubectl apply -f pod.yaml
# -> pod/web created
kubectl get pods
# -> NAME   READY   STATUS    RESTARTS   AGE
# -> web    1/1     Running   0          8s
Destructive: kubectl delete removes live objects immediately and a -f dir/ deletes everything the directory declares. Double-check your context first (kubectl config current-context) — the current context is global to your shell, so it is dangerously easy to run a "quick test" against production.

Deployments & ReplicaSets

Beginner A Deployment declares how many identical Pods you want and handles rolling updates and rollbacks. It manages a ReplicaSet, whose only job is to keep the right number of Pod copies alive. Change the Pod template and the Deployment creates a new ReplicaSet, shifting Pods from old to new gradually.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web            # which Pods this Deployment owns
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1         # allow 1 extra pod during rollout
      maxUnavailable: 0   # never drop below replicas (zero-downtime)
  template:
    metadata:
      labels:
        app: web          # MUST match spec.selector.matchLabels
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
          readinessProbe:          # only take traffic when ready
            httpGet: { path: /, port: 80 }
            periodSeconds: 5
          livenessProbe:           # restart if the process deadlocks
            httpGet: { path: /, port: 80 }
            periodSeconds: 10
kubectl set image deployment/web web=nginx:1.27.1   # trigger a rollout
kubectl rollout status deployment/web
# -> deployment "web" successfully rolled out
kubectl rollout undo deployment/web                 # roll back one revision
Never point a livenessProbe at a path that depends on a downstream service (like your database). If the DB blips, every Pod fails liveness and restarts in a storm, turning a small outage into a total one. Liveness checks the process; use readinessProbe for dependency checks.

Services

Beginner Pods are ephemeral — they get new IPs on every restart. A Service gives a stable virtual IP and DNS name in front of a label-selected set of Pods, and load-balances across them. kube-proxy programs the rules so traffic to the Service IP reaches a healthy backend Pod.

  • ClusterIP (default) — reachable only inside the cluster. In-cluster DNS resolves <service>.<namespace>.svc.cluster.local.
  • NodePort — opens a port (30000–32767) on every node's IP, forwarding to the Service.
  • LoadBalancer — on a cloud, provisions an external L4 load balancer with a public IP.
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: ClusterIP
  selector:
    app: web            # matches Pod labels dynamically
  ports:
    - port: 80          # the port other objects call
      targetPort: 80    # the containerPort the Pod listens on
kubectl get endpoints web      # exactly which Pod IPs back the Service
# -> NAME   ENDPOINTS                            AGE
# -> web    10.244.0.5:80,10.244.0.6:80,...      2m
One cloud load balancer per Service gets expensive fast. In production you run a single LoadBalancer in front of an Ingress controller and route many hostnames/paths through it at L7.

Ingress

Intermediate An Ingress is an L7 HTTP/HTTPS routing rule set: "shop.example.com &rarr; the shop Service, /api &rarr; the api Service." The Ingress object alone does nothing — you must run an Ingress controller (ingress-nginx, Traefik) that watches Ingress objects and configures itself.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: site
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod   # auto TLS via cert-manager
spec:
  ingressClassName: nginx
  tls:
    - hosts: [shop.example.com]
      secretName: shop-tls          # cert-manager creates/renews this Secret
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: shop
                port: { number: 80 }
Let's Encrypt has strict rate limits. Test against the staging issuer first (acme-staging-v02.api.letsencrypt.org) — its certs are untrusted by browsers but do not count against production quotas. Switch to prod only once DNS and the HTTP-01 challenge clearly work.

ConfigMaps & Secrets

Intermediate Never bake config into images. A ConfigMap holds non-sensitive settings, a Secret holds sensitive ones, and either can be injected as environment variables or mounted as files.

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  FEATURE_FLAGS: "beta=true"
---
apiVersion: v1
kind: Secret
metadata:
  name: dbpass
type: Opaque
stringData:               # plaintext here; encoded for you on apply
  PG_PASS: "s3cr3t"
spec:
  containers:
    - name: app
      image: myorg/app:1.0
      env:
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef: { name: app-config, key: LOG_LEVEL }
        - name: PG_PASS
          valueFrom:
            secretKeyRef: { name: dbpass, key: PG_PASS }
A Secret's data is only base64-encoded, not encrypted — anyone with read access can decode it, and by default it sits in etcd unencrypted. Enable etcd encryption-at-rest, lock down RBAC, and for real workloads pull from an external manager (AWS Secrets Manager / Vault) via the External Secrets Operator.

Storage

Intermediate Container filesystems are ephemeral. For durable data you use PersistentVolumes, split between what the cluster offers and what a workload requests:

  • StorageClass — a "type" of storage (e.g. AWS gp3 SSD) plus the provisioner that creates it on demand.
  • PersistentVolume (PV) — an actual disk, pre-created or auto-provisioned by a StorageClass.
  • PersistentVolumeClaim (PVC) — a workload's request ("I need 10Gi, ReadWriteOnce"), bound to a matching PV.
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: gp3
  resources:
    requests:
      storage: 10Gi

Stateful apps (databases, Kafka) use a StatefulSet instead of a Deployment: each Pod gets a stable ordinal name (db-0, db-1), a stable hostname, and its own PVC via a volumeClaimTemplate that survives rescheduling.

Namespaces, limits, and RBAC

Intermediate As clusters get shared you need boundaries, fairness, and access control.

A Namespace is a virtual cluster within the cluster. Requests are what the scheduler reserves; limits are the hard ceiling. Exceed a CPU limit and you get throttled; exceed a memory limit and the container is OOM-killed.

spec:
  containers:
    - name: app
      image: myorg/app:1.0
      resources:
        requests: { cpu: "250m", memory: "256Mi" }   # reserved
        limits:   { cpu: "500m", memory: "512Mi" }   # ceiling

RBAC answers "who can do what to which objects." A Role is a set of allowed verbs on resources; a RoleBinding grants it to a subject (user, group, or ServiceAccount). Pods authenticate using a ServiceAccount.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
Follow least privilege. Never bind the built-in cluster-admin ClusterRole to application ServiceAccounts, and avoid wildcard verbs: ["*"] rules — a compromised Pod inherits exactly its ServiceAccount's permissions.

Helm

Advanced Writing raw YAML for every environment gets unmanageable. Helm is the package manager for Kubernetes: it bundles templated manifests into a versioned chart and lets you override values per environment. An installed instance is a release.

helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update

helm install my-db bitnami/postgresql \
  --namespace data --create-namespace \
  --set auth.database=appdb \
  --set primary.persistence.size=20Gi
# -> NAME: my-db
# -> STATUS: deployed
# -> REVISION: 1
Prefer helm upgrade --install in CI — it is idempotent, creating the release on first run and upgrading it after, so the same pipeline step works for both. Pass per-environment overrides with -f prod-values.yaml; a --set flag wins over a values file.

Autoscaling

Advanced The Horizontal Pod Autoscaler (HPA) adds or removes Pods based on a metric (usually CPU). But when Pods cannot schedule because there is not enough node capacity, you need to add machines — that is cluster autoscaling.

kubectl autoscale deployment web --cpu-percent=70 --min=2 --max=10
kubectl get hpa
# -> NAME   REFERENCE        TARGETS   MINPODS   MAXPODS   REPLICAS
# -> web    Deployment/web   35%/70%   2         10        3

On AWS, Karpenter is a modern node autoscaler: instead of scaling fixed node groups, it watches for unschedulable Pods, reads their exact combined requirements, and launches the optimal EC2 instances (choosing Spot/On-Demand in real time). When nodes become underutilized it consolidates workloads onto fewer nodes and terminates the empties.

Pair HPA (scale Pods) with a cluster autoscaler (scale nodes). HPA alone leaves Pods stuck Pending when the cluster is full; a node autoscaler alone has nothing telling it the workload grew.

Common mistakes

Common mistakes
  • Selector/label mismatch. A Deployment's selector.matchLabels and its Pod template.metadata.labels must agree, or it never adopts the Pods it creates.
  • Liveness probe on a dependency. Pointing liveness at a path that calls the database turns a DB blip into a cluster-wide restart storm. Use readiness for dependencies.
  • Trusting Secrets as encrypted. They are base64, not encrypted. Enable etcd encryption and tight RBAC.
  • No resource requests. Without requests the scheduler cannot bin-pack and your Pods are first to be evicted under pressure (BestEffort QoS).
  • Deploying to the wrong context. The current context is shell-global. Confirm with kubectl config current-context before any apply/delete.
  • Reading only get, not describe. CrashLoopBackOff, ImagePullBackOff, and Pending all explain themselves in the Events section of kubectl describe pod.

Exercises

  • Spin up a local kind cluster, apply a 3-replica Deployment, delete one Pod, and watch the ReplicaSet recreate it with kubectl get pods -w.
  • Put a ClusterIP Service in front of the Deployment and reach it from a throwaway kubectl run -it --rm debug --image=busybox -- sh using the service name.
  • Trigger a rolling update with kubectl set image, then kubectl rollout undo and confirm the revision changed with kubectl rollout history.
  • Create a ConfigMap and a Secret, inject both into a Pod as env vars, and read them with kubectl exec … -- env.
  • Deliberately deploy a Pod referencing a nonexistent image and diagnose the ImagePullBackOff from kubectl describe pod alone.

Mini-project: deploy a stack end to end

On a local kind cluster, deploy a web app plus a Postgres StatefulSet. Give the app a Deployment with readiness and liveness probes and resource requests/limits, a ClusterIP Service, and config injected from a ConfigMap and a Secret. Bind Postgres to a PVC. Add an Ingress (install ingress-nginx first) routing a hostname to the app. Trigger a rolling update to a new image tag, verify zero dropped requests, then rollout undo and confirm it reverted. Finish by scaling the Deployment with an HPA and watching replicas respond to load.
