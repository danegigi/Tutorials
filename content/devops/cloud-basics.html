The cloud is someone else's data centres, rented by the hour and driven by an API. This lesson builds the AWS mental model everything else stands on: regions and availability zones for resilience, the VPC networking foundations (subnets, gateways, routing, firewalls), the two load balancer types and when each fits, DNS with Route 53, and the handful of core managed services you will reach for most.

Regions & availability zones

Beginner A Region is a geographic area (us-east-1, eu-west-1). Inside each region are multiple Availability Zones (AZs) — physically separate data centres with independent power and networking, joined by low-latency links.

The single most important high-availability rule in AWS: spread your instances across at least two AZs. If one AZ loses power or network, the others keep serving. Two instances in the same AZ share a failure domain and a load balancer in front of them buys you nothing when that AZ fails.

Pick a region close to your users for latency and mind data-residency rules. Some services (IAM, Route 53, CloudFront) are global; most (EC2, VPC, RDS, S3 buckets) are regional. A resource in us-east-1 is invisible to the console view of eu-west-1 — a frequent "where did my instance go?" moment.

VPC networking foundations

Beginner A VPC (Virtual Private Cloud) is your own isolated network in the cloud, defined by a CIDR block such as 10.0.0.0/16. Inside it you carve out subnets, each pinned to one AZ with a smaller CIDR range.

  • Public subnet — has a route to an Internet Gateway, so resources in it can have public IPs. This is where load balancers and bastion hosts live.
  • Private subnet — no direct route in from the internet. Application servers and databases live here; they reach out through a NAT gateway but nobody reaches in directly.
VPC 10.0.0.0/16
├── Public  subnet  10.0.1.0/24   (AZ a)   -> Internet Gateway
├── Public  subnet  10.0.2.0/24   (AZ b)   -> Internet Gateway
├── Private subnet  10.0.11.0/24  (AZ a)   -> NAT Gateway
└── Private subnet  10.0.12.0/24  (AZ b)   -> NAT Gateway

Gateways & route tables

An Internet Gateway (IGW) is the door between your VPC and the public internet — one per VPC. A subnet only becomes "public" because its route table sends 0.0.0.0/0 (all non-local traffic) to the IGW. A private subnet instead routes 0.0.0.0/0 to a NAT Gateway for outbound-only access.

# Public subnet route table
Destination   Target
10.0.0.0/16   local          # traffic inside the VPC stays local
0.0.0.0/0     igw-0abc123    # everything else -> Internet Gateway

# Private subnet route table
10.0.0.0/16   local
0.0.0.0/0     nat-0def456    # outbound only, via NAT

Security Groups vs NACLs

Both control traffic, at different layers — and the difference trips up beginners constantly.

  • Security Group (SG) — a stateful firewall attached to an instance/ENI/load balancer. You write allow rules only; if you allow an inbound request, its response is automatically allowed back out. Per-resource.
  • Network ACL (NACL) — a stateless firewall attached to a subnet, with ordered allow and deny rules. Because it is stateless you must explicitly allow both the request and the return traffic. Per-subnet.
# Security group for a web server behind an ALB
Inbound:
  Allow TCP 80   from sg-alb            # only the ALB's SG, not the whole internet
  Allow TCP 443  from sg-alb
  Allow TCP 22   from 203.0.113.10/32   # SSH from your office IP only
Outbound:
  Allow ALL      to 0.0.0.0/0
Never open 0.0.0.0/0 on port 22 (SSH) or on a database port. Lock SSH to a known IP such as 203.0.113.10/32, and never expose databases to the internet — put them in a private subnet and reference security groups by ID so only the load balancer's SG can reach your instances.

Load balancers: ALB vs NLB

Intermediate AWS's managed load-balancing service is Elastic Load Balancing. Two modern types matter: the Application Load Balancer (L7) and the Network Load Balancer (L4). Every ELB is assembled from the same pieces: a load balancer (the entry point in your public subnets), listeners (protocol + port), target groups (a pool of targets plus a health check), and targets (the backends).

FeatureApplication LB (ALB)Network LB (NLB)
OSI layerLayer 7 (HTTP/HTTPS)Layer 4 (TCP/UDP/TLS)
ProtocolsHTTP, HTTPS, gRPC, WebSocketTCP, UDP, TLS
Host / path routingYesNo
Static IPNo (DNS name only)Yes (one Elastic IP per AZ)
Throughput / latencyGoodBest (millions of req/s)
Reach for it whenWeb apps; routing; ACM TLS; EKS IngressRaw TCP/UDP; static IP; extreme speed

The ALB routes by request. You add rules to a listener, evaluated by priority; the first match wins, with the listener's default action as fallback:

# On the HTTPS:443 listener, in priority order:
Rule 10  IF host-header = api.example.com   THEN forward -> api-tg
Rule 20  IF path-pattern = /blog/*          THEN forward -> blog-tg
Default  (no match)                         THEN forward -> web-tg
The NLB preserves the client's source IP by default, so backend security groups must allow the client CIDRs, not the NLB's. This surprises people migrating from an ALB, which replaces the source IP with its own. Rule of thumb: HTTP app &rarr; ALB; raw TCP/UDP or a required static IP &rarr; NLB.

DNS & Route 53

Intermediate Route 53 is AWS's DNS service. Its headline feature is the ALIAS record — a special record that behaves like an A record at the apex (bare) domain but points at an AWS resource by name and tracks its changing IPs automatically. That solves the problem that you cannot put a CNAME on an apex domain, yet a load balancer has no fixed IP to use in an A record.

# In a Route 53 public hosted zone for example.com:
example.com       A   ALIAS -> my-alb-123.us-east-1.elb.amazonaws.com   (apex)
www.example.com   A   ALIAS -> my-alb-123.us-east-1.elb.amazonaws.com

Route 53 also offers routing policies beyond simple answers: weighted (split traffic by percentage for canaries), latency-based (send each user to the fastest region), failover (health-checked primary/secondary), and geolocation.

Beginner The point of the cloud is renting managed building blocks instead of operating them yourself. The ones you meet first:

IAM is where security lives or dies. Grant least privilege, never attach AdministratorAccess to application roles, prefer short-lived role credentials (and OIDC federation from CI) over long-lived access keys, and never commit an access key to Git — treat a leaked key as compromised and rotate it immediately.

Where it all fits together

A typical resilient web stack: Route 53 ALIAS &rarr; an internet-facing ALB in public subnets across two AZs &rarr; application instances (or EKS pods) in private subnets across the same two AZs &rarr; an RDS database in private subnets with a standby in the second AZ. The ALB is the only thing with a public face; everything stateful stays private, reachable only through security-group references.

Common mistakes

Common mistakes
  • Everything in one AZ. A load balancer only buys availability if the backends live in different AZs.
  • Databases in public subnets. Put stateful resources in private subnets; expose only the load balancer.
  • Opening SSH/DB ports to 0.0.0.0/0. Lock SSH to a known IP; reference the LB's security group by ID for app ports.
  • Looking in the wrong region. Most resources are regional and invisible from another region's console view.
  • Over-privileged IAM. Application roles with admin access turn one compromised instance into a full account breach.
  • Confusing SG and NACL behaviour. SGs are stateful (return traffic auto-allowed); NACLs are stateless (you must allow both directions).

Exercises

  • Sketch a two-AZ VPC with public and private subnets, an IGW, and a NAT gateway, and write the route table for each subnet type.
  • Write a security group for a web instance that accepts traffic only from an ALB's SG and SSH only from your IP.
  • Decide ALB vs NLB for: a REST API with path routing, a MySQL endpoint needing a static IP, and a WebSocket chat service — and justify each.
  • Explain, with the apex-CNAME rule, why a Route 53 ALIAS record is needed to point example.com at an ALB.
  • List which of EC2, S3, IAM, Route 53, and RDS are global vs regional, and why that matters operationally.

Mini-project: design a resilient two-AZ stack

On paper (or in the AWS console free tier), design a highly-available web stack in one region across two AZs. Define the VPC CIDR and four subnets (two public, two private), the IGW and NAT routing, and the security groups so only the ALB is public and the database is reachable only from the app tier. Place an internet-facing ALB in the public subnets forwarding to app instances in the private subnets, and an RDS instance (with a standby in the second AZ) in the private subnets. Add a Route 53 ALIAS record pointing the apex at the ALB. Write a one-paragraph failure analysis: what happens, end to end, when one entire AZ goes dark.
