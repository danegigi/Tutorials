Things break. Incident response is the discipline of detecting, mitigating, and learning from outages so they're short, calm, and don't recur. The payoff metric is MTTR — mean time to restore — and the culture that makes it low is blameless.

Severity levels

Beginner Classify incidents so the response matches the impact. A typical scale:

SevImpactResponse
SEV1Full outage / data lossAll-hands, page immediately, exec comms
SEV2Major feature down / severe degradationPage on-call, war room
SEV3Minor/partial, workaround existsBusiness-hours fix
SEV4Cosmetic / low impactBacklog

On-call and roles

An on-call rotation ensures someone is always responsible for responding. In a real incident, assign roles explicitly so it doesn't descend into chaos:

  • Incident Commander — coordinates, makes decisions, is not hands-on-keyboard.
  • Operations/responders — investigate and apply fixes.
  • Communications — updates the status page and stakeholders on a cadence.
  • Scribe — timestamps everything in the incident channel for the postmortem.
The Incident Commander's job is coordination, not debugging. The most common small-team failure is everyone diving into the logs and nobody steering, communicating, or deciding when to roll back.

The response loop

DETECT → TRIAGE → MITIGATE → RESOLVE → LEARN
  alert    how bad?   stop the    fix the     postmortem
           who's      bleeding    root cause  & actions
           affected?  (rollback!)
Mitigate before you diagnose. The first goal is to stop user pain, not to understand the bug. If a deploy caused it, roll back now and investigate the root cause afterward from a stable state. Teams lose precious MTTR minutes debugging a live outage they could have ended with one rollback.

SLOs and error budgets

Intermediate You can't have 100% uptime, so define the target explicitly:

TermMeaning
SLIA measured indicator, e.g. % of requests < 300ms.
SLOThe target for an SLI, e.g. 99.9% of requests succeed/month.
Error budgetThe allowed failure: 99.9% → ~43 min/month of "down" you can spend.

The error budget turns reliability into a shared, quantified decision: budget left → ship features fast; budget exhausted → freeze features and spend the sprint on reliability. It ends the dev-vs-ops "ship vs stabilize" argument with data.

Blameless postmortems

Intermediate After every significant incident, write a postmortem — blamelessly. The premise: people act reasonably given the information and tools they had, so a human "mistake" is a signal that the system let it happen.

# Postmortem skeleton
- Summary + impact (who, how long, how many users)
- Timeline (detection → mitigation → resolution, with timestamps)
- Root cause (the systemic "why", not "Alice pushed a bad config")
- What went well / what was hard
- Action items (owner + due date) — concrete fixes to prevent recurrence
The point of a postmortem is action items, not blame. If people fear being punished, they hide information and the same incident recurs. "The deploy script allowed an untested config to reach prod" is actionable; "Alice was careless" is not — and it poisons the honesty you need.

Runbooks

A runbook is a step-by-step guide for a known operational task or failure ("API latency high: check X, then Y, roll back with Z"). Good runbooks turn a 3am page from improvisation into following a checklist — and are a prime action-item output of postmortems.

Exercises

  • Define SLIs/SLOs for a web API and compute the monthly error budget for 99.9% vs 99.95%.
  • Write a runbook for one failure mode of a service you know (symptoms → checks → mitigation → rollback).
  • Take a past incident and draft a blameless root cause as a system gap, not a person's error.

Mini-project: an incident response kit

Assemble a kit for the app you've been building: a severity matrix, an on-call + roles definition, a status-page/comms template, two runbooks (e.g. "high error rate after deploy", "database connection exhaustion"), an SLO with its error budget, and a blameless postmortem template. Then run a tabletop drill: walk a simulated SEV2 through detect→mitigate→resolve→learn.
