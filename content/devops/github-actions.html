GitHub Actions runs your CI/CD pipelines inside GitHub, triggered by repo events. You describe workflows in YAML under .github/workflows/; GitHub provisions runners, executes your jobs, and reports status on commits and PRs.

The building blocks

ConceptMeaning
WorkflowA YAML file in .github/workflows/; triggered by events.
EventWhat starts it: push, pull_request, schedule, workflow_dispatch.
JobA set of steps on one runner; jobs run in parallel by default.
StepA single action or shell command.
ActionA reusable unit, e.g. actions/checkout.
RunnerThe VM/container the job runs on (ubuntu-latest, self-hosted…).

A first workflow

# .github/workflows/ci.yml
name: CI
on:
  push: { branches: [main] }
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: "1.23" }
      - run: go vet ./...
      - run: go test -race ./...

Beginner This runs on every push to main and every PR: check out the code, install Go, vet, and test with the race detector. The result appears as a check on the commit/PR.

Matrix builds

Intermediate Run the same job across versions/OSes in parallel:

jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest, macos-latest]
        go: ["1.22", "1.23"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: "${{ matrix.go }}" }
      - run: go test ./...
# → 4 parallel jobs: {ubuntu,macos} × {1.22,1.23}

Caching for speed

      - uses: actions/cache@v4
        with:
          path: ~/.cache/go-build
          key: go-${{ hashFiles('**/go.sum') }}
# Most setup-* actions have built-in caching: with: { cache: true }
Cache dependencies keyed by the lockfile hash (go.sum, bun.lockb, package-lock.json). The cache is reused until dependencies change, cutting minutes off every run. This is the single highest-ROI pipeline optimization.

Secrets and permissions

      - run: ./deploy.sh
        env:
          AWS_ROLE: ${{ secrets.AWS_ROLE_ARN }}   # from repo/org Secrets

permissions:            # least privilege for the GITHUB_TOKEN
  contents: read
  id-token: write       # for OIDC cloud auth (no long-lived keys!)
Security musts: never echo a secret (run: echo ${{ secrets.X }}) — it can leak into logs. Pin third-party actions to a full commit SHA, not a mutable tag, so a compromised tag can't inject code. Prefer OIDC federation (id-token: write) over storing long-lived cloud keys as secrets.

A build-and-deploy job

jobs:
  deploy:
    needs: test                     # only after tests pass
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production         # enables required reviewers / protection
    steps:
      - uses: actions/checkout@v4
      - name: Build & push image
        run: |
          docker build -t ghcr.io/${{ github.repository }}:${{ github.sha }} .
          echo "${{ secrets.GHCR_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin
          docker push ghcr.io/${{ github.repository }}:${{ github.sha }}
      - run: ./deploy.sh ${{ github.sha }}   # promote the SHA-tagged image

Note needs: test (gating), the if branch guard, tagging the image with github.sha (immutable artifact), and environment: production which can require manual approval.

Reusable & composite workflows

Factor shared pipeline logic into a workflow_call reusable workflow and call it from many repos — the DRY principle for pipelines.
