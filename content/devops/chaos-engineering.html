Chaos engineering is the practice of deliberately injecting failure into a system to find weaknesses before they cause an outage. It's not "breaking things for fun" — it's a disciplined experiment with a hypothesis, a limited blast radius, and a rollback.

Why inject failure on purpose

Intermediate Distributed systems fail in ways no one designed: a dependency gets slow (not down), a node vanishes mid-request, a retry storm amplifies a blip. You can't unit-test these interactions. Chaos engineering surfaces them in a controlled setting so you fix them on your schedule, not at 3am.

The goal is confidence, not chaos. A good experiment that finds nothing is still valuable: it's evidence the system tolerates that failure mode. A good experiment that finds something is a bug caught cheaply.

The experiment loop

1. STEADY STATE   Define a measurable "healthy" (e.g. p99 < 300ms, error rate < 1%).
2. HYPOTHESIS     "If one API pod is killed, steady state holds (traffic reroutes)."
3. BLAST RADIUS   Smallest scope that tests it: one pod, in staging first, 5% of traffic.
4. INJECT         Introduce the failure.
5. OBSERVE        Did steady state hold? Watch the RED/USE dashboards.
6. HALT & LEARN   Stop immediately if real users are harmed; record findings.
Non-negotiable: always define the blast radius and an abort switch before injecting, and run in staging before production. An experiment with no bound and no stop button isn't chaos engineering — it's an outage you caused. Start small (one instance) and widen only after it holds.

Resilience patterns the experiments validate

Advanced Chaos tests whether these are actually in place and tuned:

  • Timeouts on every network call — the default of "wait forever" is how one slow dependency hangs the whole system.
  • Retries with backoff + jitter — but capped, or you create a retry storm that DDoSes your own backend.
  • Circuit breaker — after N failures, stop calling a sick dependency and fail fast / serve a fallback, giving it room to recover.
  • Bulkheads — isolate resource pools so one overloaded path can't starve the others.
  • Graceful degradation — serve stale cache or a reduced feature set instead of a 500.
Common mistake: uncapped retries without jitter. When a dependency hiccups, every client retries in lockstep, the synchronized wave keeps it down, and a 2-second blip becomes a 20-minute outage. Always cap attempts, back off exponentially, and add jitter.

Game days

A game day is a scheduled, team-wide chaos exercise: pick a scenario ("the primary database fails over"), run it in a controlled window, and watch how both the system and the on-call process respond. It validates runbooks, alerts, and people — often the weakest link — and feeds directly into the incident-response practices from that lesson.

Exercises

  • Write a chaos hypothesis for a service with an explicit steady-state metric and blast radius.
  • In staging, kill one pod of a Deployment with a PDB and confirm steady state holds (no dropped requests).
  • Add a timeout + capped jittered retry + circuit breaker to one network call and verify behavior under injected latency.

Mini-project: a resilience game day

Design and run a game day on your app in staging: define steady state from your RED dashboard, run three experiments (pod kill, 300ms dependency latency, dependency outage) each with a stated hypothesis, blast radius, and abort switch. For every weakness found, add the matching resilience pattern (timeout/retry/circuit breaker/degradation) and re-run to confirm the fix. Write it up as a blameless report with action items — the same format as a postmortem.
