An AGENTS.md file is a markdown document in your repository that coding agents read automatically at the start of every session. It's the single highest-leverage tool for getting an agent to produce code that fits your project — not just code that compiles. This lesson covers what to put in it, what to leave out, how to structure it, and the rules that save you from the model's confident mistakes.

What AGENTS.md actually is

Beginner An AGENTS.md is a persistent system message for your repo. When you start an agent session (Codex CLI, Kiro CLI, Claude Code, or any tool that supports the convention), the harness reads AGENTS.md from the repo root and injects it into the model's context before your first message. From that point on, the model "knows" your project's rules without you restating them every time.

The name comes from the agents.md convention, which several tools have adopted. Different tools discover the file in slightly different ways:

ToolFile(s) discoveredWhere
Codex CLIAGENTS.mdRepo root (and nested directories)
Kiro CLIAGENTS.md + .kiro/steering/*.mdRepo root + .kiro/steering/
Claude CodeCLAUDE.mdRepo root
Any agentAGENTS.mdAny directory the agent operates in

The principle is the same across all of them: the file is read, not executed. It's plain markdown. The model treats it as instructions — not a script, not a config file, not code.

If you work across multiple agent tools, AGENTS.md is the universal one — it's recognized by the most tools. Kiro also reads .kiro/steering/*.md for topic-specific steering files that complement AGENTS.md, and Claude Code reads CLAUDE.md. You can symlink or keep them in sync if you use more than one.

The structure that works

Beginner A good AGENTS.md follows a predictable structure. Every section earns its place by answering a question the agent would otherwise have to guess at:

# AGENTS.md

## What this project is          ← context the model can't infer
## Layout                        ← where things live (directory map)
## Commands                      ← how to build, test, run, lint
## Adding or editing a lesson    ← the workflow for the most common task
### Conventions                  ← the house style (what good output looks like)
## Determinism and CI            ← rules with consequences (gotchas, traps)
## Verifying changes             ← how to know your change works
## Git                           ← branching, committing, pushing rules
## Don't                         ← explicit prohibitions

Not every project needs every section. A simple library might need only "What this is," "Commands," and "Don't." A monorepo might need per-directory AGENTS.md files. The point is: each section answers a question the agent would otherwise answer wrong by default.

A real example

Here's the AGENTS.md from this very Tutorials PWA project, abridged to show the structure:

# AGENTS.md

## What this project is
A static, offline-capable tutorial PWA published at https://danegigi.github.io/Tutorials/.
A small zero-dependency generator, run under Bun, turns hand-authored HTML
lesson fragments into the site in docs/, which GitHub Pages serves.

- Runtime: **Bun** only. No npm dependencies — don't add any without approval.
- No framework, no bundler, no TypeScript build step. Plain ES modules.

## Layout
scripts/lessons.js       # single source of truth: sections + lessons
scripts/build-site.js     # generator -> docs/
scripts/check.js          # post-build checks (run in CI)
content/<section>/<slug>.html   # lesson bodies (HTML fragments)
docs/                    # BUILD OUTPUT. Committed. Never hand-edit.

## Commands
bun run build    # generate docs/
bun run check    # run all post-build checks
bun run dev      # build + serve on :8792

## Determinism and CI (important)
CI builds, runs check.js, then **fails if committed docs/ differs from a fresh build**.
- Always rebuild and commit docs/ alongside any change.
- Keep the build **deterministic**. Don't put timestamps, Date.now(), or the
  current date into any output.
- The SW cache version is a SHA-256 content hash, not a timestamp.
- sitemap.xml deliberately has no <lastmod>.

## Don't
- Hand-edit anything in docs/.
- Append new lessons to the end of a section without considering flow.
- Introduce dependencies, a framework, or a bundler.
- Add nondeterministic output to the build.

What to include: rules with consequences

Intermediate The highest-value content in an AGENTS.md is rules with consequences — things that, if the agent gets them wrong, cause real damage or wasted time. The model already knows general programming; it doesn't know your project's traps.

Good things to include:

  • The build command and what it produces. "Run bun run build to generate docs/." The model can't guess this. Without it, the agent might edit source files and not rebuild, or try npm run build and fail.
  • The test command and what passing looks like. "Run bun run check. It must print 'All checks passed.' with zero failures." This gives the agent a clear acceptance criterion.
  • What's generated vs. hand-authored. "docs/ is build output — never hand-edit it. Edit content/ and scripts/, then rebuild." This prevents the model from "fixing" generated files.
  • Conventions that aren't enforceable by linters. "Lessons end with Common mistakes, Exercises, and a Mini-project section. Don't add a Further reading section — it's generated." A linter can't check structural conventions; an AGENTS.md can.
  • Determinism requirements. "The build must be deterministic. Don't use Date.now(), random values, or the current date in any output." This is the kind of rule that, if violated, silently breaks CI.
  • Git rules. "Stage explicit paths, not git add -A. Don't push. Commit sources and regenerated docs/ together."
  • Explicit prohibitions. "Don't introduce dependencies. Don't hand-edit docs/. Don't append lessons without considering flow." The model's default is to do the most obvious thing; your job is to override the defaults that are wrong for your project.
Test each rule by asking: "If this rule weren't here, what would the model do by default, and would that be wrong?" If the default is already right, you don't need the rule. If the default is wrong — the model would edit generated output, use npm, append to the wrong place — the rule earns its place.

What NOT to include

Intermediate An AGENTS.md is not documentation for humans, not a project README, and not a place to dump everything you know. Including too much dilutes the signal:

Don't includeWhy
Architecture explanations for humansThat belongs in README.md or docs. The AGENTS.md is for rules, not education.
Every detail of every fileThe agent can read files. Point it to the right files; don't inline their contents.
Aspirational rules ("always write perfect code")Vague aspirations don't change behavior. Specific rules do.
Secrets, credentials, API keysAGENTS.md is committed to git. Never put secrets in it. Reference env vars by name only.
General programming adviceThe model already knows how to write a for loop. Include project-specific rules, not programming tutorials.
Documentation about the product (user-facing)That's for README.md. AGENTS.md is for the agent, not the user.
Never put secrets in AGENTS.md. It's committed to git and visible to anyone who reads the repo. If the agent needs a credential, reference it by environment variable name (DATABASE_URL), never the value. If you need to tell the agent that a key is "already configured in .env," say that — but never paste the key itself.

Scope and hierarchy

Advanced AGENTS.md files compose hierarchically. The agent reads all of them, from the repo root down to the current working directory, and they stack — more specific (deeper) rules refine more general (root) rules:

repo/
├── AGENTS.md                  ← global rules (runtime, build, git)
├── src/
│   ├── AGENTS.md              ← rules for src/ (conventions, patterns)
│   └── api/
│       └── AGENTS.md          ← rules for the API (auth patterns, rate limits)
└── docs/
    └── AGENTS.md              ← rules for docs/ (don't hand-edit generated files)

When the agent works in src/api/, it reads all three: the root, src/, and src/api/. This lets you keep the root AGENTS.md focused on project-wide rules and push section-specific rules down to where they apply.

Kiro CLI also supports steering files in .kiro/steering/*.md, which work the same way — topic-specific markdown files that are loaded based on what the session is about. You can split rules across multiple steering files (e.g., jw-projects.md for project-specific conventions, security.md for auth rules) and they're combined at session start.

Global vs. project-level rules

Some rules apply to every project you work on, not just one repo. These belong in a global AGENTS.md (Kiro: ~/.kiro/steering/; Codex: ~/.codex/AGENTS.md), not in each repo:

# ~/.kiro/steering/global.md (applies to every project)

# Secrets
- Never display, print, or echo the VALUE of any secret.
- Refer to secrets by KEY NAME only (e.g. DATABASE_URL), never the value.
- Never commit .env files or credentials.

# Git
- Stage explicit paths, not git add -A.
- Don't push without being asked.
- Never run destructive git commands (reset --hard, push --force) without permission.

# Scope
- Work only within the current working directory.
- Don't read ~/.aws, ~/.ssh, or other credential trees.

Project-level AGENTS.md then adds the specific rules on top: the build command, the conventions, the traps. Global rules are the floor; project rules are the ceiling.

Writing rules that actually work

Advanced The difference between a rule that works and one that doesn't is specificity. Compare:

# Vague (doesn't work — the model ignores it)
"Write clean code."

# Specific (works — the model can follow it)
"Use early returns, not nested if/else. Extract functions longer than 30 lines.
 Name test functions Test_What_It_Tests. Never use any in TypeScript."

# Negative (works — explicitly overrides the default)
"Don't use Prisma. The runtime ORM is Drizzle. The Prisma schema is
 reference-only — do NOT use @prisma/client at runtime."

# Conditional (works — tells the model when to apply the rule)
"When adding a DB table, update the schema-parity test count assertion
 AND the uuid-identifiers test's meta.tables.length assertion, or tests break."

The pattern: state the rule, state the consequence of breaking it, and be specific enough that the model can verify it followed the rule. "Don't use Prisma" is better than "prefer Drizzle" because it's unambiguous — there's no judgment call.

The strongest rules are the ones backed by a consequence the model can observe. "Don't hand-edit docs/ because CI will fail with 'docs/ is out of date'" is stronger than "don't hand-edit docs/ because it's generated." When the model knows the rule has teeth (CI, tests, a check that fails), it follows it more reliably.

Lessons vs. rules

A lesson is a correction the model made that you want to prevent in the future. Kiro and Codex both support "learn" or "memory" systems that persist corrections across sessions. But lessons and AGENTS.md rules serve different purposes:

  • AGENTS.md — rules that apply to anyone (or any agent) working on this repo. Committed to git. Shared with the team.
  • Lessons/memory — corrections that are specific to your personal workflow. Stored locally. Not shared. Good for "I keep forgetting that this project's staging DB is truncated."

If a rule should apply to everyone who touches the repo, it belongs in AGENTS.md. If it's a personal preference or a one-time correction, it belongs in the agent's memory system.

Iterating on AGENTS.md

Advanced Your first AGENTS.md will be incomplete, and that's fine. The effective loop is:

  1. Start with the essentials — what the project is, the commands, and the top 3 traps.
  2. Run agent sessions and watch where the model makes project-specific mistakes.
  3. Add a rule for each recurring mistake. If the model keeps editing generated files, add "never hand-edit docs/." If it keeps using npm, add "runtime is Bun only."
  4. Remove rules that never trigger. If a rule has been there for 20 sessions and the model never violated it even without the rule, it might be noise.
  5. Keep it short. The model reads the whole file every session. A 50-line file it follows is better than a 500-line file it skims. Aim for rules you can count on one hand per section.
Don't over-engineer your first AGENTS.md. A 10-line file with "runtime is Bun, run bun run check, don't edit docs/" will prevent 80% of agent mistakes. The remaining 20% you discover by running sessions and adding rules reactively. A 200-line AGENTS.md written before any sessions is usually full of rules the model would have followed anyway.

AGENTS.md vs. README.md

These serve different audiences and shouldn't be conflated:

AGENTS.mdREADME.md
AudienceThe AI agentThe human developer
ContentRules, traps, commands, conventionsWhat the project is, how to get started, architecture
ToneImperative ("Don't...", "Always...")Explanatory ("This project does...")
LengthShort — only rules with consequencesFull — as much as humans need
Example"Never hand-edit docs/. Run bun run build and commit the result.""The build output in docs/ is the GitHub Pages source. To deploy, push to main."

If you find yourself writing architecture explanations in AGENTS.md, move them to README.md. If you find yourself restating the build command in README.md, make sure AGENTS.md has it too — the agent reads AGENTS.md, not README.md, by default (though some tools read both).

Common mistakes

  • Putting secrets in AGENTS.md. It's committed to git. Never paste API keys, passwords, or connection strings. Reference env vars by name.
  • Writing documentation instead of rules. AGENTS.md is for rules the agent must follow, not architecture education. That belongs in README.md.
  • Vague rules. "Write clean code" doesn't change behavior. "Use early returns, not nested if/else" does. Be specific.
  • Too long. A 500-line AGENTS.md gets skimmed. Keep it short — rules with consequences only. Aim for 50–150 lines for most projects.
  • Rules the model would follow anyway. "Write valid syntax" is noise. "Don't use Prisma at runtime, even though the schema exists" is signal — the default would be wrong.
  • No "Don't" section. Explicit prohibitions are the most effective rules. The model's default behavior is to do the obvious thing; your job is to override the defaults that are wrong for your project.
  • Not iterating. Your first draft will miss rules you only discover by watching the agent make mistakes. Add rules reactively.
  • Confusing AGENTS.md with memory/lessons. AGENTS.md is for rules that apply to everyone. Personal corrections belong in the agent's memory system.
  • Forgetting nested files. If you have a subdirectory with different conventions (e.g., a legacy module), add an AGENTS.md there. The agent reads nested files and stacks them.

Exercises

  1. Read the AGENTS.md for this project (it's in the repo root). Count the rules. Which ones would the model violate if they weren't there? Which are the "consequence-backed" rules?
  2. Write an AGENTS.md for a project you work on. Start with: what the project is, the build/test commands, and 3 rules with consequences. Keep it under 50 lines.
  3. Run an agent session with your AGENTS.md, then run the same task without it. Compare: did the agent follow the conventions? What did it get wrong that a rule could have prevented?
  4. Add a rule to your AGENTS.md that uses a consequence the model can observe: "If you do X, the test at line Y will fail" or "CI will reject this." Test whether the model follows it more reliably than a rule without a consequence.
  5. Create a nested AGENTS.md in a subdirectory of a project (e.g., src/api/AGENTS.md). Run an agent session in that directory. Verify the agent reads both the root and nested files and applies both.

Mini-project: Write and test an AGENTS.md end to end

Pick a small project (or use this one). Write an AGENTS.md with: (1) what the project is and its runtime, (2) the build and test commands, (3) 5 specific rules with consequences, and (4) a "Don't" section with 3 prohibitions. Then run two agent sessions on the same task — one with the AGENTS.md present and one with it temporarily renamed. Diff the results: did the agent follow the conventions? Did it violate any of your "Don't" rules? How much time did the rules save? Finally, add one rule you discovered was missing based on what the agent did wrong.
