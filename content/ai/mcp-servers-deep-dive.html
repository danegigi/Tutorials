The Model Context Protocol (MCP) is the standard that lets AI agents talk to external tools, data sources, and services. Instead of hard-coding API integrations into each agent, you build an MCP server that exposes your capabilities through a uniform interface — and any MCP-aware agent (Claude Code, Codex CLI, Kiro CLI, or your own) can use it without knowing your implementation. This lesson builds MCP servers from scratch, covers the three primitives (tools, resources, prompts), the two transports (stdio and SSE), testing, and real-world integrations.

What MCP solves

Beginner Before MCP, every AI agent that needed to read a database, search a wiki, or call an API had that integration baked into its own code. Change the agent, rewrite the integration. MCP decouples them:

┌─────────┐    MCP (JSON-RPC)    ┌─────────────┐
│  Agent   │ ◄──────────────────► │  MCP Server  │ ──► PostgreSQL
│ (client) │                      │  (your code)  │ ──► Jira API
└─────────┘                      └─────────────┘ ──► File system

The agent is the client. Your MCP server is the server. They communicate over JSON-RPC 2.0. The agent discovers what your server offers, calls the tools it needs, reads resources, and uses prompts — all through the standard protocol.

The three primitives

Beginner An MCP server exposes three types of capabilities:

PrimitiveWhat it isAnalogyExample
ToolsFunctions the agent can call (with arguments)API endpointsquery_database(sql), search_tickets(query)
ResourcesData the agent can read (no arguments, keyed by URI)GET endpoints / filesfile://config.json, db://schema
PromptsPre-built prompt templates the agent can useSnippets / shortcutscode_review(code), debug_error(trace)

Tools are the workhorse — most MCP servers are mostly tools. Resources are for exposing static or semi-static data. Prompts are for reusable instruction templates.

Building an MCP server with the TypeScript SDK

Beginner The official @modelcontextprotocol/sdk works under Node and Bun. Here's a complete server that exposes a file-search tool:

// search-server.ts — an MCP server for searching project files
// Run: bun run search-server.ts
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";
import { Glob } from "bun";

const server = new McpServer({
  name: "file-search",
  version: "1.0.0",
});

// Register a TOOL: the agent can call this with arguments
server.tool(
  "search_files",
  "Search for files matching a glob pattern in the project root",
  {
    pattern: z.string().describe("Glob pattern, e.g. '**/*.ts'"),
    cwd: z.string().describe("Project root directory"),
  },
  async ({ pattern, cwd }) => {
    const globber = new Glob(pattern);
    const matches = [];
    for await (const path of globber.scan({ cwd, absolute: false })) {
      matches.push(path);
    }
    return {
      content: [
        {
          type: "text",
          text: matches.length === 0
            ? `No files matching '${pattern}' in ${cwd}`
            : `Found ${matches.length} files:\n${matches.slice(0, 50).join("\n")}`,
        },
      ],
    };
  }
);

// Register a RESOURCE: the agent can read this without arguments
server.resource(
  "project-structure",
  "file://project-structure",
  async () => ({
    contents: [
      {
        uri: "file://project-structure",
        mimeType: "text/plain",
        text: await getProjectTree(),
      },
    ],
  })
);

async function getProjectTree() {
  // Return a text representation of the project structure
  const globber = new Glob("**/*");
  const files = [];
  for await (const f of globber.scan({ cwd: process.cwd(), absolute: false })) {
    files.push(f);
  }
  return files.sort().join("\n");
}

// Register a PROMPT: a reusable template the agent can invoke
server.prompt(
  "code_review",
  "Generate a code review prompt for a given file",
  { file: z.string().describe("Path to the file to review") },
  async ({ file }) => ({
    messages: [
      {
        role: "user",
        content: {
          type: "text",
          text: `Review the following file for bugs, security issues, and improvements:\n\nFile: ${file}\n\n${await Bun.file(file).text()}`,
        },
      },
    ],
  })
);

// Start the server over stdio transport
const transport = new StdioServerTransport();
await server.connect(transport);
console.error("file-search MCP server running on stdio");  // stderr only; stdout is the protocol
MCP servers communicate over stdout for the JSON-RPC protocol. Any console.log() you write goes to stdout and corrupts the protocol stream. Use console.error() for logging — it goes to stderr, which the client ignores.

Transports: stdio vs SSE

Intermediate MCP supports two transports:

TransportHow it worksBest for
stdioAgent spawns your server as a subprocess, talks over stdin/stdoutLocal tools, CLI agents, editor integrations
SSE (Server-Sent Events)Your server runs as an HTTP server; the agent connects over the networkRemote/shared servers, web-based agents, team-wide tools

The stdio transport is simpler — the agent manages the process lifecycle. SSE is for when the server needs to be shared or run remotely:

// SSE transport — runs as an HTTP server
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { SSEServerTransport } from "@modelcontextprotocol/sdk/server/sse.js";
import express from "express";

const app = express();
const server = new McpServer({ name: "remote-tools", version: "1.0.0" });

// ... register tools/resources/prompts ...

let transport: SSEServerTransport;

app.get("/sse", (req, res) => {
  transport = new SSEServerTransport("/messages", res);
  server.connect(transport);
});

app.post("/messages", (req, res) => {
  transport.handlePostMessage(req, res);
});

app.listen(3001, () => console.log("MCP SSE server on http://localhost:3001/sse"));

Building an MCP server with the Python SDK

Intermediate If your tools are Python-heavy (data analysis, ML, database queries), the Python SDK is natural:

# db_server.py — an MCP server that queries PostgreSQL
# Run: python db_server.py
from mcp.server.fastmcp import FastMCP
import asyncpg

mcp = FastMCP("postgres-query")

@mcp.tool()
async def run_sql(query: str, database: str = "app") -> str:
    """Execute a read-only SQL query and return results as text."""
    # Safety: only allow SELECT
    if not query.strip().upper().startswith("SELECT"):
        return "Error: only SELECT queries are allowed"

    conn = await asyncpg.connect(f"postgresql://localhost/{database}")
    rows = await conn.fetch(query)
    await conn.close()

    if not rows:
        return "No rows returned."

    # Format as a text table
    cols = list(rows[0].keys())
    header = " | ".join(cols)
    sep = "-+-".join("-" * len(c) for c in cols)
    body = "\n".join(" | ".join(str(r[c]) for c in cols) for r in rows)
    return f"{header}\n{sep}\n{body}"

@mcp.resource("db://schema/{table}")
async def get_schema(table: str) -> str:
    """Return the column definitions for a table."""
    conn = await asyncpg.connect("postgresql://localhost/app")
    rows = await conn.fetch("""
        SELECT column_name, data_type, is_nullable
        FROM information_schema.columns
        WHERE table_name = $1
    """, table)
    await conn.close()
    lines = [f"Table: {table}", "-" * 40]
    for r in rows:
        null = "NULL" if r["is_nullable"] == "YES" else "NOT NULL"
        lines.append(f"  {r['column_name']:20} {r['data_type']:20} {null}")
    return "\n".join(lines)

if __name__ == "__main__":
    mcp.run()  # stdio transport by default

Connecting an agent to your server

Beginner The agent side is a one-line config. In Claude Code, Codex CLI, and Kiro CLI, MCP servers are registered in a config file:

// Claude Code: ~/.claude/mcp_servers.json (or project .mcp.json)
{
  "mcpServers": {
    "file-search": {
      "command": "bun",
      "args": ["run", "/path/to/search-server.ts"]
    },
    "postgres-query": {
      "command": "python",
      "args": ["/path/to/db_server.py"]
    }
  }
}

// Kiro CLI: kiro mcp add file-search -- bun run /path/to/search-server.ts
// Codex CLI: add to config.toml under [mcp_servers]

Once registered, the agent discovers your tools on startup and can call them. You don't need to change the agent's code at all — the MCP protocol handles discovery, calling, and response parsing.

Advanced: tool annotations and validation

Advanced The quality of your tool descriptions directly affects whether the agent calls them correctly. A vague description leads to the wrong tool being called:

// BAD: the agent doesn't know when to use this
server.tool("get_data", "Gets data", {}, async () => { ... });

// GOOD: specific, describes what it returns and when to use it
server.tool(
  "get_user_orders",
  "Retrieve all orders for a user from the database. "
  + "Returns order_id, status, total, and created_at. "
  + "Use this when the user asks about their purchase history.",
  {
    user_id: z.number().int().positive().describe("The user's ID"),
    limit: z.number().int().min(1).max(100).default(10).describe("Max results"),
  },
  async ({ user_id, limit }) => {
    const orders = await db.query(
      "SELECT order_id, status, total, created_at FROM orders WHERE user_id = $1 LIMIT $2",
      [user_id, limit]
    );
    return { content: [{ type: "text", text: JSON.stringify(orders, null, 2) }] };
  }
);
Write tool descriptions for the model, not for humans. The model reads your description to decide whether to call the tool. Include: what the tool does, what it returns (field names), and when to use it vs other tools. This is the single biggest factor in MCP server quality.

Testing MCP servers

Intermediate The MCP Inspector is a built-in debugging tool:

# Run the inspector against your server
npx @modelcontextprotocol/inspector bun run search-server.ts

# Opens a web UI (http://localhost:5173) where you can:
#   - See all registered tools/resources/prompts
#   - Call tools with test arguments
#   - Inspect the JSON-RPC messages
#   - Debug why a tool isn't being called by the agent

For automated tests, use the SDK's test client:

// search-server.test.ts
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";
import { test, expect } from "bun:test";

test("search_files finds TypeScript files", async () => {
  const transport = new StdioClientTransport({
    command: "bun",
    args: ["run", "search-server.ts"],
  });
  const client = new Client({ name: "test", version: "1.0.0" }, {});
  await client.connect(transport);

  // List tools
  const { tools } = await client.listTools();
  expect(tools.map(t => t.name)).toContain("search_files");

  // Call the tool
  const result = await client.callTool({
    name: "search_files",
    arguments: { pattern: "**/*.ts", cwd: "/tmp/test-project" },
  });
  expect(result.content[0].text).toContain(".ts");

  await transport.close();
});

Production patterns

Advanced

Error handling

Tools should return errors as content, not throw — the agent can read an error message and decide what to do:

server.tool("query_db", "Run a SQL query", { sql: z.string() }, async ({ sql }) => {
  try {
    const result = await db.query(sql);
    return { content: [{ type: "text", text: JSON.stringify(result) }] };
  } catch (err) {
    // Return the error as content so the agent can reason about it
    return {
      content: [{ type: "text", text: `SQL error: ${err.message}` }],
      isError: true,
    };
  }
});

Security: least privilege

Your MCP server runs with the same permissions as the agent. If the agent is running on a developer's machine, your server can access their filesystem, env vars, and network. Design for this:

// Scope file access to a project root, not the whole filesystem
const PROJECT_ROOT = process.env.PROJECT_ROOT || process.cwd();

server.tool("read_file", "Read a file from the project", { path: z.string() }, async ({ path }) => {
  const resolved = await Bun.file(resolve(PROJECT_ROOT, path));

  // Prevent directory traversal
  if (!resolved.name.startsWith(PROJECT_ROOT)) {
    return { content: [{ type: "text", text: "Access denied: path outside project root" }], isError: true };
  }

  if (!await exists(resolved)) {
    return { content: [{ type: "text", text: `File not found: ${path}` }], isError: true };
  }

  return { content: [{ type: "text", text: await Bun.file(resolved).text() }] };
});

Caching resources

Resources that return large or computed data should cache:

let schemaCache: string | null = null;
let schemaCacheTime = 0;
const CACHE_TTL = 60_000;  // 1 minute

server.resource("db-schema", "db://schema", async () => {
  if (schemaCache && Date.now() - schemaCacheTime < CACHE_TTL) {
    return { contents: [{ uri: "db://schema", text: schemaCache }] };
  }
  schemaCache = await computeSchema();
  schemaCacheTime = Date.now();
  return { contents: [{ uri: "db://schema", text: schemaCache }] };
});

Common mistakes

  • Logging to stdout. console.log() corrupts the JSON-RPC stream. Always use console.error().
  • Vague tool descriptions. "Gets data" tells the agent nothing. Describe what the tool returns and when to use it — the description is the model's only guide.
  • No input validation. Without Zod schemas, the model can pass wrong types. Always validate with a schema and describe each parameter.
  • Throwing instead of returning errors. A thrown exception crashes the server. Return isError: true with a message so the agent can handle it.
  • Unrestricted file access. An MCP server with filesystem access should scope to a project root and block directory traversal.
  • Not testing with the Inspector. Before connecting to an agent, run the Inspector to verify tools are registered and callable. It catches 90% of issues.
  • Forgetting that resources are read-only. Resources expose data; they can't take arguments. If you need parameters, use a tool.
