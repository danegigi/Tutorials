Kiro CLI is Kiro's terminal-based coding agent. It reads your codebase, writes code, runs commands, and connects to external services — all through natural conversation. This lesson covers install, interactive chat, agents and skills, steering files, specs and workflows, MCP servers, hooks, permissions, the headless/CI mode, and the slash commands you'll use every day.

Install and sign in

Beginner

# macOS or Linux
curl -fsSL https://cli.kiro.dev/install | bash

# Windows 11 (PowerShell in Windows Terminal)
irm 'https://cli.kiro.dev/install.ps1' | iex

# Verify
kiro-cli --version

# Sign in (browser-based)
kiro-cli login

# Sign in via device code (no browser on this machine)
kiro-cli login --use-device-flow

# Check your identity
kiro-cli whoami
# → Signed in as user@example.com

# Sign out
kiro-cli logout
Kiro CLI uses advanced agent functionality from the Q Developer CLI (agent mode, MCP, steering, custom agents) and adds social login and Kiro's "Auto" model, which balances performance, efficiency, and output quality. The Auto model is the default — it picks the best model for the task automatically.

Starting a chat

Beginner

# Start an interactive session in the current directory
kiro-cli chat

# Start with an initial prompt
kiro-cli chat "Explain this repository"

# Start with a specific agent profile
kiro-cli chat --agent project-helper

# Start with a specific model
kiro-cli chat --model "claude-sonnet-4-5"
kiro-cli chat --model "ollama/qwen2.5-coder:7b"

# Set reasoning effort
kiro-cli chat --effort high

# List available models
kiro-cli chat --list-models
kiro-cli chat --list-models --format json

# Resume the previous session in this directory
kiro-cli chat --resume
kiro-cli chat -r

# Resume a specific session by ID
kiro-cli chat --resume-id SESSION_ID

# Pick from saved sessions
kiro-cli chat --resume-picker

# List saved sessions
kiro-cli chat --list-sessions

# Delete a session
kiro-cli chat --delete-session SESSION_ID

Harness versions (V2 vs V3)

Kiro CLI has two agent harnesses. Their saved session formats are incompatible — resume a session with the harness that created it:

# Select the harness for this invocation
kiro-cli chat --v2     # V2 harness
kiro-cli chat --v3     # V3 harness (newer, has specs, workflows, tangents)

# Force the terminal UI
kiro-cli --tui

# Use the deprecated Classic UI (V2 only)
kiro-cli --classic

Agents, skills, and steering

Intermediate Kiro CLI's power comes from its extensibility — custom agents, installed skills, and steering files that customize behavior per project.

Agents

An agent is a named profile with a model, tools, and instructions. You can switch agents mid-session:

# List available agents
kiro-cli agent list

# Create a custom agent profile
kiro-cli agent create code-reviewer

# Edit an agent profile (opens in $EDITOR)
kiro-cli agent edit code-reviewer

# Set the default agent for new sessions
kiro-cli agent set-default code-reviewer

# Validate an agent configuration file
kiro-cli agent validate path/to/agent.json

# Switch agents during chat
/agent list
/agent swap code-reviewer

Agent profiles live in .kiro/agents/ (workspace) or ~/.kiro/agents/ (user). A workspace profile takes precedence over a same-name user profile:

// .kiro/agents/project-helper.json
{
  "name": "project-helper",
  "model": "claude-sonnet-4-5",
  "resources": [
    "file://.kiro/steering/**/*.md",
    "skill://.kiro/skills/*/SKILL.md"
  ]
}

Skills

A Skill is an installed capability — a markdown file with instructions the agent can invoke on demand:

# Invoke an installed skill (in chat)
/code-review       # runs the code-review skill
/deploy-check      # runs the deploy-check skill

# Skills are dynamic — they appear as slash commands when installed
# Install skills through the Kiro UI or by placing them in .kiro/skills/

Skills live in .kiro/skills/<name>/SKILL.md (workspace) or ~/.kiro/skills/<name>/SKILL.md (user). Each skill's YAML frontmatter declares its name and description.

Steering files

Steering files are markdown instructions loaded at session start — like AGENTS.md but more flexible, since you can split them by topic:

# Workspace steering files (loaded for every session in this repo)
.kiro/steering/
├── project-conventions.md    ← coding style, patterns
├── security.md               ← auth rules, secret handling
└── deployment.md              ← how to deploy, what not to touch

# User-level steering (applies to all your projects)
~/.kiro/steering/
└── global.md                  ← secrets, git rules, scope rules

# View what's loaded
/context show

Instructions from both scopes are combined. Workspace instructions take precedence when they conflict. See the AGENTS.md Best Practices lesson for how to write effective steering rules.

Specs, workflows, and goals (V3)

Advanced V3 adds structured workflows for complex tasks.

Specs

A spec is a structured design document that drives implementation. Specs live in .kiro/specs/:

# Create a spec
/spec new add-auth

# View a spec document (requirements, design, or tasks)
/spec view add-auth requirements
/spec view add-auth design
/spec view add-auth tasks

# Execute spec tasks (the agent works through the task list)
/spec run add-auth

# Resume spec work
/spec add-auth

Workflows

Workflows are reusable, multi-step recipes:

# Enable workflows first (Settings → Features → Workflows, then restart)
/settings features

# Start a workflow recipe
/workflow run review-pr inputs '{"pr_number": 42}'

# Create a reusable workflow from a description
/workflow new "Review a PR: read the diff, check for security issues, post comments"

# List workflow runs
/workflow list

# Check status of a run
/workflow status WORKFLOW_ID

# Pause/resume a run
/workflow pause WORKFLOW_ID
/workflow resume WORKFLOW_ID

# Cancel a run (file changes already made remain on disk)
/workflow cancel WORKFLOW_ID

# Retry failed work (preserves completed sibling work)
/workflow retry WORKFLOW_ID [nodeId]

Goals

A goal is a bounded iteration loop — the agent pursues an objective up to N times:

# Pursue an objective (default max 5 iterations)
/goal "Make all tests pass"

# Set a custom max
/goal --max 10 "Migrate all endpoints from Express to Hono"

# Stop the goal loop (completed changes remain)
/goal clear

Tangents (conversation branches)

# Switch to or create a named branch
/tangent experiment-a
/tangent refactor-auth

# List branches
/tangent ls

# Return to root conversation
/tangent root

MCP servers

Advanced Connect external tools via the Model Context Protocol:

# Add a local MCP server (stdio)
kiro-cli mcp add \
  --name github \
  --command "npx -y @modelcontextprotocol/server-github" \
  --scope workspace

# Add with environment variables
kiro-cli mcp add --name db --command "npx my-db-server" \
  --env API_KEY=secret --timeout 30000 --scope global

# List configured servers
kiro-cli mcp list
kiro-cli mcp list workspace

# Remove a server
kiro-cli mcp remove --name github --scope workspace

# Import from a JSON file
kiro-cli mcp import --file mcp-servers.json workspace

# Check a server's status
kiro-cli mcp status --name github

# Inside chat:
/mcp                    # Inspect MCP servers
/mcp auth <server>      # Start OAuth authentication
/mcp logout <server>    # Clear OAuth login
/mcp add                # Manage registry servers (org-required)

MCP configuration lives in .kiro/settings/mcp.json (workspace) or ~/.kiro/settings/mcp.json (user):

// .kiro/settings/mcp.json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    },
    "my-api": {
      "url": "https://api.example.com/mcp",
      "headers": { "Authorization": "Bearer ${API_TOKEN}" }
    },
    "disabled-server": {
      "command": "...",
      "disabled": true
    }
  }
}
Configure MCP credentials separately from Kiro authentication. Project .env files no longer load automatically into chats, tools, or MCP servers — export required environment variables before launch.

Hooks (V3)

Advanced Hooks are lifecycle events that trigger commands or instructions. They're stored as JSON files in .kiro/hooks/ or ~/.kiro/hooks/:

// .kiro/hooks/repository-status.json
{
  "version": "v1",
  "hooks": [
    {
      "name": "repository-status",
      "trigger": "UserPromptSubmit",
      "action": {
        "type": "command",
        "command": "git status --short"
      },
      "timeout": 60,
      "enabled": true
    }
  ]
}

Available triggers:

TriggerWhen it fires
SessionStartWhen a new V3 session starts
SessionEndWhen the session shuts down (V3)
UserPromptSubmitWhen you submit a prompt
PreToolUseBefore a tool executes (exit code 2 blocks it)
PostToolUseAfter a tool executes
StopAfter the agent finishes a response
 
# Inspect configured hooks
/hooks

Permissions and workspace trust

Advanced V3 uses capability-based permissions. Rules live in permissions.yaml — user rules at ~/.kiro/settings/permissions.yaml, workspace rules at ~/.kiro/workspace-roots/<hash>/permissions.yaml:

# User-level permissions (~/.kiro/settings/permissions.yaml)
rules:
  # Always allow file reads
  - capability: fs_read
    effect: allow

  # Ask before writing files
  - capability: fs_write
    effect: ask

  # Ask before running shell commands
  - capability: shell
    effect: ask

  # Never allow recursive deletes
  - capability: shell
    effect: deny
    match: "rm -rf *"

  # Ask before web access
  - capability: web_fetch
    effect: ask

Rule effects: allow, ask, deny. The most restrictive matching effect wins: deny > ask > allow. Patterns support * within one path component and ** across directories.

# Inside chat:
/tools              # Inspect runtime tool controls
/tools schema       # Show the tool schema
/tools reset        # Reset to defaults
/tools trust-all    # V3: grant session-wide override (shows warning)
/tools trust read   # V2: trust a tool category
/tools untrust read # V2: untrust a tool category
V3 prompts for workspace trust on first open. Untrusted workspaces have restricted shell execution and writes. This is a safety feature — if you're in an unfamiliar repo, don't trust it until you've reviewed it.

Headless mode and CI

Advanced For scripts and CI, run Kiro CLI without the interactive UI:

# Headless: non-interactive, V2
kiro-cli chat --v2 --no-interactive \
  --trust-tools=read,grep \
  --output-format stream-json \
  "Summarize this repository"

# Headless: non-interactive, V3
kiro-cli chat --v3 --no-interactive \
  --output-format stream-json \
  "Fix the failing tests"

# Pipe a task via stdin
cat task.txt | kiro-cli chat --v3 --no-interactive

# Trust all tools for the session (hard denies remain)
kiro-cli chat --no-interactive --trust-all-tools "Run the linter"

# Wait for MCP startup before sending the prompt
kiro-cli chat --no-interactive --require-mcp-startup "Query the database"

# API key required for headless mode
export KIRO_API_KEY="your-api-key"

Common mistakes

  • Mixing V2 and V3 session formats. V2 and V3 have incompatible saved session formats. Resume a session with the harness that created it.
  • Forgetting --no-interactive in CI. Without it, the CLI tries to open the TUI and hangs waiting for input. Always set it for scripts.
  • Not setting KIRO_API_KEY for headless mode. Headless runs require an API key, available with Pro/Pro+/Pro Max/Power access.
  • Forgetting to enable Workflows. Workflows require enabling under /settings features and a restart before /workflow commands appear.
  • Trusting an unfamiliar workspace. V3 prompts for trust on first open. Don't trust a repo you haven't reviewed — untrusted workspaces restrict shell and writes.
  • Expecting .env to auto-load. Project .env files no longer load automatically. Export environment variables before launch, or configure them in MCP server settings.
  • Not using steering files. Without .kiro/steering/*.md or AGENTS.md, every session starts from scratch. A few well-written steering files massively improve consistency.
  • Letting context grow without compaction. Long sessions fill the window. Use /compact when the agent starts losing track.
  • Using --trust-all-tools carelessly. It grants a session-wide override. Hard denies in permissions.yaml remain in force, but everything else runs without asking.

Exercises

  1. Install Kiro CLI, sign in, and start a chat. Ask it to "explain the project structure" and observe how it reads files and reasons about them.
  2. Create a custom agent profile (e.g., a "test-runner" agent) in .kiro/agents/ with a specific model and resources. Switch to it mid-session with /agent swap.
  3. Write a steering file in .kiro/steering/project-conventions.md with 5 project-specific rules. Start a new session and verify with /context show that it's loaded.
  4. Configure an MCP server (e.g., the GitHub or filesystem server) and ask Kiro CLI to use it. List the available tools with /mcp.
  5. Run a headless session: kiro-cli chat --v3 --no-interactive --output-format stream-json "Summarize this repo". Parse the JSON output in a script.
  6. Create a hook that runs git status --short on UserPromptSubmit. Start a session and verify the hook fires when you submit a prompt.

Mini-project: Build a Kiro CLI CI review pipeline

Write a GitHub Actions workflow that runs kiro-cli chat --v3 --no-interactive --output-format stream-json --require-mcp-startup "Review the PR diff and list security issues as JSON" on every pull request. Store KIRO_API_KEY as a CI secret. Parse the JSONL output to extract the issues and post them as a PR comment using the GitHub API. Add a steering file (.kiro/steering/review-rules.md) that defines the review rules (flag SQL injection, missing auth checks, hardcoded secrets). Test the pipeline on a PR with a deliberate security issue and verify it's caught.
