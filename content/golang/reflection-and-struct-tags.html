Reflection lets a program inspect and manipulate types and values it didn't know at compile time. It's how encoding/json turns an arbitrary struct into JSON, how ORMs map rows to structs, and how validators read rules off a field. It's also slow and easy to misuse — so this lesson shows how it works, builds something real with it, and marks exactly when to reach for it.

The three laws of reflection

Advanced Go's reflection rests on three ideas from Rob Pike's "Laws of Reflection":

  1. Reflection goes from interface value to reflection object. reflect.TypeOf(x) and reflect.ValueOf(x) take an interface{} and give you a reflect.Type / reflect.Value.
  2. Reflection goes from reflection object back to interface value. v.Interface() returns to a normal value.
  3. To modify a value, it must be settable — meaning you reflected over a pointer and called .Elem(). Reflecting over a copy can't change the original.
x := 3.14
t := reflect.TypeOf(x)        // float64
v := reflect.ValueOf(x)       // 3.14
fmt.Println(t.Kind(), v.Float()) // float64 3.14

// Settability: need a pointer
p := reflect.ValueOf(&x).Elem()
p.SetFloat(2.71)              // x is now 2.71 — works because p is addressable
Type vs Kind: Type is the specific named type (main.Celsius); Kind is the underlying category (float64). Switch on Kind() when you care about the shape (struct, slice, int), on Type() when you care about the exact type.

Walking a struct's fields

type User struct {
    Name  string `json:"name" validate:"required"`
    Email string `json:"email" validate:"required,email"`
    Age   int    `json:"age"   validate:"min=0"`
}

func dump(s any) {
    v := reflect.ValueOf(s)
    t := v.Type()
    for i := 0; i < t.NumField(); i++ {
        f := t.Field(i)                 // reflect.StructField (the type/metadata)
        val := v.Field(i)               // reflect.Value (the data)
        fmt.Printf("%s = %v  (json tag: %q)\n", f.Name, val.Interface(), f.Tag.Get("json"))
    }
}
// Name = Ada  (json tag: "name") ...

Struct tags: metadata on fields

A struct tag is a raw-string literal after a field. It's a space-separated set of key:"value" pairs, parsed with Tag.Get / Tag.Lookup. The json package reads the json key; you can define your own.

f.Tag.Get("json")                 // "name"
tag, ok := f.Tag.Lookup("validate") // ok=false if the key is absent
// A json tag can carry options: `json:"name,omitempty"` — split on "," yourself.
The exported-field rule: reflection (and therefore encoding/json) can only read/write exported (capitalized) fields. A lowercase name string is invisible to JSON marshalling and to reflect.Value.Set — the single most common "why is my field missing from the JSON?" cause.

Build a real thing: a tiny validator

Advanced This is where reflection earns its keep — generic behavior over any struct:

func Validate(s any) error {
    v := reflect.ValueOf(s)
    if v.Kind() == reflect.Pointer { v = v.Elem() }
    t := v.Type()
    for i := 0; i < t.NumField(); i++ {
        rules, ok := t.Field(i).Tag.Lookup("validate")
        if !ok { continue }
        val := v.Field(i)
        for _, rule := range strings.Split(rules, ",") {
            switch {
            case rule == "required":
                if val.IsZero() {
                    return fmt.Errorf("%s is required", t.Field(i).Name)
                }
            case strings.HasPrefix(rule, "min="):
                n, _ := strconv.Atoi(rule[4:])
                if val.Kind() == reflect.Int && val.Int() < int64(n) {
                    return fmt.Errorf("%s must be >= %d", t.Field(i).Name, n)
                }
            }
        }
    }
    return nil
}
// Validate(User{Age: -1}) → "Name is required"

This is exactly how libraries like go-playground/validator work, minus the breadth of rules.

The cost — and when NOT to use it

Reflection is slow and unsafe-at-compile-time. It allocates, bypasses the type checker (errors surface as runtime panics), and is harder to read. Benchmark: reflective field access can be 10–50× slower than a direct one. Reach for it ONLY when the alternative is worse:
  • Writing a library that must work with any user struct (JSON, ORM, validator, CLI flag binder).
  • Mapping between formats where the fields aren't known until runtime.
Do NOT use it when a plain interface, a type switch, or (since Go 1.18) generics would do — generics give you compile-time safety and zero reflection cost for most "works over many types" needs. "Can I express this with a type parameter instead?" is the right first question.

Common mistakes

  • Trying to set an unaddressable value — you must reflect over a pointer and call .Elem(), or Set* panics.
  • Expecting unexported fields to work — reflection skips them for read/write.
  • Confusing Kind() and Type(), then calling .Int() on a non-int Value and panicking.
  • Reaching for reflection when generics fit — you trade compile-time safety and speed for nothing.
  • Not calling .Interface() to get back to a usable value, or passing a reflect.Value where a plain value was expected.
  • Hot-path reflection — caching the reflect.Type and field indices once (not per call) is essential if you must use it repeatedly.

Exercises

  • Write a function that prints every field name, type, and json tag of any struct passed to it.
  • Extend the validator with an email rule (regex) and a max=N rule, and test it against a struct with several failing fields.
  • Write a function that, given a pointer to a struct, sets every zero-valued string field to "N/A" — proving you understand settability.
  • Benchmark reflective field access vs direct access with go test -bench -benchmem and record the ratio.
  • Take one of your reflection functions and rewrite the same capability with generics where possible; note what you could and couldn't replace.

Mini-project

Build a small struct-to-CSV encoder: given a slice of any struct type, read a csv:"ColumnName" tag off each exported field to produce the header row, then reflect over each element to emit the data rows (formatting ints, floats, strings, and time.Time sensibly). Cache the field metadata once per type rather than per row, handle a pointer-to-slice input, and skip unexported and csv:"-" fields. Write a benchmark comparing it to a hand-written encoder for one concrete type so you can see — and defend — the reflection cost.
