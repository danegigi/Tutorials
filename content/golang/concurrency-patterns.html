The concurrency lesson introduced goroutines and channels; this one is the toolbox you reach for in real code. Worker pools to bound parallelism, fan-out/fan-in to split and merge work, pipelines to stream it, context to cancel it, errgroup to coordinate failure, and the race detector to prove it's correct.

The guiding rules

Intermediate Two Go proverbs decide most designs: "Don't communicate by sharing memory; share memory by communicating," and "the goroutine that creates a channel owns closing it." A reader never closes a channel; a writer closes it exactly once to signal "no more values." Violating the second rule is how you get panic: close of closed channel and send on closed channel.

Worker pool: bound your parallelism

Spawning one goroutine per task sounds great until a million tasks spawn a million goroutines and exhaust memory or a downstream API. A worker pool fixes the count:

func workerPool(tasks []int, workers int) []int {
    in := make(chan int)
    out := make(chan int)

    var wg sync.WaitGroup
    for i := 0; i < workers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for t := range in {        // ranges until `in` is closed
                out <- t * t           // the actual work
            }
        }()
    }

    go func() { for _, t := range tasks { in <- t }; close(in) }() // feed, then close
    go func() { wg.Wait(); close(out) }()                          // close out when all workers done

    var results []int
    for r := range out { results = append(results, r) }
    return results
}
The classic deadlock: forgetting close(in) — the workers' range never ends, wg.Wait() blocks forever, and out is never closed, so the final range out hangs. Every channel a range reads from must eventually be closed by its owner.

Fan-out / fan-in

Fan-out = multiple goroutines read from one channel (that's the pool above). Fan-in = merge multiple channels into one:

func fanIn(chans ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, c := range chans {
        wg.Add(1)
        go func(c <-chan int) { defer wg.Done(); for v := range c { out <- v } }(c)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

Pipelines

Each stage is a function that takes an input channel and returns an output channel, so stages compose and stream — stage N starts producing before stage N-1 finishes.

func gen(nums ...int) <-chan int {
    out := make(chan int)
    go func() { for _, n := range nums { out <- n }; close(out) }()
    return out
}
func sq(in <-chan int) <-chan int {
    out := make(chan int)
    go func() { for n := range in { out <- n * n }; close(out) }()
    return out
}
// usage: for v := range sq(sq(gen(2, 3))) { fmt.Println(v) }  // 16, 81

Cancellation with context

Advanced A long pipeline needs a way to stop early (caller gave up, timeout). Thread a context.Context and select on ctx.Done() alongside every send, so a goroutine never blocks forever on a reader that's gone:

func sqCtx(ctx context.Context, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            select {
            case out <- n * n:
            case <-ctx.Done():   // caller cancelled — stop, don't leak
                return
            }
        }
    }()
    return out
}
Goroutine leak: a goroutine blocked forever on out <- v because the consumer stopped reading is never garbage-collected — it leaks for the life of the process. The select-on-ctx.Done() above is the standard guard. Leaks are invisible until you watch goroutine count climb under load.

errgroup: coordinate failure

When you launch N concurrent operations and want "wait for all, but abort everything if one fails," golang.org/x/sync/errgroup is the idiomatic answer — it bundles a WaitGroup, a shared cancellable context, and first-error capture:

g, ctx := errgroup.WithContext(ctx)
for _, url := range urls {
    url := url
    g.Go(func() error {
        req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
        resp, err := http.DefaultClient.Do(req)
        if err != nil { return err }           // first error cancels ctx for the rest
        defer resp.Body.Close()
        return nil
    })
}
if err := g.Wait(); err != nil { return err }  // returns the first error
g.SetLimit(8)  // cap concurrency, like a pool

Rate limiting

limiter := time.NewTicker(200 * time.Millisecond) // 5 req/sec
defer limiter.Stop()
for _, req := range requests {
    <-limiter.C         // block until the next tick
    go handle(req)
}
// For bursts, use golang.org/x/time/rate.Limiter (token bucket).

Prove it's correct: the race detector

go test -race ./...
go run -race .
# WARNING: DATA RACE
#   Write at 0x... by goroutine 7:
#   Previous read at 0x... by goroutine 6:
A data race is undefined behavior, not "usually fine" — run -race in CI. It catches unsynchronized access to shared variables (the kind you avoid by passing data through channels or guarding with a sync.Mutex).

Common mistakes

  • Not closing a channel a range depends on → deadlock. The owner (writer) closes, once.
  • Closing from the reader side, or closing twice → panic.
  • Goroutine leaks from a send that blocks forever after the consumer left — guard sends with select { case out<-v: case <-ctx.Done(): return }.
  • Capturing the loop variable in a goroutine (pre-Go 1.22) — shadow it with x := x. Go 1.22+ fixed the loop-var semantics, but the habit is still worth knowing.
  • Unbounded goroutine spawning — one per request with no pool exhausts memory under load.
  • Assuming a passing test means no race — races are nondeterministic; only -race reliably finds them.

Exercises

  • Build a worker pool that fetches a list of URLs with a fixed concurrency of 5, then rewrite it with errgroup.SetLimit and compare.
  • Write a three-stage pipeline (generate → filter even → square) and confirm with prints that values stream rather than batch.
  • Deliberately create a goroutine leak (a send with no reader), observe the hung goroutine, then fix it with a context guard.
  • Write code with an intentional data race on a shared counter, confirm go run -race flags it, then fix it two ways: a sync.Mutex and a channel.
  • Implement a token-bucket rate limiter with golang.org/x/time/rate capping an API client to 10 req/s with bursts of 3.

Mini-project

Build a concurrent web crawler: given a seed URL and a max depth, fetch pages with a bounded worker pool, parse links with the stdlib, deduplicate visited URLs behind a mutex-guarded set, and respect a context deadline so the whole crawl can be cancelled. Use errgroup for per-page fetches, a rate limiter to stay polite, and run the whole thing under -race to prove the shared visited-set is synchronized correctly. Report pages crawled, links found, and whether it finished or was cancelled.
