The Testing & Benchmarks lesson covered go test, table tests, and benchmarks. This one goes further: native fuzzing that generates inputs to break your code, golden-file tests for complex output, deterministic concurrency testing with testing/synctest, parallel subtests, and integration tests that run against real dependencies — the techniques that catch the bugs example-based tests never will.

Native fuzzing intermediate

A fuzz test feeds your function a stream of mutated inputs, hunting for one that panics or violates a property. It's built into go test — no external tooling. The signature takes *testing.F:

func Reverse(s string) string {
    r := []rune(s)
    for i, j := 0, len(r)-1; i < j; i, j = i+1, j-1 { r[i], r[j] = r[j], r[i] }
    return string(r)
}

func FuzzReverse(f *testing.F) {
    f.Add("hello")        // seed corpus: known interesting inputs
    f.Add("")             // edge cases
    f.Add("héllo 世界")

    f.Fuzz(func(t *testing.T, s string) {
        rev := Reverse(Reverse(s))
        if rev != s {     // PROPERTY: reversing twice is the identity
            t.Errorf("double reverse: got %q want %q", rev, s)
        }
        if !utf8.ValidString(s) { t.Skip() } // ignore invalid UTF-8 inputs
    })
}
# Run as a normal unit test (just the seed corpus):
go test ./...

# Actually fuzz — generate inputs until it finds a failure or you stop:
go test -fuzz=FuzzReverse -fuzztime=30s
Fuzzing shines on parsers, encoders/decoders, and anything with a round-trip property (encode→decode == original, parse→format == input). When it finds a crasher, Go writes the exact input to testdata/fuzz/ and it becomes a permanent regression test automatically.

Table-driven tests, done right beginner

The idiomatic Go pattern — one slice of cases, one loop, a named subtest per case so failures point at the right row:

func TestAdd(t *testing.T) {
    tests := []struct {
        name     string
        a, b     int
        want     int
    }{
        {"positives", 2, 3, 5},
        {"with zero", 0, 7, 7},
        {"negatives", -2, -3, -5},
    }
    for _, tc := range tests {
        t.Run(tc.name, func(t *testing.T) { // subtest: run/filter individually
            if got := Add(tc.a, tc.b); got != tc.want {
                t.Errorf("Add(%d,%d) = %d, want %d", tc.a, tc.b, got, tc.want)
            }
        })
    }
}

Run one row: go test -run TestAdd/negatives.

Golden-file tests intermediate

When the expected output is large or complex (rendered HTML, formatted reports, generated code), inline strings become unreadable. Store the expected output in a testdata/*.golden file and regenerate it with a flag:

var update = flag.Bool("update", false, "update golden files")

func TestRender(t *testing.T) {
    got := Render(sampleInput)
    golden := filepath.Join("testdata", "render.golden")

    if *update {
        os.WriteFile(golden, []byte(got), 0o644) // regenerate on demand
        return
    }
    want, _ := os.ReadFile(golden)
    if got != string(want) {
        t.Errorf("output mismatch — run `go test -update` if intentional\n%s", got)
    }
}
# Intentionally changed the output? Regenerate and review the diff in git:
go test -run TestRender -update
Always review the git diff after -update. The whole point is that an unexpected change is visible — blindly updating goldens defeats the test.

Deterministic concurrency with testing/synctest advanced

Testing time-based or concurrent code with real time.Sleep is slow and flaky. testing/synctest (Go 1.24+, now stable) runs a "bubble" with a fake clock that advances instantly when all goroutines are blocked — so a test of a 5-second timeout runs in microseconds and is fully deterministic:

import "testing/synctest"

func TestTimeout(t *testing.T) {
    synctest.Test(t, func(t *testing.T) {
        ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
        defer cancel()

        start := time.Now()
        <-ctx.Done()                 // fake clock jumps straight to 5s
        synctest.Wait()              // let all goroutines settle

        if d := time.Since(start); d != 5*time.Second {
            t.Errorf("got %v, want exactly 5s", d) // deterministic, not "about 5s"
        }
    })
}

Integration tests with real dependencies advanced

Unit tests mock; integration tests use the real thing. Gate them behind testing.Short() so go test -short skips them in fast loops, and spin up real services with testcontainers-go:

func TestUserRepo(t *testing.T) {
    if testing.Short() { t.Skip("integration test") }

    ctx := context.Background()
    pg, err := postgres.Run(ctx, "postgres:16-alpine",
        postgres.WithDatabase("test"), postgres.WithPassword("secret"))
    if err != nil { t.Fatal(err) }
    t.Cleanup(func() { pg.Terminate(ctx) }) // tears the container down after the test

    dsn, _ := pg.ConnectionString(ctx)
    db, _ := sql.Open("pgx", dsn)
    // ... migrate, then test the repo against a REAL Postgres ...
}

For simpler cases, prefer interfaces + fakes over heavy mocking libraries: define the dependency as an interface the consumer owns, and pass a hand-written fake in tests. It's clearer and survives refactors better than generated mocks.

Coverage & parallelism intermediate

# Coverage with a visual report:
go test -coverprofile=cover.out ./...
go tool cover -html=cover.out    # open annotated source in the browser

# Mark independent subtests parallel to speed up the suite:
t.Parallel()  // inside t.Run; they interleave with other parallel subtests
The classic parallel-subtest bug: capturing the loop variable. Before Go 1.22 you had to write tc := tc inside the loop or every parallel subtest saw the last case. Go 1.22+ gives each iteration its own variable, so the shadow is no longer needed — but check which Go version your module targets.

Common mistakes

  • Asserting time.Since is "about" a value. Real-clock timing tests are flaky under load. Use testing/synctest for exact, instant results.
  • Blindly running -update. Golden files only catch regressions if you review the diff before committing the new golden.
  • No seed corpus on a fuzz test. Without f.Add seeds the fuzzer starts cold; good seeds (edge cases, known-tricky inputs) find bugs far faster.
  • Mixing integration tests into the fast loop. Not gating slow tests behind testing.Short() makes go test ./... painfully slow and discourages running it.
  • Over-mocking. A pile of generated mocks for behavior you could cover with one hand-written fake makes tests brittle and hard to read.
  • Forgetting t.Cleanup. Leaked containers/temp dirs/goroutines accumulate across a run; register teardown with t.Cleanup instead of hoping a defer in the right scope fires.

Exercises

  1. Write a FuzzParse for a small parser you have (or a JSON round-trip). Let it run 30s and turn any crasher it finds into a committed regression case.
  2. Convert a test with a big inline expected string into a golden-file test with an -update flag. Change the output on purpose and confirm the diff is reviewable.
  3. Test a function that waits on a context timeout using testing/synctest and assert the exact elapsed fake-time.
  4. Add an integration test gated by testing.Short() that uses testcontainers-go (or a local service) and tears it down with t.Cleanup.

Mini-project: break your own encoder

Take (or write) a function pair that encodes and decodes a small format — e.g. a URL query-string codec or a simple binary record. Write: (1) table-driven unit tests for the known cases, (2) a golden-file test for a representative encoded output, and (3) a fuzz test asserting the round-trip property decode(encode(x)) == x. Run the fuzzer until it finds a failing input (feed it tricky seeds — empty strings, unicode, embedded delimiters), fix the bug it exposes, and confirm the auto-saved corpus entry now passes. You'll have proven the difference between "my examples pass" and "no input breaks it."
