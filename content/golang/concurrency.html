Concurrency is built into Go: start a goroutine with go, communicate over channels, coordinate with select and the sync package, and cancel work cleanly with context. "Don't communicate by sharing memory; share memory by communicating."

Goroutines

Beginner A goroutine is a function running concurrently, scheduled by the Go runtime onto OS threads. They're cheap — thousands are routine.

func main() {
	go say("hello")   // runs concurrently
	say("world")      // runs on the main goroutine
}
// Without synchronization, main may exit before the goroutine runs —
// that's the whole reason channels and WaitGroups exist.

Channels

ch := make(chan int)       // unbuffered: send blocks until a receiver is ready
ch := make(chan int, 10)   // buffered: send blocks only when full

go func() { ch <- 42 }()   // send
v := <-ch                  // receive (blocks until a value arrives)

// Close signals "no more values"; receivers can detect it
close(ch)
v, ok := <-ch              // ok=false once drained & closed

// Range receives until the channel is closed
for v := range ch { use(v) }
Common mistakes: (1) sending on a closed channel — panics. (2) closing a channel twice — panics. (3) forgetting to close, so a range blocks forever (deadlock). Rule of thumb: the sender closes, and only once.

select

select {
case v := <-ch1:
	fmt.Println("from ch1:", v)
case ch2 <- 99:
	fmt.Println("sent to ch2")
case <-time.After(time.Second):
	fmt.Println("timeout")       // a timeout without goroutine leaks
default:
	fmt.Println("nothing ready") // non-blocking select
}

sync primitives

Intermediate When you genuinely share state (a counter, a cache), guard it:

var (
	mu    sync.Mutex
	count int
)
func incr() { mu.Lock(); count++; mu.Unlock() }

// Wait for a set of goroutines to finish
var wg sync.WaitGroup
for _, url := range urls {
	wg.Add(1)
	go func(u string) {   // Go 1.22+: closure capture of range var is safe
		defer wg.Done()
		fetch(u)
	}(url)
}
wg.Wait()

// Run something exactly once
var once sync.Once
once.Do(func() { initExpensiveThing() })
The race detector catches most data races: go test -race ./... or go run -race .. Run it in CI — it finds the bugs that only appear under load in production.

context: cancellation and deadlines

Advanced context.Context carries cancellation signals and deadlines across API boundaries. Every blocking or long-running function should accept one as its first argument.

ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()   // always call cancel to release resources

req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
resp, err := http.DefaultClient.Do(req)   // aborts if ctx expires

// Honor cancellation in your own loops
func worker(ctx context.Context, jobs <-chan Job) {
	for {
		select {
		case <-ctx.Done():
			return                 // caller cancelled — stop
		case j := <-jobs:
			process(j)
		}
	}
}

Pattern: a worker pool

func pool(ctx context.Context, jobs []Job, workers int) []Result {
	in := make(chan Job)
	out := make(chan Result)
	var wg sync.WaitGroup

	for i := 0; i < workers; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := range in {
				out <- do(j)
			}
		}()
	}
	go func() { for _, j := range jobs { in <- j }; close(in) }()
	go func() { wg.Wait(); close(out) }()

	var results []Result
	for r := range out { results = append(results, r) }
	return results
}

Exercises

  • Fetch 5 URLs concurrently with a WaitGroup and collect the status codes.
  • Reproduce a data race on a shared counter, confirm it with -race, then fix it with a Mutex.
  • Add a 500ms timeout to an HTTP call with context.WithTimeout and handle the cancellation.

Mini-project: a concurrent link checker

Given a list of URLs, use a worker pool of N goroutines to fetch each and report its status code and latency. Add a global context timeout so the whole run can't exceed, say, 10 seconds, and use the race detector to prove your result aggregation is safe.
