How you organize a Go codebase shapes how easy it is to change. Go's conventions are light but opinionated: packages by capability, internal/ to enforce boundaries, cmd/ for entrypoints, interfaces at the edges, and dependencies passed in — not reached for.

Packages are about capability, not category

Beginner Name packages for what they do, not for a layer. package store, package auth, package billing — not package models, package utils, package helpers.

Common mistakes: (1) a grab-bag util package — it becomes a dumping ground everything imports, creating a dependency hairball. (2) Naming a package after a design pattern (interfaces, abstractions). (3) Stuttering: http.HTTPServer — the package name is already the prefix, so it's http.Server. Name the package so its exported identifiers read well at the call site.

A typical layout

myapp/
├── go.mod
├── cmd/
│   └── server/
│       └── main.go          # thin entrypoint: wire deps, start
├── internal/                # private to this module — can't be imported outside
│   ├── store/               # database access
│   │   ├── store.go
│   │   └── store_test.go
│   ├── user/                # user domain logic
│   └── http/                # handlers + routing
├── pkg/                     # (optional) code meant for OTHER modules to import
└── README.md
  • cmd/<name>/main.go — one per binary; keep it thin (parse config, construct dependencies, run).
  • internal/ — the compiler forbids import from outside the module, so it's your enforced private API.
  • pkg/ — only if you publish reusable libraries; many apps skip it (it's a convention, not a rule).
Start flat. A small program is fine as a single main package in the root — don't scaffold a 10-directory tree for 300 lines. Introduce internal/ packages when the file count or the need for boundaries actually appears. Premature structure is as bad as none.

Dependency injection by hand

Intermediate Go doesn't need a DI framework. Pass dependencies in as struct fields or constructor arguments — explicit, testable, no magic:

type Service struct {
	store  Store          // an interface (below)
	mailer Mailer
	logger *slog.Logger
}

func NewService(s Store, m Mailer, l *slog.Logger) *Service {
	return &Service{store: s, mailer: m, logger: l}
}

// main.go wires the concrete implementations together:
func main() {
	db := store.NewPostgres(dsn)
	svc := user.NewService(db, mail.NewSES(), slog.Default())
	srv := httpapi.New(svc)
	srv.Run(":8080")
}

Accept interfaces, return structs

// Define the interface where it's CONSUMED, listing only what you use
package user
type Store interface {           // user's needs, not store's full surface
	GetUser(ctx context.Context, id string) (*User, error)
	SaveUser(ctx context.Context, u *User) error
}

// The concrete type returns itself; callers depend on the small interface.
Two Go idioms do a lot of work here: "accept interfaces, return structs" (functions take the minimal interface they need and return concrete types), and define the interface in the consuming package (so the dependency arrow points inward and tests can supply a fake). This keeps packages decoupled without a framework.

Testing benefits from the structure

// Because Service depends on the Store INTERFACE, tests inject a fake:
type fakeStore struct{ users map[string]*user.User }
func (f *fakeStore) GetUser(_ context.Context, id string) (*user.User, error) {
	return f.users[id], nil
}
svc := user.NewService(&fakeStore{...}, nil, slog.Default())
// No database needed — fast, deterministic unit tests.

Config and wiring

Load config once in main (env vars / flags, per the Deployment lesson), construct everything, and pass it down. Avoid global variables and init() side effects — they make the dependency graph invisible and tests order-dependent.

Exercises

  • Refactor a single-file program into cmd/ + internal/ packages named by capability.
  • Define a consumer-side Store interface and inject a fake in a unit test.
  • Find a util package (or write one) and split it into capability-named packages.
