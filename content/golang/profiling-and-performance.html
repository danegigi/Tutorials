Go ships first-class profiling in the toolchain. Before optimizing anything, measure: benchmark the hot path, capture a CPU or memory profile with pprof, read it, and let allocation and escape analysis tell you where the time and garbage actually go.

Benchmark first

func BenchmarkJoin(b *testing.B) {
	parts := []string{"a", "b", "c", "d"}
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		_ = strings.Join(parts, "-")
	}
}
go test -bench=. -benchmem -count=5 ./...
# BenchmarkJoin-8   24000000   48 ns/op   16 B/op   1 allocs/op
#                   ^iters      ^time      ^bytes    ^allocations per op
Run with -count=5 and compare runs with benchstat, which reports the mean and whether a change is statistically significant. A single run's number is noise; benchstat tells you if your "optimization" actually did anything.

CPU profiling with pprof

Intermediate

# From a benchmark:
go test -bench=BenchmarkJoin -cpuprofile=cpu.out ./...
go tool pprof cpu.out
#   (pprof) top10        ← functions by CPU time
#   (pprof) list Join    ← annotated source, line by line
#   (pprof) web          ← a call graph (needs graphviz)
// From a running server: import for the /debug/pprof endpoints
import _ "net/http/pprof"
// then: go tool pprof http://localhost:8080/debug/pprof/profile?seconds=30

Memory profiling

go test -bench=. -memprofile=mem.out ./...
go tool pprof -alloc_space mem.out      # total allocated (where garbage is made)
go tool pprof -inuse_space mem.out      # live heap (where a leak lives)
#   (pprof) top -cum
#   (pprof) list YourFunc
Common mistake: optimizing without a profile — "I think this loop is slow". You will almost always be wrong about where the time goes. Profile first; the bottleneck is frequently I/O, allocations, or a hot function you didn't suspect, not the code you were eyeing.

Escape analysis & allocations

Advanced A value that "escapes" to the heap costs an allocation and GC pressure. The compiler tells you what escapes and why:

go build -gcflags="-m" ./...
# ./main.go:12:9: &user escapes to heap
# ./main.go:20:13: make([]int, n) does not escape

Common fixes once a profile points at allocation:

// Preallocate when the size is known — avoids repeated slice growth
out := make([]int, 0, len(in))

// strings.Builder instead of += in a loop
var b strings.Builder
for _, s := range parts { b.WriteString(s) }

// sync.Pool to reuse expensive buffers on a hot path
var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}

The execution tracer

go test -trace=trace.out ./...
go tool trace trace.out     # goroutine scheduling, GC pauses, blocking

Use the tracer when the problem is concurrency, not raw CPU — goroutines blocking on each other, GC stop-the-world pauses, or an under-utilized worker pool. pprof says "where the CPU goes"; the tracer says "why things are waiting".

A sane optimization loop

  1. Write a benchmark that reproduces the slow path.
  2. Profile it (CPU, then memory) and find the real hotspot.
  3. Change one thing; re-benchmark with benchstat to confirm it helped.
  4. Stop when it's fast enough — don't trade readability for nanoseconds that don't matter.
Don't micro-optimize prematurely. Readable code that's fast enough beats clever code that saved 5ns on a path called twice a day. Optimize the paths a profile proves are hot, under a benchmark that proves the win — and leave the rest clear.

Mini-project: profile and speed up a real function

Take a function that parses or transforms a large input (e.g. the JSON⇄CSV converter from the Files lesson). Write a benchmark, capture CPU + memory profiles, find the top allocator, and apply the right fix (preallocation / strings.Builder / sync.Pool). Prove the improvement with benchstat comparing before/after — and record one optimization you tried that didn't help, to internalize "measure, don't guess".
