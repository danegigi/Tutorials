gRPC is a high-performance RPC framework: you define your service and messages once in a .proto file, generate strongly-typed Go client and server code from it, and communicate over HTTP/2 with compact binary Protocol Buffers instead of JSON. This lesson takes you from a schema to a running server and client, through the four call types, to interceptors — and when gRPC beats REST.

Why gRPC exists

Intermediate REST+JSON is universal but loose: the contract lives in docs, every service re-parses text, and there's no streaming built in. gRPC trades universality for rigor — a single schema generates matching code on both ends, Protobuf is smaller and faster to encode than JSON, and HTTP/2 gives you multiplexing and bidirectional streaming for free. The cost: it's not browser-native (needs gRPC-Web/a proxy) and the payloads aren't human-readable.

The schema: .proto

// greet/greet.proto
syntax = "proto3";
package greet;
option go_package = "github.com/me/app/greet;greetpb";

service Greeter {
  rpc SayHello(HelloRequest) returns (HelloReply);
}

message HelloRequest {
  string name = 1;      // the number is the field's wire tag — NEVER reuse or renumber
}
message HelloReply {
  string message = 1;
}
Field numbers are the contract, not the names. Protobuf encodes field 1, field 2… by number. You may rename a field freely, but changing or reusing a number breaks every peer that was built against the old schema. To remove a field, mark it reserved so the number can't be accidentally recycled.

Generate the Go code

# one-time: install the plugins
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest

protoc --go_out=. --go_opt=paths=source_relative \
       --go-grpc_out=. --go-grpc_opt=paths=source_relative \
       greet/greet.proto
# produces greet.pb.go (messages) and greet_grpc.pb.go (client + server interfaces)
Most teams drive this with buf (buf generate) instead of raw protoc — it manages plugin versions, lints the schema, and detects breaking changes in CI. Learn protoc once to understand it, then switch to buf for real projects.

Implement the server

type server struct { greetpb.UnimplementedGreeterServer } // embed for forward-compat

func (s *server) SayHello(ctx context.Context, in *greetpb.HelloRequest) (*greetpb.HelloReply, error) {
    if in.GetName() == "" {
        return nil, status.Error(codes.InvalidArgument, "name is required")
    }
    return &greetpb.HelloReply{Message: "Hello, " + in.GetName()}, nil
}

func main() {
    lis, _ := net.Listen("tcp", ":50051")
    s := grpc.NewServer()
    greetpb.RegisterGreeterServer(s, &server{})
    log.Fatal(s.Serve(lis))
}
Always embed UnimplementedGreeterServer. It provides default methods so that when the .proto adds a new RPC, your server still compiles (the new method returns "unimplemented" instead of breaking the build). Omitting it is the most common upgrade-breaks-build mistake.

The client

conn, _ := grpc.NewClient("localhost:50051",
    grpc.WithTransportCredentials(insecure.NewCredentials())) // TLS in prod!
defer conn.Close()
client := greetpb.NewGreeterClient(conn)

resp, err := client.SayHello(ctx, &greetpb.HelloRequest{Name: "Ada"})
// resp.GetMessage() == "Hello, Ada"

The four RPC types

Advanced HTTP/2 streams let gRPC do more than request/response:

Type.protoUse for
Unaryrpc M(Req) returns (Resp)normal call
Server streamingreturns (stream Resp)a feed/large result set
Client streaming(stream Req) returns (Resp)uploads, aggregation
Bidirectional(stream Req) returns (stream Resp)chat, live sync
// server streaming handler
func (s *server) ListUpdates(req *pb.Req, stream pb.Svc_ListUpdatesServer) error {
    for _, u := range updates {
        if err := stream.Send(u); err != nil { return err }
    }
    return nil // closing the handler ends the stream
}

Interceptors: gRPC's middleware

func logging(ctx context.Context, req any, info *grpc.UnaryServerInfo,
    handler grpc.UnaryHandler) (any, error) {
    start := time.Now()
    resp, err := handler(ctx, req)
    log.Printf("%s took %v err=%v", info.FullMethod, time.Since(start), err)
    return resp, err
}
s := grpc.NewServer(grpc.UnaryInterceptor(logging))
// chain several with grpc.ChainUnaryInterceptor(auth, logging, recovery)

Interceptors handle cross-cutting concerns — auth (read a token from metadata), logging, metrics, panic recovery — the same way HTTP middleware does.

Errors and status codes

Don't return bare errors; use google.golang.org/grpc/status + codes so clients get a typed status (NotFound, InvalidArgument, Unauthenticated, DeadlineExceeded). The client inspects it with status.FromError(err). Deadlines propagate automatically through context — set one on the client and the server sees it.

Common mistakes

  • Reusing or renumbering a field number — silently corrupts the wire format for peers on the old schema. Use reserved.
  • Not embedding UnimplementedXServer, so adding an RPC to the .proto breaks the build.
  • Shipping insecure.NewCredentials() to production — that's plaintext; use TLS creds.
  • Returning plain errors instead of status.Error(codes.X, ...), so clients can't distinguish failures.
  • Committing generated *.pb.go but not regenerating after a .proto change — the code and schema drift. Regenerate in CI.
  • Expecting a browser to call gRPC directly — it can't; you need gRPC-Web + a proxy (Envoy) or gRPC-Gateway for a REST bridge.

Exercises

  • Write a .proto for a calculator service, generate the Go code, and implement unary Add/Divide (returning InvalidArgument on divide-by-zero).
  • Add a server-streaming RPC that emits a countdown, and consume it from a client with a for { stream.Recv() } loop.
  • Write a logging + a panic-recovery interceptor and chain them on the server.
  • Set a 1-second client deadline, make the server sleep 2 seconds, and confirm the client gets DeadlineExceeded.
  • Add a field to a message with a NEW number, regenerate, and verify an old client still talks to the new server (forward/backward compatibility).

Mini-project

Build a small gRPC key-value store: a .proto with unary Get/Set/Delete, a server-streaming Watch that pushes changes to subscribers, and a bidirectional Sync. Implement the server with a mutex-guarded map, use status/codes for errors (NotFound on a missing key), add auth + logging interceptors (token in metadata), and secure it with TLS. Write a CLI client that exercises every RPC type, and document how a non-Go client (or a browser via gRPC-Gateway) would consume the same schema.
