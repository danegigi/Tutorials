Go manages memory for you, but "managed" is not "free". Where a value lives — the stack or the heap — decides whether it costs the garbage collector anything at all. This lesson explains how Go decides, how its collector actually works, the two knobs that control it, and how to read a heap profile so you optimize the allocations that matter instead of guessing.

Stack vs heap beginner

Every goroutine has a stack — a cheap, per-goroutine region that grows and shrinks as functions call and return. Allocating on the stack is nearly free: it is a pointer bump, and the memory is reclaimed automatically when the function returns. The heap is shared, and anything on it must eventually be found and freed by the garbage collector.

In most languages you choose (new vs a local). In Go the compiler chooses, using escape analysis: if it can prove a value does not outlive the function, it stays on the stack; if the value might be referenced after the function returns, it escapes to the heap.

The practical rule: heap allocations are what the GC has to track. Fewer heap allocations ⇒ less GC work ⇒ lower latency and CPU. You rarely need zero allocations — you need to stop allocating in the hot path.

Escape analysis in depth intermediate

Ask the compiler to show its decisions with -gcflags=-m (repeat -m for more detail):

go build -gcflags=-m ./... 2>&1 | grep -E 'escapes|moved to heap'

Three things force a value to the heap:

// 1. Returning a pointer to a local — it must outlive the function.
func newUser() *User {
    u := User{Name: "Ada"} // "moved to heap: u"
    return &u
}

// 2. Storing into an interface — the concrete value is boxed.
func log(v any) {}          // v escapes: the callee could keep it
log(User{})

// 3. A value whose size isn't known at compile time (e.g. a slice
//    that grows), or one captured by a closure that escapes.
func counter() func() int {
    n := 0                  // "moved to heap: n" — the closure outlives counter
    return func() int { n++; return n }
}

Common surprises the -m output reveals: passing a value to a function via an interface parameter (including fmt.Println(x)) usually escapes it, and taking the address of a loop variable that is stored somewhere escapes it.

Do not contort your code to avoid escapes you haven't measured. Escape analysis changes between Go releases, and a "clever" rewrite to keep something on the stack often hurts readability for zero real-world gain. Profile first; optimize the hot path only.

How Go's garbage collector works intermediate

Go uses a concurrent, tri-color mark-and-sweep collector with a write barrier. The important properties for an application developer:

  • Concurrent — most of the marking runs alongside your goroutines, not in a stop-the-world pause.
  • Non-generational, non-compacting — it does not move objects, so pointers stay valid and unsafe/cgo interop is simpler.
  • Pauses are tiny — the stop-the-world phases are sub-millisecond on modern Go; the cost shows up as CPU spent marking, not as long freezes.
  • Pacing — the GC aims to finish a cycle before the heap doubles (by default). It trades CPU for memory: collect more often and use less RAM, or less often and use more.

The two knobs: GOGC and GOMEMLIMIT advanced

GOGC (default 100) sets how much the heap may grow between collections, as a percentage of live data. GOGC=100 means "collect when the heap reaches 2× the live set." Higher = fewer GCs, more RAM; lower = more GCs, less RAM. GOGC=off disables the GC entirely (only for short-lived batch jobs).

GOMEMLIMIT (Go 1.19+) is a soft memory limit. The GC will run more aggressively as the heap approaches it, trading CPU to stay under the cap — invaluable in containers with a hard memory limit, where the real killer is the OOM-killer.

# Give a 512 MiB container some headroom and let GOGC stay default.
GOMEMLIMIT=450MiB ./server

# Or set it from code at startup:
import "runtime/debug"
debug.SetMemoryLimit(450 << 20) // 450 MiB
debug.SetGCPercent(100)         // == GOGC
GOMEMLIMIT is a soft limit: if live data genuinely exceeds it, Go will spend ever more CPU on GC ("GC death spiral") rather than crash. Set it below the container's hard limit (leave ~10–20% headroom for stacks, goroutines, and off-heap memory), and keep GOGC on so the limit is a safety ceiling, not the normal trigger.

Reading a heap profile advanced

Guessing where allocations come from wastes time. Capture a profile and let the tool point at the lines:

// Expose pprof on a debug port (dev/staging only).
import _ "net/http/pprof"
go func() { http.ListenAndServe("localhost:6060", nil) }()
# Snapshot the live heap and open the interactive explorer.
go tool pprof http://localhost:6060/debug/pprof/heap

# Inside pprof:
(pprof) top          # biggest allocators by in-use bytes
(pprof) list myFunc  # per-line allocation annotations
(pprof) web          # open a graph in the browser

# For allocation RATE (what the GC actually chews on), use alloc_space:
go tool pprof -alloc_space http://localhost:6060/debug/pprof/heap

Read -inuse_space to find memory leaks (what is still retained), and -alloc_space to find GC pressure (what churns, even if freed quickly). A classic hot-path fix once you've found it — reuse buffers with a sync.Pool instead of allocating per request:

var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}

func handle(w http.ResponseWriter, r *http.Request) {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset()
    defer bufPool.Put(buf)
    // ... build the response in buf, no per-request allocation ...
}

Common mistakes

  • Micro-optimizing escapes without a profile. You rewrite readable code to shave stack/heap decisions that never showed up in CPU or allocation profiles. Measure, then optimize the top entries only.
  • Setting GOMEMLIMIT equal to the container limit. With no headroom, off-heap and stack memory push you past the hard cap and the OOM-killer fires anyway. Set it below, with margin.
  • Turning GOGC off in a long-running service. It never collects and the heap grows without bound. GOGC=off is only for short batch jobs that exit.
  • Reading inuse_space when you meant allocation rate. A function can allocate megabytes per second that are immediately freed — invisible in in-use, but it dominates GC CPU. Use -alloc_space for pressure.
  • Keeping a huge slice alive by sub-slicing it. small := big[:10] still pins the whole backing array. Copy if you need to let the big one go.

Exercises

  1. Write a function that returns *T and one that returns T. Build both with -gcflags=-m and confirm which moves to the heap and why.
  2. Pass the same struct to a function once by concrete type and once through an any parameter. Observe the escape in the -m output.
  3. Run a small allocation-heavy loop, capture an -alloc_space heap profile, and use list to find the exact line responsible.
  4. Take a service, set GOGC=50 then GOGC=200, and compare GC CPU% (via GODEBUG=gctrace=1) and RSS. Explain the trade-off you observe.

Mini-project: tune a leaky request handler

Build a tiny HTTP service with a handler that allocates a new large buffer and a new slice on every request. Add net/http/pprof, drive load with hey or a loop, and capture -alloc_space. Then: (1) introduce a sync.Pool for the buffer, (2) pre-size the slice with make([]T, 0, n), and (3) set a sensible GOMEMLIMIT. Re-profile and record the before/after allocation rate and GC CPU% from GODEBUG=gctrace=1. Your deliverable is a short note showing the numbers moved — proof you optimized by measurement, not by guesswork.
