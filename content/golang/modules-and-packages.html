A module is the unit Go downloads, versions, and builds. Learn go.mod, how dependencies are added and pinned, how packages map to directories, and how go work lets you develop several modules at once.

Modules vs packages

Beginner A package is all the .go files in one directory sharing a package name. A module is a tree of packages versioned together, rooted at a go.mod file. You import packages; you depend on modules.

myapp/
├── go.mod                 # module example.com/myapp
├── main.go                # package main
└── internal/
    └── store/
        └── store.go       # package store → import "example.com/myapp/internal/store"
A package under a directory named internal/ can only be imported by code rooted at the parent of internal/. It's the language-level way to keep implementation packages private to your module.

go.mod

go mod init example.com/myapp
// go.mod
module example.com/myapp

go 1.23

require (
	github.com/google/uuid v1.6.0
	github.com/jmoiron/sqlx v1.4.0
)

The go directive sets the language version. The require block lists direct dependencies with exact versions. A go.sum file (committed alongside) records cryptographic checksums so every build is verifiable.

Adding and managing dependencies

# Add a dependency (fetches, records in go.mod + go.sum)
go get github.com/google/uuid@latest
go get github.com/google/uuid@v1.6.0   # pin a specific version

# Remove unused + add missing in one pass (run before committing)
go mod tidy

# See the full dependency graph / why something is pulled in
go mod graph
go mod why github.com/google/uuid
Common mistake: hand-editing go.mod to bump a version and forgetting go.sum. Always change versions with go get (or edit then run go mod tidy), which keeps the checksum file consistent — otherwise the build fails with a "missing go.sum entry" error.

Semantic import versioning

Intermediate Go encodes major versions ≥2 in the import path. v1 is implicit; v2+ appends /v2 to both the module path and the import:

require github.com/some/lib/v2 v2.3.1
import "github.com/some/lib/v2"

This lets a program depend on v1 and v2 of the same library simultaneously without conflict — they are, to the toolchain, different modules.

Multi-module workspaces (go work)

Intermediate When you're editing a library and an app that uses it at the same time, a workspace lets the app see your local, uncommitted library changes without a replace directive:

go work init ./myapp ./mylib
# creates go.work pointing at both local modules
// go.work
go 1.23
use (
	./myapp
	./mylib
)

Now go build in myapp resolves imports of mylib to your local checkout. Commit go.work only for shared monorepos; otherwise keep it local (it's often .gitignored).

Exercises

  • Create a module, go get github.com/google/uuid, print a uuid.NewString(), then run go mod why on it.
  • Move a helper into internal/util/ and import it from main; confirm an outside module cannot import it.
  • Set up a two-module go work workspace and verify an edit in the library is picked up by the app without committing.

Mini-project: a library + CLI in one workspace

Build mylib exposing func Slugify(s string) string, and slugcli that reads a line from stdin and prints its slug. Wire them with go work so you can iterate on Slugify and immediately test it through the CLI, then go mod tidy each module before "shipping".
