bun build is a fast native bundler for both browser and server targets — with tree-shaking, code splitting, minification, and the standout feature --compile, which packs your app and the Bun runtime into a single standalone binary. This lesson covers bundling, tree-shaking, standalone executables, and Docker.

bun build — the basics

Beginner Point it at one or more entry points and give it an output directory:

bun build ./src/index.ts --outdir ./dist                  # bundle
bun build ./src/index.ts --outdir ./dist --minify          # minified
bun build ./src/index.ts --outdir ./dist --target bun      # for the Bun runtime
bun build ./src/index.ts --outdir ./dist --target node     # for Node
bun build ./src/index.ts --outdir ./dist --target browser --splitting   # web + code splitting
bun build ./src/index.ts --outdir ./dist --sourcemap       # emit source maps

The --target flag changes what globals and module format the output assumes:

TargetOutput assumesUse for
browser (default)DOM globals, no Node builtinsFrontend bundles
bunThe Bun global & Bun stdlibServer apps run by Bun
nodeNode globals, CommonJS/ESMOutput meant for node

The programmatic API

Everything the CLI does, Bun.build does from code — handy for a custom build script:

// build.ts
const result = await Bun.build({
  entrypoints: ["./src/index.ts"],
  outdir: "./dist",
  target: "bun",
  minify: true,
  sourcemap: "external",
  splitting: true,
  define: { "process.env.NODE_ENV": JSON.stringify("production") },
});

if (!result.success) {
  for (const log of result.logs) console.error(log);
  process.exit(1);
}
console.log(`built ${result.outputs.length} files`);

Tree-shaking

Bun removes unused exports automatically from ES modules. Import only what you use and dead code never reaches the bundle:

// utils.ts
export function used() { return 1; }
export function neverImported() { return expensiveThing(); }  // dropped

// index.ts
import { used } from "./utils";    // only `used` ends up in the output
console.log(used());
Tree-shaking works best with ES modules and no side effects at import time. If a module does something just by being imported (registers a global, mutates state), the bundler must keep it. Mark genuinely side-effect-free packages with "sideEffects": false in their package.json so the bundler can prune aggressively.

Standalone executables — bun build --compile

Advanced --compile bundles your app and the Bun runtime into one self-contained binary. The target machine needs no Bun install, no node_modules, nothing — just the file.

# current platform
bun build ./src/cli.ts --compile --outfile myapp
./myapp

# production binary: minified, with a source map for stack traces
bun build ./src/cli.ts --compile --minify --sourcemap --outfile myapp

Cross-compilation

Build for another OS/arch from your dev machine — ship Linux and Windows binaries from a Mac:

bun build ./src/cli.ts --compile --target=bun-linux-x64    --outfile myapp-linux
bun build ./src/cli.ts --compile --target=bun-linux-arm64  --outfile myapp-arm
bun build ./src/cli.ts --compile --target=bun-darwin-arm64 --outfile myapp-mac
bun build ./src/cli.ts --compile --target=bun-windows-x64  --outfile myapp.exe

Embedding assets

Files you import with { type: "file" } get baked into the binary and resolve at runtime from inside it:

import icon from "./icon.png" with { type: "file" };
import schema from "./schema.sql" with { type: "text" };

// `icon` is a path that resolves inside the compiled binary
console.log(await Bun.file(icon).bytes());
console.log(schema);   // the SQL text, embedded

Dockerizing a Bun app

Use the official oven/bun image with a multi-stage build so your runtime image stays small and dependency installs are cached:

# Dockerfile
FROM oven/bun:1.4.2 AS base
WORKDIR /app

# install deps first — this layer is cached unless package.json/lockfile change
FROM base AS deps
COPY package.json bun.lockb ./
RUN bun install --frozen-lockfile --production

# runtime image
FROM base AS release
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ENV NODE_ENV=production
EXPOSE 3000
USER bun                           # run as the non-root bun user
CMD ["bun", "run", "src/index.ts"]
docker build -t my-bun-app .
docker run -p 3000:3000 --env-file .env.production my-bun-app

Even smaller: ship a compiled binary in a scratch-like image

# Build the binary in a bun stage, then copy ONLY the binary into a tiny base
FROM oven/bun:1.4.2 AS build
WORKDIR /app
COPY package.json bun.lockb ./
RUN bun install --frozen-lockfile
COPY . .
RUN bun build ./src/cli.ts --compile --minify --outfile /app/server

FROM gcr.io/distroless/base
COPY --from=build /app/server /server
EXPOSE 3000
CMD ["/server"]

No runtime, no node_modules in the final image — just one binary. The result is often an order of magnitude smaller than a full Node image.

Common mistakes

Common mistake: bundling a server with --target browser (the default). The output then assumes DOM globals and strips Node/Bun builtins, so Bun.serve or node:fs blow up at runtime. Pass --target bun (or node) for server code. Two more: forgetting --sourcemap on a --compile binary (production stack traces become unreadable minified gibberish), and expecting a cross-compiled binary built from a dynamically-constructed import path to embed assets — only statically-analyzable import ... with { type } references get baked in.

Exercises

  • Bundle a server entry with --target bun --minify and run the output from dist/.
  • Add an unused export to a util module, bundle with --minify, and confirm (via the output size or search) it was tree-shaken away.
  • Compile a CLI to a standalone binary with --compile --minify and run it on a machine (or container) that has no Bun installed.
  • Cross-compile the same CLI for bun-linux-x64 and verify the file type with file myapp-linux.

Mini-project: a cross-platform CLI, built, embedded, and shipped three ways

Build a small CLI that embeds a template file, then produce three deliverables from the same source: a bundle, a native binary, and a Docker image — the three ways you'd actually ship a Bun tool.

// src/cli.ts
import banner from "./banner.txt" with { type: "text" };   // embedded at compile time

const [, , cmd = "help"] = Bun.argv;
switch (cmd) {
  case "version": console.log(`myapp ${Bun.version}`); break;
  case "hello":   console.log(banner, "\nhello from a standalone binary!"); break;
  default:        console.log("usage: myapp <version|hello>");
}
# 1) BUNDLE — a single JS file to run with Bun
bun build ./src/cli.ts --outdir dist --target bun --minify

# 2) STANDALONE BINARIES — no runtime needed on the target
bun build ./src/cli.ts --compile --minify --sourcemap \
  --target=bun-linux-x64    --outfile dist/myapp-linux-x64
bun build ./src/cli.ts --compile --minify --sourcemap \
  --target=bun-darwin-arm64 --outfile dist/myapp-macos-arm64
./dist/myapp-macos-arm64 hello      # runs standalone, banner.txt baked in

# 3) DOCKER IMAGE — compiled binary in a distroless base
docker build -t myapp .             # using the "build + distroless" Dockerfile above
docker run --rm myapp /server hello

One source file, three artifacts: the bundle for environments that already have Bun, the native binaries for direct distribution (download one file, run it — the whole appeal of --compile), and the tiny Docker image for orchestrated deploys. The embedded banner.txt travels inside every one of them.
