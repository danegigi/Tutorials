Sometimes the capability you need already exists as a C library, or a hot loop would be far faster in a compiled language. Bun lets you call native code from JavaScript three ways: bun:ffi to call into an existing shared library, Bun.CC to compile and call C inline, and N-API addons for the Node ecosystem. This lesson shows each, with the sharp edges that make native interop risky.

When native code is worth it (and when it isn't)

Advanced FFI shines when you need to reuse a mature C/Rust/Zig library (image codecs, crypto, a database driver), or when a measured hot path is CPU-bound enough that the per-call FFI overhead is dwarfed by the work done. It is the wrong tool for ordinary application logic: you lose memory safety, portability, and the type checker, and a mistake crashes the whole process instead of throwing. Profile first — most code is fast enough in JS, and Bun's own built-ins are already native.

Every FFI call has fixed overhead (marshalling arguments across the JS/native boundary). A function called millions of times with tiny work per call can be slower through FFI than pure JS. FFI pays off for coarse-grained calls that do a lot per invocation, not fine-grained ones.

bun:ffi — call an existing shared library

import { dlopen, FFIType, suffix } from "bun:ffi";

// `suffix` resolves to .so / .dylib / .dll for the current OS
const { symbols: libm } = dlopen(`libm.${suffix}`, {
  sqrt: { args: [FFIType.f64], returns: FFIType.f64 },
  pow:  { args: [FFIType.f64, FFIType.f64], returns: FFIType.f64 },
});

console.log(libm.sqrt(144));     // 12
console.log(libm.pow(2, 10));    // 1024

You declare each symbol's signature with FFIType so Bun knows how to marshal arguments and the return value. Common types: i32, u32, i64, f64, bool, ptr, cstring, void.

Pointers, strings, and buffers

import { CString, ptr, FFIType } from "bun:ffi";

// Pass a JS buffer to C as a pointer:
const buf = Buffer.from("hello\0");       // NUL-terminate C strings yourself
someLib.takesString(ptr(buf));

// Read a C string the library returned (a pointer):
const result = new CString(returnedPtr);  // decodes until the NUL
console.log(String(result));
This is where FFI gets dangerous. You are responsible for memory the way C is: NUL-terminate strings, keep JS buffers alive while C holds a pointer to them (or the GC frees memory C is still using → use-after-free → crash), and free anything the library allocated for you. A wrong signature or a dangling pointer doesn't throw — it segfaults the process. Treat every pointer as unsafe.

Bun.CC — compile C inline

import { cc } from "bun:ffi";

const { symbols } = cc({
  source: `
    int add(int a, int b) { return a + b; }
    double scale(double x) { return x * 1.5; }
  `,
  symbols: {
    add:   { args: ["int", "int"], returns: "int" },
    scale: { args: ["double"], returns: "double" },
  },
});
console.log(symbols.add(2, 3));   // 5

Bun.CC compiles the C with the system toolchain (clang/tinycc) at runtime and gives you callable symbols — handy for a small performance-critical kernel without a separate build step. It needs a C compiler available on the machine.

N-API addons

Bun also implements Node-API (N-API), the stable ABI Node uses for native addons. Many existing npm packages ship prebuilt .node addons; Bun can load a lot of them unchanged:

import addon from "./build/Release/addon.node";
// or a package that bundles a prebuilt addon:
import sharp from "sharp";   // works in Bun via N-API in many versions

N-API is the path when you want the Node ecosystem's native modules rather than writing your own FFI bindings. Coverage is broad but not total — test the specific package.

Choosing among the three

UseWhen
bun:ffi + dlopena prebuilt shared library (C/Rust/Zig) exists and you want to call it directly
Bun.CCa small, self-contained C kernel you want to compile and call inline
N-API addonconsuming an existing npm native module, or targeting Node compatibility

Common mistakes

  • Reaching for FFI before profiling — most JS is fast enough and Bun's built-ins are already native.
  • Fine-grained FFI calls where per-call overhead exceeds the work — benchmark against pure JS.
  • Wrong FFIType signature — misreads memory and segfaults with no stack trace.
  • Letting the GC free a buffer C still points to — keep a reference alive for the pointer's whole lifetime.
  • Forgetting to NUL-terminate C strings or to free library-allocated memory → corruption / leaks.
  • Assuming every N-API addon loads — compatibility is high but not universal; test the exact package/version.

Exercises

  • Use dlopen on the system math library and call sqrt, pow, and floor with correct FFIType signatures.
  • Compile a C add and a C string-length function with Bun.CC, calling both from JS.
  • Pass a JS Buffer into a C function as a pointer and read back a C string with CString.
  • Benchmark a tiny FFI call (e.g. add) in a tight loop against the equivalent JS, and find the crossover where FFI overhead dominates.
  • Load an existing npm native module (e.g. an image or crypto package) and confirm it works under Bun via N-API.

Mini-project

Build a small checksum/hashing utility that computes a CRC32 (or similar) over a file three ways and benchmarks them: pure TypeScript, a Bun.CC-compiled C kernel, and a dlopen call into a system library if one is available. Pass the file bytes as a pointer to the native versions, handle the buffer-lifetime safety correctly, verify all three produce identical checksums, and write up the throughput numbers plus a clear recommendation on when the native path is worth the complexity for this workload.
