Bun has a built-in, Jest-compatible test runner — no Jest, Vitest, or Mocha to install. Name files *.test.ts (or .spec.ts) and run bun test. This lesson covers matchers, mocks and spies, snapshots, lifecycle hooks, coverage, and DOM testing.

Your first test

Beginner Import from bun:test and write test/describe/expect exactly as you would in Jest.

// math.test.ts
import { test, expect, describe } from "bun:test";

test("adds numbers", () => {
  expect(2 + 2).toBe(4);
});

describe("strings", () => {
  test("uppercases", () => {
    expect("bun".toUpperCase()).toBe("BUN");
  });
});
bun test               # run every *.test.ts / *.spec.ts
bun test math          # only files matching "math"
bun test --watch       # re-run on change
bun test -t "uppercases"   # only tests whose name matches the pattern
# bun test v1.4.2
# math.test.ts:
# ✓ adds numbers [0.12ms]
# ✓ strings > uppercases [0.08ms]
#  2 pass  0 fail  2 expect() calls

Matchers

expect(value).toBe(4);                 // === (Object.is)
expect(obj).toEqual({ a: 1 });         // deep equality
expect(obj).toMatchObject({ a: 1 });   // subset match
expect(arr).toContain("x");
expect(fn).toThrow("boom");
expect(str).toMatch(/regex/);
expect(value).toBeDefined();
expect(value).toBeNull();
expect(n).toBeGreaterThan(3);

// async
await expect(Promise.resolve(42)).resolves.toBe(42);
await expect(Promise.reject(new Error("x"))).rejects.toThrow("x");

Lifecycle hooks

import { beforeAll, afterAll, beforeEach, afterEach } from "bun:test";

beforeAll(() => { /* once, before all tests in the file */ });
afterAll(()  => { /* once, after all */ });
beforeEach(() => { /* before each test — great for a fresh fixture */ });
afterEach(()  => { /* after each test — teardown */ });

Use beforeEach to build a clean fixture per test (a fresh in-memory DB, a reset counter) so tests never leak state into each other — the single biggest cause of flaky suites.

Mocks & spies

Intermediate

import { mock, spyOn, test, expect } from "bun:test";

// A mock function with an implementation
const fn = mock((x: number) => x * 2);
fn(21);
expect(fn).toHaveBeenCalledTimes(1);
expect(fn).toHaveBeenCalledWith(21);
expect(fn.mock.results[0].value).toBe(42);

// Spy on an existing method (records calls, keeps real behavior unless you override)
const obj = { greet: (n: string) => `hi ${n}` };
const spy = spyOn(obj, "greet");
obj.greet("Ada");
expect(spy).toHaveBeenCalledWith("Ada");

// Replace a whole module
mock.module("./config", () => ({ default: { env: "test" } }));
Mock the boundary, not your own code. Replace third-party I/O you don't control — a payment gateway, an email sender, the system clock — with mock()/spyOn(). Do not mock your own database or router; test those for real against an in-memory instance (shown below), or you end up testing your mocks instead of your app.

Snapshots

test("renders", () => {
  const output = render({ title: "Bun" });
  expect(output).toMatchSnapshot();      // writes __snapshots__ on first run
});

// Inline snapshot — stored in the test file itself
expect({ ok: true }).toMatchInlineSnapshot(`{ "ok": true }`);
bun test --update-snapshots      # accept new/changed snapshots

Snapshots are great for serializable output (rendered HTML, a config object). Review every snapshot change in code review — a diff you blindly accept defeats the purpose.

Skip, only, todo, parametrized

test.skip("not yet", () => {});
test.only("focus on this one", () => {});   // runs ONLY this in the file
test.todo("write me later");

// Parametrized — one case per row
test.each([[1, 1], [2, 4], [3, 9]])("square(%i) = %i", (n, sq) => {
  expect(n * n).toBe(sq);
});

DOM testing

Bun can run @testing-library / happy-dom for component tests. Register the DOM in a preload file so document exists before tests load:

bun add -d @happy-dom/global-registrator @testing-library/dom
// test/setup.ts  (preloaded via bunfig.toml)
import { GlobalRegistrator } from "@happy-dom/global-registrator";
GlobalRegistrator.register();      // installs document/window globals
// button.test.ts
import { test, expect } from "bun:test";
import { getByRole } from "@testing-library/dom";

test("button renders its label", () => {
  document.body.innerHTML = `<button>Save</button>`;
  const btn = getByRole(document.body, "button");
  expect(btn.textContent).toBe("Save");
});

Common mistakes

Common mistake: leaving test.only in a committed file — it silently skips every other test in that file, so CI goes green while most tests never run. Grep for .only in a pre-commit hook. Two more: sharing mutable state between tests (set up a fresh fixture in beforeEach instead), and blindly running --update-snapshots to make a red test green — that just records the broken output as the new "correct" baseline. Read the snapshot diff first.

Exercises

  • Write a describe block with three test.each rows exercising a slugify function.
  • Use spyOn to assert a function called Date.now exactly once, then restore it.
  • Add --coverage with an 80% threshold and intentionally leave one branch untested to see the failure.
  • Set up happy-dom in a preload and test that a rendered form has an input with name="email".

Mini-project: integration-test an API route against a real in-memory DB

The highest-value test is one that exercises the full request→handler→database path with no mocking of your own code. Use a fresh :memory: SQLite per test for perfect isolation and Hono's app.request() harness (no network, no open port).

// orders.test.ts
import { test, expect, beforeEach, afterEach } from "bun:test";
import { Database } from "bun:sqlite";
import { makeApp } from "../src/app";          // (db) => Hono app

let db: Database;
let app: ReturnType<typeof makeApp>;

beforeEach(() => {
  db = new Database(":memory:");               // fresh DB per test
  db.run("CREATE TABLE orders (id INTEGER PRIMARY KEY, total INTEGER)");
  app = makeApp(db);
});
afterEach(() => db.close());

test("POST /orders creates an order", async () => {
  const res = await app.request("/orders", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ total: 99 }),
  });
  expect(res.status).toBe(201);
  expect(await res.json()).toMatchObject({ id: 1, total: 99 });

  // Assert the side effect actually hit the database
  const row = db.query("SELECT total FROM orders WHERE id = 1").get();
  expect(row).toEqual({ total: 99 });
});

test("GET /orders/:id returns 404 for a missing order", async () => {
  const res = await app.request("/orders/999");
  expect(res.status).toBe(404);
});

test("POST /orders rejects a negative total", async () => {
  const res = await app.request("/orders", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ total: -5 }),
  });
  expect(res.status).toBe(400);
});

Why this is the pattern to copy: app.request(...) hits the real router (routing bugs, status codes, body parsing are all exercised), the per-test :memory: DB gives total isolation with zero teardown cost, and you assert both the response and the side effect. Reserve mock() for the genuine third-party edges your test can't reach — never for your own database.
