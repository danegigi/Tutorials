The last step: shipping a Bun app to production — environment configuration, end-to-end tests with Playwright under Bun, the official oven/bun Docker image, and the hardening (non-root, health checks, graceful shutdown, pinned versions) that keeps a deploy reliable.

Environment configuration

Beginner Production config comes from real environment variables (highest priority), with committed defaults in .env and per-environment overrides. Validate required secrets at startup so a misconfigured deploy fails loudly instead of serving broken.

// src/config.ts
function required(key: string): string {
  const v = Bun.env[key];
  if (!v) throw new Error(`FATAL: missing env ${key}`);
  return v;
}

export const config = {
  env:         Bun.env.NODE_ENV ?? "development",
  port:        Number(Bun.env.PORT ?? 3000),
  databaseUrl: required("DATABASE_URL"),
  accessSecret: required("ACCESS_SECRET"),
};
# run a specific env file in prod
bun --env-file=.env.production run src/index.ts
NODE_ENV=production bun run src/index.ts
Common mistake: baking secrets into the image or committing .env.production. Secrets belong in the orchestrator's secret store (or --env-file at run time), never in the Docker layers or git. Keep .env.local and .env.production gitignored, and pass secrets with docker run --env-file or your platform's secret manager.

Playwright E2E under Bun

Intermediate Playwright drives a real browser against your running app. Pin it and install a browser:

bun add -d @playwright/test@1.48.0
bunx playwright install chromium
// e2e/login.spec.ts
import { test, expect } from "@playwright/test";

test("user can log in", async ({ page }) => {
  await page.goto("http://localhost:3000/login");
  await page.fill('input[name="email"]', "alice@example.com");
  await page.fill('input[name="password"]', "secret");
  await page.click('button[type="submit"]');
  await expect(page.locator("h1")).toHaveText("Welcome, Alice");
});
// playwright.config.ts — start the Bun server automatically for the suite
import { defineConfig } from "@playwright/test";

export default defineConfig({
  testDir: "./e2e",
  webServer: {
    command: "bun run src/index.ts",
    url: "http://localhost:3000",
    reuseExistingServer: !process.env.CI,   // reuse a dev server locally, fresh in CI
  },
});
bunx playwright test            # run the E2E suite
bunx playwright test --ui       # interactive debugging UI
Playwright runs its own test runner, not bun test. Keep unit/integration tests on bun test (fast, in-process) and reserve Playwright for genuine browser-level flows. The webServer block means CI doesn't need a separate "start the server" step — Playwright boots it, waits for the URL, and tears it down.

The official oven/bun Docker image

A production-grade, multi-stage image: deps are cached in their own layer, the runtime image runs as the non-root bun user, and a health check lets the orchestrator restart an unhealthy container.

# Dockerfile
FROM oven/bun:1.4.2 AS deps
WORKDIR /app
COPY package.json bun.lockb ./
RUN bun install --frozen-lockfile --production   # skip devDependencies, fail on drift

FROM oven/bun:1.4.2 AS release
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ENV NODE_ENV=production
EXPOSE 3000
USER bun                                          # drop root
HEALTHCHECK --interval=30s --timeout=3s \
  CMD bun --eval "fetch('http://localhost:3000/health').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"
CMD ["bun", "run", "src/index.ts"]
docker build -t my-bun-app .
docker run -p 3000:3000 --env-file .env.production my-bun-app

Graceful shutdown

A rolling deploy sends SIGTERM. Stop accepting new connections, finish what's in flight, then exit — otherwise you drop live requests on every deploy:

const server = Bun.serve({ port: config.port, fetch: handler });

process.on("SIGTERM", async () => {
  console.log("draining…");
  await server.stop();        // stop accepting, let in-flight requests finish
  process.exit(0);
});

Deploying as a standalone binary

For a CLI or single service, the simplest deploy is often no runtime at all — a compiled binary (see the Bundling lesson):

bun build ./src/index.ts --compile --minify --sourcemap --outfile server
# copy ONE file to the host and run it — no Bun install, no node_modules
./server

Common mistakes

Common mistake: version drift between CI, the image, and local dev — one uses Bun 1.4.2, another "latest", and a bug appears only in production. Pin the exact version in all three places. Two more: running the container as root (set USER bun), and shipping without a SIGTERM handler so every rolling deploy drops in-flight requests. Pair the HEALTHCHECK with graceful shutdown so the orchestrator both detects an unhealthy container and drains a terminating one.

Exercises

  • Add a required()-based config module and confirm the app refuses to start when a secret is missing.
  • Write a Playwright test with a webServer block that boots your Bun server, and run it with bunx playwright test.
  • Build the multi-stage Docker image, run it with --env-file, and confirm docker inspect shows the health status going healthy.
  • Add a SIGTERM handler, start the server, send it SIGTERM mid-request, and verify the in-flight request completes before exit.

Mini-project: a full CI/CD release pipeline

Wire the whole lifecycle into one GitHub Actions workflow: type-check, unit + integration tests, E2E, and — on a version tag — cross-compile standalone binaries and attach them to the release. This is the end-to-end shape of shipping a Bun app.

# .github/workflows/release.yml
name: release
on:
  push:
    tags: ["v*"]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
        with: { bun-version: 1.4.2 }        # pinned — matches Docker + engines
      - run: bun install --frozen-lockfile
      - run: bunx tsc --noEmit               # type-check (Bun doesn't check at runtime)
      - run: bun test --coverage             # unit + integration
      - run: bunx playwright install --with-deps chromium
      - run: bunx playwright test            # E2E against the booted server

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
        with: { bun-version: 1.4.2 }
      - run: bun install --frozen-lockfile
      - name: Cross-compile standalone binaries
        run: |
          bun build ./src/index.ts --compile --minify --sourcemap \
            --target=bun-linux-x64    --outfile dist/myapp-linux-x64
          bun build ./src/index.ts --compile --minify --sourcemap \
            --target=bun-darwin-arm64 --outfile dist/myapp-macos-arm64
      - uses: softprops/action-gh-release@v2
        with:
          files: dist/*

The ordering is the point: the build job needs: test, so binaries are only cut after type-check, unit, integration, and E2E all pass. The pinned bun-version in both jobs matches the Docker tag and engines field, closing the drift gap. Add a parallel docker/build-push-action step if you deploy the image instead of (or alongside) the binaries, and pair the deployed container's HEALTHCHECK with the SIGTERM drain so rolling updates never drop a request. That is a Bun app shipped end to end.
