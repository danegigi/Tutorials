Bun has two built-in database APIs — bun:sqlite, a fast low-level SQLite driver, and Bun.sql, a unified Promise-based client for PostgreSQL, MySQL, and SQLite — plus first-class support for Drizzle ORM on top of them. This lesson covers all three with runnable examples.

bun:sqlite — the low-level SQLite driver

Beginner bun:sqlite is a synchronous, zero-dependency SQLite driver. It's the fastest way to talk to a local database in Bun.

import { Database } from "bun:sqlite";

const db = new Database("app.db");            // or ":memory:" for an ephemeral DB
db.run("CREATE TABLE IF NOT EXISTS users (id INTEGER PRIMARY KEY, name TEXT)");

// Prepared statements — compiled once, reused (fast on the hot path)
const insert = db.query("INSERT INTO users (name) VALUES (?)");
insert.run("Alice");
insert.run("Bob");

// Query shapes
const all   = db.query("SELECT * FROM users").all();              // [{id,name}, ...]
const one   = db.query("SELECT * FROM users WHERE id = ?").get(1); // single row or null
const names = db.query("SELECT name FROM users").values();         // [["Alice"], ...]

// Named parameters
db.query("SELECT * FROM users WHERE name = $name").all({ $name: "Alice" });

Transactions

Wrap a batch in db.transaction — it's all-or-nothing and much faster than individual writes (one fsync, not N):

const insertMany = db.transaction((people: string[]) => {
  for (const name of people) insert.run(name);
});
insertMany(["Carol", "Dave", "Eve"]);   // commits together, or rolls back on throw
Turn on WAL mode for concurrency and foreign-key enforcement at startup: db.run("PRAGMA journal_mode = WAL") and db.run("PRAGMA foreign_keys = ON"). SQLite does not enforce foreign keys unless you enable them per connection — a surprise that silently lets orphan rows through.

Bun.sql — one client for Postgres, MySQL & SQLite

Intermediate The same tagged-template interface targets any of the three databases, chosen from the connection string. Values in ${...} are always parameterized — safe against SQL injection by construction.

import { sql, SQL } from "bun";

// PostgreSQL (default) — reads DATABASE_URL / POSTGRES_URL
const users = await sql`SELECT * FROM users WHERE active = ${true} LIMIT ${10}`;

// MySQL
const mysql = new SQL("mysql://user:pass@localhost:3306/mydb");
await mysql`SELECT * FROM users WHERE id = ${42}`;

// SQLite
const lite = new SQL("sqlite://app.db");
await lite`SELECT * FROM users WHERE id = ${1}`;

Inserting with the sql() helper

const user = { name: "Alice", email: "alice@example.com" };

// object -> (name, email) VALUES (...)
const [created] = await sql`INSERT INTO users ${sql(user)} RETURNING *`;

// bulk insert from an array of objects
await sql`INSERT INTO users ${sql([{ name: "Bob" }, { name: "Carol" }])}`;

// WHERE IN
await sql`SELECT * FROM users WHERE id IN ${sql([1, 2, 3])}`;

Transactions & pooling

await sql.begin(async (tx) => {
  await tx`INSERT INTO users (name) VALUES (${"Alice"})`;
  await tx`UPDATE accounts SET balance = balance - 100 WHERE user_id = 1`;
  // auto-COMMIT on success, auto-ROLLBACK on throw
});

const pool = new SQL({ max: 20, idleTimeout: 30 });
using reserved = await pool.reserve();     // exclusive connection, auto-released
await reserved`SELECT 1`;
await pool.close();
Common mistake: building a query by string concatenation — sql(\`SELECT * FROM users WHERE id = \${id}\`) as a plain string is an injection hole. With Bun.sql's tagged template, sql\`... WHERE id = ${id}\` parameterizes id automatically. Also note: Postgres bigint comes back as a string by default to avoid precision loss — pass { bigint: true } to the client if you need real BigInt values.

Drizzle ORM with Bun SQLite

Advanced When you want end-to-end type safety and real migrations, add Drizzle on top of bun:sqlite. You declare tables in TypeScript, get fully-typed queries, and generate SQL migrations from the same source of truth.

bun add drizzle-orm
bun add -d drizzle-kit @types/bun

Schema — the source of truth

// src/db/schema.ts
import { sqliteTable, int, text } from "drizzle-orm/sqlite-core";
import { relations } from "drizzle-orm";

export const users = sqliteTable("users", {
  id:    int().primaryKey({ autoIncrement: true }),
  name:  text().notNull(),
  email: text().notNull().unique(),
});

export const posts = sqliteTable("posts", {
  id:        int().primaryKey({ autoIncrement: true }),
  authorId:  int("author_id").notNull().references(() => users.id, { onDelete: "cascade" }),
  title:     text().notNull(),
  published: int({ mode: "boolean" }).notNull().default(false),
  createdAt: int("created_at", { mode: "timestamp" }).notNull().$defaultFn(() => new Date()),
});

// relations power the db.query.* nested API
export const usersRelations = relations(users, ({ many }) => ({ posts: many(posts) }));
export const postsRelations = relations(posts, ({ one }) => ({
  author: one(users, { fields: [posts.authorId], references: [users.id] }),
}));

// row types for free
export type User = typeof users.$inferSelect;
export type NewPost = typeof posts.$inferInsert;

Connection

// src/db/index.ts
import { drizzle } from "drizzle-orm/bun-sqlite";
import { Database } from "bun:sqlite";
import * as schema from "./schema";

const sqlite = new Database(Bun.env.DB_FILE_NAME ?? "app.db");
sqlite.exec("PRAGMA journal_mode = WAL;");
sqlite.exec("PRAGMA foreign_keys = ON;");       // Drizzle emits FKs; the driver enforces them
export const db = drizzle({ client: sqlite, schema });

Migrations with drizzle-kit

// drizzle.config.ts
import { defineConfig } from "drizzle-kit";
export default defineConfig({
  out: "./drizzle",
  schema: "./src/db/schema.ts",
  dialect: "sqlite",
  dbCredentials: { url: Bun.env.DB_FILE_NAME ?? "app.db" },
});
bunx drizzle-kit push        # dev: apply schema directly, no files
bunx drizzle-kit generate    # prod: write ./drizzle/0000_xxx.sql + snapshot
bunx drizzle-kit migrate     # apply pending migrations
bunx drizzle-kit studio      # browse data in a local GUI

Querying — the two APIs

import { eq, and, gt, desc } from "drizzle-orm";
import { db } from "./db";
import { users, posts } from "./db/schema";

// SQL-like builder — mirrors SQL one-to-one
const [alice] = await db.insert(users)
  .values({ name: "Alice", email: "alice@example.com" }).returning();

const recent = await db.select().from(posts)
  .where(and(eq(posts.published, true), gt(posts.id, 100)))
  .orderBy(desc(posts.id)).limit(20);

// Relational query API — typed nested objects, no manual join
const withPosts = await db.query.users.findMany({ with: { posts: true } });
const post = await db.query.posts.findFirst({
  where: eq(posts.id, 10),
  with: { author: { columns: { name: true } } },
});

Which API when

Reach forWhen
bun:sqliteLocal SQLite, raw control, hot-path prepared statements, zero deps
Bun.sqlOne API across Postgres/MySQL/SQLite, ad-hoc parameterized queries
DrizzleA growing schema that wants type safety and reviewable migrations

Common mistakes

Common mistake: re-preparing a statement inside a loop with bun:sqlite. Call db.query(sql) once to compile the statement, then .run()/.get()/.all() it many times — recompiling each iteration throws away the whole point of prepared statements. With Drizzle, the recurring trap is editing an already-applied migration: never do that; add a new migration instead, and commit the ./drizzle folder as your reviewable schema history. And always index foreign keys you query through — an unindexed FK join is a full table scan.

Exercises

  • With bun:sqlite, create a table, insert 1,000 rows inside a single db.transaction, and time it against 1,000 individual inserts.
  • Use Bun.sql against a sqlite:// URL to run a parameterized WHERE IN query with the sql([...]) helper.
  • Define a Drizzle schema with a one-to-many relation, run bunx drizzle-kit push, and fetch a parent with its children via db.query.*.
  • Add a unique index to the Drizzle schema, regenerate the migration, and read the emitted SQL.

Mini-project: a typed orders repository with reporting

Build the data layer a web route would call: Drizzle for the typed hot-path app queries and Bun.sql for an ad-hoc reporting query — the common split of "typed everyday access" plus "raw analytics."

// orders.repo.ts
import { db } from "./db";
import { posts } from "./db/schema";
import { sql as rawSql } from "bun";
import { eq, desc } from "drizzle-orm";

type NewPost = typeof posts.$inferInsert;

export const OrdersRepo = {
  // Typed CRUD via Drizzle — the compiler guarantees the shape
  create: (data: NewPost) => db.insert(posts).values(data).returning().get(),

  byId: (id: number) =>
    db.query.posts.findFirst({ where: eq(posts.id, id), with: { author: true } }),

  feed: (limit = 20) =>
    db.select().from(posts).where(eq(posts.published, true))
      .orderBy(desc(posts.id)).limit(limit),

  publish: (id: number) =>
    db.update(posts).set({ published: true }).where(eq(posts.id, id)).returning().get(),

  // Ad-hoc reporting via Bun.sql (raw, parameterized) against Postgres
  dailyPublishedCount: () => rawSql`
    SELECT date_trunc('day', created_at) AS day, count(*) AS n
    FROM posts WHERE published = ${true}
    GROUP BY 1 ORDER BY 1 DESC LIMIT 30
  `,
};
// usage
import { OrdersRepo } from "./orders.repo";
const post = OrdersRepo.create({ authorId: 1, title: "Hello", published: false });
OrdersRepo.publish(post!.id);
const feed = OrdersRepo.feed();

Keeping all DB access in one module (and leaning on Drizzle's inferred types) means a column rename is a single edit the compiler propagates everywhere, while the one raw reporting query stays parameterized and injection-safe. That division — typed everyday queries, raw analytics behind the same repository — is how real services keep both ergonomics and flexibility.
