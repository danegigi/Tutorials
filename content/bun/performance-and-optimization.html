Bun is fast by default — JavaScriptCore for execution, native Zig-backed APIs for I/O — but "fast language" is not "fast program." This lesson is about measuring before you optimize: writing honest micro-benchmarks that the optimizer can't cheat, understanding why Bun's hot paths are fast so you stay on them, cutting startup time, avoiding the allocations and shims that dominate real workloads, and profiling production with CPU profiles instead of guessing.

Where Bun is fast, and why

Beginner Two things drive Bun's speed, and knowing them tells you which code paths to prefer.

SourceWhat it means for your code
JavaScriptCore (Safari's engine)Fast startup and low memory vs V8; your JS/TS runs well without a warm-up for short-lived processes (CLIs, serverless).
Native APIs (Bun.file, Bun.serve, bun:sqlite, Bun.password)I/O and crypto are implemented in native code, not JS — using the Bun-native API is faster than an npm package doing the same thing in userland JS.
Fast TS transpileNo separate tsc/ts-node step — files run directly, so dev iteration is cheap.

The practical rule: on a hot path, prefer the Bun-native primitive over an npm shim doing the same job in JavaScript. Bun.file(path).text() beats a userland fs wrapper; bun:sqlite beats a pure-JS SQLite; Bun.password beats a JS bcrypt.

Benchmarking with bun test

Beginner The cheapest honest measurement is wall-clock time around real work, repeated enough to dwarf noise. Bun.nanoseconds() is a high-resolution monotonic clock for this.

// bench-simple.ts
function measure(label: string, iters: number, fn: () => void) {
  fn();                                        // warm up (let JIT compile it)
  const start = Bun.nanoseconds();
  for (let i = 0; i < iters; i++) fn();
  const ms = (Bun.nanoseconds() - start) / 1e6;
  console.log(`${label}: ${ms.toFixed(2)}ms total, ${(ms / iters * 1000).toFixed(3)}µs/op`);
}

measure("JSON.parse", 100_000, () => JSON.parse('{"a":1,"b":[2,3]}'));
# -> JSON.parse: 48.21ms total, 0.482µs/op

mitata-style micro-benchmarks

Intermediate A real benchmark harness (mitata is the one the Bun ecosystem reaches for: bun add -d mitata) handles warm-up, runs enough samples for a stable estimate, and reports a distribution rather than one number — so you compare approaches honestly.

// bench.ts  —  bun run bench.ts
import { run, bench, group } from "mitata";

const data = Array.from({ length: 1000 }, (_, i) => i);

group("sum 1000 numbers", () => {
  bench("for loop", () => {
    let s = 0; for (let i = 0; i < data.length; i++) s += data[i]; return s;
  });
  bench("reduce", () => data.reduce((a, b) => a + b, 0));
  bench("for...of", () => { let s = 0; for (const n of data) s += n; return s; });
});

await run();
# benchmark        avg          min … max        p75
# for loop     1.02 µs     0.98 µs … 1.4 µs    1.03 µs
# reduce       2.81 µs     2.70 µs … 3.9 µs    2.85 µs
# for...of     1.44 µs     1.40 µs … 2.1 µs    1.46 µs
Read the distribution, not just the average: a low average with a long tail (big max, high p99) means occasional stalls — often GC pauses from allocation in the hot loop. mitata's warm-up also matters: the first call of a JIT-compiled function is slow because it hasn't been optimized yet, so an un-warmed measurement overstates cost.

Benchmarking honestly — don't measure the optimizer away

The classic micro-benchmark lie: JavaScriptCore sees that your result is never used and deletes the whole computation, so you "measure" an empty loop and conclude your code is infinitely fast.

// WRONG — the result is dead, JSC may eliminate the call entirely
bench("hash", () => { Bun.hash("some input"); });     // return discarded

// RIGHT — consume the result so it can't be optimized out
let sink = 0n;
bench("hash", () => { sink ^= Bun.hash("some input"); });
// (print `sink` after the run so even the accumulation isn't dead)

Also benchmark realistic inputs. Hashing the literal "some input" every iteration lets the engine cache or specialize in ways a real variable workload won't. Feed varied, representative data.

Reducing startup time

Intermediate For CLIs and serverless, startup time is the latency. Two levers: import less eagerly, and compile ahead of time.

# lazy-import a heavy module only on the code path that needs it
async function exportPdf() {
  const { makePdf } = await import("./pdf");   // not loaded unless export runs
  return makePdf();
}
# compile to a standalone binary — no module resolution at launch
bun build --compile ./cli.ts --outfile mycli
./mycli            # starts faster than `bun run cli.ts`: deps are baked in

Measure startup directly rather than guessing which import is expensive:

time bun run cli.ts --version
# then bisect: comment imports, or `bun --inspect` the startup and read the flame graph
Top-level side effects run at import time — a module that opens a DB connection or reads a large file at the top level pays that cost on every startup even when the command doesn't need it. Keep top-level code to declarations; do work inside functions called on demand.

Hot-path tips

Advanced Once a benchmark points at a real hot path, these are the levers that actually move it:

  • Avoid unnecessary allocations in loops. Each {...}, [...arr], .map, or string concatenation in a tight loop creates garbage the collector must later reclaim — the GC pause is the long tail in your benchmark. Mutate in place or preallocate.
  • Reuse buffers. Allocate one Uint8Array/Buffer and write into it repeatedly instead of allocating per iteration; for streaming I/O, reuse a fixed-size read buffer.
  • Prefer Bun-native APIs over npm shims. Bun.file, bun:sqlite, Bun.CryptoHasher, Bun.serve are native; a JS package doing the same thing runs in the interpreter/JIT and allocates more.
  • Keep object shapes stable. JSC optimizes objects whose set of keys doesn't change; adding/deleting properties after creation deoptimizes the inline caches. Build objects with all their keys at once.
  • Batch I/O. One query returning 100 rows beats 100 queries; one Bun.write of a joined string beats 100 appends.
// allocation-heavy: new array + object per row, every call
const slow = (rows: Row[]) => rows.map((r) => ({ id: r.id, label: `#${r.id}` }));

// hot-path: write into a reused buffer, no per-row object churn
const out: string[] = [];
function fast(rows: Row[]) {
  out.length = 0;                               // reuse the array
  for (let i = 0; i < rows.length; i++) out.push(rows[i].id);
  return out;
}

Production profiling

Advanced When a real service is slow, profile it rather than theorize. bun --inspect opens a debugger/profiler endpoint; capture a CPU profile under load and read the flame graph to find where wall-clock time actually goes.

# run with the inspector enabled
bun --inspect server.ts
# -> prints a devtools:// URL; open it, go to the Profiler tab, record under load

# or a one-off inspect that waits for a debugger to attach before running
bun --inspect-wait server.ts

In the CPU profile, the widest frames are where time is spent. Look for: a function far wider than you expected (an accidental O(n²), a sync call on the request path), a tall GC band (allocation pressure — revisit the hot-path tips), or time in a userland npm package where a Bun-native API exists. Fix the widest frame first; re-profile; repeat. The flame graph turns "the server feels slow" into "68% of request time is in JSON serialization of a field we don't even use."

Common mistakes

Common mistakes: (1) Premature optimization — rewriting readable code into a clever micro-optimized version before any measurement shows it matters. Most code is not hot; optimizing cold code adds bugs and complexity for zero user-visible gain. Profile first, optimize the widest frame, stop when it's fast enough. (2) Benchmarking the optimizer away — discarding the result so JSC deletes the computation, or using a constant input it can specialize, then reporting an impossibly fast number. Consume the result (XOR into a sink, print it) and feed varied realistic data. (3) Measuring without warm-up — the first call of a JIT function is slow; an un-warmed benchmark overstates cost. (4) Trusting a single number — one run hides variance; use a harness that reports a distribution and watch the tail (p99), where GC pauses hide. (5) Optimizing by vibes — assuming you know the hot path instead of profiling it; the slow part is almost never where you first guess.

Exercises

  • Write a measure harness with Bun.nanoseconds() and compare JSON.parse vs a hand-rolled parse on 100k iterations; add a warm-up call and watch the number change.
  • Install mitata and benchmark for vs reduce vs for...of summing an array; identify which has the worst tail and reason about why.
  • Take a benchmark whose result is discarded, confirm the suspiciously-fast number, then XOR the result into a sink and re-measure — note the honest number.
  • Compare startup time of bun run cli.ts vs a bun build --compile binary with time; then move a heavy import behind a dynamic import() and measure again.
  • Run a Bun.serve app under bun --inspect, hit it with a load tool, record a CPU profile, and name the single widest frame.

Mini-project: find and fix one real bottleneck, with evidence

Take a slow endpoint, profile it, fix the widest frame, and prove the fix with a before/after benchmark. The point is the discipline — measure, change one thing, measure again — not any specific trick.

// slow.ts — an endpoint that re-parses config and allocates per request
import { Hono } from "hono";
const app = new Hono();

app.get("/report", (c) => {
  const config = JSON.parse(require("fs").readFileSync("config.json", "utf8")); // re-read EVERY request
  const rows = loadRows();                                   // 10k rows
  const out = rows
    .map((r) => ({ ...r, label: `#${r.id}` }))                // allocate a new object per row
    .filter((r) => r.active)
    .map((r) => JSON.stringify(r));                           // stringify twice (here + c.json)
  return c.json({ config, count: out.length });
});
export default app;
// fixed.ts — config read once at startup; single pass; no double stringify
import { Hono } from "hono";
const config = JSON.parse(await Bun.file("config.json").text());   // ONCE, at boot

const app = new Hono();
app.get("/report", (c) => {
  const rows = loadRows();
  let count = 0;
  for (let i = 0; i < rows.length; i++) if (rows[i].active) count++;  // one pass, no allocation
  return c.json({ config, count });                                   // c.json serializes once
});
export default app;
# before/after, same harness
import { bench, run } from "mitata";
bench("slow /report",  async () => { await slowApp.request("/report"); });
bench("fixed /report", async () => { await fixedApp.request("/report"); });
await run();
# slow /report    1.82 ms
# fixed /report   0.11 ms   -> ~16x, from: config read once, single pass, no double serialize

Every change was justified by a measurement: the profile showed readFileSync and the double map/stringify as the widest frames, moving the config read to startup and collapsing to a single pass removed them, and the benchmark proves the result instead of asserting it. That loop — profile, fix the widest frame, re-benchmark — is the whole method.
