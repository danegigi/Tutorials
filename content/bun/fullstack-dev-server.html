Bun can serve a complete full-stack app from one process with no separate bundler, dev-server, or build config: you point Bun.serve at an HTML file, and Bun automatically bundles the <script> and <link> it references — TypeScript, JSX, CSS and all — with hot reloading in dev and an optimized build for production. This lesson shows the HTML-import model, mixing API routes with the frontend, and shipping it.

The idea: HTML as the entry point

Intermediate In most stacks the frontend build (Vite/webpack) and the backend server are two separate tools you wire together. Bun collapses that: an .html file is a route, and Bun treats the assets it references as a bundle graph it builds for you. One command runs both the API and the frontend.

// index.html
<!doctype html>
<html>
  <head><link rel="stylesheet" href="./styles.css"></head>
  <body>
    <div id="root"></div>
    <script type="module" src="./app.tsx"></script>  <!-- TSX, bundled automatically -->
  </body>
</html>

Serving it

// server.ts
import index from "./index.html";   // importing HTML gives you a routable asset

const server = Bun.serve({
  routes: {
    "/": index,                      // serves the HTML + its bundled assets
    "/api/hello": () => Response.json({ msg: "hi from the API" }),
    "/api/users/:id": (req) => Response.json({ id: req.params.id }),
  },
  development: true,                  // hot reload + detailed errors
});
console.log(`→ http://localhost:${server.port}`);
bun run server.ts
# Bun bundles app.tsx + styles.css on the fly; editing either hot-reloads the page.
No vite.config, no webpack.config, no concurrently-run dev servers. The import index from "./index.html" is the whole wiring — Bun resolves and bundles everything the HTML references, and serves your API from the same routes table.

The frontend code is just modules

// app.tsx — TypeScript + JSX, no separate build step
import { createRoot } from "react-dom/client";

function App() {
  const [msg, setMsg] = (globalThis as any).React?.useState?.("…") ?? ["", () => {}];
  // fetch the SAME server's API:
  fetch("/api/hello").then(r => r.json()).then(d => console.log(d.msg));
  return <h1>Hello from a bundled TSX app</h1>;
}
createRoot(document.getElementById("root")!).render(<App />);

Because the frontend and API share an origin and a process, there's no CORS to configure and no proxy — the browser calls /api/... on the same server that served the page.

Hot reloading in development

With development: true, Bun watches the asset graph: editing app.tsx or styles.css pushes an update to the browser without a full reload, and server errors render with a readable overlay instead of a blank page. Flip it off (or set NODE_ENV=production) and the same code serves optimized, cached bundles.

Multiple pages & assets

import home from "./index.html";
import about from "./about.html";

Bun.serve({
  routes: {
    "/": home,
    "/about": about,
    "/api/*": apiHandler,            // wildcard for an API surface
  },
});
// Each HTML entry gets its own bundle; shared imports are de-duplicated.

Building for production

# Produce static, hashed, minified assets for deploy:
bun build ./index.html --outdir=dist --minify
# → dist/index.html referencing dist/app-[hash].js, dist/styles-[hash].css
# Serve dist/ from any static host or CDN, and run the API separately,
# OR keep the single-process model and serve with development:false.

You choose the deployment shape: single process (API + frontend from Bun.serve) for simplicity, or split (static dist/ on a CDN + the API as its own service) for scale. The same source supports both.

The trade-off: Vite's plugin ecosystem is larger and some framework meta-frameworks assume it. Bun's full-stack server is excellent for apps you control end to end; reach for the established toolchain when you need a specific plugin or a framework that's tightly coupled to it.

Common mistakes

  • Leaving development: true in production — you ship unminified bundles and error overlays. Gate it on NODE_ENV.
  • Adding a bundler config "just in case" — Bun bundles the HTML's asset graph itself; extra tooling fights it.
  • Hardcoding an API origin in the frontend when it's same-origin — just call /api/....
  • Expecting every Vite plugin to have an equivalent — check feature coverage before porting a plugin-heavy app.
  • Not hashing assets for production — use bun build --outdir so clients cache correctly.
  • Mixing route styles — prefer the routes object (with :params and wildcards) over hand-rolled fetch switch statements.
