Bun.serve is enough for simple routing, but real apps want middleware, validation, grouped routes, and typed handlers. Two frameworks lead on Bun: Hono — tiny, portable across runtimes, with a Zod validator — and Elysia — Bun-first, with an end-to-end type system driven by its own t schema. This lesson builds the same small CRUD API in each, shows request parsing, validation, middleware, and route groups, and ends with a straight answer to which one to pick.

Hono — routing and the context object

Beginner Hono is a third-party router that runs on Bun.serve (bun add hono@4.6.3). Every handler receives a context c: c.req for the request, c.json/c.text to respond, c.req.param/c.req.query for inputs.

// server.ts
import { Hono } from "hono";

const app = new Hono();

app.get("/", (c) => c.text("Hello from Hono"));
app.get("/users/:id", (c) => c.json({ id: c.req.param("id") }));     // path param
app.get("/search", (c) => c.json({ q: c.req.query("q") }));          // query string
app.post("/echo", async (c) => c.json(await c.req.json()));          // JSON body

export default app;      // Bun auto-serves a default export with a fetch handler
bun --hot server.ts
# curl localhost:3000/users/42        -> {"id":"42"}
# curl 'localhost:3000/search?q=bun'  -> {"q":"bun"}

Hono — middleware and route groups

Intermediate Middleware is any handler that calls next(); register it with app.use. A route group is a sub-Hono mounted under a prefix with app.route, so related routes (and their own middleware) stay together.

import { Hono } from "hono";
import { logger } from "hono/logger";

const app = new Hono();
app.use("*", logger());                       // built-in request logger

// a bearer-token guard as middleware
async function requireAuth(c: any, next: any) {
  const token = (c.req.header("Authorization") ?? "").replace(/^Bearer /, "");
  if (token !== Bun.env.API_TOKEN) return c.json({ error: "unauthorized" }, 401);
  await next();
}

// a route group mounted at /admin, protected as a unit
const admin = new Hono();
admin.use("*", requireAuth);
admin.get("/stats", (c) => c.json({ users: 1234 }));

app.route("/admin", admin);                   // GET /admin/stats requires the token

app.onError((err, c) => { console.error(err); return c.json({ error: "internal" }, 500); });
export default app;

Hono — validation with @hono/zod-validator

Never trust a request body. @hono/zod-validator (bun add @hono/zod-validator zod) runs a Zod schema over a target (json, query, param, form) and hands the handler the parsed, typed value via c.req.valid() — rejecting bad input with a 400 before your code runs.

import { Hono } from "hono";
import { zValidator } from "@hono/zod-validator";
import { z } from "zod";

const app = new Hono();

const NewTask = z.object({
  title: z.string().min(1).max(200),
  done: z.boolean().default(false),
});

app.post("/tasks", zValidator("json", NewTask), (c) => {
  const task = c.req.valid("json");          // typed { title: string; done: boolean }
  return c.json({ id: crypto.randomUUID(), ...task }, 201);
});

// validate query params too
const ListQuery = z.object({ page: z.coerce.number().int().positive().default(1) });
app.get("/tasks", zValidator("query", ListQuery), (c) => {
  const { page } = c.req.valid("query");     // page is a number, defaulted to 1
  return c.json({ page });
});

export default app;
# curl -X POST localhost:3000/tasks -d '{"title":""}' -H 'content-type: application/json'
# -> 400 {"success":false,"error":{..."title": "String must contain at least 1 character"...}}

Hono — a full CRUD API

import { Hono } from "hono";
import { zValidator } from "@hono/zod-validator";
import { z } from "zod";

type Task = { id: string; title: string; done: boolean };
const tasks = new Map<string, Task>();

const app = new Hono();
const TaskInput = z.object({ title: z.string().min(1), done: z.boolean().default(false) });

app.get("/tasks", (c) => c.json([...tasks.values()]));

app.get("/tasks/:id", (c) => {
  const t = tasks.get(c.req.param("id"));
  return t ? c.json(t) : c.json({ error: "not found" }, 404);
});

app.post("/tasks", zValidator("json", TaskInput), (c) => {
  const t: Task = { id: crypto.randomUUID(), ...c.req.valid("json") };
  tasks.set(t.id, t);
  return c.json(t, 201);
});

app.put("/tasks/:id", zValidator("json", TaskInput), (c) => {
  const id = c.req.param("id");
  if (!tasks.has(id)) return c.json({ error: "not found" }, 404);
  const t: Task = { id, ...c.req.valid("json") };
  tasks.set(id, t);
  return c.json(t);
});

app.delete("/tasks/:id", (c) =>
  tasks.delete(c.req.param("id")) ? c.body(null, 204) : c.json({ error: "not found" }, 404));

export default app;

Elysia — routing and typed handlers

Intermediate Elysia is Bun-first (bun add elysia). Its distinguishing feature is end-to-end type safety driven by schemas: you describe body/params/query with the built-in t schema builder, and Elysia both validates at runtime and infers the handler's types from the same declaration — one source of truth, no separate validator wiring.

// server.ts
import { Elysia, t } from "elysia";

const app = new Elysia()
  .get("/", () => "Hello from Elysia")
  .get("/users/:id", ({ params: { id } }) => ({ id }), {
    params: t.Object({ id: t.String() }),              // validated + typed
  })
  .post("/echo", ({ body }) => body, {
    body: t.Object({ message: t.String() }),           // body is typed { message: string }
  })
  .listen(3000);

console.log(`Elysia on ${app.server?.hostname}:${app.server?.port}`);
bun --hot server.ts
# curl localhost:3000/users/42       -> {"id":"42"}
# curl -X POST localhost:3000/echo -d '{"message":"hi"}' -H 'content-type: application/json'
#   -> {"message":"hi"}   (a bad body is rejected 400 automatically)

Elysia — the t schema, plugins, and groups

The t builder (a TypeBox wrapper) describes body, query, params, headers, and response. A plugin is an Elysia instance you compose in with .use — the equivalent of shared middleware. .group mounts routes under a prefix.

import { Elysia, t } from "elysia";

// a plugin: shared state + a derived auth value, composed into any app
const auth = new Elysia()
  .derive(({ headers }) => ({
    user: headers.authorization === `Bearer ${Bun.env.API_TOKEN}` ? "admin" : null,
  }))
  .onBeforeHandle(({ user, set }) => {
    if (!user) { set.status = 401; return { error: "unauthorized" }; }
  });

const app = new Elysia()
  .group("/admin", (g) =>
    g.use(auth)                                          // guard the whole group
     .get("/stats", () => ({ users: 1234 }))
  )
  .get("/search", ({ query }) => ({ q: query.q }), {
    query: t.Object({ q: t.String() }),
  })
  .onError(({ error, set }) => { set.status = 500; return { error: "internal" }; })
  .listen(3000);
Because the t schema drives both validation and inference, Elysia also powers Eden — a typed client that imports your server's type and gives the frontend compile-time-checked calls to each route, like tRPC but derived from the same schemas you already wrote for validation.

Elysia — a full CRUD API

import { Elysia, t } from "elysia";

type Task = { id: string; title: string; done: boolean };
const tasks = new Map<string, Task>();

const TaskBody = t.Object({ title: t.String({ minLength: 1 }), done: t.Boolean({ default: false }) });

const app = new Elysia()
  .get("/tasks", () => [...tasks.values()])

  .get("/tasks/:id", ({ params: { id }, set }) => {
    const t = tasks.get(id);
    if (!t) { set.status = 404; return { error: "not found" }; }
    return t;
  }, { params: t.Object({ id: t.String() }) })

  .post("/tasks", ({ body, set }) => {
    const t: Task = { id: crypto.randomUUID(), ...body };
    tasks.set(t.id, t);
    set.status = 201;
    return t;
  }, { body: TaskBody })

  .put("/tasks/:id", ({ params: { id }, body, set }) => {
    if (!tasks.has(id)) { set.status = 404; return { error: "not found" }; }
    const t: Task = { id, ...body };
    tasks.set(id, t);
    return t;
  }, { params: t.Object({ id: t.String() }), body: TaskBody })

  .delete("/tasks/:id", ({ params: { id }, set }) => {
    if (!tasks.delete(id)) { set.status = 404; return { error: "not found" }; }
    set.status = 204;
  }, { params: t.Object({ id: t.String() }) })

  .listen(3000);

Which one to pick

ConsiderationHonoElysia
Runtime targetBun, Node, Deno, Cloudflare Workers, LambdaBun-first (Node via adapter)
Validationopt-in: @hono/zod-validator + Zodbuilt-in: the t schema, always on
Typed clientHono RPC (hc)Eden (tight, schema-derived)
Philosophyminimal, portable, bring-your-ownbatteries-included, Bun-optimized

Choose Hono when you want portability (the same app on Bun locally and a Cloudflare Worker or Lambda in prod), a minimal core, or you already use Zod and want one validation story across front and back. Choose Elysia when you're all-in on Bun and want the tightest schema-to-types-to-client experience with the least wiring — the t schema doing validation and inference from one declaration is its headline feature.

Common mistakes

Common mistakes: (1) Skipping validation and trusting await c.req.json() / body — an untyped cast (as NewTask) is a lie the runtime doesn't enforce; use zValidator (Hono) or a t schema (Elysia) so bad input is rejected before your handler. (2) In Hono, reading the body twice — c.req.json() consumes the stream, so a second read throws; read once. (3) Pinning neither framework version — a web framework is load-bearing; pin it (hono@4.6.3) so a minor bump doesn't shift behavior under you. (4) In Elysia, re-declaring the same schema inline on every route instead of defining it once (const TaskBody = t.Object(...)) and reusing it — drift between create and update schemas is a classic bug. (5) Mounting auth middleware too broadly or too narrowly — group protected routes so the guard applies to exactly the set you intend.

Exercises

  • Add a requireAuth middleware to a Hono route group under /admin and confirm a missing Authorization header gets 401 while a valid token passes.
  • Build the same CRUD in Elysia using the t schema for body and params; confirm a non-string title is rejected automatically.
  • Write an Elysia plugin that derives a user from the Authorization header and rejects unauthenticated requests in onBeforeHandle; compose it into a group.

Mini-project: the same notes API in both frameworks, then choose

Implement a notes API — list, create (validated), delete — once in Hono and once in Elysia, run both, and write down which you'd ship and why. Building the same thing twice makes the trade-off concrete instead of abstract.

// hono-notes.ts
import { Hono } from "hono";
import { zValidator } from "@hono/zod-validator";
import { z } from "zod";

const notes = new Map<string, { id: string; text: string }>();
const app = new Hono();

app.get("/notes", (c) => c.json([...notes.values()]));
app.post("/notes", zValidator("json", z.object({ text: z.string().min(1) })), (c) => {
  const n = { id: crypto.randomUUID(), text: c.req.valid("json").text };
  notes.set(n.id, n);
  return c.json(n, 201);
});
app.delete("/notes/:id", (c) =>
  notes.delete(c.req.param("id")) ? c.body(null, 204) : c.json({ error: "not found" }, 404));

export default app;
// elysia-notes.ts
import { Elysia, t } from "elysia";

const notes = new Map<string, { id: string; text: string }>();

new Elysia()
  .get("/notes", () => [...notes.values()])
  .post("/notes", ({ body, set }) => {
    const n = { id: crypto.randomUUID(), text: body.text };
    notes.set(n.id, n);
    set.status = 201;
    return n;
  }, { body: t.Object({ text: t.String({ minLength: 1 }) }) })
  .delete("/notes/:id", ({ params: { id }, set }) => {
    if (!notes.delete(id)) { set.status = 404; return { error: "not found" }; }
    set.status = 204;
  }, { params: t.Object({ id: t.String() }) })
  .listen(3001);
bun --hot hono-notes.ts      # :3000
bun --hot elysia-notes.ts    # :3001
# POST an empty {"text":""} to each — both reject with 400 BEFORE the handler runs,
# Hono via the explicit zValidator, Elysia via the inline t schema.

Compare: in Hono the validator is an explicit piece you add and the app ports unchanged to a Cloudflare Worker; in Elysia the schema is the route definition and the inferred types flow into an Eden client for free. If you deploy only to Bun and want the least wiring, Elysia; if you value portability and an existing Zod investment, Hono. Both are correct — the choice is about where you deploy and how much you value one source of truth over cross-runtime reach.
