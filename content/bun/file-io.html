Bun's file API is built on the Web Blob interface: Bun.file(path) returns a lazy handle and Bun.write() writes almost anything to almost anywhere. This lesson covers reading, writing, incremental writers, streaming, the transparent s3:// protocol, the Bun.$ shell, and spawning subprocesses with Bun.spawn.

Reading files

Beginner Bun.file(path) is lazy — nothing is read from disk until you call a method on it. The handle is a Blob, so it has the standard reader methods plus metadata.

const file = Bun.file("./data.json");   // no read yet

await file.text();          // string
await file.json();          // parsed JSON
await file.bytes();         // Uint8Array
await file.arrayBuffer();   // ArrayBuffer
file.stream();              // ReadableStream (for large files)

// metadata without a full read
file.size;                  // bytes
file.type;                  // MIME type inferred from the extension
await file.exists();        // boolean

Partial reads

const head = Bun.file("big.log").slice(0, 1024);   // first 1 KB only
console.log(await head.text());

Writing files

Bun.write(dest, data) is the universal writer. dest is a path, a BunFile, or a file descriptor; data is a string, bytes, a Blob, a Response, or another BunFile.

await Bun.write("out.txt", "Hello!");                       // string
await Bun.write("copy.json", Bun.file("data.json"));         // copy a file
await Bun.write("page.html", await fetch("https://example.com"));  // save a response
await Bun.write("bytes.bin", new Uint8Array([1, 2, 3]));     // raw bytes
Bun.write consumes a Blob/File/Response as a stream — it never materializes the whole payload in a JS string first. For a large upload or download, pass the File/Response straight in; do not call await res.arrayBuffer() and then write the buffer, which pulls everything into memory.

Incremental writing

For streaming output or many small appends, use a writer so you aren't opening the file repeatedly:

const writer = Bun.file("log.txt").writer();
writer.write("line 1\n");
writer.write("line 2\n");
await writer.flush();     // push buffered data to disk
writer.write("line 3\n");
await writer.end();       // flush and close

Standard streams

const input = await Bun.stdin.text();          // read all of stdin
await Bun.write(Bun.stdout, "to stdout\n");
await Bun.write(Bun.stderr, "to stderr\n");

The s3:// protocol

Intermediate The same Bun.file and fetch APIs transparently target S3-compatible storage, so code written against local files works unchanged against the cloud:

// Read an S3 object with the exact same API as a local file
const remote = Bun.file("s3://my-bucket/report.json");
const data = await remote.json();

// fetch works too
const res = await fetch("s3://my-bucket/report.json");

// Write back to S3
await Bun.write("s3://my-bucket/out.json", JSON.stringify({ ok: true }));

Credentials come from S3_* / AWS_* environment variables, or an explicit Bun.S3Client (see the Building APIs lesson for presigned URLs and multipart uploads).

Bun.$ — shell scripting

Bun.$ is a cross-platform shell as a tagged template. Same behavior on macOS, Linux, and Windows (no bash needed), and interpolated values are escaped automatically — safe against injection.

import { $ } from "bun";

await $`echo Hello from the shell`;                 // run, inherit stdout
const branch = (await $`git rev-parse --abbrev-ref HEAD`.text()).trim();  // capture
const pkg = await $`cat package.json`.json();        // parse JSON output

const dir = "my files";
await $`ls ${dir}`;                                  // runs: ls 'my files'  (escaped)

await $`cat access.log | grep ERROR > errors.txt`;   // pipes & redirection

const { exitCode, stderr } = await $`false`.nothrow();   // don't throw on non-zero
Common mistake: building a shell command by string concatenation — $(\`rm \${userInput}\`) as a plain string invites injection. With Bun.$, interpolated values are escaped automatically, so $\`ls ${dir}\` is safe even when dir contains spaces or shell metacharacters. Never bypass that by passing a pre-built string; always let ${...} interpolation do the escaping.

Bun.spawn — subprocesses

// Async spawn, capture stdout
const proc = Bun.spawn(["echo", "hello"], { stdout: "pipe" });
const out = await new Response(proc.stdout).text();
await proc.exited;                       // wait for exit
console.log(proc.exitCode, out);

// Synchronous spawn
const { stdout, exitCode } = Bun.spawnSync(["git", "status", "--short"]);
console.log(exitCode, stdout.toString());

// Feed stdin
const cat = Bun.spawn(["cat"], { stdin: "pipe", stdout: "pipe" });
cat.stdin.write("piped input\n");
cat.stdin.end();
console.log(await new Response(cat.stdout).text());

When to use which: Bun.$ for shell-style pipelines and quick commands; Bun.spawn when you need fine control over stdio, environment, or a long-running child process you stream from.

Common mistakes

Common mistake: loading a large file entirely into memory. await Bun.file("huge.csv").text() on a multi-GB file will exhaust RAM — use .stream() (or .slice() for a range) and process chunks instead. A second trap: assuming Bun.file(path) read the file — it didn't; it's lazy, and errors (missing file, permission denied) surface only when you call .text()/.json()/etc., so wrap those in try/catch, not the Bun.file() call. A third: passing an untrusted user string directly as a file path — that's an arbitrary-read primitive; validate/allow-list the path first.

Exercises

  • Read a JSON file with Bun.file(...).json(), modify a field, and write it back with Bun.write.
  • Use a writer to append 1,000 numbered lines to a log file with a single flush/end.
  • Use Bun.$ to capture git log --oneline -5 and parse it into an array of { sha, msg }.
  • Spawn sort as a subprocess, feed it unsorted lines on stdin, and print the sorted stdout.

Mini-project: a streaming upload endpoint + log tailer

Two production-shaped file patterns. First, an upload endpoint that streams a multipart file straight to disk (or S3) without buffering the whole body — the right way to accept large uploads:

Bun.serve({
  routes: {
    "/upload": {
      POST: async (req) => {
        const form = await req.formData();
        const file = form.get("file");
        if (!(file instanceof File)) return Response.json({ error: "no file" }, { status: 400 });

        // Guard size + type BEFORE touching disk
        if (file.size > 25 * 1024 * 1024) return Response.json({ error: "too large" }, { status: 413 });
        const ALLOWED = ["image/png", "image/jpeg", "application/pdf"];
        if (!ALLOWED.includes(file.type)) return Response.json({ error: "bad type" }, { status: 415 });

        // Stream the Blob to disk — Bun.write consumes it without a full in-memory copy
        const key = `uploads/${crypto.randomUUID()}-${file.name}`;
        const bytesWritten = await Bun.write(key, file);
        // Same call works for S3: await Bun.write(`s3://bucket/${key}`, file);
        return Response.json({ key, bytes: bytesWritten }, { status: 201 });
      },
    },
  },
});

Second, a tail -f style follower that prints new lines as they're appended, tracking the byte offset so it never re-reads what it's seen:

// tail.ts  —  usage: bun tail.ts app.log
const path = Bun.argv[2] ?? "app.log";
let offset = (await Bun.file(path).stat()).size;   // start at end of file

setInterval(async () => {
  const file = Bun.file(path);
  const size = (await file.stat()).size;
  if (size > offset) {
    const chunk = await file.slice(offset, size).text();   // only the new bytes
    process.stdout.write(chunk);
    offset = size;
  } else if (size < offset) {
    offset = 0;                                            // file was truncated/rotated
  }
}, 500);
console.log(`following ${path}  (Ctrl-C to stop)`);

Together they show the core discipline of file I/O at scale: validate before you read, stream instead of buffering, and track offsets so you process each byte exactly once. Swap the local path for an s3:// URL and the upload code runs unchanged against the cloud.
