A Bun monorepo keeps many packages — apps and the libraries they share — in one repository, installed and linked together by a single bun install. Internal packages are symlinked (never copied), scripts run across every package with bun run --filter, and a catalog pins one version of a shared dependency for the whole workspace. This lesson covers the layout, the linking, cross-package scripts, catalogs, and the mistakes — version drift and circular dependencies — that make monorepos painful when they're done wrong.

Declaring workspaces

Beginner Workspaces live in the root package.json. The root is private (it is never published), and the workspaces globs tell Bun which directories hold packages.

// package.json  (repo root)
{
  "name": "acme",
  "private": true,
  "workspaces": ["apps/*", "packages/*"],
  "engines": { "bun": ">=1.0.0" }
}
bun install
# bun install v1.4.2
# + @acme/ui@workspace:packages/ui
# + @acme/config@workspace:packages/config
# + @acme/web@workspace:apps/web
# + @acme/api@workspace:apps/api
# 4 workspaces, 86 packages installed [412.00ms]
Common mistake: forgetting "private": true on the root. Without it, Bun ignores workspaces entirely and bun publish at the root tries to publish the whole repo as one package. The root is scaffolding — it must stay private.

A realistic structure

The convention that scales: apps/* are deployable units (a web server, an API, a worker) and packages/* are the libraries they share. Apps depend on packages; packages depend on each other sparingly and never on apps.

acme/
├─ package.json          # root: private, workspaces, catalog
├─ bun.lockb             # one lockfile for the whole repo — commit it
├─ bunfig.toml
├─ tsconfig.base.json    # shared compiler options, extended by each package
├─ apps/
│  ├─ web/               # @acme/web   — the frontend
│  │  ├─ package.json
│  │  └─ src/
│  └─ api/               # @acme/api   — the HTTP server
│     ├─ package.json
│     └─ src/
└─ packages/
   ├─ ui/                # @acme/ui    — shared components
   ├─ config/            # @acme/config — shared eslint/tsconfig/env schema
   └─ core/              # @acme/core  — domain types + logic used by web AND api

Linking internal packages

Beginner A package depends on a sibling by its name, using the workspace: protocol. Bun symlinks the real directory into node_modules, so edits in packages/core are seen by apps/api immediately — no build-and-republish loop.

// apps/api/package.json
{
  "name": "@acme/api",
  "private": true,
  "dependencies": {
    "@acme/core": "workspace:*",     // always the local version
    "hono": "catalog:"               // version comes from the catalog (below)
  },
  "scripts": { "dev": "bun --hot src/index.ts" }
}
// packages/core/package.json
{
  "name": "@acme/core",
  "version": "0.0.0",
  "module": "src/index.ts",          // Bun resolves TS source directly — no build step to consume it
  "types": "src/index.ts"
}

Now the import just works:

// apps/api/src/index.ts
import { Order, priceOf } from "@acme/core";   // resolves to packages/core/src/index.ts

console.log(priceOf({ qty: 3, unit: 1200 } as Order));
Because Bun runs TypeScript natively, an internal package can expose its .ts source as module/types and skip a build step entirely for in-repo consumers. You only need to build a package when something outside the monorepo (a published artifact, a Docker image's runtime) consumes it.

Running scripts across packages: --filter

Intermediate bun run --filter <pattern> <script> runs a script in every matching workspace. The pattern matches package names (or paths), and Bun runs them respecting the dependency graph — a package builds after the packages it depends on.

bun run --filter='*' build              # build every workspace, in dependency order
bun run --filter='@acme/*' test         # every package in the @acme scope
bun run --filter='@acme/api' dev        # exactly one package
bun run --filter='./apps/*' lint        # match by path instead of name
bun add zod --filter @acme/core         # add a dep to one specific workspace
bun run --filter='*' build
# @acme/core    build  $ bun build src/index.ts --outdir dist   ✓
# @acme/config  build  $ bun build src/index.ts --outdir dist   ✓
# @acme/ui      build  $ bun build src/index.ts --outdir dist   ✓   (after @acme/core)
# @acme/api     build  $ bun build src/index.ts --outdir dist   ✓   (after @acme/core)
# @acme/web     build  $ bun build src/index.ts --outdir dist   ✓   (after @acme/ui)

The ordering matters: if @acme/ui imports @acme/core, Bun builds core first so ui sees the fresh output. You do not script this yourself — it falls out of the workspace: dependency edges.

Catalogs — one version for a shared dependency

Intermediate The hardest monorepo problem is version drift: apps/web pins zod@3.23.8 while packages/core pins zod@3.24.1, two copies load, and a z.instanceof check across the boundary mysteriously fails. A catalog declares the version once at the root and every package references it by name.

// package.json (root)
{
  "name": "acme",
  "private": true,
  "workspaces": ["apps/*", "packages/*"],
  "catalog": {
    "zod": "3.23.8",
    "hono": "4.6.3"
  },
  "catalogs": {
    // named catalogs for groups that must move together
    "testing": { "@faker-js/faker": "9.0.3" }
  }
}

Packages opt in with catalog: (the default catalog) or catalog:<name>:

// packages/core/package.json
{
  "dependencies": { "zod": "catalog:" },
  "devDependencies": { "@faker-js/faker": "catalog:testing" }
}

// apps/web/package.json
{
  "dependencies": { "zod": "catalog:", "hono": "catalog:" }
}

Now a version bump happens in one place — edit the root catalog, run bun install, and every package moves together. There is no way for two packages to disagree on zod, because neither names a version itself.

Reach for a catalog for a dependency shared by multiple packages (validation libs, your HTTP framework, test helpers). Reach for overrides (root package.json) when you need to force a transitive dependency — one you don't depend on directly — to a specific version across the whole tree, e.g. patching a CVE before the direct dep bumps it.

Circular dependencies

Advanced A cycle — @acme/core imports @acme/ui which imports @acme/core — breaks dependency-ordered builds (there is no "first") and produces fragile load-order bugs where one module sees the other half-initialized. Bun will install a cycle, so the tooling won't always stop you; the discipline has to.

# spot cycles in the install graph
bun pm ls --all

# a cycle shows up as a build that can't be ordered:
# bun run --filter='*' build
# error: cyclic workspace dependency: @acme/core <-> @acme/ui

The fix is structural, not a flag: extract the shared pieces both packages need into a third, lower package (often @acme/types or @acme/core) that neither of the two imports back. Dependencies should flow one direction only — apps depend on packages, packages depend on more foundational packages, and nothing depends upward.

Monorepo CI

CI for a monorepo is a single deterministic install plus graph-ordered build and test. --frozen-lockfile fails the build if the committed bun.lockb would change — catching an un-committed dependency bump before it merges.

# .github/workflows/ci.yml
jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
        with: { bun-version: 1.4.2 }

      # one install for the whole repo; fail on any lockfile drift
      - run: bun install --frozen-lockfile

      # graph-ordered: dependencies build/test before their consumers
      - run: bun run --filter='*' typecheck
      - run: bun run --filter='*' build
      - run: bun test
Common mistakes: (1) Version drift — two packages pinning different versions of the same lib, loading two copies, and failing cross-package instanceof/identity checks. Use a catalog so a version is declared once. (2) Circular dependencies — a mutual import between two packages, which has no valid build order and produces half-initialized-module bugs; extract the shared code into a lower package instead. (3) Running a second package manager (npm install) in a Bun workspace, producing a competing lockfile and divergent trees — commit bun.lockb only. (4) Forgetting "private": true on the root, which silently disables workspaces.

Exercises

  • Create a workspace with apps/web and packages/core; have web import a function from core via workspace:* and run it with bun run --filter='@acme/web' dev.
  • Add a catalog entry for zod at the root and switch both packages to "zod": "catalog:"; bump the catalog version once and confirm both move after bun install.
  • Give packages/ui a dependency on packages/core, then run bun run --filter='*' build and observe that core builds before ui.
  • Deliberately introduce a cycle (core imports ui) and watch the ordered build fail; then break the cycle by extracting shared types into a third package.

Mini-project: a two-app monorepo with a shared core and a catalog

Build a monorepo where an API and a web app both consume one domain package, pinned dependencies come from a catalog, and CI installs deterministically. This is the shape a real product repo takes.

// package.json (root)
{
  "name": "shop",
  "private": true,
  "workspaces": ["apps/*", "packages/*"],
  "engines": { "bun": ">=1.0.0" },
  "catalog": { "zod": "3.23.8", "hono": "4.6.3" },
  "scripts": {
    "build": "bun run --filter='*' build",
    "test": "bun test",
    "typecheck": "bunx tsc --noEmit"
  }
}
// packages/core/package.json
{ "name": "@shop/core", "version": "0.0.0", "module": "src/index.ts", "types": "src/index.ts",
  "dependencies": { "zod": "catalog:" } }

// packages/core/src/index.ts
import { z } from "zod";
export const Order = z.object({ id: z.string(), total: z.number().int().nonnegative() });
export type Order = z.infer<typeof Order>;
export const describe = (o: Order) => `order ${o.id}: $${(o.total / 100).toFixed(2)}`;
// apps/api/package.json
{ "name": "@shop/api", "private": true,
  "dependencies": { "@shop/core": "workspace:*", "hono": "catalog:" },
  "scripts": { "dev": "bun --hot src/index.ts", "build": "bun build src/index.ts --outdir dist" } }

// apps/api/src/index.ts
import { Hono } from "hono";
import { Order, describe } from "@shop/core";

const app = new Hono();
app.post("/orders", async (c) => {
  const parsed = Order.safeParse(await c.req.json());        // validate with the SHARED schema
  if (!parsed.success) return c.json({ error: parsed.error.flatten() }, 400);
  return c.json({ message: describe(parsed.data) }, 201);    // SHARED logic
});
export default app;
# one install, graph-ordered build + test
bun install
bun run --filter='*' build
bun test

# the API validates with @shop/core's schema; the web app would import the SAME
# Order type, so a change to the shape is a single edit in packages/core.

The payoff: the Order schema and its formatting live in @shop/core and are the single source of truth for both the API and the web app. Change the shape once and both consumers get it; the catalog guarantees they resolve the same zod; --frozen-lockfile in CI guarantees the install is the one you committed.
