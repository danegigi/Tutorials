Bun's package manager is a drop-in replacement for npm/yarn/pnpm — it reads package.json, installs from the npm registry, and is dramatically faster thanks to a global cache and a binary lockfile. This lesson covers install/add/remove, the lockfile, outdated checks, workspaces, overrides, and bunx.

install, add, remove

Beginner The core commands mirror npm but run faster:

bun install                 # install everything in package.json
bun add hono                # add a runtime dependency
bun add -d @types/bun       # add a dev dependency
bun add zod@3.23.8          # pin an exact version
bun add -g wrangler         # install a global tool
bun remove hono             # remove a dependency
bun update                  # update within the semver ranges in package.json
bun update hono             # update just one package
bun add hono
# bun add v1.4.2
# installed hono@4.6.3
# 1 package installed [142.00ms]
Prefer exact/pinned versions for reproducibility — set exact = true under [install] in bunfig.toml so bun add writes "hono": "4.6.3" instead of "^4.6.3". A pinned dependency that looks unusual or near a popular name may be a typosquat — read the name twice before adding.

The binary lockfile: bun.lockb

Bun writes a binary lockfile, bun.lockb, which parses far faster than a huge JSON lockfile. Commit it; never hand-generate package-lock.json or yarn.lock alongside it.

bun install --frozen-lockfile    # CI: fail if the lockfile would change at all
bun pm ls                        # print the installed dependency tree
bun pm ls --all                  # include transitive deps
bun pm cache rm                  # clear the global install cache

Because it's binary you can't eyeball a diff. In code review, trust that a changed bun.lockb means dependencies moved, and rely on --frozen-lockfile in CI to catch an un-committed bump.

bun outdated

bun outdated
# ┌──────────┬─────────┬────────┬────────┐
# │ Package  │ Current │ Update │ Latest │
# ├──────────┼─────────┼────────┼────────┤
# │ hono     │ 4.6.1   │ 4.6.3  │ 4.6.3  │
# │ zod      │ 3.23.8  │ 3.23.8 │ 3.24.1 │
# └──────────┴─────────┴────────┴────────┘

Update is the newest version your semver range allows; Latest is the absolute newest (which may be a major bump outside your range). bun update moves to the Update column; reaching Latest for a major bump means editing the version and re-adding.

Workspaces (monorepos)

Intermediate Declare workspaces in the root package.json; Bun installs them together and symlinks internal dependencies.

// package.json (repo root)
{
  "name": "my-monorepo",
  "private": true,
  "workspaces": ["packages/*", "apps/*"],
  "engines": { "bun": ">=1.0.0" }
}

A package depends on a sibling by name using the workspace: protocol:

// apps/web/package.json
{ "dependencies": { "@myorg/ui": "workspace:*" } }
bun install                     # links every workspace together
bun run --filter='*' build      # run "build" in every workspace
bun run --filter='@myorg/ui' test   # run a script in one workspace
bun add lodash --filter apps/web    # add a dep to a specific workspace

Overrides — pin a transitive dependency

When a package deep in your tree pulls a version you need to fix (a security patch, a compatibility pin), force it across the whole tree with overrides in the root package.json:

{
  "overrides": {
    "semver": "7.6.3",             // force this exact version everywhere
    "foo": { "bar": "1.2.3" }       // scoped: only bar inside foo
  }
}

After editing, run bun install to re-resolve. This is the escape hatch for "a transitive dep has a CVE but the direct dependency hasn't bumped it yet."

bunx — run a package without installing

bunx cowsay "hello from bun"    # like npx, but fast (cached)
bunx --bun vite                 # force the tool to run under Bun's runtime
bunx prettier --write .         # one-off tool invocation

bunx <pkg> downloads (once, into the cache) and runs a package's binary without adding it to your project. --bun forces the tool to execute on Bun rather than any Node on your PATH — useful for tools that behave differently per runtime.

Scripts and lifecycle

// package.json
{
  "scripts": {
    "dev": "bun --watch src/index.ts",
    "build": "bun build src/index.ts --outdir dist",
    "test": "bun test",
    "prepare": "bun run build"     // lifecycle hook: runs after install
  }
}
Common mistake: running two package managers in the same repo. If you bun install and a teammate npm install, you end up with both bun.lockb and package-lock.json resolving to different trees, and "works on my machine" bugs follow. Pick Bun, commit bun.lockb, delete any package-lock.json/yarn.lock, and add --frozen-lockfile to CI so a drifted lockfile fails the build instead of silently installing something else. A second trap: forgetting private: true on a monorepo root — without it, workspaces is ignored and you'll accidentally try to publish the root.

Exercises

  • In a fresh project, bun add zod@3.23.8 and confirm package.json records the exact version (set exact = true if it wrote a ^).
  • Run bun pm ls and bun outdated; identify one package where Update and Latest differ and explain why.
  • Run a one-off tool with bunx cowsay and confirm it was never added to package.json.
  • Create a two-package workspace where apps/web imports packages/ui via workspace:*, then bun run --filter='*' build.

Mini-project: a reproducible monorepo + CI install

Set up a monorepo with a shared UI package consumed by an app, then write the exact CI steps that make installs deterministic. This is the real-world shape of a Bun monorepo.

// package.json (root)
{
  "name": "acme",
  "private": true,
  "workspaces": ["packages/*", "apps/*"],
  "engines": { "bun": ">=1.0.0" },
  "scripts": {
    "build": "bun run --filter='*' build",
    "test": "bun test",
    "typecheck": "bunx tsc --noEmit"
  },
  "overrides": { "semver": "7.6.3" }
}
// packages/ui/package.json
{ "name": "@acme/ui", "version": "0.0.0", "module": "index.ts",
  "scripts": { "build": "bun build index.ts --outdir dist" } }

// apps/web/package.json
{ "name": "@acme/web", "private": true,
  "dependencies": { "@acme/ui": "workspace:*" },
  "scripts": { "build": "bun build src/index.ts --outdir dist" } }
# .github/workflows/ci.yml (install step)
- uses: oven-sh/setup-bun@v2
  with: { bun-version: 1.4.2 }

# Fail if the committed lockfile would change — catches an un-committed bump
- run: bun install --frozen-lockfile

# Build + test every workspace in one pass
- run: bun run --filter='*' build
- run: bun test

The workflow to internalize: run bun install locally (which updates bun.lockb), commit the lockfile, and let CI run --frozen-lockfile so any drift fails loudly instead of silently resolving different versions. The overrides entry pins a transitive package across every workspace at once.
