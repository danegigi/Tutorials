Terraform turns infrastructure into code: you declare the resources you want in HCL, Terraform computes the difference between that declaration and reality, and applies only the changes needed. This lesson goes from your first resource to the patterns that keep a real team's infrastructure reproducible — modules, remote state, loops, and safe imports.

The mental model: declare, plan, apply

Beginner You never write "create a server" as an imperative step. You declare "a server with these properties should exist," and Terraform's core loop figures out the verbs:

CommandWhat it does
terraform initdownloads providers & modules, configures the backend. Run after any provider/module change.
terraform planshows the diff between your config and real state — read this every time.
terraform applymakes reality match (after you confirm the plan).
terraform destroydeletes everything the state tracks.

Your first configuration

# main.tf
terraform {
  required_version = ">= 1.9"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_s3_bucket" "assets" {
  bucket = "my-app-assets-prod"
  tags   = { Environment = "prod", ManagedBy = "terraform" }
}
terraform init
terraform plan
#   + resource "aws_s3_bucket" "assets" { ... }
# Plan: 1 to add, 0 to change, 0 to destroy.
terraform apply

A resource has a type (aws_s3_bucket) and a local name (assets). You reference it elsewhere as aws_s3_bucket.assets.id — and those references are how Terraform builds its dependency graph and orders operations.

Variables, outputs, and locals

# variables.tf
variable "environment" {
  type    = string
  default = "dev"
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "environment must be dev, staging, or prod."
  }
}

# locals.tf — computed values, named once
locals {
  name_prefix = "myapp-${var.environment}"
  common_tags = { Environment = var.environment, ManagedBy = "terraform" }
}

# outputs.tf — surface values after apply (and to other configs)
output "bucket_name" {
  value = aws_s3_bucket.assets.bucket
}
terraform apply -var environment=prod
# or a file:
terraform apply -var-file=prod.tfvars
terraform output bucket_name
Precedence (lowest to highest): defaults → terraform.tfvars / *.auto.tfvars → -var-file → -var → TF_VAR_* env vars. Keep secrets out of tfvars checked into Git.

State: Terraform's memory

Intermediate Terraform records what it created in a state file. State maps your config to real resource IDs — without it, Terraform can't tell "already exists" from "needs creating." The default is a local terraform.tfstate, which breaks the moment a second person runs apply.

Never commit terraform.tfstate to Git — it contains resource IDs and often secrets in plaintext, and two people editing it diverge instantly. Use a remote backend.

Remote state & locking

# backend.tf — S3 + DynamoDB lock (classic AWS setup)
terraform {
  backend "s3" {
    bucket         = "mycompany-tfstate"
    key            = "prod/app.tfstate"
    region         = "us-east-1"
    dynamodb_table = "tf-locks"   # prevents two applies at once
    encrypt        = true
  }
}

Remote state puts the state in shared storage; the lock (DynamoDB here, or the newer S3-native lockfile) stops two people from applying simultaneously and corrupting it. HCP Terraform and other backends give the same guarantees.

Modules: the unit of reuse

Intermediate A module is a folder of .tf files you can call with inputs — the function of infrastructure code. The standard structure:

modules/
  web-service/
    main.tf        # resources
    variables.tf   # inputs
    outputs.tf     # outputs
environments/
  prod/main.tf     # calls the module
# environments/prod/main.tf
module "api" {
  source      = "../../modules/web-service"
  name        = "api"
  environment = "prod"
  replicas    = 4
}

output "api_url" {
  value = module.api.service_url
}
Pin remote modules to a version (version = "5.1.2" from a registry, or a Git ?ref=v1.2.0 tag). An unpinned module can change under you between applies.

Loops: count, for_each, and dynamic

# count — simple N copies (indexed; reordering is disruptive)
resource "aws_instance" "worker" {
  count         = 3
  instance_type = "t3.micro"
  tags          = { Name = "worker-${count.index}" }
}

# for_each — keyed copies (STABLE to add/remove — prefer this)
resource "aws_iam_user" "team" {
  for_each = toset(["alice", "bob", "carol"])
  name     = each.key
}
# dynamic — generate repeated nested blocks
resource "aws_security_group" "web" {
  dynamic "ingress" {
    for_each = [80, 443]
    content {
      from_port   = ingress.value
      to_port     = ingress.value
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}
count vs for_each — a real footgun: with count, resources are tracked by index ([0], [1]). Remove the middle item from the list and everything after it shifts index, so Terraform plans to destroy & recreate them. for_each tracks by key, so removing one leaves the others untouched. Prefer for_each for anything with identity.

Lifecycle and dependencies

resource "aws_db_instance" "main" {
  # ...
  lifecycle {
    prevent_destroy       = true    # refuse to delete this (prod DB)
    create_before_destroy = true    # avoid downtime on replacement
    ignore_changes        = [tags["LastModified"]]  # don't fight an external process
  }
}

# explicit ordering when there's no reference to infer it
resource "aws_s3_bucket_policy" "p" {
  depends_on = [aws_s3_bucket.assets]
}

Importing existing infrastructure

Advanced Resources created by hand (clickops) can be brought under Terraform. Modern Terraform uses an import block so the import itself is reviewable in a plan:

import {
  to = aws_s3_bucket.legacy
  id = "my-existing-bucket"
}
# then: terraform plan -generate-config-out=generated.tf
# Terraform writes a starting resource block AND shows what (if anything) would change.
After import, run terraform plan until it shows no changes — that proves your HCL now exactly matches the real resource. If the plan wants to modify something, your config drifted from reality; fix the config, not the resource.

Workspaces and multi-environment

Workspaces give one config multiple independent states (terraform workspace new staging). They're fine for small cases, but for truly different environments most teams prefer separate directories or separate backends per environment — it keeps prod and dev state physically apart and makes blast radius obvious. Reach for workspaces when the environments are near-identical; reach for directories when they diverge.

Common mistakes

  • Committing state to Git or using local state on a team — the fastest way to corrupt everything.
  • Applying without reading the plan. The plan is your diff review; "1 to destroy" on a database is how outages happen.
  • Using count for resources with identity, then shuffling the list and triggering destroy/recreate. Use for_each.
  • Hardcoding secrets in .tf or .tfvars. Pull them from a secrets manager or environment at apply time.
  • Editing resources by hand after Terraform created them, causing drift the next plan wants to undo. Change it in code and apply.
  • No prevent_destroy on stateful resources, so one bad refactor plans to delete the production database.

Exercises

  • Write a config that creates two S3 buckets with for_each, then remove one key and confirm the plan touches only that bucket (not the other).
  • Configure an S3 remote backend with locking, run an apply, and inspect the state object in the bucket.
  • Extract your resources into a module with input variables and an output, then call it twice (dev and prod) with different inputs.
  • Create a resource by hand in your cloud console, write an import block for it, and use -generate-config-out to get a config that plans clean.
  • Add a lifecycle { prevent_destroy = true } to a resource and try to destroy it — read the error, then understand why it's your friend.

Mini-project

Build a small but complete, reusable infrastructure module: a network module (VPC + subnets) and a web-service module (compute + security group + load balancer) that consumes the network's outputs. Wire them together in two environment directories (staging, prod) each with its own remote backend and tfvars, using for_each where there's identity, variable validation on the environment name, and prevent_destroy on anything stateful. Run plan for both environments and confirm each shows only its own changes — proving the module is genuinely reusable and the environments are isolated.
