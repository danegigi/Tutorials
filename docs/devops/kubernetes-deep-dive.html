Kubernetes is a declarative system for running containers across a fleet of machines: you describe the desired state in YAML, submit it to the API server, and a set of controllers works continuously to make reality match. This lesson builds that picture from the ground up — a single pod, then the objects you layer on top for real workloads, then the control-plane internals that make it all reconcile.

The one idea that makes Kubernetes click

Beginner Everything is declarative reconciliation. You never tell Kubernetes "start three copies" as a command; you record "I want three copies" as desired state, and a controller loops forever comparing desired to actual and taking action to close the gap. Kill a pod and the controller makes a new one — not because something caught the event, but because the next reconcile sees two where it wants three.

Hold this in mind for the whole lesson: an object is a record of intent, and a controller is a loop that enforces it. Almost every "how does Kubernetes do X" answer is "a controller reconciles an object."

Get a cluster to practice on

# A throwaway local cluster (pick one):
kind create cluster --name demo        # Docker-based, fast
# or
minikube start

kubectl version --short
kubectl get nodes
# NAME                 STATUS   ROLES           AGE   VERSION
# demo-control-plane   Ready    control-plane   40s   v1.31.0

kubectl is your remote control. It reads ~/.kube/config to know which cluster and credentials to use. kubectl config current-context tells you which cluster you're about to change — check it before every destructive command.

Pods: the smallest unit

A pod is one or more containers that share a network namespace (same IP, same localhost) and can share volumes. You rarely create bare pods — but understanding one is the foundation.

apiVersion: v1
kind: Pod
metadata:
  name: web
  labels: { app: web }
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports: [{ containerPort: 80 }]
kubectl apply -f pod.yaml
kubectl get pods -o wide
kubectl logs web
kubectl exec -it web -- sh         # shell inside the container
kubectl port-forward pod/web 8080:80   # reach it from your laptop
Why not bare pods in production: a pod has no self-healing. If its node dies, the pod is gone for good — nothing recreates it. That's what Deployments are for.

Deployments: self-healing, scaling, rollouts

Beginner A Deployment manages a ReplicaSet, which manages pods. You declare how many replicas and which image; the Deployment controller keeps that many running and handles rolling updates.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:                 # the pod template — this IS a pod spec
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports: [{ containerPort: 80 }]
kubectl apply -f deploy.yaml
kubectl get deploy,rs,pods
kubectl scale deploy/web --replicas=5
kubectl set image deploy/web nginx=nginx:1.27.1   # triggers a rolling update
kubectl rollout status deploy/web
kubectl rollout undo deploy/web                   # roll back to the previous ReplicaSet
The #1 beginner trap: the selector.matchLabels and the template.metadata.labels MUST agree, or the Deployment manages zero pods (or the wrong ones). The selector is how the controller finds "its" pods.

Services: a stable address for a moving target

Pods are ephemeral — their IPs change on every restart. A Service gives a stable virtual IP and DNS name that load-balances across whichever pods currently match its selector.

apiVersion: v1
kind: Service
metadata: { name: web }
spec:
  selector: { app: web }     # same labels the Deployment's pods carry
  ports:
    - port: 80               # the Service's port
      targetPort: 80         # the container's port
# type defaults to ClusterIP (reachable only inside the cluster)

Inside the cluster, other pods reach it as web (same namespace) or web.default.svc.cluster.local. Service types:

TypeReachable fromUse for
ClusterIPinside the cluster onlyinternal services (default)
NodePortevery node's IP on a high portquick external access, dev
LoadBalancera cloud load balancerpublic services on a cloud provider

Ingress: HTTP routing at the edge

Intermediate A LoadBalancer per service is expensive. An Ingress + an ingress controller (NGINX, Traefik) gives you one entry point that routes by host/path and terminates TLS.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: site }
spec:
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: web, port: { number: 80 } } }
  tls:
    - hosts: [shop.example.com]
      secretName: shop-tls
An Ingress object does nothing on its own — you must install an ingress controller that watches Ingress objects and configures the actual proxy. Forgetting this is why "my Ingress has no address."

Configuration: ConfigMaps and Secrets

kubectl create configmap app-config --from-literal=LOG_LEVEL=info
kubectl create secret generic db --from-literal=PASSWORD=s3cr3t
# inject into a container
envFrom:
  - configMapRef: { name: app-config }
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef: { name: db, key: PASSWORD }
Secrets are only base64-encoded, not encrypted, and anyone with read access to the namespace can decode them. Enable encryption-at-rest on etcd, restrict access with RBAC, and for real secrets reach for the Secrets Management lesson (Vault, External Secrets, Sealed Secrets).

Storage and StatefulSets

Intermediate Deployments are for stateless workloads — any replica is interchangeable. For databases and anything needing stable identity + persistent per-pod storage, use a StatefulSet, which gives each pod a stable name (db-0, db-1) and its own PersistentVolumeClaim.

volumeClaimTemplates:
  - metadata: { name: data }
    spec:
      accessModes: [ReadWriteOnce]
      resources: { requests: { storage: 10Gi } }
# db-0 gets its OWN 10Gi volume that survives restarts and follows the pod identity.

A PersistentVolumeClaim (PVC) requests storage; a StorageClass defines how it's provisioned (which cloud disk type). Pods mount the PVC, not the volume directly.

Namespaces, quotas, and multi-tenancy

kubectl create namespace team-a
kubectl apply -n team-a -f deploy.yaml

Namespaces partition a cluster: names are unique per namespace, and you can attach ResourceQuota (cap total CPU/memory/object counts) and LimitRange (default/limit per pod) to keep one team from starving others.

RBAC: who can do what

Advanced Role-Based Access Control binds subjects (users, groups, ServiceAccounts) to verbs (get, list, create, delete) on resources.

kind: Role                 # namespaced; ClusterRole for cluster-wide
metadata: { namespace: team-a, name: pod-reader }
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
---
kind: RoleBinding
metadata: { namespace: team-a, name: read-pods }
subjects: [{ kind: ServiceAccount, name: ci, namespace: team-a }]
roleRef: { kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io }
kubectl auth can-i delete pods --as=system:serviceaccount:team-a:ci -n team-a
# no

Under the hood: the control plane

When you run kubectl apply, here is what actually happens:

ComponentRole
API serverthe only thing that talks to etcd; validates and stores every object. All reads/writes go through it.
etcdthe cluster's database — the single source of truth for desired + actual state.
schedulerwatches for unscheduled pods and picks a node (based on requests, affinity, taints).
controller-managerruns the reconcile loops (Deployment, ReplicaSet, Node, Job… controllers).
kubeleton each node: pulls images, starts containers, reports status back to the API server.
kube-proxyon each node: programs iptables/IPVS so Service IPs route to pod IPs.

The flow: kubectl → API server validates & writes to etcd → the Deployment controller sees a new Deployment and creates a ReplicaSet → the ReplicaSet controller creates pods → the scheduler assigns each pod a node → the kubelet on that node starts the container → kube-proxy wires up the Service. Every arrow is a controller watching the API server and reconciling.

Debugging the way you actually will

kubectl get pods                      # STATUS tells you a lot
kubectl describe pod web-xxxx         # Events at the bottom = why it won't start
kubectl logs web-xxxx --previous      # logs from the crashed container
kubectl get events --sort-by=.lastTimestamp
STATUSUsual cause
ImagePullBackOffwrong image name/tag or missing registry credentials
CrashLoopBackOffthe container starts then exits — read the logs
Pendingno node can fit it (requests too big, taints, no volume)
CreateContainerConfigErrora referenced ConfigMap/Secret key doesn't exist

Common mistakes

  • Selector/label mismatch between a Deployment and its pod template, or a Service and its pods — the controller silently manages nothing.
  • Treating Secrets as secure because they look encoded. They're base64 only.
  • No resource requests, so the scheduler can't place pods sensibly and nodes get overcommitted.
  • Using a Deployment for a database. Rolling two replicas onto the same volume corrupts data — stateful workloads need StatefulSets with per-pod storage.
  • Editing live objects with kubectl edit and losing the change on the next apply. Keep YAML in Git and apply from there (see GitOps).
  • Not checking kubectl config current-context before a destructive command — deleting in prod when you meant staging.

Exercises

  • Create a Deployment of 3 nginx replicas and a ClusterIP Service, then kubectl exec into a temporary pod (kubectl run tmp --rm -it --image=busybox -- sh) and wget -qO- web to prove in-cluster DNS and load balancing work.
  • Scale to 5, then run kubectl set image to a new tag and watch kubectl rollout status; then rollout undo and confirm the old ReplicaSet comes back.
  • Break a Deployment on purpose (a nonexistent image tag) and diagnose it end-to-end using only get, describe, and logs.
  • Add a ResourceQuota to a namespace that caps total memory, then try to schedule a pod that exceeds it and read the rejection.
  • Write a Role + RoleBinding that lets a ServiceAccount list pods but not delete them, and verify both with kubectl auth can-i.

Mini-project

Deploy a complete two-tier app to your local cluster: a stateless API Deployment (3 replicas) with a ClusterIP Service, a PostgreSQL StatefulSet with a PersistentVolumeClaim, a ConfigMap for app config and a Secret for the DB password, and an Ingress routing app.localtest.me to the API through an installed ingress controller. Add readiness/liveness probes, resource requests/limits, and a ResourceQuota on the namespace. Then simulate a node/pod failure (kubectl delete pod) and document how each object reacts — proving to yourself which parts self-heal and which (the data) persist.
