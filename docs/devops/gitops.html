GitOps is a way of running infrastructure and applications where Git is the single source of truth: everything you want running is described declaratively in a repository, and automated agents continuously make the real world match what the repo says. This lesson takes you from the core idea through push-based CI versus pull-based GitOps, Flux and its reconciliation loop, and an end-to-end workflow tying Terraform, Helm, and GitHub Actions together.

Git as the source of truth

Beginner GitOps rests on one idea: if you can describe your whole system as text files and store them in Git, then Git becomes the authoritative record of what should exist. Nothing is changed by hand on a server — you change a file, commit it, and automation reconciles reality to match. That buys three things almost for free:

  • Auditability — git log is your complete change history: who changed what, when, and (via the PR) why.
  • Rollback — reverting a bad change is just git revert; the automation notices and rolls the live system back.
  • Reproducibility — you can rebuild the whole environment from the repo, because the repo is the environment's definition.

GitOps depends on declarative tooling — Kubernetes manifests, Terraform HCL, Helm charts all describe the end state, not the steps. Because desired state is a value you can diff, a machine can always compute the difference between "what the repo says" and "what is actually running."

The reconciliation loop

Beginner The engine of GitOps is a control loop that runs forever:

  1. Observe the actual state of the system.
  2. Compare it to the desired state defined in Git.
  3. Act to close any gap — apply, update, or delete resources until reality matches Git.

This runs continuously, not just at deploy time. If someone manually edits a live resource, the loop detects the divergence and corrects it — drift detection and self-healing.

Mental model: CI = "is the code good?" (build, test, produce artifacts). CD in GitOps = "make the cluster match Git." Keeping them separate is what makes GitOps auditable and secure — your CI system never needs cluster credentials.

Push-based CI vs pull-based GitOps

Intermediate In traditional push-based CD, a pipeline holds cluster credentials and reaches in from outside:

# inside a GitHub Actions job — the "push" model
- run: |
    aws eks update-kubeconfig --name my-cluster
    kubectl set image deployment/web web=ghcr.io/org/web:${{ github.sha }}

It works, but it has real drawbacks: your CI system holds powerful cluster credentials (a compromised workflow is now a cluster breach); the cluster is only updated at deploy time, so out-of-band changes drift uncorrected; and "what is actually deployed?" is answered by cluster inspection plus CI-log archaeology.

In pull-based GitOps, an agent (Flux, Argo CD) runs inside the cluster and:

  • pulls the desired state from Git (no inbound access to the cluster required),
  • reconciles it against live state on a schedule and on every change,
  • reports status back (synced / drifted / failed).

Because the agent only needs read access to Git, no external system ever holds cluster credentials. CI's job shrinks to "build image, update manifest in Git." The cluster deploys itself and self-heals on drift.

CI with GitHub Actions

Intermediate GitHub Actions is the CI half. Workflows are YAML files under .github/workflows/, triggered by events; the crucial GitOps step is building a container image and pushing it to a registry, tagged with the commit SHA so every build is uniquely identifiable.

name: Build and Push Image
on:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write          # needed to push to GHCR

jobs:
  docker:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:${{ github.sha }}
            ghcr.io/${{ github.repository }}:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max
Pin to an immutable tag (the commit SHA), not :latest, so rollbacks are real: a specific, revertable image. ${{ secrets.GITHUB_TOKEN }} is auto-provisioned and scoped to the repo — use it to push to GHCR without minting a personal token.

Flux

Advanced Flux is a set of Kubernetes controllers — the GitOps Toolkit — that implement the pull model. You install it, point it at a Git repo, and it reconciles the cluster to match. The controllers: source-controller (fetches from Git/Helm/OCI), kustomize-controller (applies manifests), helm-controller (manages Helm releases), notification-controller (events in/out), and the image-reflector/automation controllers (auto-bump tags).

# Bootstrap: installs Flux AND commits its own manifests into your repo
export GITHUB_TOKEN=<your-pat>
flux bootstrap github \
  --owner=my-org \
  --repository=fleet-infra \
  --branch=main \
  --path=clusters/production
# -> ✔ all components are healthy

Two CRDs do the core work. A GitRepository (a source) says where and how often to fetch; a Kustomization says which path to apply and reconcile.

apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: app-config
  namespace: flux-system
spec:
  interval: 1m
  url: https://github.com/my-org/app-config
  ref: { branch: main }
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: apps-production
  namespace: flux-system
spec:
  interval: 5m
  sourceRef: { kind: GitRepository, name: app-config }
  path: ./apps/production
  prune: true          # delete resources removed from Git
  wait: true
prune: true makes deletion GitOps-native: remove a manifest from Git and Flux removes it from the cluster. The trade-off is that a bad path change can prune more than you meant — scope your Kustomization paths carefully.

Helm via Flux

Flux deploys Helm charts declaratively through a HelmRelease — the helm-controller runs the equivalent of helm upgrade --install for you, with auto-rollback on a failed upgrade.

apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: podinfo
  namespace: default
spec:
  interval: 5m
  chart:
    spec:
      chart: podinfo
      version: "6.5.4"            # pin exact; edit + commit to upgrade
      sourceRef: { kind: HelmRepository, name: podinfo, namespace: flux-system }
  upgrade:
    remediation: { retries: 3 }   # auto-rollback a bad upgrade
  values:
    replicaCount: 2
    ingress:
      enabled: true
      hosts:
        - host: podinfo.example.com
# Watch Flux reconcile
flux get kustomizations
flux get helmreleases
# -> NAME      REVISION    SUSPENDED  READY  MESSAGE
# -> podinfo   6.5.4       False      True   Release reconciliation succeeded
flux reconcile kustomization apps-production --with-source   # force an immediate sync

End-to-end GitOps workflow

Advanced Here is the whole thing tied together across two repos — an app repo (source code) and a config repo (manifests / desired state).

  1. One-time: provision the platform. Terraform creates the VPC, the cluster, IAM, and the S3+DynamoDB state backend — its config lives in Git and runs through a plan-on-PR / apply-on-merge Actions workflow.
  2. One-time: bootstrap Flux. flux bootstrap github installs the toolkit and points a GitRepository + Kustomization at the config repo.
  3. A developer pushes app code to the app repo's main.
  4. Actions runs CI — lint, test, build the image, push it tagged with ${{ github.sha }}.
  5. The manifest is updated — either Actions commits the new tag into the config repo, or Flux image-automation writes it back. Either way the change is a commit in the config repo.
  6. Flux reconciles — source-controller sees the new commit (interval or webhook), the kustomize/helm controller applies it, Kubernetes rolls out the new image.
  7. Rollback = git revert. If the release is bad, revert the commit in the config repo and push; Flux rolls the cluster back — no special tooling, fully audited.
Notice where the boundary sits: CI never touches the cluster, and the cluster never trusts CI. The only thing crossing between them is a commit in the config repo. That single seam is what gives GitOps its auditability and blast-radius control.

A Terraform plan-on-PR, apply-on-merge gate

on:
  pull_request:  { paths: ['infra/**'] }
  push:          { branches: [main], paths: ['infra/**'] }

jobs:
  plan:
    if: github.event_name == 'pull_request'
    steps:
      - run: terraform init
      - run: terraform fmt -check
      - run: terraform validate
      - run: terraform plan -no-color       # reviewers see the proposed change

  apply:
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    environment: production                 # requires approval + holds prod secrets
    steps:
      - run: terraform init
      - run: terraform apply -auto-approve
Destructive: terraform apply -auto-approve in CI applies whatever merges to main with no human at the keyboard. Protect that path — require PR review, run plan on the PR, and put apply behind a protected environment with required reviewers. The plan you approve on the PR is your last human checkpoint.

Best practices

Advanced The patterns that keep a GitOps setup maintainable as it grows.

  • Separate app repo and config repo. An image bump is a config-repo commit, not churn in the app repo's history; CI and CD get clean ownership boundaries.
  • Environment overlays with Kustomize. Keep a base/ and thin overlays/staging, overlays/production that patch it, instead of copy-pasting manifests per environment.
  • PR-based promotion. Promote a tag from staging to production by opening a PR against the production overlay — a reviewed, audited gate, with rollback still just git revert.
  • Least privilege. Flux gets read-only Git access; CI gets registry push but no cluster credentials; use short-lived OIDC-federated cloud creds in Actions.
Never commit a plaintext Secret, a .tfvars with credentials, or a raw kubeconfig. Once it is in Git history it is effectively permanent — rotate the credential rather than trying to scrub the repo. For secrets in GitOps use SOPS (encrypt the values; Flux decrypts at apply) or Sealed Secrets (only the cluster can decrypt).

Common mistakes

Common mistakes
  • Giving CI cluster credentials. That is the push anti-pattern GitOps avoids — a leaked workflow secret becomes a cluster breach. Let an in-cluster agent pull instead.
  • Deploying off :latest. You cannot roll back to a specific image. Tag with the commit SHA and reference that in Git.
  • Committing secrets. Plaintext Secrets or secret tfvars in Git are permanent; use SOPS/Sealed Secrets and rotate anything leaked.
  • Editing live resources by hand. Flux reverts the drift on the next reconcile; make the change in Git or it will not stick.
  • Unscoped prune: true. A careless path change can delete more than intended — scope Kustomization paths tightly.
  • Auto-apply with no human gate. terraform apply -auto-approve on merge needs PR review + a protected environment, or a bad merge ships straight to prod.

Exercises

  • Write a GitHub Actions workflow that builds an image and pushes it to GHCR tagged with ${{ github.sha }}.
  • Explain, in two or three sentences each, the security and drift differences between push-based CD and pull-based GitOps.
  • On a kind cluster, flux bootstrap against a test repo, add a GitRepository + Kustomization, and watch a committed manifest appear in the cluster.
  • Deploy an app via a Flux HelmRelease, change a value in Git, and confirm the release upgrades on the next reconcile.
  • Make a bad change, then git revert it, and verify Flux rolls the cluster back without any kubectl.

Mini-project: a full GitOps pipeline

Set up two repos — an app repo and a config repo — and a kind (or cloud) cluster. In the app repo, a GitHub Actions workflow lints, tests, builds a SHA-tagged image, and pushes it to GHCR. Bootstrap Flux against the config repo, where a base/ plus overlays/staging and overlays/production (Kustomize) describe the deployment, and image-automation bumps the tag back into Git. Promote a release from staging to production via a reviewed PR against the production overlay, store a secret with SOPS, and finally break a release and roll it back with a single git revert — proving the whole loop is auditable and self-healing with CI never holding cluster credentials.
