Half of "it works on my machine but not in prod" is networking. This lesson goes under the hood: how DNS resolves, what TCP and TLS actually do on the wire, how HTTP/1.1 vs 2 vs 3 differ, load-balancing algorithms, service discovery, and the tools to debug all of it.

DNS: name → address

Beginner Before any connection, the name resolves to an IP through a chain of caches and servers:

dig example.com            # the full resolution + answer section
dig +short example.com     # just the IP
dig example.com MX         # mail records; also A, AAAA, CNAME, TXT, NS
# Record types that bite: TTL (how long it's cached — low TTL before a migration),
# CNAME (alias → another name), A/AAAA (IPv4/IPv6).
The #1 DNS gotcha: caching/TTL. You change a record, it works for you, but others still hit the old IP for up to the TTL (and some resolvers ignore TTL). Before a cutover, lower the TTL (e.g. to 60s) a day ahead so the change propagates fast. "DNS propagation" delays are really just caches expiring.

TCP: the reliable connection

# The 3-way handshake opens a connection:
#   client → SYN → server
#   client ← SYN-ACK ← server
#   client → ACK → server   (now data flows)
ss -tnp                     # live TCP connections + owning process
ss -s                       # summary (established, time-wait…)
A pile of connections stuck in TIME_WAIT is normal (the OS holding a closed connection briefly); a pile in SYN-SENT or SYN-RECV suggests the other end isn't answering (firewall? wrong port? service down?). Reading connection states with ss tells you where a connection is failing.

TLS: the encrypted layer

# Inspect what a server presents (cert chain, protocol, SNI):
openssl s_client -connect example.com:443 -servername example.com </dev/null
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -dates

Intermediate TLS does a handshake (negotiate version + cipher, verify the server's certificate chain to a trusted CA, exchange keys), then encrypts the HTTP traffic. SNI (Server Name Indication) tells the server which cert to present when many sites share one IP — relevant to the reverse-proxy and TLS lessons.

HTTP/1.1 vs 2 vs 3

VersionKey traitFixes
HTTP/1.1One request at a time per connection (head-of-line blocking)—
HTTP/2Multiplexing many streams over one TCP connection; header compressionHTTP-level HOL blocking
HTTP/3Runs over QUIC (UDP), not TCPTCP-level HOL blocking; faster handshakes/reconnects
Common misread: enabling HTTP/2 "for speed" but terminating it at a proxy that then speaks HTTP/1.1 to the backend, so the multiplexing benefit stops at the edge — often fine, but know where each hop downgrades. And HTTP/2 over a lossy network can still suffer TCP head-of-line blocking (one lost packet stalls all streams) — exactly what HTTP/3's QUIC fixes.

Load-balancing algorithms

# How a load balancer picks a backend:
#   round-robin       — rotate evenly (default; fine for uniform requests)
#   least-connections — send to the backend with fewest active conns (uneven work)
#   ip-hash / consistent-hash — same client → same backend (sticky, cache affinity)
#   weighted          — bigger boxes get more traffic
# Plus HEALTH CHECKS: a backend failing its check is removed from rotation.
The health check is what makes a load balancer safe during deploys (it stops routing to a draining/unhealthy backend) — the same readiness-probe idea from the Advanced Kubernetes lesson, one layer out. L4 (TCP) vs L7 (HTTP) LBs: L7 can route by path/host and inspect requests; L4 is faster and protocol-agnostic (ties to the Reverse Proxies lesson).

Service discovery

Advanced In dynamic environments, backends come and go, so you can't hard-code IPs. Service discovery resolves a logical name to current healthy instances: Kubernetes does it via DNS (my-svc.my-ns.svc.cluster.local → the Service's endpoints); Consul and cloud service meshes do it with a registry + health checks.

Debugging the network

ping host                  # reachable at all? (ICMP — some hosts block it)
traceroute host            # the path + where it stalls
dig name                   # does the name resolve correctly?
curl -v https://host/      # full request/response incl. TLS + redirects
nc -zv host 443            # is the PORT open? (connection refused vs timeout matters)
tcpdump -i any port 443    # last resort: watch the actual packets
Connection refused vs timeout tells you the layer: "refused" = something answered and said no (service down, wrong port — the host is reachable). "Timed out" = nothing answered (firewall dropping packets, wrong IP, routing). Diagnosing in the wrong layer wastes the most time — resolve the name, confirm the port, then look at the app.

Exercises

  • Use dig to find a domain's A, CNAME, and TTL; explain what lowering the TTL before a migration buys you.
  • Inspect a site's TLS cert and expiry with openssl s_client.
  • Diagnose a deliberately-wrong endpoint: distinguish DNS failure vs connection-refused vs timeout using dig/nc/curl -v.

Mini-project: trace a request end to end

Pick a request to a service behind a load balancer and document every hop: DNS resolution (with TTL), the TCP handshake, TLS negotiation (version + cert chain), the HTTP version in use, which LB algorithm routes it and how the health check gates backends, and how the backend's name was discovered. Then simulate three failures (bad DNS, closed port, dead backend) and show the exact tool + signal that identifies each — a networking runbook that complements the Linux networking and DevOps TLS lessons.
