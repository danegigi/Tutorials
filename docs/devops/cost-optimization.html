Cloud bills grow quietly until someone asks "why are we spending this much?" FinOps makes cost a first-class engineering concern: make spend visible and attributable, then act on it — rightsizing, buying capacity smartly, and killing waste — in a continuous loop.

The FinOps loop

INFORM  →  OPTIMIZE  →  OPERATE  →  (back to INFORM)
visibility  rightsize,    make it a
& allocation spot/reserved  habit: budgets,
            kill waste     alerts, culture

Beginner You can't optimize what you can't see. Step one is always visibility: whose spend is this, on what, and is it going up?

Visibility starts with tagging

# Tag every resource so cost can be split by team / service / environment
tags = {
  team        = "payments"
  service     = "checkout-api"
  environment = "production"
  cost-center = "cc-4471"
}
# Then cost tools group the bill by tag → "payments spent $X on prod this month"
Untagged resources are the root of all cost confusion. If 40% of the bill is "untagged", no one owns it and no one optimizes it. Enforce tagging in your IaC (make the required tags a module input) and in policy (deny creation of untagged resources). Retrofitting tags onto a sprawling account is miserable — bake it in from the Terraform lesson onward.

The big levers

LeverIdeaTypical saving
RightsizingMatch instance size to actual usage (most are over-provisioned)large
Spot/preemptibleUse interruptible capacity for fault-tolerant workloadsup to ~70–90%
Reserved / Savings PlansCommit 1–3 yrs for steady baseline load~30–60%
AutoscalingScale to zero / down off-peak (dev envs at night)large
Storage tieringMove cold data to cheaper tiers; expire logsmoderate
Kill wasteUnattached disks, idle load balancers, old snapshots, zombie envsfree money
Rightsizing is usually the biggest, easiest win. Teams provision for peak-of-peak "to be safe" and then run at 10% utilization forever. Pull real CPU/memory metrics (the Observability lesson), size to the actual p95 plus headroom, and let autoscaling handle spikes. Pair reserved/savings-plan commitments with your steady baseline and spot with the burst on top.

Spot vs reserved: match to the workload

# Steady 24/7 baseline (e.g. always-on API)  → Reserved / Savings Plan (commit, save)
# Fault-tolerant / batch / stateless replicas → Spot (cheap, can be reclaimed)
# Spiky / unpredictable                        → On-demand + autoscaling
# A real cluster mixes all three (e.g. Karpenter picks spot where safe).
Common mistake: putting a stateful primary (a database, a singleton) on spot capacity. Spot can be reclaimed with ~2 minutes' notice — fine for a stateless replica behind a load balancer, a disaster for your only database node. Match the capacity type to the workload's tolerance for interruption.

Kubernetes cost

Intermediate In a shared cluster, the bill is one number but the usage is many teams. Tools like OpenCost/Kubecost allocate cost per namespace/label using each pod's requests. This is another reason the resource requests from the Advanced K8s lesson matter: wrong requests mean wrong cost allocation and wasted reserved capacity.

Operate: make it a habit

# Budgets + alerts so a runaway cost is caught in days, not at month-end
aws budgets ...        # alert at 80% / 100% of a monthly budget
# Anomaly detection flags a sudden spike (a misconfigured job, a leak)
# A monthly cost review per team, with spend shown next to the owning tag.

Exercises

  • Audit a cloud account (or a sample bill): what % is untagged, and what are the top 3 line items?
  • Pick a workload and decide the right capacity mix (on-demand / spot / reserved) with justification.
  • Find three "zombie" resources (unattached volume, idle LB, old snapshot) and estimate their monthly cost.

Mini-project: a cost-reduction plan

For a real or sample environment, produce a FinOps plan: enforce a tagging scheme in Terraform (required tags as module inputs), set a budget + anomaly alert, identify rightsizing candidates from utilization metrics, map each workload to the cheapest safe capacity type (spot/reserved/on-demand), schedule dev environments to scale to zero off-hours, and list waste to delete. Estimate the total monthly saving and which single change delivers the most.
