Before anyone can reach your server securely, three things have to work: a domain name must resolve to your server's address, a TLS certificate must prove the server is who it claims to be, and the two must be wired together. This lesson covers DNS record types, how the TLS handshake and certificate chain actually work, Let's Encrypt and the ACME protocol, pointing a registrar like GoDaddy at a server or load balancer, and AWS Certificate Manager.

DNS records

Beginner DNS is the phone book of the internet: it maps human names to machine addresses. A zone is the set of records for a domain, and each record has a type that says what it answers.

RecordMapsExample
AA name &rarr; an IPv4 addressexample.com &rarr; 203.0.113.10
AAAAA name &rarr; an IPv6 addressexample.com &rarr; 2001:db8::1
CNAMEA name &rarr; another name (alias)www &rarr; example.com
MXA domain &rarr; its mail servers (with priority)10 mail.example.com
TXTArbitrary text (verification, SPF, ACME challenges)"v=spf1 include:_spf.google.com ~all"
NSA zone &rarr; its authoritative nameserversns-123.awsdns-45.com
 
# Query records yourself with dig
dig example.com +short
# -> 203.0.113.10
dig NS example.com +short
# -> ns-123.awsdns-45.com.
dig TXT example.com +short
# -> "v=spf1 include:_spf.google.com ~all"

TTL (time to live) is how long resolvers may cache a record. A low TTL (e.g. 300s) makes changes propagate fast but increases query load; raise it once a record is stable.

You cannot put a CNAME on the apex (bare) domain example.com: the apex must also carry SOA and NS records, and a CNAME cannot coexist with other records. This single rule drives most of the domain-wiring decisions below.

How TLS/HTTPS works

Intermediate HTTPS is HTTP carried inside a TLS session. TLS gives you three guarantees: encryption (eavesdroppers see ciphertext), integrity (tampering is detected), and authentication (you are talking to the real server, proven by its certificate).

The handshake

When a browser connects to https://example.com:

  1. ClientHello — the client offers its TLS versions and cipher suites.
  2. ServerHello + certificate — the server picks a cipher and sends its certificate (containing its public key and the domain it is valid for).
  3. Verification — the client checks the certificate: is it for this hostname, unexpired, and signed by a trusted authority?
  4. Key exchange — both sides derive a shared symmetric session key (modern TLS 1.3 uses ephemeral Diffie-Hellman for forward secrecy).
  5. Encrypted session — all further traffic uses the fast symmetric key.

Asymmetric crypto (slow) is used only to establish trust and exchange keys; the bulk data then flows under symmetric crypto (fast).

The certificate chain

Your browser does not trust your server's certificate directly. It trusts a small set of root CAs baked into the OS/browser. Those roots sign intermediate CA certificates, which sign your leaf (server) certificate. The server must present the leaf and the intermediates (the fullchain.pem) so the client can build a path from leaf up to a trusted root.

# Inspect what a server actually serves
openssl s_client -connect example.com:443 -servername example.com < /dev/null \
  | openssl x509 -noout -subject -issuer -dates
# -> subject=CN = example.com
# -> issuer=C = US, O = Let's Encrypt, CN = R11
# -> notBefore=... notAfter=...
The #1 TLS deployment bug is serving the leaf certificate without its intermediates. Desktop browsers often cache the intermediate and seem fine, while mobile clients and API calls fail with "unable to get local issuer certificate." Always deploy the full chain.

Let's Encrypt & ACME

Intermediate Let's Encrypt is a free, automated certificate authority. ACME (Automatic Certificate Management Environment) is the protocol a client uses to prove domain control and get a certificate issued and renewed with no human in the loop. You prove control by solving a challenge:

  • HTTP-01 — the CA asks you to serve a specific token at http://your-domain/.well-known/acme-challenge/<token>. Simple; needs port 80 reachable.
  • DNS-01 — the CA asks you to publish a specific TXT record. Works behind a firewall and is the only method that can issue wildcard certs (*.example.com).
  • TLS-ALPN-01 — proof happens during a special TLS handshake on port 443 (what Traefik's tlschallenge uses).
# certbot: issue a cert for a domain served by Nginx (HTTP-01)
sudo certbot --nginx -d example.com -d www.example.com
# -> Successfully received certificate.
# -> Certificate is saved at: /etc/letsencrypt/live/example.com/fullchain.pem

# A systemd timer renews automatically; test the renewal path with:
sudo certbot renew --dry-run
# -> Congratulations, all simulated renewals succeeded
Let's Encrypt has strict rate limits (e.g. failed-authorization and duplicate-certificate caps per hour/week). While fixing a broken setup, test against the staging environment (its certs are untrusted but do not count against quotas) and stop retrying a failing challenge — each failure burns the quota and can lock you out of that domain for the cooldown window.

Wiring a domain to a server or load balancer

Intermediate Your domain is registered at a registrar like GoDaddy, and you need example.com to resolve to your server or load balancer. A single server has a fixed IP, which is easy. A load balancer typically has a DNS name whose underlying IPs rotate — which is where the apex-CNAME rule bites.

Pointing at a single server (fixed IP)

# In GoDaddy -> Domain -> DNS -> Manage Zones:
Type   Name   Value           TTL
A      @      203.0.113.10     600    # apex -> the server's IP
CNAME  www    example.com      600    # www aliases to the apex

Pointing at a load balancer (rotating IPs)

A load balancer gives you a name like my-alb-123.us-east-1.elb.amazonaws.com, not a stable IP — so you cannot use a plain A record, and a CNAME is illegal at the apex.

# Sub-domain is fine — CNAME to the LB's DNS name:
Type   Name   Value                                          TTL
CNAME  www    my-alb-123.us-east-1.elb.amazonaws.com          600

# Apex example.com — a CNAME is ILLEGAL here. Options:
#   - Use GoDaddy Forwarding to redirect example.com -> www.example.com
#   - Use a DNS provider with ANAME/ALIAS flattening at the apex
#   - Move DNS to Route 53 and use an ALIAS record (below)
A common mistake is "set the A record to the load balancer's DNS name." An A record only holds an IP, and the LB's IPs rotate — this breaks the moment AWS changes them. Use CNAME for sub-domains and ALIAS/ANAME (or forwarding) for the apex.

The clean path: Route 53 ALIAS

Route 53 solves the apex problem with an ALIAS record — it behaves like an A record at the apex but points at an AWS resource by name and tracks its changing IPs automatically. Keep the domain registered at GoDaddy but let Route 53 answer DNS:

# 1. Create a Public Hosted Zone for example.com in Route 53.
#    It gives you 4 nameservers, e.g. ns-123.awsdns-45.com ...

# 2. In GoDaddy -> Nameservers -> "Enter my own": replace GoDaddy's
#    nameservers with the 4 from Route 53. (Registration stays at GoDaddy.)

# 3. In the Route 53 zone, create ALIAS records:
#    example.com       A  ALIAS -> your ALB/NLB   (apex — works!)
#    www.example.com   A  ALIAS -> your ALB/NLB

# 4. Verify after propagation (minutes to a couple of hours):
dig NS example.com +short
dig example.com +short

AWS Certificate Manager (ACM)

Intermediate ACM issues free public TLS certificates for use with AWS load balancers and CloudFront, and renews them automatically. You never touch private key files — ACM holds them and the load balancer uses them.

Request a cert with DNS validation: ACM gives you a CNAME to add to your DNS; once it resolves, the cert is issued and auto-renews for as long as the record stays in place.

Type   Name                            Value
CNAME  _a1b2c3.example.com             _x9y8z7.acm-validations.aws.
# Request a cert (DNS validation) via the CLI
aws acm request-certificate \
  --domain-name example.com \
  --subject-alternative-names "*.example.com" \
  --validation-method DNS
# -> { "CertificateArn": "arn:aws:acm:us-east-1:...:certificate/abc-123" }
The certificate must live in the same region as the load balancer that uses it. The one exception is CloudFront, which always wants its certificate in us-east-1. Requesting a cert in the wrong region is a classic "why won't the HTTPS listener accept my cert" trap.

Attach the issued cert to an HTTPS listener and redirect HTTP to it:

aws elbv2 create-listener \
  --load-balancer-arn $ALB_ARN \
  --protocol HTTPS --port 443 \
  --certificates CertificateArn=$ACM_CERT_ARN \
  --ssl-policy ELBSecurityPolicy-TLS13-1-2-2021-06 \
  --default-actions Type=forward,TargetGroupArn=$TG_ARN

Common mistakes

Common mistakes
  • CNAME on the apex. Illegal — the bare domain already has SOA/NS records. Use ALIAS/ANAME or redirect to www.
  • Putting a DNS name in an A record. An A record holds an IP only; a load balancer's name must be a CNAME (sub-domain) or ALIAS (apex).
  • Serving the leaf cert without intermediates. Works in some desktop browsers, fails on mobile/API. Always deploy fullchain.pem.
  • ACM cert in the wrong region. Must match the load balancer's region (CloudFront excepted — always us-east-1).
  • Retrying a failing ACME challenge. Each failure burns the rate limit. Fix the root cause, test in staging, then issue once.
  • Expecting instant propagation. Nameserver changes follow the TLD's schedule (minutes to ~48h). Verify with dig before assuming the config is wrong.

Exercises

  • Use dig to pull the A, NS, and MX records of a domain you know, and explain what each answers.
  • Run openssl s_client -connect …:443 against a public site and read the subject, issuer, and validity dates of its certificate.
  • On a test server with a real domain, issue a Let's Encrypt cert with certbot (HTTP-01), then run certbot renew --dry-run.
  • Write the exact DNS records (apex + www) to point a GoDaddy domain at (a) a fixed-IP server and (b) an AWS load balancer, and justify each record type.
  • Request an ACM certificate with DNS validation and describe where the validation CNAME must live and why the cert must share the LB's region.

Mini-project: a domain to a secure site, end to end

Take a domain registered at GoDaddy and bring up a server (or AWS load balancer) serving a small app. Decide and implement the DNS wiring: a fixed-IP server gets an apex A record plus a www CNAME; a load balancer gets Route 53 ALIAS records (moving nameservers while keeping registration at GoDaddy). Obtain a trusted certificate — Let's Encrypt on the server, or ACM on the load balancer — validate the full chain with openssl s_client, confirm http:// redirects to https://, and verify renewal works (certbot dry-run, or confirm ACM auto-renew with the validation record in place).
