Security in DevOps ("DevSecOps") means building safeguards into the pipeline rather than bolting them on at the end. The high-leverage habits: least privilege, real secrets management, scanning dependencies and images, and securing the supply chain.

Least privilege, everywhere

Beginner Every identity — a human, a CI job, a container, a cloud role — should have the minimum permissions it needs and nothing more. When something is compromised, least privilege is what limits the damage.

# Bad: a CI role with AdministratorAccess
# Good: a role scoped to exactly the actions it performs
{ "Effect": "Allow", "Action": ["ecr:PutImage", "ecs:UpdateService"], "Resource": "arn:...:service/myapp" }
Containers: run as a non-root user, drop Linux capabilities, mount filesystems read-only where possible. A distroless or minimal base image has no shell and far fewer packages — less to exploit.

Secrets management

Secrets are credentials: DB passwords, API keys, signing keys, tokens. They must never live in source control or baked into images.

The cardinal sins: committing a .env with real keys, hard-coding a password in code, printing a secret in CI logs, or baking credentials into a Docker image layer (they persist in the image history even if a later layer "removes" them). If a secret is ever committed, consider it compromised — rotate it, don't just delete the commit.
# Inject secrets at runtime from a manager, never from the repo:
#   AWS Secrets Manager / SSM, HashiCorp Vault, Kubernetes Secrets,
#   GitHub Actions Secrets, Docker/Compose secrets.
# gitignore .env, scan the repo for leaked secrets (gitleaks, trufflehog) in CI.

Supply-chain security

Advanced Attacks increasingly target the build process, not the running app. Defenses:

  • Pin dependencies to exact versions + checksums (lockfiles); pin CI actions to a commit SHA, not a tag.
  • Watch for typosquats — a package named reqwests or colorsama is a red flag.
  • SBOM — generate a Software Bill of Materials so you know exactly what's in a build.
  • Sign artifacts (e.g. with cosign) and verify signatures before deploy.
Common mistake: running curl … | bash from an unpinned URL in a build, or using a Docker base tag like :latest. Both pull mutable, unverified content into your pipeline. Pin to digests (image@sha256:…) so a build is reproducible and can't be swapped under you.

The web app basics still apply

HTTPS everywhere, HttpOnly+Secure+SameSite cookies, input validation and parameterized queries (no SQL injection), output encoding (no XSS), and a security headers set (CSP, HSTS). The OWASP Top Ten is the canonical checklist.

Hardening checklists

Don't invent your hardening from scratch — the CIS Benchmarks give vetted, step-by-step hardening guides for Linux, Docker, Kubernetes, and the major clouds. Run kube-bench/docker-bench to check against them automatically.

Exercises

  • Scan a container image with Trivy and triage the HIGH/CRITICAL findings.
  • Add gitleaks to CI and confirm it fails the build on a planted fake secret.
  • Rewrite an over-privileged IAM/CI role down to the exact actions it needs.

Mini-project: secure the pipeline

Harden the GitHub Actions pipeline from the earlier lesson: add dependency + image + secret scanning that fails on critical findings, pin every action and base image to a digest, inject all secrets from a manager (none in the repo), run the container as non-root with a read-only root filesystem, and generate an SBOM artifact. Verify with a scan report showing zero criticals.
