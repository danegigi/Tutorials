DevOps is a way of working, not a tool you install. It closes the gap between writing software and running it by shortening feedback loops, sharing ownership, and automating everything repeatable. The tools in the rest of this section only matter in service of that.

The core idea: shorten the feedback loop

Beginner Every delay between making a change and learning whether it worked is waste and risk. DevOps attacks those delays: fast builds, automated tests, quick deploys, good observability. The faster you learn, the smaller and safer each change can be.

Small, frequent changes are less risky than large infrequent ones — each has a tiny blast radius and is easy to roll back. "Deploy more often to deploy more safely" sounds paradoxical until you internalize that big-bang releases are where incidents hide.

Shared ownership: "you build it, you run it"

The anti-pattern DevOps replaces: developers "throw code over the wall" to a separate ops team who get paged when it breaks but can't fix the code. When the people who write a service also operate it, incentives align — they feel the pain of flaky deploys and bad logging, so they fix it.

The CALMS lens

LetterPillarIn practice
CCultureBlameless, collaborative; dev and ops share goals.
AAutomationBuild, test, deploy, provision — scripted, not manual.
LLeanSmall batches, limit work-in-progress, remove waste.
MMeasurementInstrument everything; decide with data.
SSharingOpen knowledge, runbooks, postmortems.

Measuring what matters: the DORA metrics

Intermediate The DORA research program found four metrics that distinguish high-performing teams:

MetricQuestionElite ballpark
Deployment frequencyHow often do you ship?On demand (many/day)
Lead time for changesCommit → production?< 1 day
Change failure rate% of deploys causing a problem?0–15%
Time to restoreIncident → recovery?< 1 hour

Notice the balance: the first two reward speed, the last two reward stability. High performers get both — speed and stability are not a trade-off, they reinforce each other through automation and small batches.

Common mistake: gaming the metrics. Chasing "deploys per day" by splitting one release into ten does nothing; optimizing lead time by skipping tests spikes your change-failure rate. The metrics are a thermometer, not a target — improve the system (CI, test coverage, deploy automation) and the numbers follow.

Everything-as-code

The through-line of modern DevOps is putting everything in version control: application code, infrastructure (Terraform), configuration, pipelines (GitHub Actions YAML), and even the desired cluster state (GitOps). If it's in Git, it's reviewable, auditable, reproducible, and revertible. The rest of this section is largely "how to express X as code".

Exercises

  • Estimate the four DORA metrics for a project you know. Which is weakest, and what single automation would most improve it?
  • Identify one manual, repeated task in your workflow and sketch how you'd script it.
  • Write a one-paragraph "you build it, you run it" statement for a service: who's on call, where are the runbooks, what are the alerts?

Mini-project: a DevOps maturity assessment

For a real or hypothetical project, write a short assessment against CALMS and the four DORA metrics: where it is today, the single biggest bottleneck in its path from commit to production, and a concrete 3-step plan (e.g. "add CI tests → automate deploy → add deploy-frequency dashboard") to tighten the feedback loop. This frames every tool you'll adopt in the following lessons.
