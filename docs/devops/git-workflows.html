Git is the backbone of every DevOps workflow — the source of truth for code, infrastructure, and pipelines. Beyond the basic commands, what matters is a branching strategy that lets a team ship continuously, review changes, and roll back safely.

The commands you actually use

git status                       # what's changed
git add -p                       # stage hunks interactively (review as you stage)
git commit -m "fix: handle nil user"
git switch -c feat/rate-limit    # create + switch to a branch
git push -u origin feat/rate-limit
git pull --rebase                # update, replaying your commits on top (linear history)
git log --oneline --graph --all  # see the shape of history
Write commit messages in the imperative mood ("add X", not "added X") and keep the subject under ~50 chars with detail in the body. Conventional Commits (feat:, fix:, chore:) make history scannable and can drive automated changelogs/versioning.

Branching strategies

Intermediate Two dominant models:

Trunk-basedGitFlow
BranchesShort-lived feature branches off main; merge dailyLong-lived develop, release/*, hotfix/*
SuitsContinuous delivery, feature flagsScheduled releases, versioned products
RiskNeeds strong CI + flagsPainful merges, slow integration

Most modern teams doing continuous delivery use trunk-based: branch, open a PR within a day or two, merge to main, deploy. Long-lived branches drift and produce agonizing merges — the longer a branch lives, the more it hurts.

Pull requests and review

gh pr create --title "Add upload rate limiting" --body "…"
gh pr status
gh pr merge --squash   # squash the branch into one tidy commit on main

A PR is where code review, CI, and discussion converge. Keep them small (a reviewer can hold ~400 lines in their head, not 4000), with a description saying what changed, why, and how it was tested. Require green CI and at least one approval before merge via branch protection.

Rebase vs merge

# Rebase your feature branch onto the latest main (linear history)
git switch feat/x
git fetch origin
git rebase origin/main
# resolve conflicts, then:
git push --force-with-lease     # safe force-push: fails if someone else pushed
Golden rule: never rebase (or force-push) a branch others are working on — it rewrites history out from under them. Rebase your own unshared feature branch to keep it current; use plain merge for shared/long-lived branches. And prefer --force-with-lease over --force: it refuses to clobber work you haven't seen.

Undoing safely

git revert <sha>          # NEW commit that undoes a bad one — safe on shared history
git reset --soft HEAD~1   # undo last commit, keep changes staged (local only)
git restore --staged file # unstage
git reflog                # your safety net: find "lost" commits after a bad reset
git reset --hard and git clean -f permanently discard uncommitted work — there is no undo. On a shared branch, use git revert (which adds a new undo commit) rather than rewriting history. git reflog can rescue commits lost to a bad reset, but not uncommitted changes.

Hooks and automation

Intermediate Git hooks run scripts on events; teams use them (via tools like pre-commit or husky) to format, lint, and run fast tests before a commit or push — catching problems before CI even starts.

Exercises

  • Make a feature branch, commit with a Conventional Commit message, open a PR with gh, and squash-merge it.
  • Rebase a feature branch onto an updated main, resolve a conflict, and push with --force-with-lease.
  • Make a bad commit on main, then git revert it; explain why revert (not reset) is correct here.

Mini-project: a team workflow doc

Write a CONTRIBUTING.md defining your team's Git workflow: trunk-based with short feature branches, Conventional Commits, PRs with required green CI + one review via branch protection, squash-merge, and the rebase/force-with-lease rules. Add a pre-commit hook config that formats and lints. This is the exact artifact every well-run repo has.
