CI/CD is the automation that carries code from a commit to production. The three terms get blurred — continuous integration, continuous delivery, and continuous deployment are distinct stages, and knowing the difference tells you what to automate next.

The three C's, precisely

TermWhat's automatedHuman gate?
Continuous IntegrationEvery push is built & tested, merged to a shared branch often—
Continuous DeliveryEvery passing build is deployable and pushed to staging automaticallyYes — a human clicks "deploy to prod"
Continuous DeploymentEvery passing build goes to production automaticallyNo — fully automated

Beginner CI is the foundation everyone needs. Delivery vs deployment differ only by whether a human approves the final production step. Many teams do CD-to-staging + one-click prod (delivery); mature teams with strong tests and monitoring go all the way to continuous deployment.

Anatomy of a pipeline

push/PR → ┌─────────┐  ┌──────┐  ┌───────┐  ┌─────────┐  ┌────────┐
          │  build  │→ │ test │→ │ scan  │→ │ package │→ │ deploy │
          └─────────┘  └──────┘  └───────┘  └─────────┘  └────────┘
             compile    unit +    lint,      build the    staging →
             deps       integ.    SAST, deps  artifact/     (gate) →
                                   vuln scan   image         prod

Each stage is a gate: if it fails, the pipeline stops and nothing downstream runs. The ordering puts fast, cheap checks first (lint, unit tests) so failures surface in seconds, not after a slow build.

Artifacts and immutability

Intermediate A pipeline produces an artifact — a container image, a binary, a bundle — built once and promoted unchanged through environments. The same image you tested in staging is the one that runs in prod.

Common mistake: rebuilding the artifact for each environment ("build for staging", then "build for prod"). Now staging and prod are different binaries and you've tested the wrong thing. Build once, tag it (ideally with the commit SHA), and promote that exact artifact. Config differs per environment; the artifact does not.

Environments and promotion

dev  →  staging  →  production
       (auto)      (gated / auto)

# Config injected per environment (not baked into the artifact):
#   DATABASE_URL, API keys, feature flags → from env / secrets store

What belongs in CI

  • Build — compile, resolve dependencies (with caching so it's fast).
  • Test — unit first (seconds), then integration, then slower E2E.
  • Quality gates — formatting, linting, type-checking.
  • Security — dependency vulnerability scan, static analysis (SAST), image scan.
  • Package — build the immutable artifact and push to a registry.
Keep CI fast — a pipeline that takes 40 minutes gets bypassed and resented. Cache dependencies, parallelize test suites, run only affected tests where possible, and fail fast on the cheapest checks. Aim for under ~10 minutes to green.

Pipeline as code

Modern CI config lives in the repo (GitHub Actions YAML, GitLab CI, etc.) — versioned, reviewed, and changed via PR like any other code. The next lesson implements a real pipeline in GitHub Actions.

Rollbacks

CD is only safe if rolling back is trivial. Because artifacts are immutable and tagged, rollback is "redeploy the previous image tag" — fast and predictable. If rolling back is scary, you don't really have continuous delivery.

Exercises

  • Classify three real projects you know as doing CI only, continuous delivery, or continuous deployment — and justify it.
  • Draw the stages of a pipeline for a web app and mark which ones should fail fastest.
  • Explain, with the "build once" principle, why rebuilding per environment is a bug.

Mini-project: design a pipeline

For an app from the Go or Bun section, design (on paper or as a diagram) a full CI/CD pipeline: ordered stages with their gates, where the immutable artifact is built and tagged with the commit SHA, how it's promoted dev→staging→prod, where config/secrets are injected, and the exact rollback step.
