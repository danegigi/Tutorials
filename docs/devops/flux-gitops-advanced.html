The GitOps lesson covered the idea; this one is hands-on Flux. Flux is a set of controllers that run inside your cluster, continuously pulling from Git and reconciling the cluster to match. Here you'll wire up its source and apply controllers, drive Helm releases declaratively, automate image updates, structure multiple environments with Kustomize overlays, and watch Flux correct drift.

Why pull-based, in one paragraph

Beginner In a push pipeline, your CI system holds cluster credentials and runs kubectl apply from the outside. In GitOps with Flux, the cluster pulls: the controllers live in the cluster, read a Git repo they have access to, and apply changes themselves. CI never touches the cluster — it only builds images and commits manifests. That shrinks the blast radius (no cluster creds in CI), makes the cluster self-healing (it re-pulls and corrects drift on a schedule), and makes Git the audit log of every change.

Bootstrap Flux

flux check --pre                      # verify your cluster is compatible

export GITHUB_TOKEN=<a-pat-with-repo-scope>
flux bootstrap github \
  --owner=myorg --repository=fleet \
  --branch=main --path=./clusters/prod --personal

# This commits Flux's own manifests into the repo under clusters/prod/flux-system
# AND installs the controllers. Flux now manages itself from Git.
flux get all

Bootstrap is self-referential on purpose: Flux's own configuration lives in the repo it watches, so upgrading Flux is a commit like any other.

A source + a Kustomization

# A source: where to pull from, and how often
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata: { name: app, namespace: flux-system }
spec:
  interval: 1m
  url: https://github.com/myorg/app
  ref: { branch: main }
---
# What to build from that source and keep applied
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata: { name: app, namespace: flux-system }
spec:
  interval: 10m
  sourceRef: { kind: GitRepository, name: app }
  path: ./deploy/overlays/prod
  prune: true          # delete resources removed from Git
  wait: true           # wait for applied resources to become ready
  timeout: 5m
prune: true is what makes Git truly authoritative — remove a manifest from the repo and Flux deletes it from the cluster. Without pruning, deleted files leave orphaned resources running. It's also the setting that bites hardest if your path is wrong: double-check path before enabling prune.

HelmRelease: Helm without the client

Intermediate Instead of running helm upgrade from a pipeline, you declare a HelmRelease and the helm-controller reconciles it.

apiVersion: source.toolkit.fluxcd.io/v1
kind: HelmRepository
metadata: { name: bitnami, namespace: flux-system }
spec:
  interval: 1h
  url: https://charts.bitnami.com/bitnami
---
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata: { name: redis, namespace: data }
spec:
  interval: 10m
  chart:
    spec:
      chart: redis
      version: "20.x"            # a semver RANGE — see image automation below
      sourceRef: { kind: HelmRepository, name: bitnami, namespace: flux-system }
  values:
    architecture: standalone
  install: { remediation: { retries: 3 } }
  upgrade: { remediation: { retries: 3 } }   # auto-rollback on a failed upgrade

Image update automation

Advanced Flux can watch a container registry and commit the new tag back into Git itself — so even image bumps flow through Git and stay auditable.

apiVersion: image.toolkit.fluxcd.io/v1beta2
kind: ImageRepository
metadata: { name: app, namespace: flux-system }
spec: { image: ghcr.io/myorg/app, interval: 5m }
---
apiVersion: image.toolkit.fluxcd.io/v1beta2
kind: ImagePolicy
metadata: { name: app, namespace: flux-system }
spec:
  imageRepositoryRef: { name: app }
  policy: { semver: { range: ">=1.0.0" } }   # or a timestamp/numeric policy
# In the manifest, mark where the tag lives with a setter comment:
image: ghcr.io/myorg/app:1.2.3 # {"$imagepolicy": "flux-system:app"}
# ImageUpdateAutomation then commits "1.2.4" to Git when it appears,
# and the Kustomization applies it. The deploy is a Flux commit you can revert.
This closes the loop: CI builds & pushes an image → Flux detects the new tag → Flux commits the manifest change → Flux applies it. Rolling back a bad deploy is git revert, and Flux undoes it on the cluster.

Multi-environment with Kustomize overlays

Keep one base and per-environment overlays that patch it — the proven structure for dev/staging/prod from one source of truth.

deploy/
  base/
    kustomization.yaml       # resources: deployment.yaml, service.yaml
    deployment.yaml
  overlays/
    staging/
      kustomization.yaml     # bases: ../../base ; replicas patch ; namespace: staging
    prod/
      kustomization.yaml     # bases: ../../base ; replicas patch ; namespace: prod
# overlays/prod/kustomization.yaml
resources: [../../base]
namespace: prod
replicas:
  - { name: app, count: 4 }
patches:
  - path: resources-patch.yaml   # bump CPU/memory for prod

Then one Kustomization per environment points at its overlay path. A base change rolls out everywhere; an overlay change affects only that environment.

Watching reconciliation & drift correction

flux get kustomizations        # READY / SUSPENDED / last applied revision
flux get helmreleases -A
flux reconcile kustomization app --with-source   # force a pull now
flux suspend kustomization app                   # pause (e.g. during an incident)
flux resume kustomization app

# Prove self-healing: hand-edit a live resource, then watch Flux revert it
kubectl scale deploy/app --replicas=99 -n prod
flux reconcile kustomization app    # Flux resets it to the Git-declared count
Suspended ≠ safe forever. A suspended Kustomization stops reconciling, so a manual fix during an incident won't be reverted — but it also means Git drift accumulates silently. Resume it (and reconcile Git back to the fixed state) once the incident is over, or your repo and cluster diverge.

Secrets in a GitOps repo

You can't commit plaintext Secrets. The two common answers: SOPS (encrypt Secret files in Git; the kustomize-controller decrypts with a key held in the cluster) or the External Secrets Operator (commit a reference; it pulls the real value from Vault/cloud secret manager at runtime). Both keep Git authoritative without exposing the secret — see the Secrets Management lesson.

Common mistakes

  • Wrong path with prune: true — Flux prunes resources it thinks you removed, deleting live workloads. Verify the path renders what you expect with kustomize build first.
  • Still running kubectl apply by hand on a Flux-managed cluster — Flux reverts you, so you fight the controller instead of committing to Git.
  • Committing plaintext Secrets. Use SOPS or External Secrets.
  • Leaving a Kustomization suspended after an incident, so drift silently accumulates.
  • No upgrade remediation on HelmReleases, so a bad chart upgrade sticks instead of auto-rolling-back.
  • Mega-repo with one giant Kustomization — split by app/environment so a failure in one doesn't block the rest.

Exercises

  • Bootstrap Flux against a repo, add a GitRepository + Kustomization for a simple app, and confirm it deploys with flux get kustomizations.
  • Scale a Flux-managed Deployment by hand, then flux reconcile and watch it snap back — the drift-correction demo.
  • Convert a Helm install into a HelmRelease with auto-rollback remediation and prove a bad values change rolls back.
  • Build a base + staging/prod overlays with Kustomize, point one Kustomization per environment at them, and change a base value to see it roll out to both.
  • Set up ImagePolicy + ImageUpdateAutomation and push a new image tag; watch Flux commit the bump back to Git.

Mini-project

Build a complete GitOps fleet repo for a two-environment app: a Kustomize base with staging/prod overlays, one Flux Kustomization per environment with prune and health wait, a HelmRelease for a dependency (e.g. Redis) with auto-rollback remediation, image automation that commits new app tags into the staging overlay only, and SOPS-encrypted Secrets. Demonstrate the full loop: push a new image → Flux promotes it to staging via a Git commit → you promote to prod by editing the prod overlay → you simulate an incident by suspending prod, hand-patching, then resuming and reconciling Git back to truth.
