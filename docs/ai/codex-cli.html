Codex CLI is OpenAI's terminal-based coding agent. You describe a task in plain language, and it reads your codebase, proposes changes, runs commands, and iterates — with as much or as little involvement from you as you choose. This lesson covers install, the interactive TUI, non-interactive exec mode, code review, session management, the sandbox system, MCP servers, configuration, and the slash commands you'll use every day.

Install and sign in

Beginner

# Install via npm (the scoped package — NOT bare "codex")
npm install -g @openai/codex

# Or via Homebrew
brew install codex

# Verify
codex --version
# → codex 0.166.0

# Sign in (browser OAuth with ChatGPT account, or API key)
codex login
# → Opens browser for sign-in...
# → Or: codex login --with-api-key (reads OPENAI_API_KEY)

# Check you're signed in
codex login status
# → Signed in as user@example.com
The npm package is @openai/codex (scoped). The bare codex package is an unrelated 2012 project — installing it silently succeeds and does nothing useful. Always use npm install -g @openai/codex.

Interactive mode (the TUI)

Beginner Run codex with no arguments to start an interactive terminal session in the current directory. You type a task in plain language; the agent reads files, proposes edits, and runs commands, asking for approval before changes land.

# Start an interactive session in the current repo
codex
# → Interactive TUI opens
# > Fix the failing tests in the auth package

# The agent will:
# 1. Run the tests (with your approval)
# 2. Read the failing test + the source file
# 3. Propose an edit (review and approve or reject)
# 4. Re-run the tests to verify
# 5. Report the result

# Start with an initial prompt
codex "Explain the build process in this repo"

# Start in a specific directory
codex -C /path/to/project

# Attach an image (screenshot of an error, UI mockup)
codex -i screenshot.png "Fix the layout shown in this screenshot"

# Use a specific model
codex -m o3 "Refactor this for readability"
codex -m gpt-4.1 "Write tests for the auth module"

Non-interactive mode (exec)

Intermediate codex exec runs a task without interactive prompts and streams output to stdout. This is the mode you use in scripts, CI pipelines, and automation:

# Run a task non-interactively
codex exec "Fix the failing tests"
codex exec "Add error handling to every API endpoint"

# Output as JSONL (one JSON event per line — for scripts)
codex exec --json "Summarize the architecture"
# → {"type":"message","content":"The project is a..."}
# → {"type":"tool_use","tool":"read_file",...}
# → {"type":"message","content":"In summary..."}

# Save the agent's last message to a file
codex exec -o /tmp/result.txt "List all TODO comments"

# Run in a specific directory
codex exec -C /path/to/project "Run the linter and fix issues"

# Run outside a git repo (normally Codex requires one)
codex exec --skip-git-repo-check "Explain this file"

# Run with a specific model and reasoning effort
codex exec -m o3 -c model_reasoning_effort='"xhigh"' "Find the race condition"

Sandbox modes for exec

# read-only: the agent can read but not write (safe, good for analysis)
codex exec -s read-only "Explain this codebase"

# workspace-write: can write in the repo (default for most tasks)
codex exec -s workspace-write "Fix the bug in auth.go"

# danger-full-access: no restrictions (rare, only in hardened environments)
codex exec -s danger-full-access "Install dependencies and run setup"

# Approval policy (must appear BEFORE exec):
codex -a never exec -s workspace-write "Fix the tests"     # never ask (CI)
codex -a on-request exec "Refactor the models"              # ask when it wants to (default)
For CI and automation, always set the approval policy explicitly: codex -a never exec -s workspace-write "...". Without -a never, the agent will wait for approval that never comes and hang. The -a flag is global and must appear before the exec subcommand.

Resuming and forking sessions

# Resume the last session (interactively)
codex resume

# Resume non-interactively
codex exec resume --last "Continue with the tests"

# Fork a previous session into a new thread
codex exec fork SESSION_ID "Try a different approach"

# Fork interactively
codex fork

Code review

Intermediate codex review analyzes code changes non-interactively and prints results to stdout. It doesn't modify files — it's a reviewer, not an editor:

# Review uncommitted changes (staged, unstaged, untracked)
codex review --uncommitted

# Review changes against a base branch
codex review --base main

# Review a specific commit
codex review --commit abc1234

# Review with custom instructions (focus on security)
codex review "Focus on SQL injection and authentication issues"

# Review with custom instructions via stdin
echo "Check for goroutine leaks" | codex review -

# Output as JSON (for CI integration)
codex exec review --uncommitted --json

Session management

Intermediate Non-ephemeral sessions are saved locally. You can resume, fork, archive, or delete them:

# Resume an interactive session (session picker)
codex resume

# Archive a session (removes from picker, keeps transcript)
codex archive SESSION

# Restore an archived session
codex unarchive SESSION

# Permanently delete a session
codex delete SESSION

# List sessions (in the TUI, use the session picker)
# In the TUI: /resume

Slash commands (in the TUI)

Intermediate Inside the interactive TUI, type / to open the command list. The most useful ones:

CommandPurpose
/new [name]Start a new chat
/resume [ID]Resume a saved session
/model [id]Choose or change the model (and reasoning effort)
/compactSummarize conversation to free context space
/diffShow the Git diff (including untracked files)
/clearClear terminal and start a fresh chat
/initGenerate an AGENTS.md scaffold for project context
/mcpList MCP tools (verbose shows details)
/memoriesConfigure memory use and generation
/plan [prompt]Switch to plan mode (read-only, no writes)
/skillsBrowse and use skills
/configOpen settings search and change options
/themeChoose syntax highlighting theme
/export [path]Export the conversation as Markdown
/usage [daily|weekly]View account token usage
/quitExit (alias: /exit)
 
# In the TUI:
/model gpt-4.1 --reasoning=high    # switch model + reasoning
/init                                # generate AGENTS.md scaffold
/compact                             # free context when the session gets long
/diff                                # see what the agent has changed

Sandbox modes (deep dive)

Advanced The sandbox limits what model-generated shell commands can do. Codex uses OS-native sandboxing — Seatbelt on macOS, Bubblewrap on Linux:

ModeFile writesNetworkUse case
read-onlyNowhereBlocked by defaultQuestions, explanations, code analysis
workspace-writeWorkspace + permitted roots + tempBlocked by default (can enable)Default for most tasks
danger-full-accessOS permissions (anywhere)YesOnly when truly needed (e.g., installing deps)
 
# Grant additional writable directories
codex --add-dir ../backend exec "Fix the shared types"

# Run any command inside the sandbox (without the agent)
codex sandbox -- npm test
codex sandbox -- go build ./...

# Approval policies (global flag, before subcommand)
codex -a on-request exec "..."   # model decides when to ask (default)
codex -a never exec "..."         # never asks (for CI)
codex --approve-for-me exec "..." # auto-reviews within sandbox
--yolo (alias for --dangerously-bypass-approvals-and-sandbox) disables all safety. Use it only inside an externally hardened container or VM. On your development machine, it lets the model run any command, including destructive ones, without asking.

MCP servers

Advanced Codex can connect to MCP (Model Context Protocol) servers for extra tools — databases, APIs, GitHub, and more:

# Add an MCP server (stdio)
codex mcp add github -- npx -y @modelcontextprotocol/server-github

# Add an HTTP MCP server
codex mcp add my-api --transport http --url https://api.example.com/mcp

# List configured MCP servers
codex mcp list

# Show a server's configuration
codex mcp get github

# Remove a server
codex mcp remove github

# OAuth login for an MCP server
codex mcp login github

# Inside the TUI: list MCP tools
/mcp           # list tools
/mcp verbose   # show details

Configuration (config.toml)

Advanced Base configuration lives at ~/.codex/config.toml. Named profiles use separate files like ~/.codex/quick.config.toml, loaded with --profile:

# ~/.codex/config.toml — base configuration

model = "gpt-4.1"
model_reasoning_effort = "high"
web_search = "cached"       # "cached" (default), "live", "disabled"

# Named profile (loaded with codex -p thorough)
# Lives in ~/.codex/thorough.config.toml (separate file since v0.134)

# Use a named profile
codex -p thorough "Complex refactoring task"

# Override config on the fly (TOML syntax)
codex -c model_reasoning_effort='"xhigh"' "Hard reasoning problem"
codex -c model='"o3"' "Find the subtle bug"

# Enable/disable a feature flag for one run
codex --enable shell_snapshot exec "..."
codex --disable shell_snapshot exec "..."

# Run with a local Ollama model
codex --oss --local-provider ollama "Explain this code"

Key config options

OptionValuesNotes
modelModel id stringDefault model for all sessions
model_reasoning_effort"xhigh", "high", "medium", "low"Reasoning depth for complex tasks
web_search"cached", "live", "disabled"Cached is default (cheaper); live for current info

Cloud mode

Advanced Codex Cloud runs tasks in a remote sandbox environment. This is useful for long-running tasks or when you don't want to tie up your local machine:

# Submit a cloud task (requires --env)
codex cloud exec --env ENV_ID "Run the full test suite and fix failures"

# List cloud tasks
codex cloud list
codex cloud list --json --limit 5

# Check status
codex cloud status TASK_ID

# Show the diff of a cloud task
codex cloud diff TASK_ID

# Apply a cloud task's diff locally
codex cloud apply TASK_ID

Diagnostics and troubleshooting

# Check installation, config, sign-in, runtime, and git health
codex doctor
codex doctor --summary

# Print the model catalog as JSON
codex debug models
codex debug models --bundled    # only bundled, without refreshing

# Print the model-visible prompt (system instructions + context) as JSON
codex debug prompt-input

# Check for updates and install
codex update

# Generate shell completions
codex completion zsh   # or: bash, fish, elvish, powershell

Common troubleshooting

ProblemFix
Authentication failscodex logout, then codex login
codex exec hangsApproval policy needs confirmation in unattended mode. Use -a never -s workspace-write
Command blocked in sandboxUse --add-dir for extra write paths, or danger-full-access deliberately
MCP server won't connectCheck codex mcp get <name>, then remove and re-add
Session won't resumeSession was started with --ephemeral. Restart without it
Codex won't start after updateRun codex --strict-config and codex doctor --summary

Common mistakes

  • Installing the wrong npm package. Use @openai/codex, not bare codex. The wrong package installs silently and does nothing.
  • Forgetting -a never in CI. Without it, codex exec waits for approval that never comes and hangs. The approval flag must appear before exec.
  • Using --yolo on your dev machine. It disables the sandbox entirely. Only use it in a throwaway container.
  • Not setting a model. The default model may not be the best for your task. Use /model in the TUI or -m on the CLI.
  • Letting context grow without compaction. Long sessions fill the window. Use /compact when the agent starts losing track.
  • Expecting codex exec to behave like the TUI. Exec is non-interactive — it doesn't prompt for approval (unless you set on-request), and it streams to stdout. For pair-programming, use the TUI.
  • Running codex exec outside a git repo without --skip-git-repo-check. Codex requires a git repo by default. Add the flag if you're outside one.

Exercises

  1. Install Codex CLI, sign in, and start an interactive session. Ask it to "explain the project structure." Observe how it reads files and reasons about them.
  2. Run codex review --uncommitted after making a small change to a file. Read the review output — does it catch real issues?
  3. Set up a CI-style non-interactive run: codex -a never exec -s workspace-write "Add a README section about testing". Observe the JSON output with --json.
  4. Configure an MCP server (e.g., the filesystem server) and ask Codex to use it. List the available tools with /mcp in the TUI.
  5. Generate an AGENTS.md scaffold with /init, customize it with 5 project-specific rules, and run a session with and without it. Compare the output.

Mini-project: Set up a Codex CI pipeline

Write a GitHub Actions workflow that runs codex exec --json -a never -s workspace-write "Review the PR diff and output issues as JSON" on every pull request. Pipe the JSON output to a script that parses the issues and posts them as a PR comment. Use codex review --uncommitted --json as an alternative. Test the pipeline on a PR with a deliberate bug (unused variable, missing error check) and verify the review catches it.
