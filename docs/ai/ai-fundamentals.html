Every AI coding tool — Ollama, Codex CLI, Kiro CLI, ChatGPT — runs on the same engine: a large language model (LLM). This lesson is the mental model that makes the rest of the AI section click. No math, no theory you'll never use. Just the concepts you need to prompt well, pick the right model, and understand what an agent is actually doing when it reads your codebase.

What an LLM actually is

Beginner A large language model is a next-token predictor. You give it a sequence of tokens, and it predicts the most likely next one. Do that in a loop, feeding each prediction back in, and you get text generation.

That's it. There's no database lookup, no search, no reasoning engine underneath. The model is a giant statistical function, trained on billions of tokens of text, that has learned which token typically follows which. The "intelligence" is an emergent property of that statistical model being very, very large and trained on very, very much data.

Tokens, not words

Models don't see words — they see tokens. A token is a chunk of text, roughly 4 characters or ¾ of a word in English. "Understanding" is one token. "Understanding tokens" is three tokens: Understand + ing + tokens.

"Hello world"         → 2 tokens
"Hello, world!"        → 4 tokens  (comma and exclamation are separate)
"def fibonacci(n):"    → 6 tokens

This matters because everything is priced and limited in tokens: API costs are per-token, context windows are token-limited, and your prompt's token count determines how much the model can "remember" at once.

A rough rule: 1 token ≈ 4 characters ≈ 0.75 English words. 100 tokens ≈ 75 words. A 4,000-token context window holds roughly 3,000 words — about 6 pages of text.

The context window

Beginner The context window is the maximum number of tokens the model can consider at once — your prompt plus the model's response plus any conversation history, all together. If the window is 128K tokens, the model can "see" about 96,000 words of input and output combined.

Window sizeWhat it fits (rough)Use case
4K tokens~3,000 words (6 pages)Short prompts, quick questions
32K tokens~24,000 words (48 pages)Medium files, multi-turn chat
128K tokens~96,000 words (a novel)Full codebases, long docs, agentic context
1M+ tokens~750,000 words (a textbook)Entire repositories, multi-file analysis

When the conversation exceeds the window, the model forgets the oldest messages. This is why long agentic sessions eventually lose the thread — the early context falls out of the window. Tools like /compact (in Kiro CLI and Codex) summarize older history to reclaim space.

The context window is a budget, not a free buffer. Every token in the window costs latency and money on every turn, and models pay less attention to things buried deep in a long context. Cramming 100K tokens of code into the prompt "just in case" makes the model slower, more expensive, and less accurate at finding the relevant parts.

Temperature and sampling

Beginner Temperature controls how random the model's token choices are. At temperature 0, the model always picks the single most likely next token — deterministic, repetitive, "safe." At temperature 1, it samples from the full probability distribution — creative, varied, sometimes surprising.

TemperatureBehaviorWhen to use
0Deterministic — always the same output for the same inputCode generation, data extraction, JSON output, tests
0.3–0.5Focused but allows slight variationDocumentation, explanations, refactoring suggestions
0.7Balanced — default for most chat interfacesGeneral chat, brainstorming, debugging help
1.0+Creative, unpredictableCreative writing, idea generation, naming
 
# API call with temperature 0 (deterministic)
curl http://localhost:11434/api/generate -d '{
  "model": "llama3.2",
  "prompt": "What is 2+2?",
  "stream": false,
  "options": { "temperature": 0 }
}'
# → "2+2 equals 4."  (same every time)

# Same call with temperature 0.9
# → "Well, 2 plus 2 equals 4. That's one of the most basic..."
# → (different wording every time, sometimes wanders)

For code and structured output, use temperature 0 (or as low as the API allows). You want the model's best guess, not a creative interpretation. For brainstorming or writing prose, higher temperature helps.

System, user, and assistant roles

Beginner LLM conversations are structured into roles, not just a blob of text. Every message has a role, and the role shapes how the model interprets it:

  • System — the instruction that defines the model's behavior, persona, and constraints. Set once at the start. "You are a senior Go engineer. Always explain trade-offs. Never use any."
  • User — your messages and questions. "Why is my goroutine leaking?"
  • Assistant — the model's responses. The model generates these, and they're fed back in as context for the next turn.
// The three roles in an API call
{
  "model": "llama3.2",
  "messages": [
    { "role": "system",    "content": "You are a concise programming teacher." },
    { "role": "user",      "content": "What is a goroutine?" },
    { "role": "assistant", "content": "A goroutine is a lightweight thread..." },
    { "role": "user",      "content": "How do I stop one?" }
  ]
}

The system message is the most powerful single tool you have. It's where you set the rules the model follows for the entire conversation — tone, format, what to refuse, what to prioritize. When an agent behaves consistently across a long session, it's because the system prompt is doing the work.

Think of the system message as a job description and the user messages as the day-to-day tasks. A vague job description ("be helpful") gives you a model that does whatever seems helpful in the moment. A specific one ("you are a code reviewer who flags security issues and suggests tests") gives you consistent, predictable behavior.

Chat vs. instruct vs. base models

Intermediate Not all models are the same kind:

  • Base models are raw next-token predictors. You give them text, they continue it. The quick brown fox → jumps over the lazy dog. Good for completion, bad for following instructions.
  • Instruct (chat) models are fine-tuned to follow the system/user/assistant format. You give them a question, they answer it. This is what you actually use — every model named "instruct", "chat", or "turbo" is this kind.
  • Reasoning models (o1, o3, etc.) add an internal "thinking" step before answering. They're slower and more expensive but better at multi-step reasoning, math, and complex planning. The reasoning_effort setting (low/medium/high) controls how much thinking they do.
# Base model: just continues text
"def fibonacci(n):"
→ "    if n <= 1:\n        return n\n    return fibonacci(n-1)..."  (completion)

# Instruct model: follows the instruction
"Write a Python fibonacci function with a docstring"
→ "def fibonacci(n):\n    \"\"\"Return the nth Fibonacci number.\"\"\"\n    ..."  (instruction-following)

# Reasoning model: thinks first, then answers
"Solve: if 3x + 7 = 22, what is x?"
→ (thinking: subtract 7 from both sides → 3x = 15 → x = 5)
→ "x = 5"

How models are trained (the 90-second version)

Intermediate You don't need the details, but the high-level shape explains a lot of model behavior:

  1. Pre-training — the model reads trillions of tokens and learns to predict the next token. This gives it language fluency, factual knowledge, and reasoning patterns, but no ability to follow instructions. A pre-trained model completes text; it doesn't answer questions.
  2. Instruction fine-tuning — the model is trained on high-quality question-answer pairs so it learns the system/user/assistant format. This is what makes a "chat" model.
  3. RLHF / preference tuning — humans rate model outputs, and the model is adjusted to prefer outputs humans liked. This is what makes a model "helpful" rather than just fluent.

Why this matters: the model's knowledge is frozen at training time. It has no live database. When it "knows" something, it's because the pattern appeared enough times in training data. When it's wrong, it's because the pattern was rare, ambiguous, or outdated — and the model has no way to check.

Hallucination, and why it's not a bug

Intermediate A model that predicts the next token will always produce fluent, confident text, whether or not it's true. It has no concept of "I don't know." If the most likely continuation of "The capital of France is" is "Paris," great. But if you ask "What is the population of Springfield?" it will confidently say a number, because "a number" is the most likely-shaped continuation — even though it has no way to know which Springfield you mean.

This is hallucination, and it's the model working as designed, not malfunctioning. The defense is structural:

  • Grounding — give the model the facts in the prompt ("here's the docs page, answer based on it").
  • Tools — let the model call out to a database, API, or search instead of guessing.
  • Constraints — instruct it to say "I don't know" when uncertain, or to only use provided context.
  • Verification — never trust model output for facts you can't verify. Read the code, run the test, check the docs.
Hallucination in code is especially dangerous because the model produces syntax-valid code that looks correct. A fabricated API method that doesn't exist, a library version that changed, a function signature that's wrong — it all compiles in your head and sometimes even in the editor, then fails at runtime. Always read what the model writes, and run the tests.

Parameter count and what it means

Models are sized by parameters (the trainable weights). More parameters generally means smarter but slower and more memory-hungry:

SizeRAM needed (quantized)QualitySpeed
1–3B2–4 GBBasic tasks, simple codeVery fast
7–8B5–8 GBGood for general useFast on modern hardware
14–32B10–20 GBStrong, near-frontier on many tasksNeeds a good GPU or lots of RAM
70B+40+ GBFrontier-class, best qualityNeeds multiple GPUs or is slow

Quantization shrinks the model (e.g., from 16-bit to 4-bit floats) to fit in less memory at a small quality cost. When Ollama says llama3.2:3b, the 3b means 3 billion parameters, and it's pre-quantized to run on a laptop.

What "multimodal" means

Advanced A multimodal model can process more than text — images, audio, or video alongside text. This lets you paste a screenshot of an error, a UI mockup, or a diagram and ask about it.

# Ollama: run a vision model
ollama run llava
>>> What's in this image? [paste image]
The image shows a terminal with a stack trace...

# API: send an image (base64-encoded)
curl http://localhost:11434/api/chat -d '{
  "model": "llava",
  "messages": [{
    "role": "user",
    "content": "What error is shown?",
    "images": ["iVBORw0KGgo..."]
  }]
}'

For coding agents, multimodal means the agent can read screenshots (for UI work), diagrams (for architecture), and paste error output visually — not just as text. Most modern models (GPT-4o, Claude 3.5+, Gemini, Llama 3.2 Vision) are multimodal.

Embeddings (the other side of LLMs)

Advanced Embeddings are vectors — lists of numbers — that represent the meaning of a piece of text. Text with similar meaning gets similar vectors. They're how search, RAG (retrieval-augmented generation), and "semantic" code search work.

# Ollama embeddings API
curl http://localhost:11434/api/embeddings -d '{
  "model": "nomic-embed-text",
  "prompt": "How do I fix a goroutine leak?"
}'
# → {"embedding": [0.123, -0.456, 0.789, ...]}  (a vector)

# Cosine similarity between two embeddings
# "goroutine leak"     → [0.12, -0.45, ...]
# "Go memory leak"     → [0.11, -0.42, ...]   ← similar!
# "chocolate cake"     → [0.89,  0.23, ...]   ← very different

Embeddings power features like "find related code," "search the docs semantically," and the knowledge bases behind tools like Kiro's Knowledge feature. You embed your documents, store the vectors, and at query time embed the query and find the closest matches — no keyword search needed.

Common mistakes

  • Treating the model as a database. It has no live data. Everything it "knows" was in its training data, which is frozen in time. Use tools or provide context for anything current.
  • Cramming the context window. More context isn't always better. Models lose signal in long prompts. Include what's relevant, not everything.
  • Using high temperature for code. Creative temperature makes code less reliable. Use temperature 0 for deterministic output.
  • Trusting syntax-valid code. The model writes code that looks right even when it's wrong. A method name can be fabricated, a library version can have changed. Always read and run.
  • Forgetting the system message. Without a system message, the model defaults to "generic helpful assistant." A specific system message is the single biggest lever for consistent behavior.
  • Confusing parameters with quality linearly. A 70B model isn't 10x smarter than a 7B. Diminishing returns are real. A 7B model on a task it's good at can outperform a 70B on a task it isn't.

Exercises

  1. Estimate the token count of this lesson's HTML fragment. How many tokens is ~2,000 words?
  2. Call a local model (via Ollama) with temperature 0 and temperature 1, asking it to "write a haiku about Linux." Compare the outputs across 5 runs each. How stable is temperature 0?
  3. Write a system message that makes a model refuse to use any in TypeScript and always explain trade-offs. Test it with "write a function that takes any argument."
  4. Pick two related concepts (e.g., "goroutine" and "thread") and two unrelated ones ("goroutine" and "pizza"). Generate embeddings for each pair and compute cosine similarity. Verify the related pair scores higher.

Mini-project: Build a model comparison script

Write a Bun script that calls a local Ollama model with the same prompt at three different temperatures (0, 0.5, 1.0), runs each 5 times, and prints the outputs side by side. The prompt should be a code-generation task ("write a Go function that reads a JSON file and prints the keys"). Observe: how does temperature affect consistency, correctness, and creativity? Which temperature gives the most reliable code?
