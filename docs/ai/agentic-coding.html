An AI coding agent is not a chatbot that writes code snippets. It's an LLM wired into a loop: it reads files, writes code, runs commands, sees the output, and adjusts — the same cycle a human developer goes through, but automated and fast. This lesson covers what makes an agent work, when the agentic loop helps versus when it hurts, and the safety mechanisms (sandboxes, approvals, context management) that keep a model with a shell from destroying your machine.

What an agent actually is

Beginner The core of every coding agent is the same loop:

loop:
    1. READ  — the model reads the task + current state (files, errors, output)
    2. THINK — the model decides what to do next
    3. ACT   — the model calls a tool (write file, run command, search)
    4. OBSERVE — the tool's output is fed back into the model's context
    5. goto 1  (until the task is done or the model asks for help)

That's it. The "agent" is the loop, not the model. The model is the brain; the loop is the body. Without the loop, the model is just a chatbot that suggests code. With the loop, it can actually do things — read your codebase, write files, run tests, fix errors, and iterate until it works.

The tools an agent has access to determine what it can do:

ToolWhat it lets the agent do
read_file / searchSee your codebase — read files, grep for patterns, find definitions
write_file / editModify your files — create, edit, delete
shell / executeRun commands — build, test, install deps, git
web_fetch / web_searchRead external docs, look up current APIs
mcp serversConnect to external tools — databases, APIs, GitHub, issue trackers

Function calling (how the model "calls" a tool)

Beginner The model doesn't execute commands directly. Instead, it outputs a structured tool call — a request to run a specific tool with specific arguments — and the agent harness (the software running the loop) executes it and returns the result.

// The model sees the task and available tools:
"Fix the failing test in auth_test.go. You can use:
  - read_file(path): read a file
  - run_command(cmd): execute a shell command
  - edit_file(path, old, new): replace text in a file"

// The model outputs a tool call (not prose):
{ "tool": "run_command", "args": { "cmd": "go test ./auth/ -v" } }

// The harness runs it, captures the output, and feeds it back:
"--- FAIL: TestLogin (0.00s)
    auth_test.go:42: expected status 200, got 401"

// The model now has the error in context, and decides the next step:
{ "tool": "read_file", "args": { "path": "auth/auth.go" } }
// ... reads the file, finds the bug, calls edit_file ...

This is called function calling or tool use, and it's the mechanism that turns a text predictor into an agent. The model doesn't have a shell — it asks the harness to run things, and the harness decides whether to allow it.

The harness is the safety boundary. The model can request any tool call, but the harness decides whether to execute it, ask for human approval, or block it. This separation is why sandboxes and approval policies work — the model is never running code directly on your machine.

The agentic loop in practice

Intermediate Here's what a real agent session looks like when you ask it to "fix the failing tests":

$ codex exec "Fix the failing tests"
# Turn 1:
  Model: run_command("go test ./... 2>&1 | grep FAIL")
  Output: "--- FAIL: TestUserValidation (user_test.go:15)"

# Turn 2:
  Model: read_file("user/user.go")
  Output: (the file contents, ~200 lines)

# Turn 3:
  Model: read_file("user/user_test.go")
  Output: (the test file, line 15 checks for empty email)

# Turn 4:
  Model: "The validation function doesn't reject empty emails.
          Line 23: if email == \"\" should be if email == \"\" { return error }"
  Model: edit_file("user/user.go",
                   "if email != \"\" {",
                   "if email == \"\" {\n\t\treturn errors.New(\"email required\")\n\t}\n\tif email != \"\" {")

# Turn 5:
  Model: run_command("go test ./user/ -v")
  Output: "PASS  ok  user  0.003s"

# Turn 6:
  Model: "Fixed. The validation was missing an empty-email check. Test now passes."

Notice what happened: the agent didn't need you to tell it which file to look at. It ran the tests, read the output, read the relevant files, made the fix, and verified it — all in one loop. That's the difference between a chatbot (you paste the error and the code, it guesses the fix) and an agent (it finds the error, finds the code, fixes it, and checks the result itself).

Context management: the agent's biggest constraint

Intermediate Every tool call output goes into the model's context window. Read a 500-line file? That's ~2,000 tokens in context. Run a test that prints 100 lines? Another ~500 tokens. After 20 tool calls, you might have 40,000 tokens of context — and if the window is 128K, you're a third of the way to full.

This is the agent's fundamental tension: more tool calls = more information = more context consumed. Eventually the context fills up, and the oldest outputs fall out of the window. If the agent read a file early in the session and needs it again 30 turns later, it may have to re-read it.

Agents manage context with several strategies:

  • Compaction — summarize older conversation history into a short summary, freeing the window. Both Codex (/compact) and Kiro CLI (/compact) support this.
  • Selective reads — read only the relevant part of a file (grep for a function, read a line range), not the whole thing.
  • Sub-agents — delegate a subtask to a separate agent session with its own fresh context window, then bring back just the result. Kiro CLI's /spawn and Codex's subagent features do this.
  • Session forking — branch off a new session from a checkpoint, so the fork has a clean window but the same starting state.
When an agent "forgets" something it knew earlier, it's usually not a bug — it's context eviction. The old output fell out of the window. If you see an agent re-reading a file it already read, or repeating a step it already did, the context was compacted or evicted. This is expected behavior, not a malfunction.

Sandboxes: keeping the model from wrecking your machine

Advanced An agent with shell access can run any command — including destructive ones. The model might decide to rm -rf a directory, git reset --hard, or install a package that overwrites your config. Sandboxes prevent this by restricting what the agent can do.

Every serious coding agent implements a sandbox:

ToolSandbox mechanismModes
Codex CLIOS-native sandboxing (Seatbelt on macOS, Bubblewrap on Linux)read-only, workspace-write, danger-full-access
Kiro CLICapability-based permissions (permissions.yaml)allow / ask / deny per capability (fs_read, fs_write, shell, mcp)
ManualRun in a container or VMDocker, Podman, or a VM
 
# Codex CLI sandbox modes
codex -s read-only exec "explain this codebase"       # can read, cannot write
codex -s workspace-write exec "fix the bug"            # can write in the repo (default)
codex -s danger-full-access exec "install dependencies" # can do anything (rare, risky)

# Kiro CLI: capability rules in ~/.kiro/settings/permissions.yaml
rules:
  - capability: fs_write
    effect: ask         # ask before writing files
  - capability: shell
    effect: ask         # ask before running commands
  - capability: fs_read
    effect: allow       # always allow reads
  - capability: shell
    effect: deny
    match: "rm -rf *"   # never allow recursive deletes
Sandbox modes exist for a reason. danger-full-access (Codex) or --yolo bypasses all safety. Use it only inside a throwaway container or VM, never on your development machine. A model that "just needs to install a package" can also delete your config, push to main, or expose secrets.

Approval policies

Advanced Even inside a sandbox, you often want the agent to ask before doing something — especially file writes or command execution. Approval policies control this:

# Codex CLI: approval policies
codex -a on-request exec "..."    # model decides when to ask (default)
codex -a never exec "..."          # never asks, runs everything (for CI)
codex --approve-for-me exec "..."  # auto-reviews requests within sandbox

# Kiro CLI: per-session tool trust
/tools trust read        # trust all reads without asking
/tools trust shell       # trust shell commands without asking
/tools trust-all          # trust everything for this session (with warning)

The right policy depends on the context:

  • Interactive development — ask before writes and commands (on-request or ask). You review each change before it lands.
  • CI / automated — never (fully autonomous, runs in a sandbox). No human to approve.
  • Trusted tasks — trust reads and grep, ask before writes. You let it explore freely but gate changes.

When agents help vs. when they hurt

Advanced Agents are powerful but not universal. Knowing when to use the loop vs. when to write a one-shot prompt is a real skill:

Good for agentsBad for agents (use a chatbot instead)
Multi-file refactors (read, edit, verify across files)Single function you can paste into chat
"Make the tests pass" (run, read failure, fix, repeat)One question about a concept
Setting up a project from scratch (create files, install, configure)Understanding existing code (read it yourself)
Migrating patterns across a codebase (find all, replace, verify)Architecture decisions (think, don't delegate)
Repetitive, well-specified tasks (add error handling to every endpoint)Vague, exploratory work ("make it better")
The rule of thumb: if the task has a clear acceptance criterion (tests pass, build succeeds, all files use the new pattern), agents excel. If the task is open-ended ("improve the architecture"), the agent will make changes that look right but aren't what you wanted. Use agents for "make it match this spec," not "figure out what the spec should be."

MCP: connecting agents to external tools

Advanced The Model Context Protocol (MCP) is a standard way to give agents access to external tools — databases, APIs, GitHub, issue trackers — without each agent implementing its own integration. An MCP server exposes tools; the agent connects to it and can call those tools in its loop.

# Codex CLI: add an MCP server
codex mcp add github -- npx -y @modelcontextprotocol/server-github

# Kiro CLI: add an MCP server
kiro-cli mcp add --name github \
  --command "npx -y @modelcontextprotocol/server-github" \
  --scope workspace

# Now the agent can call the server's tools:
# - search_code(query): search GitHub repos
# - create_issue(title, body): open an issue
# - get_file_contents(owner, repo, path): read a file from GitHub

MCP is the bridge between "the model can read and write files" and "the model can interact with the rest of your infrastructure." With a database MCP server, the agent can query your schema. With a GitHub MCP server, it can read issues and create PRs. The tools become part of the agent's loop.

Steering files: persistent instructions for agents

Advanced A steering file (AGENTS.md, .kiro/steering/*.md, CLAUDE.md) is a markdown file in your repo that the agent reads automatically at the start of every session. It's how you give the agent project-specific rules without restating them every time:

# AGENTS.md (in the repo root)
# Project: Tutorials PWA
# Runtime: Bun only. No npm dependencies.
# 
# To add a lesson: register in scripts/lessons.js, write content/
/.html,
# then `bun run build && bun run check`. The build must be deterministic (no timestamps).
# Never hand-edit docs/ — it's generated output.

Without a steering file, every agent session starts from scratch — the model knows general programming but nothing about your project's conventions. With one, the agent immediately knows your build commands, your test runner, your style rules, and your traps. The AGENTS.md Best Practices lesson covers how to write them well.

Common mistakes

  • Trusting the agent without verification. The agent writes syntax-valid code that looks right. Always read the diff and run the tests yourself.
  • Disabling the sandbox. danger-full-access or --yolo is for throwaway environments, not your development machine. The model can do real damage with shell access.
  • Vague tasks. "Make it better" gives you changes you didn't want. "Make the tests pass" or "add error handling to every endpoint that returns JSON" gives you something the agent can verify.
  • Not managing context. Long sessions fill the window. Use /compact when the agent starts losing track, or start a new session for a new task.
  • Using an agent for a single-function question. If you can paste one function into a chat window, do that. Spinning up an agent session for a one-liner is overhead for no benefit.
  • Expecting the agent to "figure out" the spec. Agents execute specs, they don't write them. If you don't know what you want, the agent's output will reflect that ambiguity.
  • Forgetting that tool outputs consume context. A verbose command output can eat thousands of tokens. Pipe through grep, head, or --format to keep it lean.

Exercises

  1. Install Codex CLI or Kiro CLI (see the dedicated lessons) and run it in read-only sandbox mode. Ask it to "explain the build process in this repo." Observe how it reads files and reasons about them.
  2. Switch to workspace-write and ask the agent to "add a comment to each exported function in one file." Review every change it makes before approving. How many did it get right?
  3. Run a long agent session (10+ turns) and then use /compact (or let it auto-compact). Observe: does the agent "remember" details from before compaction? What's lost?
  4. Configure an MCP server (e.g., the filesystem or GitHub server) in your agent. Ask it to use that server's tools. Observe how MCP tools appear in the agent's loop.
  5. Write an AGENTS.md for your project with 5 specific rules. Run two agent sessions — one with the AGENTS.md present and one without — on the same task. Compare the output quality and convention-adherence.

Mini-project: Build a test-fixing agent session

Pick a project with a failing test. Start an agent session (Codex CLI or Kiro CLI) with a workspace-write sandbox and on-request approvals. Ask it to "make all tests pass." Watch the loop: it runs the tests, reads the failure, reads the code, edits, re-runs. After it finishes, review every change, run the full test suite yourself, and document: how many turns did it take? What did it get right? What did it get wrong? Would you trust this PR?
