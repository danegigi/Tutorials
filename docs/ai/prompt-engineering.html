Prompt engineering is not "talking to the AI nicely." It's the practice of structuring your input so the model produces reliable, repeatable output. The patterns are few, they're simple, and they compound — a good system message plus structured output plus few-shot examples turns a model that sometimes writes correct code into one that almost always does.

The system message: your most powerful tool

Beginner The system message is the instruction that shapes the model's behavior for the entire conversation. Without one, the model defaults to "generic helpful assistant" — and generic is exactly what you don't want when you need consistent, specific output.

A good system message has three parts:

SYSTEM MESSAGE (the pattern):

1. ROLE       — who the model is ("You are a senior Go code reviewer")
2. RULES      — what to do and not do ("Never use any. Flag unused variables.
                 Always suggest a test for each fix.")
3. FORMAT     — how to structure output ("Respond with a bullet list of issues,
                 each followed by a suggested fix in a code block.")

// API: a system message that works
{
  "model": "llama3.2",
  "messages": [
    {
      "role": "system",
      "content": "You are a senior Go code reviewer. Rules:
        - Flag unused variables, missing error handling, and goroutine leaks
        - Suggest a test for each fix
        - Use Go idioms (not Python or Java patterns)
        - If the code is fine, say 'No issues found'
      Format: respond with a bullet list. Each issue: the problem, then the fix in a code block."
    },
    { "role": "user", "content": "Review this: func work() { go func() { ... }() }" }
  ]
}
The system message is where AGENTS.md files get their power. An AGENTS.md is essentially a persistent system message that every agent session in the repo automatically reads. The same rules that make a good system message — specific role, explicit rules, clear format — make a good AGENTS.md. See the AGENTS.md Best Practices lesson.

Few-shot prompting

Beginner Few-shot means showing the model examples of the input-output pattern you want, before asking your real question. The model is a pattern matcher — give it the pattern, and it follows it.

// Zero-shot (no examples — the model guesses the format)
USER: Extract the name and age.
INPUT: "John Smith, age 34, lives in Portland"
→ "The person's name is John Smith and they are 34 years old..."  (rambles)

// Few-shot (examples define the exact pattern)
USER: Extract the name and age.
EXAMPLES:
INPUT: "Jane Doe, age 29, lives in Seattle"
OUTPUT: {"name": "Jane Doe", "age": 29}

INPUT: "Bob Lee, age 45, lives in Austin"
OUTPUT: {"name": "Bob Lee", "age": 45}

INPUT: "John Smith, age 34, lives in Portland"
→ {"name": "John Smith", "age": 34}  (exact format, no rambling)

The number of examples matters less than their consistency. Two well-chosen examples often beat five mediocre ones. The model learns the pattern from the examples, not the content — so make sure all examples follow exactly the same format.

If your examples are inconsistent — different casing, sometimes a trailing comma, sometimes not — the model will replicate that inconsistency. Few-shot amplifies whatever pattern you show it, good or bad. Proofread your examples like production code.

Chain-of-thought

Intermediate Chain-of-thought (CoT) means asking the model to reason step by step before giving its answer. This measurably improves accuracy on multi-step problems because the model builds up context that helps each prediction.

// Without CoT (the model jumps to an answer and gets it wrong)
USER: A store has 23 apples. A customer buys 17 and returns 3. How many left?
→ 9  (wrong — it did 23 - 17 = 6, then added 3 back as 9, but
      the "returns 3" means the customer gave 3 back to the store)

// With CoT (the model shows its work and gets it right)
USER: A store has 23 apples. A customer buys 17 and returns 3. How many left?
      Think step by step.
→ Step 1: Store starts with 23 apples.
  Step 2: Customer buys 17. Store has 23 - 17 = 6 apples.
  Step 3: Customer returns 3 apples. Store has 6 + 3 = 9 apples.
  Answer: 9 apples.

You don't need the magic words "think step by step" — you can be more specific:

// Better CoT: specify what to reason about
"Before answering, identify the entities, their relationships,
 and the operations. Then compute step by step."

// For code:
"Before writing the function, list the edge cases you need to handle.
 Then write the function. Then add a comment for each edge case."
For reasoning models (o1, o3, DeepSeek-R1), you don't need to add chain-of-thought — they do it internally. In fact, telling a reasoning model to "think step by step" can hurt, because it interferes with the model's internal thinking process. Use CoT with standard models (GPT-4, Claude, Llama), not reasoning models.

Structured output (JSON mode)

Intermediate When you need the model's output to be machine-readable, ask for JSON and constrain the format. Most APIs support a JSON mode or structured output that guarantees valid JSON conforming to a schema you provide.

// OpenAI: structured output with a schema
const response = await openai.chat.completions.create({
  model: "gpt-4o",
  response_format: {
    type: "json_schema",
    json_schema: {
      name: "code_review",
      schema: {
        type: "object",
        properties: {
          issues: {
            type: "array",
            items: {
              type: "object",
              properties: {
                severity: { type: "string", enum: ["error", "warning", "info"] },
                line: { type: "number" },
                message: { type: "string" },
                suggestion: { type: "string" }
              },
              required: ["severity", "message"]
            }
          },
          summary: { type: "string" }
        },
        required: ["issues", "summary"]
      }
    }
  },
  messages: [
    { role: "system", content: "You are a code reviewer. Output JSON." },
    { role: "user", content: "Review this code: ..." }
  ]
});

// Ollama: format json forces valid JSON output
curl http://localhost:11434/api/generate -d '{
  "model": "llama3.2",
  "prompt": "List 3 git commands with descriptions as JSON",
  "format": "json",
  "stream": false
}'
# → {"commands": [
#     {"command": "git init", "description": "Initialize a repo"},
#     ...
#   ]}

Without structured output, the model might wrap JSON in markdown (```json ... ```), add a preamble ("Here's the JSON:"), or produce slightly malformed JSON. Structured output eliminates that class of error entirely.

Even with JSON mode, the content of the JSON can be wrong — the model might put a wrong line number or fabricate a suggestion. JSON mode guarantees format, not accuracy. Always validate the values, not just the structure.

Prompt templates and variables

Intermediate A prompt template is a reusable prompt with placeholders you fill in at runtime. This is how agentic tools send the same instruction with different inputs — the template stays fixed, the variables change.

// A prompt template (pseudocode)
const reviewTemplate = `
You are a {language} code reviewer.

Review the following code for:
{concerns}

Code:
\`\`\`{language}
{code}
\`\`\`

Respond with a JSON array of issues.
`;

// Usage: fill in the variables
const prompt = reviewTemplate
  .replace("{language}", "go")
  .replace("{concerns}", "goroutine leaks, missing error handling, SQL injection")
  .replace("{code}", sourceCode);

Most frameworks (LangChain, Vercel AI SDK, Ollama's Modelfile TEMPLATE) have built-in template support. The principle is the same: separate the instruction (stable, written once) from the input (varies per call).

Context priming and ordering

Advanced Models pay more attention to the beginning and end of the prompt than the middle (the "lost in the middle" effect). When you provide a large context (a codebase, a doc), structure it so the most important instruction is first or last, not buried in the middle of a 50K-token dump.

// Bad: instruction buried in the middle of a code dump
"Here's the codebase:
[file 1... file 2... file 3... 40,000 tokens of code...]
Fix the bug in the auth handler.
[file 4... file 5... more code...]"
// ↑ the model barely "sees" the instruction

// Good: instruction first, context after
"Fix the bug in the auth handler. The file is auth.go.
Here is the relevant code:
[only auth.go, not the whole repo]

Here are the related files for context:
[router.go, middleware.go]

The error message is: panic: nil pointer at line 42"
This is why coding agents don't dump your entire repo into the prompt. They use tools to search the codebase and pull in only the relevant files. The agent's job is to curate context — and curation is a skill the model can't do well with a wall of text.

Handling refusals and over-refusals

Advanced Safety-tuned models sometimes refuse legitimate requests. A prompt that looks like it could be asking for something harmful — even when it isn't — triggers a refusal. The fixes are structural:

// Model refuses: "I can't help with that"
USER: "How do I kill a process on port 8080?"
→ "I can't assist with that request."
// (the word "kill" triggered a safety filter)

// Fix 1: add context that clarifies the intent
USER: "In my development workflow, I need to stop a Go server
       running on port 8080. How do I find and stop the process
       using the terminal?"
→ "Use lsof -ti tcp:8080 | xargs kill to find and stop it."

// Fix 2: use the system message to set the context
SYSTEM: "You are a development assistant helping a programmer
         with local development tasks. All questions are about
         the user's own development environment."

For coding agents, this is rarely a problem — the system message and the context (you're in a codebase, asking about code) make the intent clear. But when you see an unexpected refusal, rephrase with context rather than fighting the model.

Iterating on prompts

Advanced Prompt engineering is empirical. You don't reason your way to the right prompt — you try, observe, and adjust. A practical loop:

  1. Start with the simplest prompt that could work. Zero-shot, no examples, minimal system message.
  2. Test on 3–5 inputs that span the cases you care about (easy, hard, edge case).
  3. Observe failure modes. Does it ramble? Get the format wrong? Miss edge cases? Hallucinate?
  4. Add one fix at a time. A system message rule. A few-shot example. A format instruction. Test after each change.
  5. Stop when it's reliable enough, not when it's perfect. Diminishing returns are real — the first three improvements matter most.
Don't add prompt complexity preemptively. A prompt with 20 rules "just in case" is harder to maintain and often less effective than a focused one, because the model has to weigh all 20 rules simultaneously. Add rules when you observe a failure, not when you imagine one.

Common mistakes

  • No system message. Without one, you get generic output. The system message is the single biggest lever for consistency.
  • Inconsistent few-shot examples. If your examples don't all follow the exact same format, the model replicates the inconsistency.
  • Asking for reasoning on a reasoning model. Telling o1 or DeepSeek-R1 to "think step by step" can interfere with their internal process. Use CoT with standard models only.
  • Dumping everything into context. More is not better. Curate the context to what's relevant — the model pays less attention to things buried in the middle of a huge prompt.
  • Adding rules preemptively. Start simple, observe failures, add one fix at a time. A 20-rule prompt is harder to maintain and often less effective.
  • Trusting JSON mode for accuracy. JSON mode guarantees valid structure, not correct values. Validate the content, not just the shape.
  • Fighting refusals by rephrasing evasively. Add context that clarifies intent instead of trying to trick the safety filter.

Exercises

  1. Write a system message for a "commit message generator" that reads a git diff and outputs a conventional commit (type(scope): description). Test it on 3 real diffs from your repo.
  2. Create a few-shot prompt that converts natural-language database queries into SQL. Use 3 examples with different query types (SELECT, JOIN, GROUP BY). Test on a query not in your examples.
  3. Call a local model with a math word problem, first without CoT and then with "think step by step." Compare the accuracy across 5 problems.
  4. Write a prompt template for a code reviewer that takes {language}, {code}, and {concerns} as variables. Run it against a real function in your codebase.
  5. Trigger an over-refusal by asking a model "how do I kill a process?" without context, then fix it by adding development context. Observe the difference.

Mini-project: Build a structured-output code reviewer

Write a Bun script that takes a source file as input, sends it to a local Ollama model with a system message defining review rules and a JSON output schema, and prints a formatted table of issues (severity, line, message, suggestion). Use the format: "json" option to guarantee valid JSON. Then test it against 5 different source files with known issues (an unused variable, a missing error check, a goroutine without context cancellation) and verify it catches them.
