Ollama lets you run large language models on your own machine — no API key, no cloud, no per-token cost. You download a model, start the server, and talk to it through the same kind of API the big providers offer, but everything runs locally. This lesson covers install, model management, the interactive REPL, the REST API, custom Modelfiles, and how to connect Ollama to coding agents like Codex CLI and Kiro CLI.

Install

Beginner Ollama installs as a single binary with no dependencies:

# macOS
brew install ollama
# or download the app from https://ollama.com/download

# Linux
curl -fsSL https://ollama.com/install.sh | sh

# Windows
# Download from https://ollama.com/download and run the installer

# Verify
ollama --version
# → ollama version 0.4.x

On macOS and Linux, the installer sets up a background service. On macOS, the app runs as a menubar process. You can also run the server manually with ollama serve.

# Start the server manually (if not running as a service)
ollama serve
# → Listening on 127.0.0.1:11434

# Check it's up
curl http://localhost:11434/api/version
# → {"version":"0.4.x"}
Ollama runs on port 11434 by default. Set OLLAMA_HOST=0.0.0.0:11434 if you need other machines on your network to reach it (e.g., a dev server). On macOS, the app binds to localhost only.

Pulling and running models

Beginner Models are downloaded with ollama pull and run with ollama run. The first pull downloads the model (a few GB); subsequent runs load from disk.

# Pull a model (downloads the quantized weights)
ollama pull llama3.2
# → pulling manifest...
# → pulling 8c8f5e... ████████████████ 100%
# → success

# Run it interactively (opens a chat REPL)
ollama run llama3.2
>>> What is a goroutine?
A goroutine is a lightweight thread of execution in Go...

>>> /bye              # exit the REPL

# Run with a one-shot prompt (no REPL)
ollama run llama3.2 "Write a haiku about Linux"
# → Pinguins waddle far / Kernel boots the system up / Tux smiles in the dark

Choosing a model

The Ollama model library has hundreds of models. Here are the ones worth knowing:

ModelSizeRAM neededBest for
llama3.2 (3B)2 GB4 GBGeneral use, fast on any machine
llama3.3 (70B)40 GB48+ GBFrontier quality, needs a big GPU
qwen2.5-coder (7B–32B)5–20 GB8–24 GBCode generation, completion
deepseek-r1 (7B–671B)5–400 GBvariesReasoning, math (open-weight reasoning model)
phi3 (3.8B)2.5 GB4 GBSmall, fast, Microsoft's model
mistral (7B)4 GB6 GBGeneral use, efficient
nomic-embed-text274 MB1 GBEmbeddings (for RAG/search)
llava (7B + vision)5 GB8 GBVision — describe images, screenshots
 
# Pull a specific size variant
ollama pull qwen2.5-coder:7b     # 7B version
ollama pull qwen2.5-coder:32b    # 32B version (needs more RAM)

# Pull a quantized variant (smaller, slightly lower quality)
ollama pull llama3.2:3b-q4_K_M   # 4-bit quantization

# List what you have
ollama list
# → NAME               SIZE      MODIFIED
#   llama3.2:latest     2.0 GB    2 hours ago
#   qwen2.5-coder:7b    4.7 GB    yesterday

# Show model details (parameters, template, license)
ollama show llama3.2
# → Model
#   architecture        llama
#   parameters          3.2B
#   context length      32768
#   ...
The model size is the download size, but the RAM needed at runtime is roughly the same — the model loads entirely into memory. A 4 GB model needs ~4 GB of free RAM. If you don't have enough RAM, Ollama will either swap (very slow) or fail. Check your available memory before pulling a large model.

Model management commands

Beginner The full command set for managing models:

# Pull a model from the library
ollama pull llama3.2

# Remove a model (frees disk space)
ollama rm llama3.2
# → deleted 'llama3.2'

# Copy a model (useful before modifying with a Modelfile)
ollama cp llama3.2 my-llama

# List all downloaded models
ollama list

# Show running models (loaded in memory)
ollama ps
# → NAME           SIZE     PROCESSOR    UNTIL
#   llama3.2:latest 3.6 GB   100% GPU    4 minutes from now

# Stop a running model (unloads from memory)
ollama stop llama3.2

# Sign in (for pushing models to your Ollama account)
ollama signin

# Push a model to your library
ollama push myuser/my-model
Models stay loaded in memory for a few minutes after use (the "until" column in ollama ps). If you're making rapid API calls, the model is already warm and responses are fast. If it's cold, the first call loads it (a few seconds), and subsequent calls are instant.

The REST API

Intermediate Ollama serves an OpenAI-compatible REST API at http://localhost:11434. This is how coding agents and your own scripts talk to it:

Generate (single prompt)

curl http://localhost:11434/api/generate -d '{
  "model": "llama3.2",
  "prompt": "Why do we use context in Go?",
  "stream": false
}'
# → {
#   "model": "llama3.2",
#   "response": "Context in Go provides cancellation and timeouts...",
#   "done": true,
#   "total_duration": 1234567890,
#   "prompt_eval_count": 8,
#   "eval_count": 42
# }

Chat (multi-turn conversation)

curl http://localhost:11434/api/chat -d '{
  "model": "llama3.2",
  "messages": [
    {"role": "system", "content": "You are a Go expert. Be concise."},
    {"role": "user", "content": "What is a goroutine?"},
    {"role": "assistant", "content": "A lightweight thread..."},
    {"role": "user", "content": "How do I cancel one?"}
  ],
  "stream": false
}'
# → {"message": {"role": "assistant", "content": "Use context.WithCancel..."}, ...}

Streaming (token by token)

# Stream = true (default) returns one JSON object per token
curl http://localhost:11434/api/generate -d '{
  "model": "llama3.2",
  "prompt": "Count to 5"
}'
# → {"response":"1","done":false}
# → {"response":"2","done":false}
# → {"response":"3","done":false}
# → {"response":"4","done":false}
# → {"response":"5","done":true}

Structured output (JSON)

curl http://localhost:11434/api/generate -d '{
  "model": "llama3.2",
  "prompt": "List 3 git commands with descriptions",
  "format": "json",
  "stream": false
}'
# → {"commands": [
#     {"command": "git init", "description": "Initialize a new repository"},
#     {"command": "git clone", "description": "Clone a remote repository"},
#     {"command": "git commit", "description": "Record changes to the repository"}
#   ]}

Embeddings

curl http://localhost:11434/api/embeddings -d '{
  "model": "nomic-embed-text",
  "prompt": "How do I fix a goroutine leak?"
}'
# → {"embedding": [0.123, -0.456, 0.789, ...]}

Calling the API from Bun

// Simple chat wrapper
async function chat(messages, model = "llama3.2") {
  const res = await fetch("http://localhost:11434/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ model, messages, stream: false }),
  });
  const data = await res.json();
  return data.message.content;
}

const answer = await chat([
  { role: "system", content: "You are a code reviewer." },
  { role: "user", content: "Review: " + codeSnippet },
]);
console.log(answer);

Custom Modelfiles

Intermediate A Modelfile is Ollama's equivalent of a Dockerfile — it defines a custom model from a base model plus system prompt, parameters, and templates. This is how you create a model with a fixed persona or behavior:

# Modelfile — create a custom code-reviewer model
FROM llama3.2

# System prompt (the model's persona/rules)
SYSTEM """
You are a senior code reviewer. Rules:
- Flag security issues, missing error handling, and unused variables.
- Be concise — bullet points, not paragraphs.
- If the code is fine, say "No issues found."
- Use the same language as the code (Go, Python, etc.).
"""

# Parameters (temperature, context window, etc.)
PARAMETER temperature 0.3
PARAMETER num_ctx 8192
PARAMETER stop "</review>"

# Template (controls how messages are formatted)
TEMPLATE """
{{ if .System }}<|im_start|>system
{{ .System }}<|im_end|>
{{ end }}{{ range .Messages }}<|im_start|>{{ .Role }}
{{ .Content }}<|im_end|>
{{ end }}<|im_start|>assistant
"""

# Build the custom model
ollama create code-reviewer -f Modelfile
# → success

# Run it
ollama run code-reviewer "Review: func main() { fmt.Println('hello') }"
# → • fmt.Println is fine for a simple program.
#   • Consider using log.Printf in production for structured output.
#   • No issues found for a program this simple.

# The model is saved — list it
ollama list
# → NAME              SIZE     MODIFIED
#   code-reviewer     2.0 GB   just now
#   llama3.2:latest   2.0 GB   2 hours ago
A custom Modelfile model is a base model + a system prompt + parameters, not a fine-tune. The weights are the same; you've just baked in the system message and settings so you don't have to pass them on every call. This is extremely useful for agents that always need the same persona — create the model once, and the agent just calls code-reviewer without a system message.

Connecting Ollama to coding agents

Advanced Both Codex CLI and Kiro CLI can use Ollama as a local model provider, so you get an agent without sending your code to a cloud API:

Codex CLI with Ollama

# Run Codex with a local Ollama model
codex --oss --local-provider ollama exec "explain this codebase"
codex --oss --local-provider ollama "fix the failing tests"

# Or set it in config.toml:
# ~/.codex/config.toml
[oss]
provider = "ollama"
model = "qwen2.5-coder:7b"

Kiro CLI with Ollama

# Kiro CLI: list available models (includes local Ollama models)
kiro-cli chat --list-models

# Start a chat with a specific model
kiro-cli chat --model ollama/qwen2.5-coder:7b

# Or set a default in settings
kiro-cli settings chat.defaultModel "ollama/qwen2.5-coder:7b"

OpenAI-compatible endpoint

Ollama also serves an OpenAI-compatible API at /v1, so any tool that speaks OpenAI can point at it:

# OpenAI-compatible endpoint
curl http://localhost:11434/v1/chat/completions -d '{
  "model": "llama3.2",
  "messages": [{"role": "user", "content": "Hello"}]
}'

# Point any OpenAI-compatible tool at Ollama:
# OPENAI_BASE_URL=http://localhost:11434/v1
# OPENAI_API_KEY=ollama  (any string works — Ollama doesn't check)
Local models are smaller and less capable than frontier cloud models (GPT-4o, Claude Sonnet 4.5). A 7B model is fine for code completion, simple refactors, and explanations, but it will struggle with complex multi-file reasoning, subtle bugs, or following long complex instructions. Use a bigger model (32B+) for coding agents, or accept that you'll need to guide it more than you would with a cloud model.

Integration with editors

Advanced Ollama integrates with editors for inline code completion and chat:

  • VS Code — install the Ollama extension or Continue.dev, set the provider to Ollama, pick a model.
  • JetBrains — use the Continue plugin or CodeGPT, point at http://localhost:11434.
  • Neovim — codecompanion.nvim or ollama.nvim support Ollama natively.
  • Cursor / Zed — both support custom OpenAI-compatible endpoints; point them at http://localhost:11434/v1.
# Continue.dev config (~/.continue/config.json)
{
  "models": [{
    "title": "Ollama Llama 3.2",
    "provider": "ollama",
    "model": "llama3.2",
    "apiBase": "http://localhost:11434"
  }],
  "tabAutocompleteModel": {
    "title": "Qwen Coder",
    "provider": "ollama",
    "model": "qwen2.5-coder:7b"
  }
}

# Example: keep models loaded longer (good for active dev)
OLLAMA_KEEP_ALIVE=30m ollama serve

# Example: store models on an external drive
OLLAMA_MODELS=/Volumes/External/ollama-models ollama serve

Common mistakes

  • Pulling a model bigger than your RAM. A 70B model needs ~40 GB of RAM. Check ollama show <model> for the size before pulling, and check your available memory.
  • Forgetting stream: false in API calls. Without it, the API streams one JSON object per token. If your code expects a single response, set stream: false.
  • Using a 3B model for complex coding. Small models are fast but struggle with multi-file reasoning. Use qwen2.5-coder:7b or bigger for coding tasks.
  • Not checking ollama ps when calls are slow. If the model isn't loaded, the first call loads it (slow). If it is loaded and still slow, you might be out of RAM and swapping.
  • Expecting local model quality to match cloud models. A 7B local model is not GPT-4o. It's useful for privacy, offline work, and cost, but it will need more guidance and produce more errors.
  • Leaving the server exposed on 0.0.0.0. If you set OLLAMA_HOST=0.0.0.0 on a shared machine, anyone on the network can call your models. Only do this on trusted networks.
  • Forgetting to stop models. ollama stop <model> unloads it from memory. If you're done with a model, stop it to free RAM for other work.

Exercises

  1. Install Ollama, pull llama3.2, and run a chat session. Ask it to explain a concept from this lesson in its own words.
  2. Pull qwen2.5-coder:7b and ask it to write a Bun function that reads a JSON file. Compare the output quality to what a cloud model would produce.
  3. Create a custom Modelfile with a system prompt for a "commit message generator" (input: git diff, output: conventional commit format). Build it with ollama create and test it on a real diff.
  4. Write a Bun script that calls the Ollama chat API with a system message and a user message, and prints the response. Use stream: false.
  5. Configure Codex CLI or Kiro CLI to use an Ollama model. Run a simple task ("explain this file") and compare the speed and quality to a cloud model.

Mini-project: Build a local code reviewer

Create a custom Ollama model (Modelfile) that acts as a Go code reviewer with a system prompt defining review rules (flag goroutine leaks, missing error handling, unused variables). Write a Bun script that reads a .go file from disk, sends it to your custom model via the Ollama API with format: "json", and prints a formatted table of issues with severity, line number, and suggestion. Test it against 3 Go files with known issues and verify it catches them.
