A large language model trained on the internet doesn't know your codebase, your documents, or your database. Retrieval-Augmented Generation (RAG) fixes that: instead of hoping the model memorized your data during training, you search your data at query time and stuff the relevant pieces into the prompt as context. This lesson covers the full pipeline — embeddings, chunking, vector databases, similarity search, reranking, and the production patterns that separate a working RAG system from a demo that hallucinates.

Why RAG exists

Beginner There are two ways to give an LLM new knowledge:

ApproachHowCostWhen
Retrain / fine-tuneAdjust model weights on your dataHigh (GPU hours, expertise)Style/tone changes, domain adaptation
RAGSearch your data, inject results into the promptLow (a DB query + more tokens)Factual knowledge that changes, large corpora

RAG wins for most use cases because knowledge is decoupled from the model: you can add, update, or delete documents without retraining. The model is the reasoning engine; your vector database is the knowledge store.

The pipeline, end to end:

DOCUMENTS          EMBEDDINGS         VECTOR DB          QUERY TIME
──────────          ──────────         ──────────         ──────────
pdf, md, code  ──►  chunk  ──►  embed  ──►  store  ···  embed query ──► search ──► top-k chunks ──► LLM prompt ──► answer
  (ingest)         (split)    (API)      (index)           (retrieve)          (rerank?)          (generate)

Embeddings: turning text into vectors

Beginner An embedding is a vector (a list of floats) that captures the semantic meaning of a piece of text. Text with similar meaning produces vectors close together in high-dimensional space. The key property: "cat sat on the mat" and "feline rested on the rug" produce nearby vectors even though no words match.

# OpenAI embeddings API
curl https://api.openai.com/v1/embeddings \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "text-embedding-3-small",
    "input": "How do I configure pgvector for similarity search?"
  }'

# Response: a 1536-dimensional vector
{
  "data": [{
    "embedding": [0.0023, -0.0091, 0.0438, ...1536 floats...],
    "index": 0
  }],
  "model": "text-embedding-3-small",
  "usage": { "prompt_tokens": 12, "total_tokens": 12 }
}

You're not limited to OpenAI. Free local options that run on your machine:

# Ollama serves embedding models too
ollama pull nomic-embed-text
curl http://localhost:11434/api/embeddings -d '{
  "model": "nomic-embed-text",
  "prompt": "How do I configure pgvector?"
}'
# {"embedding": [0.023, -0.041, ...]}
Embedding models are much cheaper and faster than chat models. A 1536-dim embedding for a chunk of text costs fractions of a cent. Don't overthink the choice — start with text-embedding-3-small (OpenAI) or nomic-embed-text (local), measure recall on your data, and upgrade only if results are poor.

Choosing an embedding model

Intermediate The main dimensions:

ModelDimsProviderNotes
text-embedding-3-small1536OpenAICheap, good default
text-embedding-3-large3072OpenAIBetter recall, more storage
nomic-embed-text768Ollama (local)Free, runs on laptop
mxbai-embed-large1024Ollama (local)Strong open model
BGE-large-en1024HuggingFaceOpen weights, self-host

The dimension count matters for storage cost and search speed, not just quality. A 3072-dim vector takes 4x the storage of a 768-dim one. Many providers support dimension reduction — you can request fewer dimensions from a large model to trade a little recall for storage savings:

// OpenAI: request a shorter embedding (512 dims instead of 1536)
{
  "model": "text-embedding-3-small",
  "input": "...",
  "dimensions": 512   // truncates the vector; still usable
}

Chunking: splitting documents into search units

Beginner You can't embed an entire book into one vector — the model would average out all the meaning into mush. You chunk documents into smaller pieces, embed each one separately, and search over the chunks.

The simplest approach — fixed-size chunks with overlap:

def chunk_text(text, chunk_size=512, overlap=50):
    """Split text into overlapping chunks of ~chunk_size tokens."""
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end])
        start += chunk_size - overlap  # overlap keeps context at boundaries
    return chunks

text = open("docs/architecture.md").read()
for i, chunk in enumerate(chunk_text(text)):
    embedding = embed(chunk)
    vector_db.insert({"id": f"arch-{i}", "text": chunk, "embedding": embedding})

But fixed-size splitting breaks sentences and loses structure. Better approaches:

StrategyHowBest for
Fixed-size + overlapN tokens, slide by N-overlapQuick prototype, uniform text
Sentence-awareSplit on sentence boundaries, group to target sizeMost prose (docs, articles)
Recursive splittingTry paragraph → sentence → word, keep the largest intact unitMixed content (Markdown, HTML)
Structure-awareSplit on headers (##), one chunk per sectionCodebases, technical docs
Semantic chunkingEmbed sentences, split where embedding distance spikesLong-form essays, transcripts

Chunk size: the central tradeoff

Intermediate

Small chunks (100-200 tokens)Large chunks (500-1000 tokens)
↑ Precision: the embedding captures one idea↑ Context: each chunk has surrounding detail
↓ Recall: may miss info split across boundaries↓ Precision: the embedding averages multiple ideas
↓ Requires more chunks in the prompt↑ Fewer chunks needed, but each is "fatter"
Start at 256-512 tokens with 50-token overlap. That's the sweet spot for most documentation. Measure retrieval quality (did the top-k chunks actually contain the answer?) and adjust from there — not the other way around.

Metadata: the part most people skip

Every chunk should carry metadata, not just text and embedding. This is what lets you filter before searching:

{
  "text": "To configure pgvector, run CREATE EXTENSION vector...",
  "embedding": [0.002, ...],
  "metadata": {
    "source": "docs/database-setup.md",
    "section": "pgvector",
    "page": 3,
    "language": "en",
    "doc_type": "tutorial",
    "last_updated": "2026-10-15"
  }
}

With metadata filters, a query like "show me database setup for Postgres" can pre-filter to doc_type=tutorial and section=pgvector before the vector search, which dramatically improves precision.

Vector databases: storing and searching embeddings

Beginner A vector database stores embeddings and answers the question: "given this query vector, what are the K closest vectors?" The distance metric is almost always cosine similarity (how aligned two vectors are, regardless of magnitude).

Option 1: pgvector (Postgres extension)

If you already have Postgres, you may not need a separate database. pgvector adds a vector type and similarity operators:

-- Install the extension
CREATE EXTENSION vector;

-- Create a table with a vector column
CREATE TABLE documents (
  id        serial PRIMARY KEY,
  content   text NOT NULL,
  embedding  vector(1536),
  source    text,
  section   text
);

-- Insert with an embedding (generated by your app)
INSERT INTO documents (content, embedding, source, section)
VALUES ('pgvector setup guide...', '[0.002, -0.009, ...]', 'docs/db.md', 'pgvector');

-- Cosine similarity search: find the 5 most similar chunks
SELECT content, source, 1 - (embedding <=> '[0.003, ...]') AS similarity
FROM documents
WHERE section = 'pgvector'                    -- pre-filter by metadata
ORDER BY embedding <=> '[0.003, ...]'          -- cosine distance (lower = closer)
LIMIT 5;

The <=> operator is cosine distance. Add an index for speed:

-- HNSW index (faster, approximate nearest neighbor)
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- Or IVFFlat (faster to build, slightly less recall)
CREATE INDEX ON documents USING ivfflat (embedding vector_cosine_ops)
  WITH (lists = 100);

Option 2: Qdrant (dedicated vector DB)

For scale beyond what Postgres handles comfortably (millions of vectors), a dedicated vector database like Qdrant is purpose-built:

# Run Qdrant locally with Docker
docker run -p 6333:6333 qdrant/qdrant

# Create a collection
curl -X PUT http://localhost:6333/collections/docs \
  -H "Content-Type: application/json" \
  -d '{
    "vectors": { "size": 1536, "distance": "Cosine" }
  }'

# Upsert points
curl -X PUT http://localhost:6333/collections/docs/points \
  -H "Content-Type: application/json" \
  -d '{
    "points": [{
      "id": 1,
      "vector": [0.002, -0.009, ...],
      "payload": { "text": "pgvector setup...", "section": "pgvector" }
    }]
  }'

# Search with metadata filter
curl -X POST http://localhost:6333/collections/docs/points/search \
  -H "Content-Type: application/json" \
  -d '{
    "vector": [0.003, ...],
    "filter": { "must": [{ "key": "section", "match": { "value": "pgvector" }}]},
    "limit": 5
  }'

Option 3: In-process (for prototypes)

For small datasets or local-first apps, you can use an in-process store:

// ChromaDB — embeds in your Node/Bun process
import { ChromaClient } from "chromadb";
const client = new ChromaClient({ path: "http://localhost:8000" });
const collection = await client.getOrCreateCollection({ name: "docs" });

await collection.add({
  ids: ["doc-1"],
  documents: ["pgvector setup guide..."],
  metadatas: [{ source: "docs/db.md" }],
  // embeddings auto-generated if you configure an embedding function
});

const results = await collection.query({
  queryTexts: ["how to set up pgvector?"],
  nResults: 5,
  where: { source: "docs/db.md" },   // metadata filter
});
In-process stores (ChromaDB in-memory, FAISS) lose their data on restart unless you configure persistence. For production, use pgvector, Qdrant, or another server-based store that handles durability.

The full RAG pipeline in code

Intermediate Here's a complete, runnable RAG pipeline in TypeScript (works under Bun):

// rag.ts — a complete RAG pipeline
// Run: bun run rag.ts

const EMBED_MODEL = "text-embedding-3-small";
const CHAT_MODEL = "gpt-4o-mini";
const CHUNK_SIZE = 400;   // tokens
const OVERLAP = 50;
const TOP_K = 5;          // chunks to retrieve

// 1. INGEST: chunk + embed + store
async function ingest(filePath: string, store: DocStore) {
  const text = await Bun.file(filePath).text();
  const chunks = chunkText(text, CHUNK_SIZE, OVERLAP);
  for (const [i, chunk] of chunks.entries()) {
    const embedding = await embed(chunk);
    await store.insert({
      id: `${filePath}-${i}`,
      text: chunk,
      embedding,
      metadata: { source: filePath, chunkIndex: i },
    });
  }
  console.log(`Ingested ${chunks.length} chunks from ${filePath}`);
}

// 2. RETRIEVE: embed query, search top-k
async function retrieve(query: string, store: DocStore) {
  const queryEmbedding = await embed(query);
  const results = await store.search(queryEmbedding, TOP_K);
  return results;  // [{ text, score, metadata }, ...]
}

// 3. GENERATE: stuff chunks into the prompt, ask the model
async function answer(query: string, chunks: SearchResult[]) {
  const context = chunks
    .map((c, i) => `[${i + 1}] ${c.metadata.source}\n${c.text}`)
    .join("\n\n---\n\n");

  const response = await fetch("https://api.openai.com/v1/chat/completions", {
    method: "POST",
    headers: {
      "Authorization": `Bearer ${Bun.env.OPENAI_API_KEY}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      model: CHAT_MODEL,
      messages: [
        {
          role: "system",
          content: `Answer the user's question using ONLY the provided context.
If the context doesn't contain the answer, say "I don't have that information."
Cite sources by number: [1], [2], etc.`
        },
        {
          role: "user",
          content: `Context:\n${context}\n\nQuestion: ${query}`
        }
      ],
      temperature: 0.1,   // low temp = more factual, less creative
    }),
  });

  const data = await response.json();
  return data.choices[0].message.content;
}

// 4. PIPELINE: put it together
async function rag(query: string, store: DocStore) {
  const chunks = await retrieve(query, store);
  console.log(`Retrieved ${chunks.length} chunks:`);
  chunks.forEach((c, i) => console.log(`  [${i+1}] ${c.metadata.source} (score: ${c.score.toFixed(3)})`));
  return answer(query, chunks);
}

// --- helpers ---
async function embed(text: string): Promise<number[]> {
  const r = await fetch("https://api.openai.com/v1/embeddings", {
    method: "POST",
    headers: {
      "Authorization": `Bearer ${Bun.env.OPENAI_API_KEY}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ model: EMBED_MODEL, input: text }),
  });
  return (await r.json()).data[0].embedding;
}

function chunkText(text: string, size: number, overlap: number): string[] {
  const tokens = text.split(/(\s+)/);  // simplistic; use a real tokenizer
  const chunks: string[] = [];
  for (let i = 0; i < tokens.length; i += size - overlap) {
    chunks.push(tokens.slice(i, i + size).join(""));
    if (i + size >= tokens.length) break;
  }
  return chunks;
}

// Run it
const store = new MemoryDocStore();  // swap for pgvector/Qdrant in prod
await ingest("docs/architecture.md", store);
await ingest("docs/api-reference.md", store);
const result = await rag("How is the vector store configured?", store);
console.log(result);

Reranking: the step that doubles accuracy

Advanced Vector search is fast but imprecise — it finds semantically similar text, not necessarily text that answers the question. A reranker is a second model that scores each retrieved chunk against the query with a cross-attention mechanism (the query and the chunk are read together, not embedded separately).

// Two-stage retrieval: broad recall + precise rerank
async function retrieveWithRerank(query: string, store: DocStore) {
  // Stage 1: vector search — retrieve 20 candidates (broad net)
  const queryEmbedding = await embed(query);
  const candidates = await store.search(queryEmbedding, 20);

  // Stage 2: rerank — score each candidate against the query
  const reranked = await rerank(query, candidates);

  // Return only the top 5 after reranking
  return reranked.slice(0, 5);
}

// Using Cohere's rerank API
async function rerank(query: string, docs: SearchResult[]) {
  const r = await fetch("https://api.cohere.com/v2/rerank", {
    method: "POST",
    headers: {
      "Authorization": `Bearer ${Bun.env.COHERE_API_KEY}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      model: "rerank-english-v3.0",
      query: query,
      documents: docs.map(d => d.text),
      top_n: 5,
    }),
  });
  const data = await r.json();
  // data.results: [{ index: 0, relevance_score: 0.98 }, ...]
  return data.results
    .sort((a: any, b: any) => b.relevance_score - a.relevance_score)
    .map((r: any) => ({ ...docs[r.index], score: r.relevance_score }));
}
Reranking is the single highest-ROI improvement you can make to a RAG system. Retrieve 20-50 chunks with vector search (cheap, fast), then rerank to 5 (slower, but only 20-50 calls). You get the recall of a broad search with the precision of a cross-encoder. Most production RAG systems use this two-stage approach.

Advanced

Hybrid search: vector + keyword

Vector search is great for semantic similarity but terrible for exact matches (product names, error codes, IDs). Hybrid search combines vector similarity with traditional keyword search (BM25/full-text) and merges the rankings:

-- pgvector: combine full-text search with vector search
WITH vector_results AS (
  SELECT id, content, 1 - (embedding <=> $1) AS score
  FROM documents ORDER BY embedding <=> $1 LIMIT 20
),
keyword_results AS (
  SELECT id, content, ts_rank(tsv, query) AS score
  FROM documents, plainto_tsquery('english', $2) query
  WHERE tsv @@ query
  ORDER BY score DESC LIMIT 20
)
-- Reciprocal Rank Fusion: merge by rank, not raw score
SELECT id, content,
  COALESCE(1.0 / (60 + v.score_rank), 0) +
  COALESCE(1.0 / (60 + k.score_rank), 0) AS fused_score
FROM vector_results v
FULL OUTER JOIN keyword_results k USING (id)
ORDER BY fused_score DESC
LIMIT 5;

Query expansion

The user's query is often shorter and vaguer than the documents it should match. Expand it before searching:

// Ask the LLM to rewrite the query before retrieval
async function expandQuery(query: string): Promise<string[]> {
  const r = await fetch("https://api.openai.com/v1/chat/completions", {
    method: "POST",
    headers: {
      "Authorization": `Bearer ${Bun.env.OPENAI_API_KEY}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      model: "gpt-4o-mini",
      messages: [{
        role: "system",
        content: "Rewrite the user's question as 3 search queries that would find the answer in a documentation database. Return JSON array."
      }, { role: "user", content: query }],
      response_format: { type: "json_object" },
    }),
  });
  return JSON.parse((await r.json()).choices[0].message.content).queries;
}

// Search with all expanded queries, deduplicate, then rerank
const queries = await expandQuery(userQuery);
const allResults = await Promise.all(queries.map(q => retrieve(q, store)));
const unique = dedupe(allResults.flat());
const reranked = await rerank(userQuery, unique);

Parent-document retrieval

Sometimes the chunk that matches the query is too small to contain the full answer. Parent-document retrieval embeds small chunks (for precise search) but returns the larger parent document (for complete context):

// Store: small chunks for search, parent doc for context
{
  "parent_id": "architecture.md",
  "parent_text": "full section text...",
  "chunk_id": "architecture.md-3",
  "chunk_text": "small chunk for embedding...",
  "embedding": [...]
}

// At retrieval time: search chunks, return parent_text
SELECT d.parent_text, max(1 - (d.embedding <=> $1)) AS score
FROM documents d
ORDER BY d.embedding <=> $1
LIMIT 5;
-- Each result is the full parent section, not just the matching chunk

Evaluation: measuring RAG quality

A RAG system without evaluation is a black box. Build a small eval set (20-50 question-answer pairs from your docs) and measure:

MetricWhat it measuresHow to compute
Context recallDid the retrieved chunks contain the answer?LLM judge: "does the gold answer appear in the context?"
Context precisionWere the top-k chunks relevant, or mostly noise?LLM judge: "is each chunk relevant to the question?"
FaithfulnessIs the answer grounded in the context, or hallucinated?LLM judge: "is every claim in the answer supported by a source?"
Answer relevanceDoes the answer actually address the question?LLM judge: "does the answer respond to what was asked?"
 
// Simple faithfulness check
async function checkFaithfulness(answer: string, context: string): Promise<boolean> {
  const r = await fetch("https://api.openai.com/v1/chat/completions", {
    method: "POST",
    headers: { "Authorization": `Bearer ${Bun.env.OPENAI_API_KEY}`, "Content-Type": "application/json" },
    body: JSON.stringify({
      model: "gpt-4o-mini",
      messages: [
        { role: "system", content: "Is every claim in the ANSWER supported by the CONTEXT? Reply only true or false." },
        { role: "user", content: `CONTEXT:\n${context}\n\nANSWER:\n${answer}` }
      ],
      temperature: 0,
    }),
  });
  return (await r.json()).choices[0].message.content.trim() === "true";
}
Don't skip evaluation. A RAG system that "feels good" in testing can silently retrieve irrelevant chunks and hallucinate confidently. A 30-question eval set catches regressions when you change chunk size, embedding model, or top-k — and gives you numbers to optimize instead of vibes.

Cost management

Intermediate RAG costs come from two places:

OperationCost driverHow to reduce
Embedding (ingest)One-time: chunk count × tokensCache embeddings; only re-embed changed docs
Embedding (query)Per-query: one embed callNegligible — don't optimize
Vector searchDatabase computeUse HNSW indexes; filter by metadata first
LLM generationContext tokens × output tokensLimit top-k; use smaller models; cache common answers

The biggest cost lever is context length: 5 chunks × 400 tokens = 2,000 tokens of context per query. With GPT-4o at $2.50/1M input tokens, that's $0.005 per query just for context. At 10,000 queries/day, that's $50/day. Switching to GPT-4o-mini ($0.15/1M input) drops it to $3/day.

// Cache common answers to avoid redundant LLM calls
const cache = new Map<string, string>();
async function ragWithCache(query: string, store: DocStore) {
  const cacheKey = query.toLowerCase().trim();
  if (cache.has(cacheKey)) return cache.get(cacheKey)!;
  const result = await rag(query, store);
  cache.set(cacheKey, result);
  return result;
}

Common mistakes

  • Chunking too large. A 2000-token chunk means the embedding averages a whole page — precision drops. Most docs work best at 256-512 tokens.
  • No metadata filtering. Searching 100k vectors without pre-filtering is slow and noisy. Filter by source, section, date, or type first.
  • Skipping reranking. Vector search alone gets you 60-70% of the way. Reranking adds 15-20 percentage points of accuracy for a small cost.
  • No eval set. "It looks good in testing" is not evaluation. Build 20-50 QA pairs and measure context recall + faithfulness.
  • Stuffing too much context. Top-k=20 with 1000-token chunks means 20k tokens of context — the model gets lost. Use top-k=5 after reranking, with smaller chunks.
  • Not handling "I don't know." If the system prompt says "answer from context" but doesn't include an explicit escape hatch, the model will hallucinate when context is insufficient. Always include "if the context doesn't contain the answer, say so."
  • Re-embedding unchanged docs. Version your embeddings. Store a hash of each document; only re-chunk and re-embed when the hash changes.

Exercises

  1. Build a RAG pipeline over your own project's README.md and AGENTS.md. Ask it 5 questions about the project and check whether the retrieved chunks contain the answer.
  2. Add metadata filtering: tag each chunk by file and section, then filter queries to a specific file.
  3. Implement two-stage retrieval (vector search top-20 + rerank top-5) and compare answer quality to vector search alone.
  4. Build a 10-question eval set. Measure context recall and faithfulness for your pipeline. Then change chunk size from 256 to 512 and see if the numbers improve or regress.
  5. Add a cache layer. Measure the cache hit rate and cost savings over 100 repeated queries.

Mini-project: Documentation RAG bot

Build a CLI tool that ingests a folder of Markdown documentation, chunks and embeds it into a local vector store (pgvector or Qdrant), and answers questions from the command line with source citations. Requirements:

  • bun run ingest ./docs/ — walk the folder, chunk each .md file, embed, and store with metadata (filename, section header, modified date).
  • bun run ask "How do I configure X?" — embed the query, retrieve top-5, optionally rerank, and print the answer with [source: file, chunk N] citations.
  • Only re-embed files whose content hash has changed since the last ingest (store hashes in a sidecar JSON file).
  • Include a --verbose flag that prints the retrieved chunks and their similarity scores before the answer, so you can debug retrieval quality.
  • Add a 5-question eval mode (bun run eval) that checks whether the answer contains expected keywords from a eval.json file.
