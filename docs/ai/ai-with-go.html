Go is an excellent language for building AI-powered backends: compiled binaries, goroutines for high concurrency, a strong standard library for HTTP and streaming, and official SDKs from both Anthropic and OpenAI. This lesson covers calling LLM APIs, streaming responses over SSE, function calling and the agent loop, the Eino framework, and the production patterns (cost tracking, context timeouts) that keep an AI service from burning money — basic through advanced.

Why Go for AI backends

Beginner Python dominates AI research, but production AI services have different priorities. The AI model is a remote API call — your code's job is to wrap that call with error handling, streaming, rate limiting, and caching. Go excels at exactly this:

NeedWhy Go is good at it
High-concurrency API gatewaysGoroutines are lightweight and built for fan-out/fan-in patterns
Low latency, minimal overheadCompiled binary, no interpreter, no GC pauses in hot paths
Streaming responses (SSE)net/http handles chunked transfer and flushing natively
Type safetyStatic types catch errors at compile time, not runtime
Existing infra integrationGo is already in most cloud-native stacks (Kubernetes, gRPC, Terraform)
Single-binary deploymentNo runtime dependencies, no virtual environments, no pip install

Calling an LLM API: the fundamentals

Beginner Every LLM API is the same shape: send a prompt, get a completion. Here's the raw call with the official Anthropic Go SDK:

// go get github.com/anthropics/anthropic-sdk-go

package main

import (
    "context"
    "fmt"
    "github.com/anthropics/anthropic-sdk-go"
    "github.com/anthropics/anthropic-sdk-go/option"
)

func main() {
    // Reads ANTHROPIC_API_KEY from the environment
    client := anthropic.NewClient(option.WithAPIKey(""))

    resp, err := client.Messages.New(context.Background(), anthropic.MessageNewParams{
        Model:     anthropic.F("claude-sonnet-4-5"),
        MaxTokens: anthropic.F(int64(1024)),
        Messages: anthropic.F([]anthropic.MessageParam{
            anthropic.NewUserMessage(anthropic.NewTextBlock("Explain goroutines in one sentence.")),
        }),
    })
    if err != nil {
        panic(err)
    }
    fmt.Println(resp.Content[0].Text)
    // "A goroutine is a lightweight thread of execution managed by the Go runtime..."
}

package main

import (
    "context"
    "fmt"
    "github.com/openai/openai-go"

func main() {
    client := openai.NewClient(option.WithAPIKey(""))  // reads OPENAI_API_KEY

    resp, err := client.Chat.Completions.New(context.Background(), openai.ChatCompletionNewParams{
        Model: openai.F("gpt-4o"),
        Messages: openai.F([]openai.ChatCompletionMessageParam{
            openai.UserMessage("Explain goroutines in one sentence."),
        }),

Both SDKs auto-read their API key from the environment (ANTHROPIC_API_KEY / OPENAI_API_KEY). In production, inject the key from your secret manager, never hard-code it. In CI, use a masked environment variable.

Streaming responses over SSE

Beginner Streaming lets the user see tokens as they're generated instead of waiting for the full response. This is critical for chat UIs — perceived latency drops from 3 seconds to 200ms. Go's net/http package handles chunked transfer encoding and http.Flusher gives you control over when to flush:

// stream.go — streaming a Claude response over HTTP
package main

import (
    "context"
    "encoding/json"
    "fmt"
    "net/http"
    "github.com/anthropics/anthropic-sdk-go"
    "github.com/anthropics/anthropic-sdk-go/option"
)

func streamHandler(w http.ResponseWriter, r *http.Request) {
    // SSE headers
    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")

    client := anthropic.NewClient()
    stream := client.Messages.NewStreaming(context.Background(), anthropic.MessageNewParams{
        Model:     anthropic.F("claude-sonnet-4-5"),
        MaxTokens: anthropic.F(int64(1024)),
        Messages: anthropic.F([]anthropic.MessageParam{
            anthropic.NewUserMessage(anthropic.NewTextBlock("Write a haiku about Go.")),
        }),
    })

    for stream.Next() {
        event := stream.Current()
        if event.Delta != nil {
            // Send each text delta as an SSE event
            data, _ := json.Marshal(map[string]string{
                "text": event.Delta.Text,
            })
            fmt.Fprintf(w, "data: %s\n\n", data)
            w.(http.Flusher).Flush()  // flush immediately — don't buffer
        }
    }
    if err := stream.Err(); err != nil {
        fmt.Fprintf(w, "data: {\"error\": \"%s\"}\n\n", err.Error())
        w.(http.Flusher).Flush()
    }
    fmt.Fprintf(w, "data: [DONE]\n\n")
    w.(http.Flusher).Flush()
}

func main() {
    http.HandleFunc("/stream", streamHandler)
    fmt.Println("Listening on :8080")
    http.ListenAndServe(":8080", nil)
}

Test it with curl -N http://localhost:8080/stream — you'll see tokens arrive one at a time.

Don't forget w.(http.Flusher).Flush() after each write. Without it, Go's net/http buffers the response and the client sees nothing until the full response is done — defeating the point of streaming.

Function calling and the agent loop

Intermediate Function calling lets the model request that your code run a function it can't do itself — query a database, call an API, read a file — and feed the result back. In Go, you write the agent loop manually, which gives you full control:

// agent.go — a Go agent that can call tools
package main

import (
    "context"
    "fmt"
    "github.com/anthropics/anthropic-sdk-go"
)

type Tool struct {
    Name        string
    Description string
    InputSchema map[string]any
    Handler     func(params map[string]any) (string, error)
}

func main() {
    client := anthropic.NewClient()

    // Define tools the model can call
    tools := map[string]Tool{
        "get_weather": {
            Name:        "get_weather",
            Description: "Get the current weather for a city",
            InputSchema: map[string]any{
                "type": "object",
                "properties": map[string]any{
                    "city": map[string]any{
                        "type":        "string",
                        "description": "The city name",
                    },
                },
                "required": []string{"city"},
            },
            Handler: func(params map[string]any) (string, error) {
                city := params["city"].(string)
                // In reality: call a weather API
                return fmt.Sprintf("It's 72°F and sunny in %s", city), nil
            },
        },
        "query_db": {
            Name:        "query_db",
            Description: "Run a read-only SQL query on the database",
            InputSchema: map[string]any{
                "type": "object",
                "properties": map[string]any{
                    "sql": map[string]any{
                        "type":        "string",
                        "description": "SELECT query to run",
                    },
                },
                "required": []string{"sql"},
            },
            Handler: func(params map[string]any) (string, error) {
                sql := params["sql"].(string)
                // In reality: run the query
                return `[{"id":1,"name":"Alice"},{"id":2,"name":"Bob"}]`, nil
            },
        },
    }

    // The agent loop
    ctx := context.Background()
    messages := []anthropic.MessageParam{
        anthropic.NewUserMessage(anthropic.NewTextBlock("What's the weather in Tokyo?")),
    }

    // Build the tool list for the API
    toolParams := make([]anthropic.ToolParam, 0, len(tools))
    for _, t := range tools {
        toolParams = append(toolParams, anthropic.ToolParam{
            Name:        anthropic.F(t.Name),
            Description: anthropic.F(t.Description),
            InputSchema: anthropic.F(t.InputSchema),
        })
    }

    for {
        resp, err := client.Messages.New(ctx, anthropic.MessageNewParams{
            Model:     anthropic.F("claude-sonnet-4-5"),
            MaxTokens: anthropic.F(int64(1024)),
            Messages:  anthropic.F(messages),
            Tools:     anthropic.F(toolParams),
        })
        if err != nil {
            panic(err)
        }

        // Check if the model wants to call a tool
        if resp.StopReason == "tool_use" {
            for _, block := range resp.Content {
                if block.Type == "tool_use" {
                    tool := tools[block.Name]
                    result, err := tool.Handler(block.Input)
                    if err != nil {
                        result = fmt.Sprintf("Error: %v", err)
                    }

                    // Feed the tool result back to the model
                    messages = append(messages,
                        anthropic.NewAssistantMessage(resp.Content...),
                        anthropic.NewUserMessage(anthropic.NewToolResultBlock(block.ID, result, false)),
                    )
                }
            }
            continue  // loop back to let the model process the result
        }

        // No tool call — the model is done
        fmt.Println(resp.Content[0].Text)
        break
    }
}

The loop is explicit: call the API, check if it wants a tool, execute the tool, feed the result back, repeat. This is more code than a framework-based approach, but you have complete control over retries, timeouts, logging, and safety at every step.

Always add a loop limit (e.g. for i := 0; i < 10; i++) to prevent infinite tool-call cycles. An agent that keeps calling tools without converging on an answer will burn through tokens and never terminate.

Eino: building a chat chain

// go get github.com/cloudwego/eino

package main

import (
    "context"
    "fmt"
    "github.com/cloudwego/eino"
    "github.com/cloudwego/eino/components/model"
    "github.com/cloudwego/eino/schema"
)

func main() {
    ctx := context.Background()

    // Create a chat model (supports OpenAI, Anthropic, local models)
    chatModel, err := model.GetChatModel(ctx, &model.Config{
        // Configure provider, model name, API key, etc.
    })
    if err != nil {
        panic(err)
    }

    // Build a chain: system prompt + user message
    messages := []*schema.Message{
        {Role: schema.System, Content: "You are a helpful Go programming assistant."},
        {Role: schema.User, Content: "How do I read a file line by line?"},
    }

    // Generate
    result, err := chatModel.Generate(ctx, messages)
    if err != nil {
        panic(err)
    }
    fmt.Println(result.Content)
}

Eino: composable RAG pipeline

// Build a RAG pipeline with Eino's graph API
import (
    "github.com/cloudwego/eino"
    "github.com/cloudwego/eino/components/retriever"
    "github.com/cloudwego/eino/components/prompt"
)

func buildRAGPipeline(ctx context.Context) {
    // Define nodes in a graph
    g := graph.New()

    // Node 1: format the prompt with retrieved context
    g.AddLambdaNode("prompt_builder", func(ctx context.Context, input map[string]any) (map[string]any, error) {
        query := input["query"].(string)
        context := input["retrieved_docs"].([]string)
        prompt := fmt.Sprintf("Context:\n%s\n\nQuestion: %s\n\nAnswer:", join(context), query)
        return map[string]any{"prompt": prompt}, nil
    })

    // Node 2: call the LLM
    g.AddChatModelNode("llm", chatModel)

    // Connect: retriever → prompt_builder → llm
    g.AddEdge("retriever", "prompt_builder")
    g.AddEdge("prompt_builder", "llm")

    // Run the pipeline
    result, err := g.Invoke(ctx, map[string]any{"query": "How do I configure pgvector?"})
}
Don't use LangChainGo in new projects — it's effectively unmaintained. Use Eino for new Go projects, or call the Anthropic/OpenAI Go SDKs directly. The SDKs are well-maintained and give you everything you need for most use cases.

Cost tracking and budgeting

// Track token usage per request with a thread-safe counter
type UsageTracker struct {
    mu        sync.Mutex
    totalIn   int64
    totalOut  int64
    costPerM  float64  // cost per 1M tokens
}

func (t *UsageTracker) Record(usage anthropic.Usage) {
    t.mu.Lock()
    defer t.mu.Unlock()
    t.totalIn += usage.InputTokens
    t.totalOut += usage.OutputTokens
}

func (t *UsageTracker) Cost() float64 {
    return (float64(t.totalIn) + float64(t.totalOut)) * t.costPerM / 1_000_000
}

// Per-request budget guard
func callWithBudget(client *anthropic.Client, msg anthropic.MessageNewParams, maxTokens int64) (*anthropic.Message, error) {
    if msg.MaxTokens.Value > maxTokens {
        return nil, fmt.Errorf("requested %d tokens exceeds budget %d", msg.MaxTokens.Value, maxTokens)
    }
    resp, err := client.Messages.New(context.Background(), msg)
    if err != nil {
        return nil, err
    }
    tracker.Record(resp.Usage)
    if tracker.Cost() > monthlyBudget {
        return nil, errors.New("monthly budget exceeded")
    }
    return resp, nil
}

Context timeouts

// ALWAYS set a context timeout on LLM calls — they can hang for minutes
ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()

resp, err := client.Messages.New(ctx, anthropic.MessageNewParams{
    // ...
})
if err != nil {
    if errors.Is(err, context.DeadlineExceeded) {
        return fmt.Errorf("LLM call timed out after 30s")
    }
    return err
}

Rate limiting with a semaphore

// Limit concurrent LLM API calls to avoid rate-limit (429) errors
var llmSem = make(chan struct{}, 5)  // max 5 concurrent calls

func callLLM(ctx context.Context, prompt string) (string, error) {
    // Acquire a slot (blocks if 5 calls are in flight)
    llmSem <- struct{}{}
    defer func() { <-llmSem }()  // release when done

    ctx, cancel := context.WithTimeout(ctx, 30*time.Second)
    defer cancel()

    resp, err := client.Messages.New(ctx, anthropic.MessageNewParams{
        Model:     anthropic.F("claude-sonnet-4-5"),
        MaxTokens: anthropic.F(int64(1024)),
        Messages:  anthropic.F([]anthropic.MessageParam{
            anthropic.NewUserMessage(anthropic.NewTextBlock(prompt)),
        }),
    })
    if err != nil {
        return "", err
    }
    return resp.Content[0].Text, nil
}

Retry with exponential backoff

func callWithRetry(ctx context.Context, prompt string, maxRetries int) (string, error) {
    var lastErr error
    for attempt := 0; attempt < maxRetries; attempt++ {
        result, err := callLLM(ctx, prompt)
        if err == nil {
            return result, nil
        }
        lastErr = err

        // Check for rate limit error
        if isRateLimited(err) {
            backoff := time.Duration(1<<attempt) * time.Second
            jitter := time.Duration(rand.Intn(500)) * time.Millisecond
            select {
            case <-time.After(backoff + jitter):
            case <-ctx.Done():
                return "", ctx.Err()
            }
            continue
        }
        // Non-retryable error
        break
    }
    return "", fmt.Errorf("after %d retries: %w", maxRetries, lastErr)
}

Common mistakes

  • No context timeout on LLM calls. An LLM API can hang for minutes. Always use context.WithTimeout — 30 seconds is a reasonable default.
  • Not flushing in streaming handlers. Without w.(http.Flusher).Flush(), Go buffers the response and the client sees nothing until the full response is done.
  • No retry on 429. LLM APIs rate-limit aggressively. Implement exponential backoff with jitter and respect the retry-after header.
  • Not tracking cost. LLM APIs charge per token. Without usage tracking, you won't notice a runaway agent loop until the bill arrives. Log input + output tokens per request.
  • No agent loop limit. An agent that keeps calling tools without converging will burn tokens and never terminate. Always cap the loop iterations.
  • Exposing the API key. Never hard-code the key. Read from the environment or a secret manager.
  • Using LangChainGo in new projects. It's unmaintained. Use Eino or call the SDKs directly.

Mini-project: AI code review service in Go

Build a Go service that reviews code diffs and returns structured findings. Requirements:

  • An HTTP endpoint that accepts a diff and calls the Claude API with a code-review system prompt. Stream the response to the client.
  • Include a get_file tool so the model can read surrounding context from the repository.
  • Add cost tracking with a sync.Mutex-protected counter and a /stats endpoint.
  • Add a 30-second context timeout, a 5-concurrent-call semaphore, and retry on 429 with exponential backoff.
  • Cache identical diffs by SHA-256 hash so re-reviewing the same change doesn't call the API again.
