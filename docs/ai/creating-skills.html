An Agent Skill is a folder of instructions that teaches an AI agent how to do a specific task — packaged in a single SKILL.md file with YAML frontmatter and Markdown body. Published as an open standard by Anthropic in December 2025, the format has been adopted by 40+ agent platforms including Claude Code, Codex CLI, Kiro CLI, GitHub Copilot, Cursor, and Gemini CLI. This lesson covers the full format, progressive disclosure, building skills from scratch, bundling scripts and references, validation, publishing, and the security model — basic through advanced.

What a skill is (and isn't)

Beginner Three concepts are easy to confuse:

ConceptWhat it isAnalogy
AGENTS.md / CLAUDE.mdPersistent project rules loaded every sessionThe company handbook
MCP toolsCallable functions with typed parametersAPI endpoints (verbs)
Skills (SKILL.md)Task-specific instruction packages loaded on demandPlaybooks / runbooks

Skills sit above tools: they encode the judgment layer — when to call which tool, in what order, and how to interpret the result. An MCP tool exposes query_database(sql); a skill teaches the agent when to query the database, what SQL to write, and how to interpret the results for this specific workflow.

The key insight is progressive disclosure: the agent reads only the skill's name and description at startup (~100 tokens), loads the full instructions only when a task matches, and pulls in bundled scripts and references only when the instructions reference them. An agent with 50 installed skills spends ~5,000 tokens at startup — a fraction of its context window.

The SKILL.md format

Beginner A skill is a directory containing at minimum a SKILL.md file:

my-skill/
├── SKILL.md          # Required: metadata (frontmatter) + instructions (body)
├── scripts/          # Optional: executable code the agent can run
├── references/       # Optional: documentation loaded on demand
└── assets/           # Optional: templates, data files, static resources

The SKILL.md file has two parts: YAML frontmatter and a Markdown body.

Required frontmatter

---
name: commit-format
description: Format git commit messages using conventional commits with scope. Use when committing code or writing commit messages.
---

Only two fields are required, but they carry the most weight:

FieldRulesWhy it matters
name1-64 chars, lowercase alphanumeric + hyphens, must match directory nameThe agent's identifier; registries index by it
descriptionUp to 1,024 chars; describe what the skill does and when to use itThe agent reads this to decide whether to activate — vague descriptions mean unreliable activation
The name field must match the parent directory name. my-skill/SKILL.md with name: my-skill is valid; name: MySkill or name: my_skill in that directory will fail validation.

Optional frontmatter

---
name: db-migrate
description: Run and manage database migrations with alembic. Use when the user mentions migrations, schema changes, or database updates.
license: Apache-2.0
compatibility: Requires Python 3.10+ and alembic
metadata:
  author: example-org
  version: "1.0"
allowed-tools: Bash Read
---
FieldWhat it doesExample
licenseLicense name or reference to bundled LICENSE.txtApache-2.0
compatibilityEnvironment requirements (up to 500 chars)Requires Python 3.10+ and alembic
metadataArbitrary key-value pairs (author, version, etc.)author: example-org, version: "1.0"
allowed-toolsPre-approved tools (experimental, varies by agent)Bash(git:*) Read

Building your first skill

Beginner Start with a real, repeated workflow where your agent struggles or needs the same instructions every time. Here's a commit-formatting skill:

# Create the skill directory (name must match the frontmatter name)
mkdir -p commit-format/references

# commit-format/SKILL.md
cat > commit-format/SKILL.md << 'SKILL'
---
name: commit-format
description: Format git commit messages using conventional commits with scope. Use when committing code or writing commit messages.
---

Format all commit messages as:

    <type>(<scope>): <subject>

Types: feat, fix, docs, style, refactor, test, chore, perf, ci, build
Scope: the module or component affected (optional but recommended)
Subject: imperative mood, lowercase, no period, max 72 chars

Body (optional, blank line after subject):
- Explain what and why, not how
- Wrap at 72 chars

Footer (optional, blank line after body):
- BREAKING CHANGE: description
- Closes #123, Refs #456

## Rules

1. If the change is a new feature: type = feat
2. If the change fixes a bug: type = fix
3. If the change is documentation only: type = docs
4. Always include a scope when the project has multiple modules
5. Never use "updated" or "changed" in the subject — be specific

See [examples](references/examples.md) for real-world samples.
SKILL

# commit-format/references/examples.md
cat > commit-format/references/examples.md << 'REF'
# Commit Message Examples

## Feature
feat(auth): add OAuth2 login flow with Google

Adds Google OAuth2 as an alternative login method.
Users can now sign in with their Google account alongside
the existing email/password flow.

Closes #142

## Bug fix
fix(api): handle nil pointer in user handler

The /api/users/:id endpoint panicked when the database
returned a nil user. Added a nil check and return 404.

Refs #98

## Breaking change
feat(db)!: switch from JSON columns to typed schema

BREAKING CHANGE: the users.preferences column is replaced
by separate columns. Run the migration script before upgrading.
REF

That's a complete, working skill. The agent reads the name and description at startup, loads the body when the user mentions commits, and pulls in references/examples.md only when it needs to see real examples.

Where agents discover skills

Beginner Agents load skills from multiple locations, with workspace-level skills taking highest precedence:

# Discovery order (highest priority first)
<workspace>/skills/              # workspace skills (project-specific)
<workspace>/.agents/skills/      # project agent skills
~/.agents/skills/                 # personal skills (all projects)
~/.kiro/skills/                   # managed/bundled skills
# + any extra directories configured by the agent

When the same skill name exists in multiple locations, the higher-priority source wins. This lets you override a bundled skill with a project-specific version without changing global config.

Installing skills in Kiro

# Install a skill from the registry
kiro skills install @author/skill-name

# Install globally (all projects)
kiro skills install @author/skill-name --global

# List installed skills
kiro skills list

# Search the public registry
kiro skills search "database migration"

Installing skills in Claude Code

# Claude Code auto-discovers skills in these paths:
# ./skills/               (project)
# ~/.claude/skills/        (personal)
# Managed registry skills

# Install from registry
claude skills install @anthropic/skill-name

Progressive disclosure in depth

Intermediate The three-stage loading model is what makes skills scalable:

StageWhenWhat loadsToken cost
1. DiscoveryAgent startupname + description only~100 tokens per skill
2. ActivationTask matches descriptionFull SKILL.md body< 5,000 tokens recommended
3. Resource loadingInstructions reference a filescripts/, references/, assets/Only when needed

This shapes how you structure a skill:

# DON'T: cram everything into SKILL.md (slow activation, wastes context)
my-skill/
└── SKILL.md   # 2000 lines — everything is here

# DO: keep the body lean, push detail to references/
my-skill/
├── SKILL.md              # 100 lines: core steps, decision rules
├── references/
│   ├── api-schema.md     # loaded only when the agent needs the schema
│   ├── error-codes.md    # loaded only when debugging errors
│   └── provider-config.md # loaded only for specific cloud providers
├── scripts/
│   └── validate.sh       # loaded only when the agent runs validation
└── assets/
    └── template.json     # loaded only when generating output
The specification recommends keeping the SKILL.md body under 500 lines and 5,000 tokens. If your instructions exceed that, split reference material into subdirectories. The agent will find and load referenced files when needed — you're not hiding information, you're staging it.

A complete skill: database migrations

Intermediate Here's a more complete skill that demonstrates good patterns — step-by-step procedures, explicit commands, edge case handling, and reference files:

# db-migrate/SKILL.md
---
name: db-migrate
description: Run and manage database migrations with alembic. Use when the user mentions migrations, schema changes, alembic, or database updates. Handles creating, running, and rolling back migrations safely.
compatibility: Requires Python 3.10+ and alembic
---

## Creating a Migration

1. Check current state: `alembic current`
2. Generate a migration: `alembic revision --autogenerate -m "<description>"`
3. Review the generated file in `alembic/versions/`
4. Verify both `upgrade()` and `downgrade()` functions are correct
5. Test locally: `alembic upgrade head` then `alembic downgrade -1`

## Running Migrations

- Upgrade to latest: `alembic upgrade head`
- Upgrade one step: `alembic upgrade +1`
- Downgrade one step: `alembic downgrade -1`
- Downgrade to specific revision: `alembic downgrade <revision>`
- Show current state: `alembic current`
- Show history: `alembic history --verbose`

## Safety Rules

1. NEVER modify a migration that has been applied to production
2. ALWAYS test migrations locally before pushing
3. For data migrations (not schema), create a separate file and mark it
4. If autogenerate misses a change, write the migration manually
5. Include a `downgrade()` for every migration — no exceptions
6. For large tables, use batch mode: `alembic batch_alter_table`

## Edge Cases

- If the migration adds a NOT NULL column to a table with rows,
  add it as nullable first, backfill data, then alter to NOT NULL
- If renaming a column, do it in three steps: add new, copy data, drop old
  (alembic autogenerate does NOT detect renames — it sees add+drop)

See [naming conventions](references/naming.md) for revision file naming rules.
See [provider config](references/providers.md) for database-specific settings.

# db-migrate/references/naming.md
# Migration Naming Conventions

Revision files use the format: `<timestamp>_<snake_case_description>.py`

Examples:
- 20260101_001_add_user_preferences.py
- 20260115_002_rename_preferences_to_settings.py
- 20260201_003_add_index_on_user_email.py

Rules:
1. Always use a descriptive name, not "migration_001"
2. Prefix with the action: add_, remove_, rename_, alter_, drop_
3. Never reuse a revision ID, even for reverted migrations

Skills with bundled scripts

Advanced Skills can include executable scripts that the agent runs:

# deploy-check/SKILL.md
---
name: deploy-check
description: Validate a deployment is healthy after shipping. Use when the user mentions deploying, deployment verification, or post-deploy checks. Runs health checks, smoke tests, and rollback validation.
---

## Post-Deploy Validation

1. Run the health check script: `bash scripts/health-check.sh $SERVICE_URL`
2. If any check fails, see [rollback procedures](references/rollback.md)
3. If all checks pass, run smoke tests: `bash scripts/smoke-tests.sh $SERVICE_URL`

## What the health check verifies

- HTTP 200 from /health endpoint
- Database connectivity (check /health/db)
- Cache connectivity (check /health/cache)
- Response time < 500ms for /health
- No 5xx errors in the last 60 seconds (via logs API)

## Rollback

If health checks fail:
1. Check [rollback procedures](references/rollback.md) for the specific service
2. Run: `bash scripts/rollback.sh $SERVICE_NAME`
3. Verify the previous version is healthy

# deploy-check/scripts/health-check.sh
#!/bin/bash
# Usage: bash health-check.sh https://my-service.example.com
set -euo pipefail

URL="$1"
EXIT_CODE=0

echo "Checking $URL ..."

# Health endpoint
STATUS=$(curl -s -o /dev/null -w "%{http_code}" "$URL/health")
if [ "$STATUS" != "200" ]; then
  echo "FAIL: /health returned $STATUS (expected 200)"
  EXIT_CODE=1
else
  echo "OK: /health returned 200"
fi

# Database check
STATUS=$(curl -s -o /dev/null -w "%{http_code}" "$URL/health/db")
if [ "$STATUS" != "200" ]; then
  echo "FAIL: /health/db returned $STATUS"
  EXIT_CODE=1
else
  echo "OK: /health/db returned 200"
fi

# Response time
TIME=$(curl -s -o /dev/null -w "%{time_total}" "$URL/health")
if (( $(echo "$TIME > 0.5" | bc -l) )); then
  echo "WARN: /health response time ${TIME}s (> 500ms)"
else
  echo "OK: /health response time ${TIME}s"
fi

exit $EXIT_CODE
Scripts in a skill run with the same permissions as the agent. A skill that bundles scripts/health-check.sh can execute arbitrary code on your machine. Always read bundled scripts before installing a community skill. See the Security section below.

Writing effective instructions

Intermediate The quality of the Markdown body determines whether the skill actually helps. Vague instructions produce inconsistent results:

# BAD: the agent doesn't know what to do
---
name: git-helper
description: Helps with Git operations.
---
Help the user with Git commands when they ask.

# GOOD: specific, conditional, with decision rules
---
name: git-helper
description: Run Git operations safely — branch, commit, merge, rebase, resolve conflicts, and clean up. Use when the user mentions Git commands, branching, merging, or resolving merge conflicts.
---

## Branching
- Always branch from the latest main: `git checkout main && git pull && git checkout -b <branch>`
- Use descriptive names: feat/add-login, fix/null-pointer, docs/api-reference

## Committing
- Stage specific files, not `git add .`: `git add src/handler.go src/handler_test.go`
- Write conventional commit messages (see [commit format](references/commit-format.md))
- If the pre-commit hook fails, fix the issue and create a NEW commit (never --amend after a hook failure)

## Merging
- If the branch is behind main, rebase: `git rebase main`
- If there are conflicts, prefer the incoming change for feature work, the current change for config files
- After merging, delete the local branch: `git branch -d <branch>`

## What NOT to do
- Don't force push to main or master
- Don't use --no-verify unless explicitly asked
- Don't squash if the PR has meaningful individual commits
- Don't `git add -A` — stage explicit file paths

Good instruction patterns:

  • Step-by-step procedures for the primary workflow (numbered lists).
  • Conditional rules: "If the user asks for X, do Y. If the file contains Z, handle it by doing W."
  • Input/output examples so the agent knows what success looks like.
  • Edge cases and error handling for common failure modes.
  • Explicit "don't" rules — tell the agent what NOT to do, not just what to do.
  • Clear boundaries stating what the skill does not cover.

Validation and testing

Intermediate Validate before publishing:

# Validate with the skills-ref reference library
skills-ref validate ./my-skill

# Checks:
#   - name matches directory name
#   - name is lowercase, alphanumeric + hyphens only
#   - description is present and under 1024 chars
#   - frontmatter is valid YAML
#   - no missing required fields

For testing, put the skill in your workspace's skills/ directory, start a new agent session, and give it a task that should trigger the skill:

# Test: does the agent activate the skill?
mkdir -p ./skills/
cp -r my-skill ./skills/

# Start a new session (skills are loaded at startup)
claude   # or: kiro chat

# Give it a task that matches the description
> "I need to create a new database migration for adding a user preferences table"

# Check: did the agent follow the skill's instructions?
# Did it use the naming conventions? Did it handle the edge cases?

Publishing skills

Advanced Share skills through registries. The public skills registry (skills.sh) hosts community skills:

# Publish to the registry (if supported by your agent)
# Claude Code:
claude skills publish ./my-skill

# Kiro:
kiro skills publish ./my-skill

# Other registries (ClawHub, GitHub):
# Push the skill directory to a GitHub repo
# The registry indexes it from the repo URL

Install community skills:

# Search the registry
kiro skills search "pdf processing"

# Install
kiro skills install @author/pdf-processing

# Verify before installing (read the SKILL.md and bundled scripts)
kiro skills inspect @author/pdf-processing

Security: the supply chain

Advanced Skills run with the same permissions as the agent — filesystem access, shell execution, network access. A compromised or malicious skill can:

  • Read environment variables (including API keys and secrets)
  • Execute arbitrary shell commands
  • Access and exfiltrate files from your project
  • Modify your code in unexpected ways

Before installing any community skill:

# 1. Read the SKILL.md — does it do what it claims?
kiro skills inspect @author/skill-name

# 2. Read ALL bundled scripts — not just SKILL.md
# Skills can hide malicious code in scripts/ or reference files
cat skills/@author/skill-name/scripts/*.sh
cat skills/@author/skill-name/scripts/*.py

# 3. Check the metadata — who is the author? Is the repo trusted?
kiro skills info @author/skill-name

# 4. Verify the skill's allowed-tools — does it need the tools it claims?
# A "formatting" skill that requests Bash access is suspicious

# 5. Prefer skills from organizations you trust
# Anthropic's official skills repo: github.com/anthropics/skills
# Your team's internal registry
In early 2026, security researchers discovered hundreds of typosquatted malicious skills on community registries. A skill named pdf-procesing (missing an "s") looked identical to the legitimate pdf-processing but ran malware. Always verify the exact author and skill name before installing, and read bundled scripts — not just the SKILL.md.

Skills vs AGENTS.md vs MCP: when to use what

Intermediate

NeedUseWhy
Project rules that apply to every taskAGENTS.mdAlways loaded; sets conventions, commands, don'ts
A reusable workflow for a specific taskSkillLoaded on demand; packaged with instructions + scripts + references
Expose a callable function to agentsMCP serverStandardized protocol; any agent can call it
Teach the agent when to call an MCP tool and how to interpret resultsSkill + MCPSkill wraps the MCP tool with procedural knowledge
Share a workflow across teams/projectsSkillPortable; publish to registry; versioned
Persistent model behavior (tone, format)AGENTS.mdAlways in context; applies to every interaction

Common mistakes

  • Vague description. "Helps with Git" doesn't tell the agent when to activate. Include specific keywords and trigger conditions: "Use when the user mentions branching, merging, or resolving conflicts."
  • Cramming everything in SKILL.md. If the body exceeds 500 lines, move reference material to references/. The agent loads it on demand — you're staging, not hiding.
  • Name doesn't match directory. name: my-skill in a directory called my_skill/ fails validation. The name must match the parent directory exactly.
  • No "don't" rules. Telling the agent what NOT to do is as important as what to do. Without boundaries, the agent will guess and sometimes guess wrong.
  • Not testing activation. Write a skill, start a new session, give a matching task, and verify the agent actually activated and followed the instructions. A skill that never activates is dead weight.
  • Installing community skills without reading scripts. A SKILL.md that looks benign can bundle a script that reads your .env or exfiltrates data. Read every file before installing.
  • One mega-skill instead of focused skills. "Git helper" that covers branching, committing, merging, rebasing, and conflict resolution is too broad. Split into focused skills the agent can activate independently.

Exercises

  1. Create a commit-format skill with the examples from this lesson. Install it in your workspace's skills/ directory, start a new agent session, and ask it to "commit my changes." Verify it follows the format.
  2. Build a skill for your project's test workflow: how to run tests, what the test command is, what a failing test looks like, and how to debug. Include a references/debug-guide.md for common failure patterns.
  3. Write a skill that bundles a script — a lint-check skill with scripts/run-linter.sh. The agent should run the script when activated and interpret the output.
  4. Validate your skill with skills-ref validate. Fix any issues. Then test activation by starting a new session and giving a task that should trigger it.
  5. Audit a community skill from the registry: read the SKILL.md, read every bundled script, and identify whether it needs the permissions it requests. Report any concerns.

Mini-project: Code review skill package

Build a complete, publishable skill that teaches an agent to review code. Requirements:

  • SKILL.md with a description that activates on "review this code," "check for bugs," or "audit this PR."
  • Step-by-step instructions: read the diff, check for bugs (null dereference, resource leaks, race conditions), check security (injection, auth bypass), rate severity (critical/moderate/minor), output a structured review.
  • A references/severity-guide.md with criteria for each severity level and examples.
  • A scripts/parse-diff.sh that extracts changed files and line ranges from a git diff.
  • Explicit "don't" rules: don't review style nitpicks as critical, don't suggest unrelated refactors, don't approve your own changes.
  • Validate the skill, test activation in a real session, and confirm the agent follows the instructions on a real diff.
