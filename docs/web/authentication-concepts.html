Authentication proves who a user is; authorization decides what they may do. Learn the two main session models (server sessions vs JWTs), how to store tokens safely, OAuth2/OIDC for "log in with…", and the attacks the choices defend against.

Sessions vs tokens

Beginner Two ways to remember a logged-in user across requests:

Server sessionJWT (token)
StateSession ID in a cookie; data in server storeSigned claims in the token itself
RevocationEasy — delete the sessionHard — valid until expiry (need a denylist)
ScalingNeeds shared store (Redis/DB)Stateless — any server can verify
SizeTiny cookieLarger; sent on every request

Password handling

// NEVER store plaintext or a plain hash. Use a slow, salted algorithm.
// bcrypt / argon2 / scrypt — they're slow ON PURPOSE to resist brute force.
hash = argon2.hash(password)          // on signup; store the hash
ok   = argon2.verify(hash, attempt)   // on login
Non-negotiables: never store plaintext passwords; never use fast hashes (MD5/SHA-256) for passwords; always salt (bcrypt/argon2 do it for you). Rate-limit login attempts and never reveal whether the email or the password was wrong ("invalid credentials" for both).

JWTs: access + refresh

Intermediate A JWT has three base64url parts — header, payload (claims), signature — joined by dots. The signature (not encryption) lets the server verify it wasn't tampered with:

eyJhbGci...  .  eyJzdWIiOiI0MiIsImV4cCI6...  .  SflKxw...
   header              payload (claims)            signature

// payload: { "sub": "42", "role": "user", "exp": 1699999999 }

The durable pattern is short-lived access token + long-lived refresh token with rotation:

  • Access token (~15 min): sent on API calls, authorizes requests.
  • Refresh token (days/weeks): used only to mint a new access token; rotated (invalidated and reissued) on each use so a stolen refresh token is detectable.
JWT pitfalls: (1) a JWT is signed, not encrypted — never put secrets in the payload; anyone can decode it. (2) Reject the "alg": "none" trick and never let the token pick the algorithm. (3) Always check exp. (4) You cannot "log out" a JWT without server state — plan for a denylist or keep access tokens short.

Where to store tokens

Store session/access tokens in an HttpOnly, Secure, SameSite cookie — not in localStorage. localStorage is readable by any JavaScript, so a single XSS flaw leaks every user's token. HttpOnly cookies are invisible to JS, which closes that door (at the cost of needing CSRF protection — see below).
Set-Cookie: access=…; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=900

CSRF and CORS

Because cookies are sent automatically, a malicious site could trigger an authenticated request (CSRF). Defenses: SameSite=Lax/Strict cookies (blocks most cross-site sends), a CSRF token for state-changing requests, and strict CORS so other origins can't read responses.

OAuth2 & OpenID Connect

Advanced "Log in with Google/GitHub" uses OAuth2 (delegated authorization) + OIDC (an identity layer on top). The Authorization Code flow with PKCE:

1. App redirects user to the provider's /authorize (with client_id, redirect_uri,
   scope, state, code_challenge).
2. User authenticates & consents at the provider.
3. Provider redirects back with a one-time ?code=…
4. App's SERVER exchanges code (+ code_verifier) at /token for an ID token
   (OIDC: who the user is) + access token (what it can call).
5. App creates its own session for the user.
Never implement crypto or token verification by hand. Use a vetted library (your framework's auth middleware, or a provider SDK) and a battle-tested JWT library. The state parameter prevents CSRF on the callback; PKCE protects public clients.

Exercises

  • Hash a password with argon2/bcrypt and verify it; confirm two hashes of the same password differ (salt).
  • Decode a JWT at jwt.io and explain why the payload is readable but still trustworthy to the server.
  • List the cookie flags for a session token and what attack each one mitigates.

Mini-project: a login flow

Build email/password login on a small server: argon2-hashed passwords, a short-lived access JWT + rotating refresh token both in HttpOnly+Secure+SameSite cookies, a /refresh endpoint, rate-limited login, and a logout that clears + invalidates the refresh token. Then add "Log in with GitHub" via the Authorization Code + PKCE flow using a library — never hand-rolled crypto.
