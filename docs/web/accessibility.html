Accessibility (a11y) means everyone can use your site — including people using keyboards, screen readers, magnification, or voice control. Most of it comes from semantic HTML; ARIA fills the gaps; and a handful of habits prevent the common failures.

Semantic HTML does most of the work

Beginner A real <button> is focusable, clickable by keyboard (Enter/Space), and announced as "button" — all for free. A <div onclick> has none of that.

<!-- Accessible: keyboard + screen reader work automatically -->
<button type="button" onclick="save()">Save</button>

<!-- Broken: not focusable, no keyboard, announced as nothing -->
<div class="btn" onclick="save()">Save</div>
The first rule of ARIA: don't use ARIA when a native element exists. Use <button>, <a href>, <input>, <nav>, <main> — they're accessible by default and you can't out-engineer them with divs and roles.

Images, labels, and names

<img src="chart.png" alt="Sales rose 40% from Q1 to Q2">   <!-- meaningful -->
<img src="divider.png" alt="">                             <!-- decorative -->

<label for="q">Search</label>
<input id="q" name="q">                                     <!-- labelled -->

<button aria-label="Close dialog">✕</button>                <!-- icon-only needs a name -->

Every interactive element needs an accessible name — from its text, a <label>, aria-label, or aria-labelledby. Icon-only buttons are the usual offender.

Keyboard navigation and focus

Intermediate Everything clickable must be reachable and operable with the keyboard alone:

/* NEVER remove the focus outline without replacing it */
:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px; }

<!-- Skip link so keyboard users can jump past the nav -->
<a href="#main" class="skip-link">Skip to content</a>
...
<main id="main" tabindex="-1">…</main>
Common mistakes: (1) outline: none with no replacement — keyboard users lose track of where they are. (2) Positive tabindex values (tabindex="3") — they create a confusing tab order; only ever use 0 (focusable in order) or -1 (focusable only via script). (3) Opening a modal without moving focus into it or trapping focus there.

ARIA for custom widgets

When you must build something HTML has no element for (a tab panel, a disclosure, a custom combobox), ARIA describes its role, state, and relationships:

<button aria-expanded="false" aria-controls="menu">Options</button>
<ul id="menu" hidden> … </ul>
// toggle aria-expanded + the hidden attribute together in JS

<div role="alert">Form saved</div>        <!-- announced immediately -->
<div aria-live="polite">3 results</div>   <!-- announced when idle -->

Follow the ARIA Authoring Practices Guide patterns — custom widgets have expected keyboard behavior (arrow keys in a menu, Escape to close) that you must implement, not just the attributes.

Color and contrast

/* WCAG AA: 4.5:1 for normal text, 3:1 for large text (≥24px or ≥19px bold) */
Never convey information by color alone. A red/green status dot is invisible to colorblind users — add text or an icon. Check contrast with your browser's devtools or the WebAIM contrast checker.

Testing

  • Keyboard: unplug the mouse. Can you reach and operate everything with Tab/Shift+Tab/Enter/Space/arrows/Escape?
  • Screen reader: VoiceOver (⌘+F5 on macOS) or NVDA (Windows). Does it announce names, roles, and state changes?
  • Automated: Lighthouse a11y audit and axe DevTools catch ~40% of issues — a floor, not a ceiling.

Exercises

  • Replace a <div onclick> "button" with a real <button> and test it with the keyboard.
  • Add a skip link and a visible :focus-visible style; tab through the page.
  • Give every icon-only control an aria-label; verify with a screen reader.

Mini-project: an accessible disclosure + modal

Build a collapsible FAQ (button with aria-expanded toggling a region) and a modal dialog that moves focus in on open, traps Tab inside it, closes on Escape, and restores focus to the trigger on close. Pass a Lighthouse a11y audit and a full keyboard-only walkthrough — the two checks that matter most.
