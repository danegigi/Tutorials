React Aria (from Adobe's React Spectrum project) gives you the behavior and accessibility of UI components without any styling. It handles the parts that are genuinely hard to get right — keyboard interaction, focus management, ARIA attributes, screen-reader announcements, touch, and internationalization — and leaves the look entirely to you. There are two layers: ready-made Components and lower-level hooks.

The accessibility problem it solves

Beginner A "simple" custom select is a trap: it needs roving focus, type-ahead, aria-activedescendant, correct roles, Escape-to-close, click-outside, and screen-reader labels — and most hand-rolled ones get several of these wrong. React Aria implements the WAI-ARIA Authoring Practices for you, tested across real assistive tech, so your component is accessible by default and you only write the markup and CSS.

React Aria Components — the easy layer

Start with react-aria-components: styled-nothing but fully-behaving components you compose like normal JSX.

npm install react-aria-components
import { Button } from "react-aria-components";

<Button onPress={() => alert("hi")} className="btn">
  Press me
</Button>
Note onPress, not onClick. React Aria normalizes mouse, touch, and keyboard into a single press interaction — it fires correctly on Enter/Space for keyboard users and handles touch without the 300ms delay. This consistency is the whole point.

A real example: an accessible Select

The compositional API mirrors the ARIA structure. You get full keyboard support, type-ahead, and correct roles for free:

import { Select, SelectValue, Button, Popover, ListBox, ListBoxItem, Label } from "react-aria-components";

function FruitPicker() {
  return (
    <Select>
      <Label>Favorite fruit</Label>
      <Button>
        <SelectValue />
        <span aria-hidden="true">▾</span>
      </Button>
      <Popover>
        <ListBox>
          <ListBoxItem id="apple">Apple</ListBoxItem>
          <ListBoxItem id="banana">Banana</ListBoxItem>
          <ListBoxItem id="cherry">Cherry</ListBoxItem>
        </ListBox>
      </Popover>
    </Select>
  );
}

Try it with the keyboard: the listbox opens on Enter/Space/↓, arrows move the selection, typing "ch" jumps to Cherry, Escape closes, and focus returns to the button — none of which you wrote.

Forms: TextField and validation

Intermediate Form components wire up labels, descriptions, and error messages with the right aria-describedby/aria-invalid relationships automatically. React Aria also integrates with native HTML form validation:

import { TextField, Label, Input, FieldError, Text } from "react-aria-components";

<TextField name="email" type="email" isRequired>
  <Label>Email</Label>
  <Input />
  <Text slot="description">We'll never share it.</Text>
  <FieldError />   {/* announces validation errors to screen readers */}
</TextField>

Wrap fields in the Form component to get submit handling and server-error display. The label is associated, the description is linked via aria-describedby, and errors are announced — automatically.

Styling with data attributes

Components expose their state as data attributes, so you style every interaction state in CSS without JS. className and style also accept a function receiving the current state:

/* style states via data-* attributes */
.react-aria-Button[data-pressed]  { transform: translateY(1px); }
.react-aria-Button[data-focus-visible] { outline: 2px solid var(--focus); }
.react-aria-ListBoxItem[data-selected] { font-weight: 600; }
.react-aria-ListBoxItem[data-disabled] { opacity: 0.4; }
<Button
  className={({ isPressed, isFocusVisible }) =>
    `btn ${isPressed ? "btn-active" : ""} ${isFocusVisible ? "ring" : ""}`
  }
>Save</Button>
Because state is exposed as data attributes, React Aria pairs perfectly with Tailwind: use the data-[pressed]: and data-[focus-visible]: variants to style states inline, keeping all styling in your utility classes.

Focus management and overlays

Overlays (Dialog, Popover, Modal) handle the fiddly accessibility obligations: focus is trapped inside while open, scroll is locked, focus returns to the trigger on close, and Escape/click-outside dismiss. You just compose them:

import { DialogTrigger, Button, Modal, Dialog, Heading } from "react-aria-components";

<DialogTrigger>
  <Button>Delete</Button>
  <Modal>
    <Dialog>
      {({ close }) => (
        <>
          <Heading slot="title">Are you sure?</Heading>
          <Button onPress={close}>Cancel</Button>
          <Button onPress={close}>Delete</Button>
        </>
      )}
    </Dialog>
  </Modal>
</DialogTrigger>

The hooks layer — full control

Advanced When you need to build a bespoke component or integrate with your own DOM structure, drop to the hooks (react-aria) + state (react-stately) packages. A hook returns the exact props to spread onto your elements:

npm install react-aria react-stately
import { useButton } from "react-aria";
import { useRef } from "react";

function MyButton(props) {
  const ref = useRef(null);
  const { buttonProps, isPressed } = useButton(props, ref);
  return (
    <button {...buttonProps} ref={ref} data-pressed={isPressed || undefined}>
      {props.children}
    </button>
  );
}

Here useButton gives you a correct, cross-device button: it merges your handlers, adds the right ARIA, and reports isPressed. The component layer is built from exactly these hooks — so if a component is 90% right but you need custom internals, you own the markup while keeping the behavior.

React Aria vs daisyUI vs a component library

ToolGives youYou still provide
daisyUICSS styling (looks)Behavior, state, accessibility wiring
React AriaBehavior + accessibilityAll styling (looks)
MUI / ChakraBoth — opinionated looks + behaviorLess control; harder to restyle

A powerful combination: React Aria for behavior/accessibility + Tailwind/daisyUI for the styling. You get a fully accessible component that looks exactly like your design system.

Common mistakes

  • Using onClick instead of onPress. onPress is the normalized, keyboard/touch-correct event. Reaching back to onClick loses that.
  • Spreading hook props onto the wrong element or forgetting the ref. Each hook expects its props on a specific element plus the ref it was given.
  • Re-adding ARIA that the hook/component already provides. Double role/aria-* attributes can confuse screen readers — let React Aria own them.
  • Styling state with JS when a data attribute exists. Prefer [data-pressed]/[data-focus-visible] in CSS over manual state tracking.
  • Removing focus outlines entirely. Style [data-focus-visible] instead — never ship a component with no visible keyboard focus.
  • Reaching for the hooks layer first. Start with React Aria Components; only drop to hooks when you need custom internals.

Exercises

  • Render a React Aria Button and style its data-pressed and data-focus-visible states in CSS; test entirely with the keyboard.
  • Build the Select example and verify type-ahead, arrow navigation, Escape-to-close, and focus return work without extra code.
  • Create a TextField with isRequired and a FieldError; submit empty and confirm the error is announced and linked via aria-describedby.
  • Build a confirm Dialog via DialogTrigger/Modal and verify focus is trapped and returns to the trigger on close.
  • Reimplement a toggle button with the useButton hook on your own <button>, exposing isPressed as a data attribute.

Mini-project: an accessible, branded form

Build a settings form that is accessible by construction and styled to your brand (pair with Tailwind/daisyUI):

  • A Form with a TextField (name), an email field with validation and FieldError, a Select for a plan, and a Switch for notifications.
  • A "Save" Button and a confirm Dialog that opens on destructive actions, with focus trapped.
  • Style every component purely through its data attributes / render-prop state — no inline event-driven styling.
  • Audit it: tab through with the keyboard only (every control reachable, visible focus everywhere), then run a screen reader and confirm labels, descriptions, and errors are announced.
  • Run an automated check (axe DevTools or Lighthouse Accessibility) and confirm zero violations.

The result demonstrates React Aria's promise: you wrote markup and CSS, and got a form that works flawlessly with keyboard, touch, and screen readers.
