Good animation is fast, purposeful, and respectful of users who don't want it. The web gives you three layers — CSS transitions, CSS keyframe animations, and the JavaScript Web Animations API — plus a hard rule about which properties are cheap to animate. This lesson covers all three, the 60fps path, scroll-driven effects, and the accessibility obligation that prefers-reduced-motion enforces.

The 60fps rule: animate transform and opacity

Intermediate The browser renders in a pipeline: style → layout → paint → composite. Animating a property that triggers layout (width, height, top, margin) forces the browser to recompute positions every frame — janky. Animating transform and opacity only touches the composite step, which the GPU handles cheaply.

/* JANKY — animates layout every frame */
.bad { transition: left 0.3s, width 0.3s; }

/* SMOOTH — composite only, GPU-accelerated */
.good { transition: transform 0.3s, opacity 0.3s; }
.good:hover { transform: translateX(20px) scale(1.05); }
"Animate transform/opacity, not layout" is the single most important performance rule here. Move with translate (not top/left), resize with scale (not width/height), fade with opacity (not visibility steps). The look is identical; the frame cost is not.

CSS transitions: state A → state B

.btn {
  background: #4f46e5;
  transition: transform 150ms ease-out, box-shadow 150ms ease-out;
}
.btn:hover  { transform: translateY(-2px); box-shadow: 0 4px 12px rgba(0,0,0,.2); }
.btn:active { transform: translateY(0); }

Transitions animate between two states when a property changes (hover, a toggled class). Specify the property, duration, and easing. They're the right tool for the vast majority of UI motion.

CSS keyframe animations: multi-step & looping

@keyframes pulse {
  0%   { transform: scale(1);    opacity: 1; }
  50%  { transform: scale(1.08); opacity: .7; }
  100% { transform: scale(1);    opacity: 1; }
}
.badge {
  animation: pulse 1.5s ease-in-out infinite;
}
/* a one-shot entrance */
@keyframes slide-in { from { transform: translateY(12px); opacity: 0; } to { transform: none; opacity: 1; } }
.card { animation: slide-in 300ms ease-out both; }  /* `both` keeps the end state */

Use keyframes for anything with more than two steps, loops, or an independent entrance/exit — things a transition can't express.

The Web Animations API (WAAPI)

Advanced When animation must be dynamic — computed values, sequencing, pause/reverse, awaiting completion — drive it from JavaScript with element.animate(). It uses the same compositor path as CSS, so it's just as fast.

const anim = el.animate(
  [{ transform: "translateY(0)", opacity: 1 },
   { transform: "translateY(-40px)", opacity: 0 }],
  { duration: 300, easing: "ease-out", fill: "forwards" }
);
await anim.finished;      // a Promise — sequence animations cleanly
anim.pause(); anim.reverse(); anim.playbackRate = 2;
WAAPI's animation.finished Promise is what makes complex sequences readable — await one animation, then start the next, no animationend listener juggling. Reach for WAAPI when values are dynamic or you need control; stay in CSS for static, declarative motion.

Scroll-driven animations

/* Modern CSS: tie an animation's timeline to scroll — no JS, no scroll listener */
@keyframes reveal { from { opacity: 0; transform: translateY(20px); } to { opacity: 1; } }
.section {
  animation: reveal linear both;
  animation-timeline: view();   /* progresses as the element scrolls into view */
}

Where scroll-timeline isn't supported, the IntersectionObserver is the robust fallback — observe elements and add an "in-view" class to trigger a CSS transition, instead of a scroll event handler (which fires constantly and janks).

Respect prefers-reduced-motion

Motion can cause nausea, dizziness, and migraines for users with vestibular disorders. The OS exposes their preference, and honoring it is an accessibility requirement, not a nicety:

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
// WAAPI: check it in JS too
if (!matchMedia("(prefers-reduced-motion: reduce)").matches) el.animate(frames, opts);
Reduce, don't necessarily remove. The goal is to kill large motion (slides, parallax, auto-playing loops) while keeping subtle, essential feedback (a quick opacity change). An all-or-nothing kill switch is a fine default; a thoughtful reduced variant is better. Either way, never ignore the query.

Common mistakes

  • Animating layout properties (width, top, margin) instead of transform/opacity — guaranteed jank.
  • Ignoring prefers-reduced-motion — an accessibility failure that can physically harm users.
  • Driving animation from a scroll event handler instead of IntersectionObserver / scroll-timeline — fires constantly, drops frames.
  • Overusing will-change — it promotes layers; applied to everything it exhausts GPU memory and backfires. Use sparingly, remove after.
  • Forgetting animation-fill-mode (both/forwards), so an element snaps back to its start state when the animation ends.
  • Too-long or gratuitous durations — UI motion should be ~150–300ms; longer feels sluggish.

Exercises

  • Build the same "move 100px right" effect two ways — animating left vs transform: translateX — and compare in the devtools performance panel.
  • Create a looping pulse keyframe animation and a one-shot entrance with animation-fill-mode: both.
  • Sequence two animations with WAAPI using await anim.finished between them.
  • Reveal cards on scroll with IntersectionObserver adding an in-view class; then try the CSS animation-timeline: view() version.
  • Add a prefers-reduced-motion block and verify (OS setting or devtools emulation) that large motion is suppressed while essential feedback remains.

Mini-project

Build an animated product card gallery that is both smooth and accessible: cards fade/slide into view on scroll (IntersectionObserver with a scroll-timeline enhancement), hover and focus states animated purely with transform/opacity, a WAAPI-driven "add to cart" micro-interaction sequenced with await finished, and a looping subtle attention pulse on a sale badge. Then add a complete prefers-reduced-motion variant that strips the large motion while keeping essential feedback, and profile the gallery to prove every animation stays on the compositor (no layout thrash).
