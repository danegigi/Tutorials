TanStack Query manages server state — data you don't own, that lives on a backend and goes stale. It is not a replacement for useState; it is the layer that fetches, caches, dedupes, refetches, and invalidates remote data so you stop hand-rolling loading flags, race-condition guards, and manual cache busting in every component.

Why it exists

Beginner The naive approach — useEffect + fetch + three useStates — looks fine until you need any of the things real apps need:

// the problem it solves — every one of these is a line YOU don't write with Query:
// • caching (don't refetch the same data twice)
// • request deduplication (two components, one network call)
// • background refetching (keep the screen fresh)
// • stale-while-revalidate (show cached data instantly, update quietly)
// • retry on failure, with backoff
// • garbage collection of unused data
// • race-condition safety (ignore a response that arrived out of order)

Install it alongside React:

npm install @tanstack/react-query
# optional but recommended in dev:
npm install -D @tanstack/react-query-devtools

Setup: the QueryClient

Create one QueryClient for the whole app and wrap your tree in its provider. The client is the cache:

// src/main.tsx
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { ReactQueryDevtools } from "@tanstack/react-query-devtools";
import { createRoot } from "react-dom/client";
import App from "./App";

const queryClient = new QueryClient();

createRoot(document.getElementById("root")!).render(
  <QueryClientProvider client={queryClient}>
    <App />
    <ReactQueryDevtools initialIsOpen={false} />
  </QueryClientProvider>,
);
Create the QueryClient outside the component (module scope), or in a useState(() => new QueryClient()) if you must create it inside. Creating it inline in render makes a brand-new cache on every render and throws your data away.

Reading data with useQuery

A query needs two things: a query key (the cache address) and a query function that returns a promise. Query functions must throw on failure so Query can mark the query as errored:

import { useQuery } from "@tanstack/react-query";

type Todo = { id: number; title: string; done: boolean };

async function fetchTodos(): Promise<Todo[]> {
  const res = await fetch("/api/todos");
  if (!res.ok) throw new Error(`HTTP ${res.status}`); // MUST throw on error
  return res.json();
}

function TodoList() {
  const { data, isPending, isError, error } = useQuery({
    queryKey: ["todos"],
    queryFn: fetchTodos,
  });

  if (isPending) return <p>Loading…</p>;
  if (isError) return <p>Error: {error.message}</p>;

  return (
    <ul>
      {data.map((t) => (
        <li key={t.id}>{t.title}</li>
      ))}
    </ul>
  );
}
fetch does not reject on a 4xx/5xx — it only rejects on a network failure. If you forget the if (!res.ok) throw check, Query thinks a 500 was a success and caches the error page as your data.

Query keys

The query key is an array that uniquely identifies the data. Query uses it to cache, dedupe, and refetch. Treat it like a dependency array — every input the query function reads must be in the key:

// a list, filtered — the filter is part of the identity
useQuery({ queryKey: ["todos", { done: true }], queryFn: () => fetchTodos({ done: true }) });

// a single item by id
useQuery({ queryKey: ["todos", todoId], queryFn: () => fetchTodo(todoId) });

Keys are hierarchical: ["todos"] is a prefix of ["todos", 5], which lets you invalidate a whole family at once (shown below). Objects in keys are compared structurally and are order-independent, so { a: 1, b: 2 } and { b: 2, a: 1 } are the same key.

staleTime vs gcTime — the two timers everyone confuses

Intermediate These control freshness and retention, and they are completely independent:

OptionDefaultMeaning
staleTime0How long data is considered fresh. While fresh, Query serves the cache and does not refetch. After it, data is stale and will refetch on the next trigger (mount, window focus, reconnect).
gcTime5 minHow long an unused (no mounted observer) query stays in cache before garbage collection. It only starts counting once nothing is using the query.
 
useQuery({
  queryKey: ["todos"],
  queryFn: fetchTodos,
  staleTime: 60_000,   // treat as fresh for 1 min → no refetch storm on remount
  gcTime: 5 * 60_000,  // keep in cache 5 min after the last component unmounts
});
The default staleTime: 0 means data is stale immediately, so you'll see a background refetch on every mount and window focus. That is intentional (freshness-first), but if it causes a refetch storm, raise staleTime — do not disable refetching globally.

Mutations with useMutation

Reads are queries; writes are mutations. A mutation doesn't cache — it runs an async side effect and gives you status flags. After it succeeds you invalidate the affected queries so they refetch:

import { useMutation, useQueryClient } from "@tanstack/react-query";

function AddTodo() {
  const queryClient = useQueryClient();

  const addTodo = useMutation({
    mutationFn: (title: string) =>
      fetch("/api/todos", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ title }),
      }).then((r) => {
        if (!r.ok) throw new Error("create failed");
        return r.json();
      }),
    onSuccess: () => {
      // mark everything under ["todos"] stale → it refetches
      queryClient.invalidateQueries({ queryKey: ["todos"] });
    },
  });

  return (
    <button
      disabled={addTodo.isPending}
      onClick={() => addTodo.mutate("Buy milk")}
    >
      {addTodo.isPending ? "Adding…" : "Add todo"}
    </button>
  );
}

Optimistic updates

Advanced For a snappy UI, apply the change to the cache before the server responds, and roll back if it fails. The pattern has four hooks — onMutate, onError, onSettled — and uses the cache snapshot as the rollback point:

const toggle = useMutation({
  mutationFn: (todo: Todo) => updateTodo(todo),

  // 1. Before the request: snapshot + apply the optimistic change
  onMutate: async (next) => {
    await queryClient.cancelQueries({ queryKey: ["todos"] }); // stop in-flight refetches
    const previous = queryClient.getQueryData<Todo[]>(["todos"]);
    queryClient.setQueryData<Todo[]>(["todos"], (old) =>
      old?.map((t) => (t.id === next.id ? next : t)),
    );
    return { previous }; // becomes `context` below
  },

  // 2. On failure: restore the snapshot
  onError: (_err, _next, context) => {
    if (context?.previous) queryClient.setQueryData(["todos"], context.previous);
  },

  // 3. Always: resync with the server
  onSettled: () => queryClient.invalidateQueries({ queryKey: ["todos"] }),
});
The cancelQueries call matters: without it, a background refetch that was already in flight can land after your optimistic write and overwrite it with stale server data.

Pagination and infinite queries

For "load more" / infinite scroll, use useInfiniteQuery. It stores an array of pages and derives the next page param from the last one:

import { useInfiniteQuery } from "@tanstack/react-query";

const query = useInfiniteQuery({
  queryKey: ["todos", "infinite"],
  queryFn: ({ pageParam }) => fetchTodoPage(pageParam),
  initialPageParam: 0,
  getNextPageParam: (lastPage) => lastPage.nextCursor ?? undefined, // undefined = no more
});

// render: query.data.pages.flatMap(p => p.items)
// load more: <button onClick={() => query.fetchNextPage()} disabled={!query.hasNextPage}>

For classic page-number pagination, keep the page in the key (["todos", { page }]) and add placeholderData: keepPreviousData so the old page stays on screen while the next one loads instead of flashing a spinner.

The queryOptions pattern

Define a query once and reuse it across useQuery, prefetching, and imperative reads — fully typed — with the queryOptions helper. This is the recommended way to organize queries in a real app:

import { queryOptions } from "@tanstack/react-query";

export const todoQueries = {
  all: () => queryOptions({ queryKey: ["todos"], queryFn: fetchTodos }),
  detail: (id: number) =>
    queryOptions({ queryKey: ["todos", id], queryFn: () => fetchTodo(id) }),
};

// in a component
useQuery(todoQueries.detail(5));
// in a route loader (prefetch before render)
await queryClient.ensureQueryData(todoQueries.detail(5));
// imperatively
const data = queryClient.getQueryData(todoQueries.detail(5).queryKey); // typed!

Shared example: the Issues Tracker (data layer)

Intermediate The next two lessons — TanStack Router and TanStack Table, Form & Store — build the same app, an "Issues Tracker" (a stripped-down GitHub issues board). Here we lay its data foundation so Router can preload it and Table can render it. One domain type and one typed query module carry across all three lessons:

// src/issues/types.ts — the shared domain model (used in all three lessons)
export type IssueStatus = "open" | "closed";
export type Issue = {
  id: number;
  title: string;
  status: IssueStatus;
  assignee: string;
  labels: string[];
  createdAt: string; // ISO
};

A single queryOptions module is the contract every other lesson imports — the list (optionally filtered) and one issue by id:

// src/issues/queries.ts
import { queryOptions } from "@tanstack/react-query";
import type { Issue, IssueStatus } from "./types";

async function getJSON<T>(url: string): Promise<T> {
  const res = await fetch(url);
  if (!res.ok) throw new Error(`HTTP ${res.status}`); // throw so Query marks it errored
  return res.json();
}

export const issueQueries = {
  // the filter is part of the cache identity → it belongs in the key
  list: (filter: { status?: IssueStatus } = {}) =>
    queryOptions({
      queryKey: ["issues", "list", filter],
      queryFn: () =>
        getJSON<Issue[]>("/api/issues?" + new URLSearchParams(filter as Record<string, string>)),
      staleTime: 30_000,
    }),
  detail: (id: number) =>
    queryOptions({
      queryKey: ["issues", "detail", id],
      queryFn: () => getJSON<Issue>(`/api/issues/${id}`),
    }),
};

And the mutation the Table/Form lesson will call — closing an issue, optimistically — invalidating by the ["issues"] prefix so both the list and the detail refetch:

// src/issues/mutations.ts
import { useMutation, useQueryClient } from "@tanstack/react-query";
import type { Issue } from "./types";

export function useCloseIssue() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (id: number) =>
      fetch(`/api/issues/${id}/close`, { method: "POST" }).then((r) => {
        if (!r.ok) throw new Error("close failed");
        return r.json() as Promise<Issue>;
      }),
    onMutate: async (id) => {
      await qc.cancelQueries({ queryKey: ["issues"] });
      const prev = qc.getQueryData<Issue[]>(["issues", "list", {}]);
      qc.setQueryData<Issue[]>(["issues", "list", {}], (old) =>
        old?.map((i) => (i.id === id ? { ...i, status: "closed" } : i)),
      );
      return { prev };
    },
    onError: (_e, _id, ctx) => ctx?.prev && qc.setQueryData(["issues", "list", {}], ctx.prev),
    onSettled: () => qc.invalidateQueries({ queryKey: ["issues"] }), // prefix → list + detail
  });
}
Keep this src/issues/ module as you move to the next lessons. The Router lesson imports issueQueries in its loaders; the Table/Form/Store lesson imports issueQueries.list for the grid and useCloseIssue for the row action. Nothing is re-fetched twice — all three lessons share one cache.

Common mistakes

  • Not throwing in the query function. fetch resolves on a 404/500; you must throw yourself or Query caches the failure as data.
  • Missing values in the query key. If the query function reads userId but the key is just ["profile"], switching users shows the wrong cached data. Put every input in the key.
  • Confusing staleTime and gcTime. staleTime = when to refetch; gcTime = when to forget. Raising gcTime does not stop refetches.
  • Creating the QueryClient inside render. A new client every render = an empty cache every render.
  • Using Query for client-only state. Form inputs, modal open/closed, the current tab — that's useState. Query is for data that lives on a server.
  • Forgetting cancelQueries in optimistic updates. An in-flight refetch can clobber your optimistic write.

Exercises

  • Set up a QueryClient and fetch a list from a public API (e.g. jsonplaceholder) with useQuery, rendering the three states (pending/error/data).
  • Add a useMutation that POSTs a new item and invalidates the list on success; confirm the list refetches.
  • Set staleTime: 30_000 and watch the Devtools: confirm no refetch on remount within 30s, then a background refetch after.
  • Convert a page-number list to keepPreviousData so switching pages doesn't flash a spinner.
  • Implement an optimistic "toggle done" with full rollback, then force the server to 500 and confirm the UI reverts.

Mini-project: a cached, optimistic todo app

Build a todo app backed by any mock API (json-server or an in-memory handler). Requirements:

  • A todoQueries module using queryOptions for the list and the per-item detail.
  • The list uses useQuery with a sensible staleTime; the detail view prefetches on hover.
  • Add / toggle / delete are mutations. Toggle is optimistic with rollback; add and delete invalidate the list on success.
  • A "has unsaved network activity" indicator driven by useIsFetching() / useIsMutating().
  • Open the Devtools and verify: one network call feeds multiple components (dedupe), the cache survives navigation, and an unused query is garbage-collected after gcTime.

This exercises the whole model — keys, caching, freshness, invalidation, optimistic writes, and the queryOptions organization you'll use in production.
