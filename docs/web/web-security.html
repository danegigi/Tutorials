The browser runs untrusted code and handles untrusted input, so the frontend is an attack surface. The Authentication lesson covered logging users in; this one covers keeping the app itself safe: XSS, CSRF, a strong Content-Security-Policy, security headers, and HTTPS.

Cross-Site Scripting (XSS)

Beginner XSS is injecting attacker-controlled script into your page, where it runs with your users' session. The root cause is almost always rendering untrusted data as HTML.

// VULNERABLE: a comment of <img src=x onerror=steal()> executes
el.innerHTML = userComment;

// SAFE: textContent never parses HTML
el.textContent = userComment;

// If you MUST render HTML, sanitize it first
import DOMPurify from "dompurify";
el.innerHTML = DOMPurify.sanitize(userRichText);
The rule: treat all user input as hostile, and encode on output for the context it lands in (HTML body, attribute, URL, JS). Prefer textContent; reserve innerHTML for sanitized content only. This includes data from your own API — a stored comment is still user input. Server-rendered templates must auto-escape (most do; don't disable it).

Content-Security-Policy

Intermediate CSP is a defense-in-depth header that tells the browser which sources are allowed — so even if an XSS payload slips in, the browser refuses to run it:

Content-Security-Policy:
  default-src 'self';
  script-src 'self';                      # no inline scripts, no CDN unless listed
  style-src 'self';
  img-src 'self' data:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';                 # can't be framed (clickjacking)
  base-uri 'self';
  object-src 'none';
Common mistake: script-src 'unsafe-inline', which defeats CSP's main benefit by re-allowing inline <script>/onclick — exactly what XSS injects. Move inline scripts to files (or use a per-request nonce/hash) so you can drop unsafe-inline. Roll CSP out with Content-Security-Policy-Report-Only first to find violations before enforcing.

Cross-Site Request Forgery (CSRF)

CSRF tricks a logged-in user's browser into making a state-changing request to your site (cookies ride along automatically). Defenses:

Set-Cookie: session=…; SameSite=Lax; Secure; HttpOnly   # Lax/Strict blocks cross-site sends
# Plus a CSRF token for state-changing POSTs:
<input type="hidden" name="csrf" value="{{ per-session token }}">
# Server rejects the request if the token is missing/wrong.

Pure token-auth APIs (Authorization header, not cookies) aren't CSRF-prone — the browser doesn't attach the header automatically. Cookie-based sessions are, so they need SameSite + tokens.

HTTPS everywhere

Serve everything over TLS (see the DevOps TLS lesson), redirect HTTP→HTTPS, and set HSTS so browsers never try HTTP again. Mixed content (an HTTPS page loading an HTTP script) is blocked by browsers and a security hole — audit for it.

Other must-knows

  • Validate on the server — client validation is UX only (see Forms & Validation).
  • Parameterized queries on the backend — never string-concatenate SQL (no injection).
  • Dependency hygiene — bun/npm audit, keep deps patched; a vulnerable library is your vulnerability.
  • Don't leak secrets to the client — anything in the bundle is public (see Integration lesson).
Work through the OWASP Top Ten — it's the canonical list of what actually gets exploited. Most real breaches are boring: injection, broken access control, misconfiguration, and known-vulnerable dependencies, not exotic attacks.

Exercises

  • Build a comment box that safely renders user input with textContent; then show the XSS when switched to innerHTML.
  • Add a strict CSP (no unsafe-inline) to a page and fix the violations it reports.
  • Check a site's headers at securityheaders.com and add the missing ones.

Mini-project: harden a web app

Take an app with a user-content feature (comments, profiles) and harden it: sanitize/escape all rendered user input, add a strict CSP (served Report-Only first, then enforced, with no unsafe-inline), set the full security-header set + HSTS, make session cookies HttpOnly; Secure; SameSite=Lax with a CSRF token on mutations, and run a dependency audit. Verify with an A grade on securityheaders.com and a clean CSP console.
