Bun loads .env files automatically — no dotenv import — and exposes the values on both Bun.env and process.env. This lesson covers the file resolution order, the difference between the two accessors, inlining values at build time with --define, building a typed config object you validate once at startup, loading secrets from the OS keychain with Bun.secrets, and the per-environment patterns that keep development, staging, and production apart. The recurring warning throughout: a committed .env and a frontend-inlined secret are both public — treat them that way.

.env file resolution order

Beginner On startup Bun reads a fixed set of dotenv files and merges them. Later files in this precedence list win over earlier ones, and a real environment variable (one already set in the shell) always wins over any file.

SourceLoaded whenPrecedence
Real shell environmentalwayshighest — overrides every file
.env.<NODE_ENV>.localNODE_ENV is set
.env.localnot when NODE_ENV=test
.env.<NODE_ENV>NODE_ENV is set (e.g. .env.production)
.envalwayslowest
 
# .env                 — committed defaults, no secrets
PORT=3000
LOG_LEVEL=info

# .env.local           — gitignored, your machine's overrides + secrets
DATABASE_URL=postgres://localhost/app_dev
STRIPE_SECRET_KEY=sk_test_...

# .env.production      — committed production NON-secret config
LOG_LEVEL=warn
bun run src/index.ts                 # NODE_ENV unset: .env + .env.local
NODE_ENV=production bun run src/index.ts   # adds .env.production (.local skipped in prod if absent)
PORT=8080 bun run src/index.ts       # the real env var PORT=8080 wins over .env
The mental model: .env holds committed, non-secret defaults; .env.local holds machine-specific overrides and local secrets and is gitignored; .env.<NODE_ENV> holds per-environment non-secret config. Note .env.local is deliberately skipped when NODE_ENV=test so your local secrets never bleed into test runs.

Bun.env vs process.env

Both read the same merged environment, so for simple reads they're interchangeable. Bun.env is the Bun-native accessor and is what you should prefer in new Bun code; process.env exists for Node compatibility and for libraries that reach for it.

console.log(Bun.env.PORT);       // "3000"  (strings — env vars are always strings)
console.log(process.env.PORT);   // "3000"  (same value, same backing store)

// They point at the same data: a write through one is visible through the other
process.env.FEATURE_X = "on";
console.log(Bun.env.FEATURE_X);  // "on"
Common mistake: expecting a type. Everything from the environment is a string — Bun.env.PORT is "3000", not 3000, and Bun.env.DEBUG for an unset var is undefined, while Bun.env.DEBUG="" (set but empty) is a truthy-ish empty string. Coerce and validate at the edge (Number(Bun.env.PORT), an explicit === "true" check) rather than using a raw env value deep in your logic.

Inlining with --define

Intermediate For code you bundle (a frontend build, a compiled binary), --define replaces an identifier with a literal at build time. The reference is substituted into the output and dead-code-eliminated — there is no runtime env lookup.

// src/app.ts
if (process.env.NODE_ENV === "production") enableTelemetry();
console.log("build:", process.env.BUILD_ID);
bun build src/app.ts --outdir dist \
  --define process.env.NODE_ENV='"production"' \
  --define process.env.BUILD_ID='"a1b2c3"'

# dist/app.js — the branch is resolved and dead code removed:
#   enableTelemetry();
#   console.log("build:", "a1b2c3");
Common mistake & security warning: --define-ing a secret into a frontend bundle. Anything inlined into client-side JavaScript ships to the browser and is public — view-source reveals it. Only inline values that are safe to expose (a public API base URL, a feature flag, a build id, a publishable Stripe pk_ key). A sk_ secret key, a database URL, or a signing secret must never touch a frontend build. The quoting also bites: the replacement is a raw expression, so a string value needs embedded quotes — --define X='"literal"', not --define X=literal (which substitutes a bare, undefined identifier).

Typed config objects

Reading Bun.env.X scattered through the codebase means a missing or malformed variable blows up deep in a request handler, hours after startup. Instead, read and validate everything once at boot into a single typed object — the app fails fast with a clear message if config is wrong, and the rest of the code imports a fully-typed config.

// config.ts  — validated once, imported everywhere
import { z } from "zod";

const Schema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  PORT: z.coerce.number().int().positive().default(3000),      // coerce "3000" -> 3000
  DATABASE_URL: z.string().url(),                              // required — no default
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
  ENABLE_SIGNUP: z.coerce.boolean().default(false),            // "true"/"1" -> true
});

const parsed = Schema.safeParse(Bun.env);
if (!parsed.success) {
  console.error("Invalid environment configuration:");
  console.error(parsed.error.flatten().fieldErrors);
  process.exit(1);                                             // fail fast at startup
}

export const config = parsed.data;      // fully typed: config.PORT is number, config.NODE_ENV is a union
// anywhere else — no Bun.env, no coercion, no guessing
import { config } from "./config";
Bun.serve({ port: config.PORT, fetch: handler });   // config.PORT is a number
Validating against Bun.env at startup turns "the app silently used NaN for the port" into "the app refused to start and told you DATABASE_URL is missing." Pair it with a committed .env.example listing every variable by name (no values) so a new developer knows exactly what to fill in.

Loading secrets with Bun.secrets

Advanced For local developer tooling, Bun.secrets stores credentials in the OS keychain (macOS Keychain, Linux libsecret / GNOME Keyring, Windows Credential Manager) instead of a plaintext dotfile — so a stray cat .env, a screen share, or a backup never leaks the token.

import { secrets } from "bun";

// get returns the stored string, or null if absent
let token = await secrets.get({ service: "acme-cli", name: "api-token" });

if (!token) {
  token = prompt("Paste your API token:")!;          // first run only
  await secrets.set({ service: "acme-cli", name: "api-token", value: token });
  console.log("Saved to the OS keychain.");
}

// use it...
await fetch("https://api.acme.dev/me", { headers: { Authorization: `Bearer ${token}` } });

// rotate / sign out
await secrets.delete({ service: "acme-cli", name: "api-token" });

Each call takes { service, name } (set adds value). service groups a tool's credentials; name identifies one secret within it.

Bun.secrets is designed for local CLI tools and development machines, where the OS keychain is the right trust boundary. It is not the mechanism for a production server — there, inject secrets through the environment from your platform's secret manager (AWS Secrets Manager, Vault, the hosting provider's env UI) rather than reading a keychain that doesn't exist on a container.

Per-environment config patterns

Keep three concerns separate: committed non-secret defaults, per-environment non-secret overrides, and secrets. A clean split:

FileCommitted?Holds
.envyessafe defaults (PORT, LOG_LEVEL)
.env.exampleyesevery variable name, no values — the template
.env.productionyesnon-secret prod config (region, feature flags)
.env.localno — gitignoredlocal secrets + machine overrides
 
# .gitignore
.env.local
.env.*.local

Select the environment with NODE_ENV, and let the config module be environment-aware where behavior genuinely differs:

// config.ts (continued)
export const isProd = config.NODE_ENV === "production";
export const isDev  = config.NODE_ENV === "development";

// e.g. verbose errors only outside production
export const errorDetail = isProd ? "generic" : "full";

Common mistakes

Common mistakes: (1) Committing .env with real secrets. A committed file is in your git history forever even after you delete it — rotate any key that ever landed in a commit and move it to gitignored .env.local. (2) Inlining a secret into a frontend bundle via --define or a PUBLIC_/client-exposed variable — it ships to every browser. Only public values belong in client builds. (3) Treating env values as typed — they're strings; coerce and validate. (4) Relying on .env.local in CI/production — CI checkouts don't have it and it's skipped under NODE_ENV=test; inject real config through the environment instead. (5) Using Bun.secrets on a server — it's a local-dev keychain tool, not production secret management.

Exercises

  • Create .env with PORT=3000 and .env.local with PORT=4000; run the app and confirm 4000 wins, then run with PORT=5000 bun ... and confirm the real env var wins over both.
  • Write a config.ts that validates Bun.env with zod and process.exit(1)s with a readable message when DATABASE_URL is missing.
  • bun build a file that reads process.env.NODE_ENV with --define process.env.NODE_ENV='"production"' and inspect the output to see the branch resolved and dead code removed.
  • Store a token in the OS keychain with Bun.secrets.set, read it back in a second run, then delete it — confirm the second run never prompts.

Mini-project: a config module that fails fast and a keychain-backed CLI

Build the two config surfaces a real app needs: a validated server config that refuses to start on bad input, and a small CLI that keeps its credential in the OS keychain instead of a dotfile.

// config.ts — server config, validated once at startup
import { z } from "zod";

const config = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  PORT: z.coerce.number().int().positive().default(3000),
  DATABASE_URL: z.string().url(),
  JWT_SECRET: z.string().min(32, "JWT_SECRET must be at least 32 chars"),
}).parse(Bun.env);          // throws (and prints) on invalid config -> process exits non-zero

export default config;
// server.ts
import config from "./config";
console.log(`starting in ${config.NODE_ENV} on :${config.PORT}`);
Bun.serve({ port: config.PORT, fetch: () => new Response("ok") });
// cli.ts — a tool whose token lives in the OS keychain, never on disk
import { secrets } from "bun";
const SERVICE = "acme-cli";

async function tokenOrLogin() {
  let t = await secrets.get({ service: SERVICE, name: "token" });
  if (!t) {
    t = prompt("API token:")!;
    await secrets.set({ service: SERVICE, name: "token", value: t });
  }
  return t;
}

const cmd = Bun.argv[2];
if (cmd === "logout") {
  await secrets.delete({ service: SERVICE, name: "token" });
  console.log("Logged out — keychain entry removed.");
} else {
  const token = await tokenOrLogin();
  const me = await (await fetch("https://api.acme.dev/me", {
    headers: { Authorization: `Bearer ${token}` },
  })).json();
  console.log(me);
}
NODE_ENV=production DATABASE_URL=postgres://db/app JWT_SECRET=$(openssl rand -hex 32) bun server.ts
# starting in production on :3000

bun cli.ts            # first run prompts, stores in keychain; later runs are silent
bun cli.ts logout     # removes the keychain entry

Together these cover the whole surface: the server validates its environment and refuses to boot on bad or missing config instead of failing later in a handler, and the CLI never writes a secret to a file a backup or a screen-share could leak. No secret is ever committed, and nothing sensitive is inlined into a client bundle.
