Bun is designed as a drop-in Node.js replacement: it implements the Node APIs, reads package.json, and runs most existing projects unchanged. But "most" isn't "all," and the real win comes from replacing the pile of tools Node needs (nodemon, ts-node, jest, dotenv) with Bun's built-ins. This lesson is a staged, low-risk migration path with the compatibility gotchas called out.

Why migrate — and the honest caveat

Intermediate Bun gives you a faster install, native TypeScript/JSX with no build step, a built-in test runner, bundler, and .env loading — one binary instead of a toolchain. The caveat: Bun targets Node compatibility but a few native-addon-heavy or deep-internals packages still differ. So the strategy is incremental: run your existing app under Bun first, fix what breaks, then adopt Bun-native features where they pay off.

Step 1: just run it under Bun

bun install          # reads your existing package.json; writes bun.lockb
bun run start        # runs your "start" script with Bun instead of node
# or run the entry directly:
bun run src/index.ts  # no ts-node / tsc needed — Bun runs TS natively

A large fraction of Node apps work on the first try. Where they don't, the errors point at specific APIs — fix those, don't rewrite.

Step 2: the compatibility gotchas

AreaWhat to know
Built-in modulesfs, path, http, crypto, stream, os etc. are implemented. Import with or without the node: prefix.
processprocess.env, argv, cwd() all work; a few rarely-used fields may differ.
Native addonsN-API addons work in many cases; some C++-heavy packages may not. Test them specifically.
Worker threadsUse the Web Worker API (Bun's model) — node:worker_threads is also supported.
ESM/CJSBun runs both and lets them interop more freely than Node, but keep your type field honest.
Don't assume — verify the packages that matter. The failures that stop a migration are almost always one or two native/low-level dependencies (certain database drivers, native crypto, instrumentation agents). Run your test suite under Bun early; a green suite is the real compatibility signal, not a clean bun install.

Step 3: replace the toolchain

Beginner This is where migrating earns its keep — delete dev dependencies and their config:

Node toolBun built-in
nodemon / node --watchbun --watch src/index.ts
ts-node / tsxnothing — bun run file.ts runs TS directly
jest / vitestbun test (Jest-compatible matchers)
dotenvbuilt-in: Bun auto-loads .env / .env.local
webpack / esbuild / rollupbun build

// package.json — scripts rewritten for Bun
{
  "scripts": {
    "dev":   "bun --watch src/index.ts",
    "start": "bun run src/index.ts",
    "test":  "bun test"
  }
}

Step 4: config files

# bunfig.toml — Bun's config (optional)
[install]
# registry, caching, etc.
[test]
coverage = true

Keep package.json as-is for metadata/dependencies; add bunfig.toml only for Bun-specific settings. .env files are loaded automatically — remove the require("dotenv").config() call.

Adopt Bun-native APIs opportunistically, not all at once: swap fs.readFile for Bun.file(), http.createServer for Bun.serve, and bcrypt for Bun.password as you touch that code. They're faster and simpler, but your Node-API code keeps working in the meantime — so the migration never has to be a big-bang rewrite.

Step 5: CI and deployment

# GitHub Actions
- uses: oven-sh/setup-bun@v2
- run: bun install --frozen-lockfile
- run: bun test
- run: bun run build

Use the official oven-sh/bun Docker image for containers, and --frozen-lockfile in CI so an unexpected dependency change fails the build instead of silently resolving.

A staged migration checklist

  1. bun install & run your test suite under Bun — fix compatibility failures (usually 1–2 native deps).
  2. Rewrite package.json scripts to use bun / bun --watch / bun test.
  3. Delete nodemon, ts-node/tsx, dotenv, and (if you adopt bun test) the old test runner.
  4. Point CI/Docker at Bun with a frozen lockfile.
  5. Opportunistically swap hot-path code to Bun-native APIs.

Common mistakes

  • Declaring success after a clean bun install — run the TEST SUITE; that's what reveals real incompatibilities.
  • Big-bang rewriting to Bun-native APIs instead of running Node-compatible code first and migrating incrementally.
  • Leaving dotenv/ts-node/nodemon in after switching — you keep the overhead you came to remove.
  • Not using --frozen-lockfile in CI, so a drifting dependency resolves differently than locally.
  • Assuming every native addon works — test the specific packages your app depends on.
  • Committing both package-lock.json and bun.lockb — pick Bun's lockfile and remove the npm one.

Exercises

  • Take an existing small Node+TypeScript project, run it under Bun with no changes, and record what (if anything) breaks.
  • Rewrite its package.json scripts to Bun equivalents and delete ts-node/nodemon.
  • Port its Jest tests to bun test and confirm the matchers work unchanged.
  • Remove dotenv and prove Bun auto-loads .env; then swap a bcrypt call for Bun.password.
  • Set up a CI workflow with setup-bun + --frozen-lockfile and a Dockerfile on the Bun image.

Mini-project

Migrate a real Express+TypeScript API from Node to Bun end to end and write the migration as a documented PR: run it unchanged under Bun and fix any failing dependencies, rewrite the scripts, replace nodemon/ts-node/dotenv/jest/bcrypt with Bun built-ins, switch CI and the Dockerfile to Bun with a frozen lockfile, and finally port the hottest route to Bun.serve-native handling. Benchmark install time, cold start, and request throughput before and after, and list exactly which compatibility issues you hit and how you resolved each.
