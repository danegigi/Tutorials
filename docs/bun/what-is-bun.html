What Bun Is & When to Use It

Bun is a single native binary that is a JavaScript/TypeScript runtime, a package manager, a bundler, and a test runner all at once — it runs .ts and .tsx directly with no compile step and ships a large standard library under the global Bun namespace. This tutorial targets Bun 1.4.2.

Four tools, one binary

In the Node.js world you assemble a toolchain: Node to run, npm/yarn/pnpm to install, webpack/esbuild to bundle, Jest/Vitest to test, ts-node/tsx to run TypeScript. Bun replaces all of them with one executable and one install.

JobTypical Node stackBun equivalent
Run JS/TSnode + ts-node/tsxbun run file.ts
Install packagesnpm / yarn / pnpmbun install
Bundlewebpack / esbuild / rollupbun build
Testjest / vitest / mochabun test
Run a package oncenpxbunx

Prove it in 30 seconds

Beginner You don't need a project to see all four facets. The same binary answers for every subcommand:

bun --version          # 1.4.2
bun --help             # run, install, add, build, test, x, create, ...

# Run TypeScript with no setup — no tsconfig, no transpile step
echo 'const n: number = 41; console.log(n + 1);' > demo.ts
bun demo.ts
# -> 42

That const n: number is TypeScript. Node would reject it outright; Bun strips the type and runs it.

The Bun global: a batteries-included stdlib

Beyond running code, Bun exposes a native standard library you'd otherwise reach for npm packages to get. A tiny tour (each has its own lesson later):

Bun.serve({ fetch: () => new Response("hi") });   // HTTP server (no express)
await Bun.file("data.json").json();               // read a file (no fs boilerplate)
await Bun.write("out.txt", "hello");              // write a file
await Bun.password.hash("pw");                     // argon2id (no bcrypt package)
new Bun.Database?.(":memory:");                    // SQLite via bun:sqlite
import { $ } from "bun";                            // a cross-platform shell

Everything above is built in. A fresh Bun project with zero dependencies can already serve HTTP, hash passwords, talk to SQLite, and script the shell.

Bun vs Node: when to pick which

Intermediate Bun aims for drop-in Node compatibility — most node:* modules and npm packages work unchanged — while being noticeably faster at process start, install, and I/O. Reach for Bun when:

  • You want one tool instead of a cobbled toolchain (new projects, CLIs, scripts).
  • Startup latency matters — serverless, short-lived scripts, test suites.
  • You want native TS execution without a build step.
  • You want the built-in SQLite / S3 / shell / test runner instead of extra deps.

Stay on Node when a critical dependency relies on a Node internal Bun hasn't implemented yet, or your platform/runtime (a managed host, a specific FaaS) only offers Node. Bun's Node compatibility is high and climbing, but it is not 100% — verify your hot-path dependencies on Bun before committing a large production service.

Performance basics (and honest caveats)

Bun's speed comes from three places: it's built on JavaScriptCore (Safari's engine) rather than V8, it's written in Zig with hand-tuned system calls, and its package manager uses a global cache plus a binary lockfile. The practical wins you'll feel:

OperationWhy Bun is fast
Process startSmaller runtime, faster cold start than node
bun installGlobal cache + binary lockfile, parallelized
File I/OBun.file/Bun.write use sendfile/mmap paths
HTTP serverBun.serve is a native server, not a JS layer over http
Benchmarks are workload-specific. "Bun is faster" is true for startup, install, and I/O-bound servers in most measurements, but a CPU-bound number-crunching loop runs on the JS engine and the gap narrows. Measure your own workload with Bun.nanoseconds() (covered in Testing) before quoting a number.

What a Bun project looks like

A minimal, idiomatic project — note the engines field pinning Bun and scripts written with bun:

// package.json
{
  "name": "my-app",
  "module": "src/index.ts",
  "type": "module",
  "engines": { "bun": ">=1.0.0" },
  "scripts": {
    "start": "bun run src/index.ts",
    "dev": "bun --watch src/index.ts",
    "test": "bun test",
    "build": "bun build src/index.ts --outdir dist"
  }
}
my-app/
├─ package.json
├─ bunfig.toml      # optional Bun config
├─ bun.lockb        # binary lockfile — commit it
├─ tsconfig.json
└─ src/index.ts

Common mistakes

Common mistake: treating Bun as "just a faster Node" and mixing lockfiles. Bun writes bun.lockb — if you also run npm install you get a conflicting package-lock.json and two tools resolving different versions. Pick Bun and commit bun.lockb; delete any stray package-lock.json/yarn.lock. A second trap is assuming every npm package works — the vast majority do, but verify a native-addon-heavy dependency on Bun before shipping it in production.

Exercises

  • Run bun --version and bun --help; list which four tools you now have in one binary.
  • Write a one-line TypeScript file that uses a typed variable, run it with bun, and confirm no build step was needed.
  • Use bun -e 'console.log(Bun.version, process.platform)' to print the runtime version and OS in a single command.
  • Open an existing small Node script of yours and run it with bun — note what works unchanged and what (if anything) doesn't.

Mini-project: the "one binary" demo

Build a throwaway folder that exercises all four facets of Bun in under 20 lines, proving the single-binary claim end to end:

mkdir bun-demo && cd bun-demo
bun init -y

# 1) RUNTIME: a TS file that uses the Bun stdlib
cat > app.ts <<'EOF'
Bun.serve({ port: 3000, fetch: () => Response.json({ ok: true, bun: Bun.version }) });
console.log("serving on http://localhost:3000");
EOF

# 2) PACKAGE MANAGER: add a dep (then we won't even need it — just prove install works)
bun add hono

# 3) TEST RUNNER: a trivial test
cat > app.test.ts <<'EOF'
import { test, expect } from "bun:test";
test("math", () => expect(2 + 2).toBe(4));
EOF
bun test

# 4) BUNDLER: produce a single output file
bun build app.ts --outdir dist
ls dist   # app.js

You installed a package, ran a test, bundled, and (if you bun run app.ts) served HTTP — without installing Node, a bundler, or a test framework. That is the whole value proposition in one directory.
