Bun runs TypeScript and JSX natively with zero configuration — no tsc build, no ts-node/tsx shim — by stripping types at load time. Type checking is a separate, explicit step. This lesson covers running TS, configuring tsconfig.json, path mapping, and type-checking with bunx tsc --noEmit.

Zero-config execution

Beginner Point Bun at a .ts or .tsx file and it runs. There is no compile step and no output directory.

// greet.ts
interface User { name: string; age: number }
const greet = (u: User): string => `Hi ${u.name} (${u.age})`;
console.log(greet({ name: "Ada", age: 36 }));
bun greet.ts
# Hi Ada (36)

JSX works the same — name the file .tsx and Bun transpiles it:

// view.tsx
const App = () => <h1>Hello</h1>;
console.log(App());   // Bun uses the automatic JSX runtime by default

The critical distinction: run ≠ type-check

Bun strips types to run fast — it does not verify them. This file runs without complaint even though it has a type error:

// buggy.ts
const n: number = "not a number";   // type error...
console.log(n.toUpperCase());        // ...and a logic error
bun buggy.ts
# NOT A NUMBER   <- Bun ran it; the type error was never checked
Common mistake: assuming "it ran under Bun, so the types are fine." Bun never type-checks during bun run. You must run bunx tsc --noEmit (in your editor, a pre-commit hook, and CI) to catch type errors. Treat bun run as execution and tsc --noEmit as verification — they are two different jobs.

tsconfig.json for Bun

Intermediate bun init generates a tsconfig tuned for Bun. The settings that matter:

// tsconfig.json
{
  "compilerOptions": {
    "lib": ["ESNext"],
    "target": "ESNext",
    "module": "ESNext",
    "moduleResolution": "bundler",        // Bun resolves like a bundler
    "allowImportingTsExtensions": true,   // import "./x.ts" explicitly if you like
    "verbatimModuleSyntax": true,
    "noEmit": true,                        // Bun runs TS; tsc only checks
    "strict": true,                        // turn on all strictness
    "skipLibCheck": true,
    "types": ["bun-types"]                 // Bun.* globals are typed
  }
}
SettingWhy Bun wants it
"moduleResolution": "bundler"Matches how Bun resolves imports (extensionless, package exports)
"noEmit": trueBun executes TS directly, so tsc should only check, never emit JS
"types": ["bun-types"]Gives Bun.*, Bun.file, import.meta.dir etc. their types
"strict": trueYou get no runtime type safety from Bun — strict static checking is your net

Path mapping

Define import aliases in tsconfig.json and Bun honors them at runtime (as does tsc for checking) — no extra bundler config, no tsconfig-paths package:

// tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"],
      "@db/*": ["src/db/*"],
      "@config": ["src/config.ts"]
    }
  }
}
// anywhere in src — Bun resolves these aliases natively
import { db } from "@db/index";
import { PORT } from "@config";
import { OrdersRepo } from "@/orders.repo";
Bun reads paths directly — you do not need tsconfig-paths, a webpack alias config, or a resolver plugin. Keep aliases shallow and consistent (@/ → src/ is a common convention) so a new reader can find a file from its import.

Type-checking with tsc --noEmit

Install TypeScript as a dev dependency and run the checker. --noEmit means "report errors but write no files" — exactly what you want, since Bun does the running.

bun add -d typescript
bunx tsc --noEmit            # check the whole project, emit nothing
bunx tsc --noEmit --watch    # re-check on save during development
// package.json — wire it into scripts
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "check": "tsc --noEmit && bun test"
  }
}
bun run typecheck
# src/buggy.ts(2,7): error TS2322: Type 'string' is not assignable to type 'number'.

Typing Bun's own APIs

With bun-types in your types array, the Bun namespace is fully typed. Hover-documentation and autocomplete work for everything:

const file = Bun.file("data.json");   // file: BunFile
const data = await file.json();        // data: any — annotate it yourself
const server = Bun.serve({ fetch: (req: Request) => new Response("ok") });

// Infer row types from a query result shape, or declare them
type Order = { id: number; total: number };
const rows = db.query("SELECT id, total FROM orders").all() as Order[];

Common mistakes

Common mistake: three recurring traps. (1) Shipping without a type-check step and discovering type errors only at runtime — add tsc --noEmit to CI. (2) Installing ts-node/tsx out of habit — they're pure overhead on Bun; delete them. (3) Setting "noEmit": false and letting tsc litter the repo with .js files that Bun never uses — keep noEmit: true and let Bun run the TS directly.

Exercises

  • Write a .ts file with an obvious type error, run it with bun (it succeeds), then run bunx tsc --noEmit and read the error it catches.
  • Add a paths alias @/* → src/* and import a module through it from both runtime (bun run) and the checker (tsc --noEmit).
  • Add a typecheck script and a check script that chains type-check + tests; run bun run check.
  • Confirm bun-types is giving you editor autocomplete on Bun.file(...) — hover the return type.

Mini-project: a typed config loader with a verified build gate

Build a strongly-typed config module behind a path alias, then prove the two-stage workflow: Bun runs it, tsc guards it. Set up the alias and a strict config, then a loader that would fail type-check if misused.

// tsconfig.json (excerpt)
{ "compilerOptions": {
    "strict": true, "noEmit": true, "moduleResolution": "bundler",
    "baseUrl": ".", "paths": { "@config": ["src/config.ts"] },
    "types": ["bun-types"]
} }
// src/config.ts
const LEVELS = ["debug", "info", "warn", "error"] as const;
type Level = (typeof LEVELS)[number];

function level(raw: string | undefined): Level {
  return (LEVELS as readonly string[]).includes(raw ?? "")
    ? (raw as Level)
    : "info";
}

export const config = {
  port: Number(Bun.env.PORT ?? 3000),
  logLevel: level(Bun.env.LOG_LEVEL),      // narrowed to the Level union
} as const;

export type Config = typeof config;         // exported, inferred — no hand-written interface
// src/index.ts
import { config, type Config } from "@config";

function start(c: Config) {
  // This line is a COMPILE error if you typo the union — tsc catches it:
  // if (c.logLevel === "verbose") {}   // TS2367: no overlap with Level
  console.log(`starting on :${c.port} @ ${c.logLevel}`);
}
start(config);
bun run src/index.ts         # runs immediately — alias resolves, types stripped
bunx tsc --noEmit            # gate: 0 errors == safe to commit

Now uncomment the "verbose" line: bun run still executes (types stripped), but bunx tsc --noEmit fails with TS2367. That failure in CI is what stops a type bug from reaching production — the division of labor at the heart of TypeScript on Bun.
