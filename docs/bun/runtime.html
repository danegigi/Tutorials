The bun CLI is the entry point to the runtime: it runs files and scripts, watches and hot-reloads, evaluates snippets, powers shebang tools, and gives you Web-standard APIs plus broad Node.js compatibility — this lesson is the day-to-day mechanics of running code.

bun run — files and scripts

Beginner bun run executes either a file path or a package.json script. For a file the run keyword is optional.

bun run index.ts        # run a file
bun index.ts            # "run" is optional for a file path
bun run dev             # run the "dev" script from package.json
bun dev                 # script name shorthand (when it isn't a builtin)
bun run --filter='*' build   # run "build" in every workspace of a monorepo
// package.json
{
  "scripts": {
    "start": "bun run src/index.ts",
    "dev": "bun --watch src/index.ts",
    "typecheck": "bunx tsc --noEmit"
  }
}
A few script names (start, test) can skip the run keyword, but a script that collides with a Bun builtin (e.g. a script named install) must be called with the explicit bun run install, otherwise Bun runs its own command. When in doubt, type bun run <name>.

--print and -e: evaluate inline

bun -e 'console.log(Bun.version)'           # evaluate a snippet
bun --print "1 + 1"                          # evaluate AND print the result -> 2
bun --print "await Bun.file('package.json').json()"   # top-level await works
echo 'console.log(42)' | bun -               # read program from stdin

-e runs the code; --print runs it and prints the last expression's value (like a one-shot REPL). Both support top-level await.

--watch vs --hot

Intermediate Both re-run on file change, but differently:

FlagBehaviorUse for
--watchRestarts the whole process on changeCLIs, scripts, tests
--hotReloads modules in place, keeps state & open socketsLong-running servers
 
bun --watch script.ts      # kill & restart on every save
bun --hot server.ts        # swap modules, keep the server listening

Under --hot, a Bun.serve() instance and in-process Bun.cron() jobs are re-registered cleanly on each reload — no leaked timers, no dropped connections, no port already in use. That's why servers want --hot and one-shot scripts want --watch.

Shebang scripts

Make a TypeScript file directly executable — a first-class way to ship CLI tools:

#!/usr/bin/env bun
// tool.ts
const [, , ...args] = Bun.argv;    // argv[0]=bun, argv[1]=script path
console.log("args:", args);
chmod +x tool.ts
./tool.ts a b c
# args: [ "a", "b", "c" ]
Reading arguments: Bun.argv is the full array including the bun executable and the script path, so your real arguments start at index 2. Destructure with const [, , ...rest] = Bun.argv to skip them. For flag parsing, Bun ships Node's util.parseArgs — import { parseArgs } from "node:util".

Web-standard APIs in Bun

Bun implements Web platform globals directly — no node-fetch, no polyfills:

// fetch, Request, Response, Headers, URL, URLSearchParams
const res = await fetch("https://api.github.com/repos/oven-sh/bun");
const repo = await res.json();

// Web Crypto
const id = crypto.randomUUID();
const digest = await crypto.subtle.digest("SHA-256", new TextEncoder().encode("x"));

// Streams, Blob, File, FormData, TextEncoder/Decoder, structuredClone, WebSocket
const blob = new Blob(["hi"], { type: "text/plain" });
console.log(await blob.text());

// Timers, queueMicrotask, AbortController all present
const ctrl = new AbortController();
setTimeout(() => ctrl.abort(), 1000);

Node.js compatibility

Bun aims to be a drop-in Node replacement. Most node:* builtins and npm packages work unchanged:

import { readFile } from "node:fs/promises";   // node builtins work
import { createServer } from "node:http";
import path from "node:path";
import { EventEmitter } from "node:events";

// process, Buffer, __dirname-like via import.meta
console.log(process.platform, process.cwd());
console.log(import.meta.dir, import.meta.file);   // Bun's dirname/filename
console.log(Buffer.from("hi").toString("base64"));

import.meta gives you Bun-native location helpers that replace CommonJS __dirname/__filename:

PropertyValue
import.meta.dirDirectory of the current file
import.meta.fileFilename of the current file
import.meta.pathAbsolute path of the current file
import.meta.maintrue if this is the entry file

Runtime introspection

Bun.version       // "1.4.2"
Bun.revision      // git sha of this build
Bun.main          // absolute path of the entry file
Bun.env.NODE_ENV  // environment
process.argv      // Node-style argv (same as Bun.argv)

Common mistakes

Common mistake: running a server with --watch and seeing "address already in use" or dropped WebSocket connections on every save — that's the full-process restart. Use --hot for servers so modules swap in place and the socket stays open. The opposite trap is using --hot for a one-shot script and being confused that it never exits; a plain run (or --watch) is right there. Also: don't reach for __dirname — in Bun's ESM modules it isn't defined; use import.meta.dir.

Exercises

  • Use bun --print to print the parsed contents of your package.json in one command.
  • Write a shebang script that echoes its arguments, chmod +x it, and run it with three arguments.
  • Start a trivial Bun.serve under --hot, change the response text, save, and hit it again without restarting — confirm the new text appears and the port never freed.
  • Print import.meta.dir, import.meta.file, and import.meta.main from both the entry file and an imported module; note how main differs.

Mini-project: a self-reloading dev dashboard

Build a tiny status server you run under --hot that holds in-memory state across reloads — proving hot reload preserves state while swapping code. Edit the HTML/logic while it runs and watch it update without losing the counter.

// dash.ts  —  run with: bun --hot dash.ts
// A module-scoped value survives --hot reloads (it isn't re-initialized).
const state = (globalThis as any).__state ??= { started: Date.now(), hits: 0 };

Bun.serve({
  port: 3000,
  routes: {
    "/": () => {
      state.hits++;
      const uptime = ((Date.now() - state.started) / 1000).toFixed(0);
      return new Response(
        `<h2>dev dashboard</h2>
         <p>bun ${Bun.version}</p>
         <p>uptime: ${uptime}s</p>
         <p>hits: ${state.hits}</p>`,
        { headers: { "Content-Type": "text/html" } },
      );
    },
    "/health": () => Response.json({ ok: true, hits: state.hits }),
  },
});
console.log("dashboard on http://localhost:3000  (edit this file and save)");

Load the page a few times to raise the counter, then change the heading text and save. The page updates on the next request, the port stays bound, and the hit counter keeps its value — the proof that --hot reloads code without discarding live state. Stash state on globalThis so it survives the module swap; a plain top-level let would reset each reload.
