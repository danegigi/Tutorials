JavaScript runs on one thread, so a CPU-heavy task — parsing a huge file, hashing, image processing — blocks everything, including the event loop that serves requests. Workers give you real parallelism: separate threads with their own event loop that communicate by message passing. This lesson covers when a Worker is the right tool, how to move data between threads cheaply, and how to build a reusable worker pool.

The problem Workers solve

Intermediate Bun (like Node and browsers) runs your code on a single main thread. Async I/O (fetch, file reads) doesn't block it — the event loop juggles those. But a synchronous CPU task does: a 2-second JSON parse freezes your server for 2 seconds. A Worker moves that work to another thread so the main thread stays responsive.

Workers are for CPU-bound work, not I/O-bound work. If your task is "await a database/HTTP call," a Worker buys you nothing — async already handles it. Reach for a Worker only when the thing blocking you is computation. Spawning a Worker has real cost (memory, startup), so it must pay for itself.

A basic Worker

// main.ts
const worker = new Worker(new URL("./worker.ts", import.meta.url).href);

worker.postMessage({ cmd: "fib", n: 42 });
worker.onmessage = (e) => {
  console.log("result:", e.data);   // result: 267914296
  worker.terminate();
};
// worker.ts — its own global scope, its own event loop
self.onmessage = (e) => {
  const { cmd, n } = e.data;
  if (cmd === "fib") {
    const fib = (x: number): number => (x < 2 ? x : fib(x - 1) + fib(x - 2));
    self.postMessage(fib(n));   // the heavy work runs OFF the main thread
  }
};
bun run main.ts   # the main thread never froze while fib(42) ran

Message passing: structured clone

Threads don't share variables; they exchange copies. postMessage serializes its argument with the structured-clone algorithm — objects, arrays, Maps, Sets, typed arrays, Dates all survive; functions, class instances' methods, and DOM nodes do not.

Travels fineDoes NOT
plain objects, arrays, Map/Setfunctions, closures
typed arrays, ArrayBuffer, Date, RegExpclass methods (only own data copies)

Transferables: move, don't copy

Advanced Copying a 100MB buffer across threads is slow. Transferables hand ownership of the underlying memory to the other thread with zero copy — but the sender loses access:

const buf = new ArrayBuffer(100_000_000);
worker.postMessage({ buf }, [buf]);   // 2nd arg = transfer list
console.log(buf.byteLength);           // 0 — ownership MOVED to the worker
After transfer, the buffer is detached in the sender (byteLength === 0). Reading it is a bug. Transfer when you're done with the data on this side; copy (plain postMessage) when both sides need it.

SharedArrayBuffer & Atomics

When threads must share the same memory (not copy, not transfer), SharedArrayBuffer + Atomics provide it with lock-free coordination:

const shared = new SharedArrayBuffer(8);
const counter = new Int32Array(shared);
worker.postMessage(shared);            // both threads see the SAME memory

// in either thread — atomic, race-free increment:
Atomics.add(counter, 0, 1);
Atomics.load(counter, 0);
Atomics.wait(counter, 0, 0);           // block until the value changes (worker only)
Atomics.notify(counter, 0);
Shared memory reintroduces data races — the reason JS avoided threads for years. Use Atomics for every read/write of shared cells; a plain counter[0]++ across threads is a race. Reserve SharedArrayBuffer for genuine high-throughput coordination; message passing is simpler and safer for most work.

A worker pool

Workers are expensive to spawn, so a pool reuses a fixed set across many tasks — the same bounded-parallelism idea as a server's connection pool:

class WorkerPool {
  private workers: Worker[] = [];
  private queue: { task: any; resolve: (v: any) => void }[] = [];
  private idle: Worker[] = [];

  constructor(size: number, url: string) {
    for (let i = 0; i < size; i++) {
      const w = new Worker(url);
      w.onmessage = (e) => this.onDone(w, e.data);
      this.workers.push(w); this.idle.push(w);
    }
  }
  run(task: any) {
    return new Promise((resolve) => {
      this.queue.push({ task, resolve });
      this.pump();
    });
  }
  private pump() {
    while (this.idle.length && this.queue.length) {
      const w = this.idle.pop()!; const job = this.queue.shift()!;
      (w as any)._resolve = job.resolve;
      w.postMessage(job.task);
    }
  }
  private onDone(w: Worker, result: any) {
    (w as any)._resolve(result);
    this.idle.push(w); this.pump();
  }
}
// const pool = new WorkerPool(navigator.hardwareConcurrency, "./worker.ts");

Size the pool to navigator.hardwareConcurrency (CPU count) — more workers than cores just adds overhead for CPU-bound work.

Common mistakes

  • Using a Worker for I/O-bound work — async already frees the main thread; the Worker just adds overhead.
  • Reading a transferred buffer in the sender — it's detached (byteLength 0).
  • Spawning a Worker per task — startup cost dominates; pool and reuse them.
  • Unsynchronized access to a SharedArrayBuffer — a data race; use Atomics.
  • Expecting functions/class instances to survive postMessage — only cloneable data crosses.
  • Never calling worker.terminate() — leaked workers hold memory for the process lifetime.

Exercises

  • Move a deliberately slow function (a big fibonacci or a tight hashing loop) into a Worker and prove the main thread stays responsive (log a timer every 100ms during the computation).
  • Transfer a large ArrayBuffer to a Worker and confirm the sender's copy is detached afterward.
  • Share an Int32Array over a SharedArrayBuffer and increment it from both threads 100k times with and without Atomics; observe the difference.
  • Build the worker pool above and feed it 1000 tasks, confirming only N workers run and the queue drains.
  • Compare a Worker to Bun.spawn for the same CPU task and note the startup/communication differences.

Mini-project

Build a parallel image-thumbnail generator: an HTTP server (Bun.serve) that accepts a batch of image paths and resizes each off the main thread using a Worker pool sized to the CPU count. Pass image bytes in as transferable ArrayBuffers to avoid copies, return the thumbnails, and keep the server responsive to a /health endpoint throughout a heavy batch. Measure throughput with 1 worker vs N, and document when the pool stops scaling (CPU saturation) — proving you understand that Workers parallelize CPU work, not magic.
