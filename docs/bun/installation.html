Install Bun with a single command, scaffold a project with bun init, run TypeScript natively with no build step, and understand how Bun resolves environment variables across .env files — the setup every later lesson assumes.

Install Bun

Beginner Pick the method for your OS. All of them land the same bun binary on your PATH.

# macOS / Linux (official installer)
curl -fsSL https://bun.com/install | bash

# Homebrew (macOS / Linux)
brew install oven-sh/bun/bun

# Windows (PowerShell)
powershell -c "irm bun.com/install.ps1 | iex"

# npm (if you already have Node) — installs the bun binary
npm install -g bun

# Verify
bun --version
# -> 1.4.2
Pin the version for reproducibility. In CI use oven-sh/setup-bun@v2 with bun-version: 1.4.2, and set "engines": { "bun": ">=1.0.0" } in package.json so collaborators get a clear error on an incompatible version. Upgrade later with bun upgrade.

Scaffold a project: bun init

mkdir my-app && cd my-app
bun init            # interactive — asks for name, entry point
bun init -y         # accept all defaults, no prompts

bun init creates a ready-to-run project:

my-app/
├─ package.json     # with "type": "module" and a dev script
├─ index.ts         # entry point
├─ tsconfig.json    # pre-tuned for Bun (bundler resolution, latest libs)
├─ bunfig.toml      # (sometimes) Bun config
├─ .gitignore
└─ README.md

The generated tsconfig.json already enables modern settings ("moduleResolution": "bundler", "allowImportingTsExtensions", latest lib) and pulls in Bun's types via bun-types, so Bun.* autocompletes in your editor immediately.

Run TS/JS natively

Bun executes TypeScript and JSX directly — no tsc, ts-node, or tsx shim. It strips types to run fast; it does not type-check (that's a separate step, see the TypeScript lesson).

// hello.ts
const name: string = "world";
const greet = (who: string): string => `Hello, ${who}!`;
console.log(greet(name));
bun hello.ts          # Hello, world!
bun run hello.ts      # identical — "run" is optional for a file path
bun -e 'console.log(1 + 1)'          # evaluate a snippet -> 2
bun --print "Bun.version"            # evaluate and print an expression

bunfig.toml — project configuration

Optional per-project (or global ~/.bunfig.toml) config. A realistic example:

# bunfig.toml
[install]
registry = "https://registry.npmjs.org"   # alternate registry / mirror
exact = true                                # bun add writes exact versions, not ^ranges

[test]
preload = ["./test/setup.ts"]               # run a setup file before every test
coverage = true

[run]
silent = true                               # suppress the "$ bun run ..." echo

# Map a loader to a file extension
[loader]
".svg" = "text"

You rarely need this on day one — defaults are good. Reach for it to pin a registry, preload test setup, or change bundler/loader behavior.

Environment variables & resolution order

Intermediate Bun auto-loads .env files with no dotenv package. It reads them in this order, and later sources win:

Priority (low → high)SourceTypical use
1.envCommitted defaults shared by everyone
2.env.<NODE_ENV> (e.g. .env.production)Per-environment values
3.env.localYour machine's secrets — gitignored
4Real OS environment variablesCI / container / shell exports — always win
 
# .env  (committed — safe defaults)
API_URL=https://api.example.com
PORT=3000

# .env.local  (gitignored — secrets)
API_KEY=sk_live_do_not_commit
// read them — Bun.env and process.env hold the SAME merged values
console.log(Bun.env.API_URL);     // https://api.example.com
console.log(process.env.PORT);    // "3000"
console.log(Bun.env.API_KEY);     // from .env.local

Bun.env vs process.env

They are the same object of values. Bun.env is the Bun-native accessor and is slightly faster; process.env exists for Node compatibility so unmodified npm packages keep working. Use Bun.env in new Bun code, process.env when a library expects it. Both are plain strings — coerce numbers/booleans yourself.

const port = Number(Bun.env.PORT ?? 3000);          // coerce to number
const debug = Bun.env.DEBUG === "true";              // coerce to boolean

Loading a specific env file

bun --env-file=.env.staging run src/index.ts   # load a named file
bun --env-file=.env.a --env-file=.env.b run app.ts  # multiple, later wins

Common mistakes

Common mistake: committing .env.local (or putting secrets in the committed .env). Keep real credentials in .env.local and add it to .gitignore — Bun loads it automatically and it never reaches the repo. A second trap: expecting bun hello.ts to catch type errors. It won't — Bun strips types to run. Run bunx tsc --noEmit for type checking. A third: assuming an exported shell variable is ignored because .env has a different value — real environment variables are the highest priority and override every file.

Exercises

  • Install Bun, run bun --version, then bun upgrade and note whether anything changed.
  • Scaffold a project with bun init -y and read the generated tsconfig.json — identify two Bun-specific settings.
  • Create .env with GREETING=hi and .env.local with GREETING=yo; print Bun.env.GREETING and confirm which wins.
  • Export GREETING=shell in your terminal and re-run — confirm the OS value overrides both files.

Mini-project: a config-aware startup banner

Write a small script that reads layered config and prints a startup banner, demonstrating the full resolution order and safe coercion. Create the three env files, then the script:

# .env
APP_NAME=Orders Service
PORT=3000
LOG_LEVEL=info

# .env.local  (gitignored)
DATABASE_URL=sqlite://local.db
// src/boot.ts
function required(key: string): string {
  const v = Bun.env[key];
  if (!v) throw new Error(`missing env: ${key}`);
  return v;
}

const config = {
  appName: Bun.env.APP_NAME ?? "app",
  port: Number(Bun.env.PORT ?? 3000),
  logLevel: Bun.env.LOG_LEVEL ?? "warn",
  databaseUrl: required("DATABASE_URL"),   // throws early if unset
  env: Bun.env.NODE_ENV ?? "development",
};

console.log(`
  ${config.appName}  [${config.env}]
  port=${config.port}  log=${config.logLevel}
  db=${config.databaseUrl.replace(/:\/\/.*/, "://***")}   // never print the raw URL
`);
bun run src/boot.ts
# Orders Service  [development]
# port=3000  log=info
# db=sqlite://***

The required() helper is the pattern to copy into real apps: fail loudly at startup when a secret is missing, rather than silently serving with an undefined connection string.
