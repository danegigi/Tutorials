When a service is down, the slowest way to fix it is to guess. The fastest is a fixed checklist you run top to bottom every time, because the fault is almost always at one specific layer and the checklist finds that layer in minutes. This lesson gives you a repeatable method — five questions, each with the exact command that answers it — and then walks a real down web service from alert to root cause using nothing else.

The method: five questions in order

Intermediate Troubleshoot from the outside in and from the bottom up. Each question narrows the fault; do not skip ahead, because a “no” early on makes the later questions moot.

#QuestionThe command that answers it
1Is it up? Is the process/service even running?systemctl status X · ps aux | grep X
2Is it reachable? DNS resolves, host answers, port open?dig +short · ping · ss -tulpn · curl
3Is it resourced? Disk, memory, CPU, file descriptors?df -h · free -h · top · uptime
4Is it logged? What does the service itself say?journalctl -u X -n 50 · tail /var/log/...
5What changed recently? Deploy, config edit, update, cert?git log · journalctl --since · file mtimes
Write the five questions on a sticky note. Under pressure the temptation is to jump straight to the fix you fixed last time — but running the checklist in order is faster and finds the faults the last-time fix would have missed. “What changed?” is last on the list but resolves the majority of incidents, because systems that were working rarely break on their own.

Question 1 — Is it up?

systemctl status myapp
# -> Active: failed (Result: exit-code) since Thu 10:01:12; 2min ago
# ->  Process: 5120 ExecStart=/opt/myapp/myapp (code=exited, status=1)

# If not managed by systemd:
ps aux | grep -v grep | grep myapp
# -> (no output = not running)

If it is not running, you already know a lot: skip straight to logs (Q4) to see why it exited, then what changed (Q5). If it is running but still broken, move to reachability.

Question 2 — Is it reachable?

Walk the network chain in order; the first failing step is your answer.

dig +short api.example.com        # DNS: does the name resolve?
# -> 203.0.113.10                 (empty = DNS problem, stop here)

ping -c2 203.0.113.10             # host reachable? (may be blocked — not definitive)

sudo ss -tulpn | grep :8080       # is anything LISTENING on the port?
# -> tcp LISTEN 127.0.0.1:8080 users:(("myapp",pid=...))

curl -sv http://localhost:8080/health   # does the app actually answer?
# -> < HTTP/1.1 200 OK   (or a connection-refused / timeout telling you where it breaks)
Common trap: the service is up and the port is listening — but on 127.0.0.1 only, so it works from the box and fails from everywhere else. The ss output above (127.0.0.1:8080 rather than 0.0.0.0:8080) is the tell. “Works locally, broken remotely” is almost always a bind-address or firewall issue, not an app bug.

Question 3 — Is it resourced?

A healthy-looking app that misbehaves is often starved of a resource. Check the big three.

df -h              # DISK — a full / or /var breaks writes, logs, sessions
# -> /dev/root  39G  39G  0  100% /       <- the smoking gun

free -h            # MEMORY — is it swapping or OOM-killing?
# -> Mem: 3.9Gi used 3.8Gi  free 48Mi

uptime             # LOAD — sustained load > core count = CPU saturation
# -> load average: 8.40, 7.90, 6.10   (on a 4-core box: overloaded)

dmesg | grep -i 'killed process'   # was the app OOM-killed by the kernel?
# -> Out of memory: Killed process 5120 (myapp)
A disk at 100% is one of the most common and most confusing outages: writes fail in ways that look like unrelated application bugs. Confirm with df -h, find the offender with du -sh /var/* | sort -h, and the culprit is usually runaway logs (/var/log) or Docker images (/var/lib/docker — prune with docker system prune).

Question 4 — Is it logged?

journalctl -u myapp -n 50 --no-pager      # last 50 lines for the service
# -> myapp[5120]: FATAL: could not connect to database "mydb": Connection refused

journalctl -u myapp -p err --since "30 min ago"   # just errors, recent window
tail -n 50 /var/log/myapp/error.log               # file-based logs too

The log line almost always names the real fault — here, the app is fine but its database is unreachable, which sends you to run the same five questions against the database. Follow the error to its source rather than restarting blindly.

Question 5 — What changed recently?

git -C /opt/myapp log --oneline -5        # recent deploys/commits
# -> a1b2c3d (HEAD) switch DB host to db-02   <- suspicious, matches the error

ls -lt /etc/myapp/                        # most-recently-modified config first
# -> -rw-r--r-- 1 root root  210 Oct  8 09:58 config.yaml   <- edited 3 min before it broke

journalctl --since "1 hour ago" | grep -iE "install|upgrade|renew"   # package/cert changes

A config edited minutes before the outage, a deploy that changed a hostname, a cert that just expired — “what changed” is where most incidents actually resolve.

Worked example: a down web service

Intermediate An alert fires: “example.com returns 502.” Run the checklist.

# Q1 Is it up? nginx is fine; the APP behind it is the question.
systemctl status nginx
# -> Active: active (running)
systemctl status myapp
# -> Active: failed (Result: exit-code)       <- found it: the backend is down

# Q2 Reachable? nginx answers but has nothing to proxy to.
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:80
# -> 502                                       (nginx up, upstream dead — consistent)
sudo ss -tulpn | grep :8080
# -> (empty)                                   the app is not listening at all

# Q4 Logged? ask the app why it died.
journalctl -u myapp -n 10 --no-pager
# -> myapp[5120]: FATAL: config: unknown key 'databse_url'   <- a typo!

# Q5 What changed? confirm the cause.
ls -lt /etc/myapp/config.yaml
# -> -rw-r--r-- 1 root root 210 Oct  8 09:58 config.yaml    (edited just before the alert)
git -C /opt/myapp diff HEAD~1 -- /etc/myapp/config.yaml
# -> -database_url: ...
# -> +databse_url: ...                          the typo that crashed startup

Root cause: a misspelled config key (databse_url) in an edit made at 09:58 crashed the app on startup; nginx then returned 502 because its upstream was gone. Fix the typo, restart, verify:

sudo sed -i 's/databse_url/database_url/' /etc/myapp/config.yaml
sudo systemctl restart myapp
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:80
# -> 200                                        service restored

Notice the checklist never guessed: Q1 located the layer (backend, not nginx), Q4 named the error, Q5 confirmed the cause. Four commands, no restarting-and-hoping.

Exercises

  • Write out the five questions from memory and the single command you would run first for each.
  • On your machine, run the full Q3 resource trio (df -h, free -h, uptime) and note which resource has the least headroom.
  • Pick any running service and answer Q1 and Q4 for it: is it up, and what are its last 20 log lines?
  • Explain why a port listening on 127.0.0.1 instead of 0.0.0.0 produces a “works locally, fails remotely” symptom.

Mini-project: a one-shot triage script

Turn the five questions into a script you can run (or hand to a teammate) the moment an alert fires. It takes a service name and a port and answers all five layers in one pass.

#!/usr/bin/env bash
set -uo pipefail
svc="${1:?usage: triage.sh SERVICE [PORT]}"
port="${2:-8080}"

echo "===== Q1: is $svc up? ====="
systemctl is-active "$svc" 2>/dev/null || echo "NOT active"
systemctl status "$svc" --no-pager -n 3 2>/dev/null | tail -3

echo; echo "===== Q2: is port $port listening? ====="
sudo ss -tulpn 2>/dev/null | grep ":$port" || echo "nothing on :$port"

echo; echo "===== Q3: resources ====="
df -h / /var 2>/dev/null | tail -2
free -h | awk 'NR==1||/Mem/'
uptime

echo; echo "===== Q4: recent errors from $svc ====="
journalctl -u "$svc" -p warning -n 15 --no-pager 2>/dev/null || echo "(no journal)"

echo; echo "===== Q5: what changed? ====="
journalctl --since "1 hour ago" 2>/dev/null | grep -iE "install|upgrade|renew" | tail -5
echo "(also check: git log in the deploy dir, and mtimes under /etc/$svc)"
sudo ./triage.sh myapp 8080
# -> ===== Q1: is myapp up? =====
# -> NOT active
# -> ===== Q2: is port 8080 listening? =====
# -> nothing on :8080
# -> ===== Q3: resources =====
# -> /dev/root 39G 12G 26G 32% /
# -> ===== Q4: recent errors from myapp =====
# -> myapp[5120]: FATAL: config: unknown key 'databse_url'
# -> ...

One command now prints every layer's answer, so you — or whoever is on call at 3am — read down the output and the broken layer announces itself. That is the entire discipline of troubleshooting: a fixed order, the right command per layer, and the patience to run them before touching anything.
