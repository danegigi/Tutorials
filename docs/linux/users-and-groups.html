Linux is multi-user to its core: every process runs as some user, every file is owned by one, and the whole permission model rests on knowing who is who. This lesson covers the three files that define accounts (/etc/passwd, /etc/group, /etc/shadow), the commands that create and modify users, how group membership grants access, and how sudo lets ordinary accounts do privileged work without ever logging in as root.

The three account files

Beginner User and group definitions are plain colon-separated text files you can read (two of them, anyway):

FileHoldsReadable by
/etc/passwdOne line per user: name, UID, GID, home, login shell.Everyone.
/etc/groupOne line per group: name, GID, and member list.Everyone.
/etc/shadowHashed passwords and expiry policy.root only (0640, group shadow).
 
grep '^ada:' /etc/passwd
# -> ada:x:1001:1001:Ada Lovelace:/home/ada:/bin/bash
#      |   | |    |    |            |          |
#      |   | |    |    comment      home       login shell
#      |   | UID  GID
#      |   password placeholder (x = see /etc/shadow)
#      username

grep '^devs:' /etc/group
# -> devs:x:1005:ada,grace,linus     (members of the devs group)

Despite the x placeholder in passwd, no password hash lives there — it is in /etc/shadow, which only root can read, so a world-readable passwd leaks no secrets.

sudo grep '^ada:' /etc/shadow
# -> ada:$6$rounds=...$hashhash:19640:0:99999:7:::
#      |  |                     |     | |     |
#      |  hashed password       |     | max   warn-before-expiry
#      |                        |     min days between changes
#      |                        last-changed (days since epoch)
#      username

UIDs tell you the kind of account

UID rangeMeaning
0root — the superuser, unrestricted.
1–999System/service accounts (www-data, sshd, systemd-*) — usually no login shell.
1000+Regular human users, created in creation order.
 
id
# -> uid=1001(ada) gid=1001(ada) groups=1001(ada),1005(devs),27(sudo)

whoami
# -> ada

getent passwd www-data        # getent reads passwd + any directory (LDAP etc.)
# -> www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin

Creating and modifying users

Intermediate The admin commands all require root. useradd is the low-level tool; adduser (Debian/Ubuntu) is a friendlier wrapper that also prompts for a password and creates the home directory.

# Create a user with a home dir and bash shell
sudo useradd -m -s /bin/bash grace

# Set (or reset) their password
sudo passwd grace

# Create a service account with NO login (for a daemon)
sudo useradd -r -s /usr/sbin/nologin widgetd

# Add grace to an existing group (the -aG is the critical part)
sudo usermod -aG devs grace

# Change a user's shell or home
sudo usermod -s /bin/zsh grace

# Remove a user and their home directory
sudo userdel -r grace
Common mistake: adding a user to a group with usermod -G devs grace (no -a) replaces all their supplementary groups with just devs, silently dropping them from sudo and everything else. Always use -aG (append). Also note that a user's group membership is only re-read at login — after usermod -aG they must log out and back in (or run newgrp devs) before the new group takes effect.

Groups and shared access

Groups are how several users share access to the same files without making them world-readable. A user has one primary group (the GID in /etc/passwd, used for files they create) and any number of supplementary groups.

groups ada
# -> ada : ada devs sudo

sudo groupadd deploy             # make a new group
sudo usermod -aG deploy ada      # add ada to it
sudo chgrp deploy /srv/release   # let the group own a directory
sudo chmod 2775 /srv/release     # setgid so new files inherit the group

Now any member of deploy can read and write /srv/release, and files they create there belong to deploy automatically — the clean alternative to loosening permissions.

sudo and the principle of least privilege

Intermediate You should almost never log in as root. Instead, give trusted users the ability to run specific (or all) commands as root through sudo, which asks for their own password, logs every command, and limits what each person can do.

sudo apt update                  # run one command as root
sudo systemctl restart nginx
sudo -i                          # start an interactive root shell (use sparingly)
sudo -u www-data whoami          # run as a specific other user
# -> www-data

Granting sudo

Membership of the sudo group (Debian/Ubuntu) or wheel (RHEL/Fedora) grants full sudo:

sudo usermod -aG sudo grace      # grace can now sudo

For finer control, drop a file in /etc/sudoers.d/ — always edited with visudo, which validates syntax before saving so a typo cannot lock everyone out:

sudo visudo -f /etc/sudoers.d/deploy
# then add, for a deploy user allowed only to restart one service:
# deploy  ALL=(root) NOPASSWD: /usr/bin/systemctl restart myapp
Never edit /etc/sudoers directly with a plain editor — a syntax error there can make sudo refuse to run at all, locking you out of privilege escalation entirely. visudo exists precisely to prevent that. And prefer narrow grants (one command for one user) over blanket ALL=(ALL) NOPASSWD:ALL: the whole point of least privilege is that a compromised deploy account should not equal full root.

Mini-project: a locked-down deploy account

Create a service account that can restart one application and nothing else — the least-privilege pattern you would use for a CI runner or a webhook.

# 1. A no-login service user
sudo useradd -r -s /usr/sbin/nologin -m -d /srv/deployer deployer

# 2. A group owning the release directory, setgid so files inherit it
sudo groupadd release
sudo usermod -aG release deployer
sudo mkdir -p /srv/release
sudo chgrp release /srv/release
sudo chmod 2775 /srv/release

# 3. A narrow sudo grant: restart ONE service, no password, nothing else
sudo visudo -f /etc/sudoers.d/deployer
# deployer ALL=(root) NOPASSWD: /usr/bin/systemctl restart myapp

# 4. Verify the account cannot do more than intended
sudo -u deployer sudo -l
# -> User deployer may run the following commands:
# ->     (root) NOPASSWD: /usr/bin/systemctl restart myapp

The deployer account cannot log in interactively, cannot read other users' files, and can run exactly one privileged command. If its credentials leak, the blast radius is a single service restart — least privilege working as designed.
