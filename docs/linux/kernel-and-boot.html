Everything your Linux server does rests on a sequence that runs in seconds at power-on: firmware hands off to a bootloader, the bootloader loads the kernel, the kernel mounts the real root filesystem and starts the init system, and only then do your services run. Understanding this chain is what lets you fix a machine that won't boot, load the right driver, and tune the kernel safely.

The boot sequence, stage by stage

Intermediate

  1. Firmware (UEFI or legacy BIOS) — the motherboard's own code runs first, does POST, and finds a bootloader. UEFI reads an EFI System Partition (ESP, a FAT filesystem at /boot/efi) and a boot entry list; legacy BIOS reads the MBR.
  2. Bootloader (GRUB) — presents the menu, loads the selected kernel + its initramfs into memory, and passes a kernel command line.
  3. Kernel — initializes hardware, mounts the initramfs as a temporary root, loads just-enough drivers to find the real disk, then pivots to the real root filesystem.
  4. init (PID 1, systemd) — the kernel starts /sbin/init (systemd), which brings up the default target and all its services.
  5. Login — getty/display manager presents a prompt.
systemd-analyze              # total boot time: firmware + loader + kernel + userspace
systemd-analyze blame        # slowest services
systemd-analyze critical-chain

GRUB: the bootloader

# You edit /etc/default/grub, NOT grub.cfg directly:
GRUB_TIMEOUT=5
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash"
# then regenerate the real config:
update-grub                  # Debian/Ubuntu
grub2-mkconfig -o /boot/grub2/grub.cfg   # RHEL/Fedora
Never hand-edit /boot/grub/grub.cfg — it's generated and your changes are wiped on the next kernel update. Edit /etc/default/grub (persistent settings) or drop scripts in /etc/grub.d/, then regenerate. At the GRUB menu you can press e to edit the command line for ONE boot — the escape hatch for a broken config.

The kernel command line

cat /proc/cmdline            # what the running kernel was booted with
# Common one-boot rescue edits (press 'e' in GRUB, append to the linux line):
#   single        → boot to single-user/rescue
#   init=/bin/bash → skip init entirely (reset a lost root password)
#   nomodeset     → disable KMS when a GPU driver breaks the display
If a box won't boot after a change, the GRUB e-edit + init=/bin/bash (or systemd.unit=rescue.target) is how you get a shell to undo it. Knowing this turns "unbootable, reinstall" into "five-minute fix."

initramfs: the chicken-and-egg solver

The kernel needs a driver to read the root disk — but the driver often lives on the root disk. The initramfs breaks the loop: a small in-memory filesystem with just enough modules (disk controller, LVM, LUKS, filesystem) to mount the real root, then it pivots away.

# rebuild it after changing modules/encryption/root layout:
update-initramfs -u          # Debian/Ubuntu
dracut --force               # RHEL/Fedora
lsinitramfs /boot/initrd.img-$(uname -r) | head   # peek inside
A root on LVM, RAID, or an encrypted (LUKS) volume that drops to an (initramfs) prompt at boot usually means the initramfs is missing the needed module — rebuild it with the device present, don't just reinstall the kernel.

Kernel modules: drivers you can load

Intermediate The kernel is modular — most drivers load on demand rather than being compiled in.

lsmod                        # loaded modules
modinfo e1000e               # details, parameters, dependencies of a module
modprobe wireguard           # load a module (and its dependencies)
modprobe -r pcspkr           # unload (e.g. silence the beep)
# persist a load across reboots:
echo wireguard > /etc/modules-load.d/wireguard.conf
# blacklist a misbehaving driver:
echo "blacklist nouveau" > /etc/modprobe.d/blacklist-nouveau.conf

sysctl: tuning the running kernel

Advanced Hundreds of kernel knobs live under /proc/sys and are read/written with sysctl.

sysctl -a | grep somaxconn           # inspect
sysctl net.ipv4.ip_forward           # read one
sysctl -w net.ipv4.ip_forward=1      # set NOW (not persistent)
# persist in /etc/sysctl.d/99-custom.conf:
#   net.core.somaxconn = 1024
#   vm.swappiness = 10
#   net.ipv4.tcp_syncookies = 1
sysctl --system                      # reload all drop-in files
Common production tunables: raise net.core.somaxconn and net.ipv4.tcp_max_syn_backlog for high-connection servers, lower vm.swappiness so the box prefers reclaiming cache over swapping, and enable net.ipv4.ip_forward on routers. Set them in /etc/sysctl.d/, never only with -w (which doesn't survive reboot).

Kernels installed, running, and switching

uname -r                     # the RUNNING kernel version
ls /boot/vmlinuz-*           # installed kernels (GRUB lists each)
dpkg --list | grep linux-image   # Debian/Ubuntu packages
# Multiple kernels let you boot the previous one from GRUB's "Advanced options"
# if a new kernel breaks a driver — a built-in rollback.

Common mistakes

  • Hand-editing grub.cfg — it's regenerated; edit /etc/default/grub + update-grub.
  • Setting sysctl only with -w and wondering why it's gone after reboot — persist in /etc/sysctl.d/.
  • Not rebuilding the initramfs after changing root encryption/LVM/RAID, then dropping to an initramfs prompt.
  • Removing all old kernels, so there's nothing to boot into when a new one breaks.
  • Panicking at an unbootable system instead of using the GRUB e-edit / rescue target to get a shell.
  • Blacklisting the wrong module or compiling-in vs loading confusion — check with lsmod/modinfo first.

Exercises

  • Run systemd-analyze and systemd-analyze blame; identify the slowest part of your boot.
  • Read /proc/cmdline, then (in a VM) use the GRUB e-edit to boot into rescue.target for one boot.
  • Load and unload a kernel module with modprobe, inspect it with modinfo, and make the load persistent.
  • Set vm.swappiness with sysctl -w, confirm it, then make it persistent in /etc/sysctl.d/ and reload with sysctl --system.
  • In a VM, practice the lost-root-password recovery: boot with init=/bin/bash, remount root read-write, reset the password, and reboot.

Mini-project

Document the complete boot chain of one machine end to end, with evidence at each stage: identify UEFI vs BIOS and locate the ESP; capture the GRUB config and kernel command line; list what's in the initramfs and explain why each module is there (especially if root is on LVM/LUKS); record the running kernel and the installed alternatives; and apply a small set of justified sysctl tunables persistently. Then deliberately break the boot in a VM (a bad GRUB cmdline), recover it with the GRUB e-edit, and write the recovery steps as a runbook you could follow at 3 a.m.
