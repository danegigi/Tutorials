When a server "can't reach" something, the fix lives in Linux's networking stack: interfaces, routing tables, the DNS resolution path, firewall rules, and the sockets a process actually opened. This lesson follows a packet from your application down to the wire and back, with the modern tools (ip, ss, nft, tcpdump) — not the deprecated ifconfig/netstat.

Interfaces and addresses with ip

Beginner The ip command (from iproute2) replaced ifconfig. Learn its subcommands:

ip addr                     # interfaces and their IPs (alias: ip a)
ip -br -c addr              # brief, coloured — great at a glance
ip link set eth0 up        # bring an interface up/down
ip addr add 10.0.0.5/24 dev eth0   # add an address (not persistent)
$ ip -br a
lo       UNKNOWN   127.0.0.1/8 ::1/128
eth0     UP        10.0.0.5/24 fe80::.../64
Changes made with ip are not persistent — they vanish on reboot. Persistent config lives in your distro's network manager (netplan on Ubuntu, NetworkManager/nmcli on RHEL/Fedora, systemd-networkd). Use ip for diagnosis and temporary tweaks; edit the manager's config for permanent changes.

The routing table: where does a packet go?

ip route                    # the routing table
# default via 10.0.0.1 dev eth0        ← the gateway for "everything else"
# 10.0.0.0/24 dev eth0 proto kernel scope link src 10.0.0.5

ip route get 8.8.8.8        # ask the kernel WHICH route a destination uses
# 8.8.8.8 via 10.0.0.1 dev eth0 src 10.0.0.5

For any destination, the kernel picks the most specific matching route; default (0.0.0.0/0) catches everything else and sends it to the gateway. ip route get is the fastest way to answer "why is this traffic going out the wrong interface?"

The DNS resolution path

Intermediate A name becomes an IP through a specific chain — know every link because any one can be the culprit:

  1. /etc/nsswitch.conf — the hosts: line decides the ORDER (files, then DNS).
  2. /etc/hosts — static overrides, checked first (this is where a stale hand-edit bites).
  3. /etc/resolv.conf — the nameservers to query. On systemd-resolved systems this points at 127.0.0.53, a local stub.
  4. The resolver queries those nameservers over UDP/TCP 53 (or DoT).
resolvectl status           # systemd-resolved: per-link DNS servers, DNSSEC
resolvectl query example.com
dig example.com +short      # the query tool; +trace to follow from the root
getent hosts example.com    # resolve the way the SYSTEM does (honours nsswitch)
dig talks straight to DNS; getent hosts uses the full nsswitch path. If dig resolves a name but your app doesn't, the difference is usually /etc/hosts or an nsswitch rule — getent reproduces what the application sees.

Sockets: what's actually listening/connected

ss -tlnp                    # TCP, Listening, Numeric, with Process (needs sudo for names)
# State   Recv-Q  Local Address:Port   Process
# LISTEN  0       0.0.0.0:8080         users:(("myapp",pid=1234,fd=3))

ss -tn state established    # current connections
ss -s                       # summary counts

ss replaced netstat (faster, same info). Reading for "is my service even listening?": a LISTEN on 0.0.0.0:8080 accepts from anywhere; on 127.0.0.1:8080 it's localhost-only — a very common "works locally, refused remotely" cause.

Firewalls: nftables (and iptables)

Advanced The kernel's packet filter is nftables (nft), the successor to iptables. Most distros ship a friendlier front end (ufw on Ubuntu, firewalld on RHEL) that drives it for you.

nft list ruleset            # the whole active firewall
# a minimal inbound policy:
nft add table inet filter
nft 'add chain inet filter input { type filter hook input priority 0; policy drop; }'
nft add rule inet filter input ct state established,related accept
nft add rule inet filter input iif lo accept
nft add rule inet filter input tcp dport {22, 80, 443} accept
# The ufw equivalent (what you'll usually use):
ufw default deny incoming
ufw allow 22/tcp && ufw allow 80,443/tcp
ufw enable && ufw status verbose
Lock yourself out drill: a policy drop input chain with no SSH-allow rule, applied over SSH, cuts your own connection instantly. Always allow established,related and your management port (22) before flipping the default to drop — and keep a console/out-of-band way in. The established,related accept rule is what keeps existing connections (including your SSH session) alive.

NAT and connection tracking

Linux can rewrite addresses (SNAT/masquerade for outbound sharing, DNAT for port-forwarding) via the nat hooks, tracked by conntrack:

# forward host port 8080 to a container/VM at 10.0.0.9:80 (DNAT)
nft add rule inet nat prerouting tcp dport 8080 dnat to 10.0.0.9:80
conntrack -L                # live connection-tracking table (needs conntrack-tools)
cat /proc/sys/net/ipv4/ip_forward   # must be 1 to route between interfaces

Capturing traffic: tcpdump

tcpdump -ni eth0 port 443 and host 10.0.0.9   # filter: don't drown in packets
tcpdump -ni any icmp                           # are pings arriving at all?
tcpdump -w cap.pcap port 80                    # write to a file, open in Wireshark
When "connection refused" vs "connection timed out" vs "no route" is unclear, tcpdump settles it: you SEE whether the SYN leaves, whether a reply comes back, or whether nothing happens at all — each points at a different layer (firewall drop, nothing listening, routing/DNS).

A debugging ladder

  1. ip a — do I have an address on the right interface?
  2. ip route get <dest> — which route/gateway will this use?
  3. getent hosts <name> / dig — does the name resolve, the way the app resolves it?
  4. ss -tlnp — is the service listening, and on the right address?
  5. nft list ruleset / ufw status — is a firewall dropping it?
  6. tcpdump — watch the actual packets to localize the failure.

Common mistakes

  • Expecting ip/nft changes to persist — they don't; edit the network manager / firewall config for permanence.
  • A service bound to 127.0.0.1 when you need remote access — it must bind 0.0.0.0 (or a specific external IP).
  • A stale /etc/hosts entry overriding real DNS, invisible to dig but seen by the app (getent reveals it).
  • Flipping a firewall to default-drop over SSH without an established,related + port-22 allow — instant lockout.
  • Forgetting ip_forward=1 when the box is supposed to route/NAT between interfaces.
  • Using deprecated ifconfig/netstat — often not installed, and they miss namespaces and some state; use ip/ss.

Exercises

  • Use ip route get to find which interface and gateway your traffic to a public IP uses, and explain the matching route.
  • Add a line to /etc/hosts, then show the discrepancy between dig and getent hosts; remove it afterward.
  • Start a service bound to 127.0.0.1, confirm ss -tlnp shows it, fail to reach it remotely, rebind to 0.0.0.0, and succeed.
  • In a VM, write an nftables input policy that allows SSH + HTTP and drops the rest — safely, with an established,related rule — and verify with nft list ruleset.
  • Use tcpdump to tell apart a firewall-dropped connection (SYN leaves, no reply) from a nothing-listening one (RST comes back).

Mini-project

In a VM, build and document a small router/firewall host: give it two interfaces, enable IP forwarding, write an nftables ruleset with a default-drop input policy (safely allowing SSH + established), SNAT/masquerade so a second machine reaches the internet through it, and a DNAT rule forwarding a public port to an internal service. Prove each piece with the debugging ladder — ip route get, ss, conntrack -L, and a tcpdump capture of a forwarded connection — and write up how you'd diagnose it if one layer were broken.
