When something breaks, the logs almost always already contain the answer — the skill is knowing where they live and how to filter the noise down to the one line that matters. On a modern Linux system that means two places: the systemd journal (queried with journalctl) and plain text files under /var/log. This lesson covers following logs live, scoping them to one service and time window, grepping for patterns, and keeping them from filling the disk with logrotate.

Two homes for logs

Beginner Services started by systemd send their stdout/stderr to the journal, a structured binary store you read with journalctl. Many traditional daemons also (or instead) write plain-text files under /var/log. You will use both.

ls /var/log
# -> auth.log  nginx  syslog  dpkg.log  journal

ls /var/log/nginx
# -> access.log  error.log

journalctl: the systemd journal

Intermediate The flags you reach for constantly are -u (one unit), -f (follow live), and --since (a time window).

CommandShows
journalctl -u nginxAll log lines for the nginx service.
journalctl -u nginx -fFollow that service live (like tail -f).
journalctl -u nginx --since "1 hour ago"Only the last hour.
journalctl -u nginx -p errOnly priority err and worse.
journalctl -bEverything since the last boot; -b -1 for the previous boot.
journalctl -kKernel messages (the dmesg equivalent).
journalctl -n 50The last 50 lines across everything.
 
sudo journalctl -u nginx --since "2026-10-08 09:00" --until "2026-10-08 10:00"
# -> Oct 08 09:14:02 web-01 nginx[814]: 203.0.113.9 - GET /api 200
# -> Oct 08 09:51:18 web-01 nginx[814]: 203.0.113.9 - GET /x 404

# Follow a service AND filter to errors as they stream
sudo journalctl -u myapp -f -p warning
# -> Oct 08 10:02:11 web-01 myapp[5120]: WARN db pool exhausted
# -> ... (new matching lines appear live; Ctrl-C to stop)

# Combine with grep when a priority filter is too coarse
sudo journalctl -u myapp --since today | grep -i timeout

Priority levels, highest to lowest severity, accepted by -p: emerg, alert, crit, err, warning, notice, info, debug. -p err means “err and anything more severe.”

The journal can grow large. Check its disk use with journalctl --disk-usage and cap it with sudo journalctl --vacuum-time=7d (keep a week) or --vacuum-size=500M. A persistent cap belongs in /etc/systemd/journald.conf (SystemMaxUse=500M).

Plain-text logs under /var/log

Beginner For file-based logs, the trio is tail -f to watch, less to browse, and grep to search.

# Watch a growing log live
tail -f /var/log/nginx/access.log
# -> 203.0.113.9 - GET /api HTTP/1.1 200
# -> ... (new lines as requests arrive)

# Follow two files at once, labelled
tail -f /var/log/nginx/access.log /var/log/nginx/error.log

# Last 100 lines, then page through
tail -n 100 /var/log/syslog | less

# Follow AND filter in real time
tail -f /var/log/myapp.log | grep --line-buffered ERROR
Common mistake: piping tail -f into grep and seeing nothing appear even though matching lines are being written. grep buffers its output when it is not writing to a terminal, so matches sit in a buffer instead of printing. Add --line-buffered to grep (as above) so each matching line prints immediately.

Searching logs with grep

Intermediate A few grep flags turn a wall of log into an answer:

FlagMeaning
-iCase-insensitive (ERROR matches error).
-vInvert — lines that do not match (drop noise).
-cCount matching lines instead of printing them.
-nShow line numbers.
-EExtended regex (alternation a|b, +, grouping).
-A/-B/-C NN lines of context After / Before / around a match.
 
# Count 500s in today's access log
grep -c " 500 " /var/log/nginx/access.log
# -> 42

# Errors OR warnings, with 3 lines of context, case-insensitive
grep -iE -C3 "error|warn|fatal" /var/log/myapp.log

# Everything EXCEPT noisy health-check lines
grep -v "/healthz" /var/log/nginx/access.log | tail

# Which client IPs hit a 404 the most?
grep " 404 " /var/log/nginx/access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head
# ->  58 203.0.113.44
# ->  12 198.51.100.7

logrotate: keeping logs from eating the disk

Intermediate Left alone, a busy log file grows without limit until the disk is full. logrotate (run daily by cron/systemd) rotates logs: it renames the current file, starts a fresh one, compresses old ones, and deletes those past a retention limit. Each package drops a config in /etc/logrotate.d/.

cat /etc/logrotate.d/nginx
# -> /var/log/nginx/*.log {
# ->     daily
# ->     rotate 14          # keep 14 old files
# ->     compress           # gzip rotated files
# ->     delaycompress
# ->     missingok
# ->     notifempty
# ->     postrotate
# ->         systemctl reload nginx >/dev/null 2>&1 || true
# ->     endscript
# -> }

ls /var/log/nginx
# -> access.log  access.log.1  access.log.2.gz  access.log.3.gz
#    (current)   (yesterday)   (older, compressed)

sudo logrotate -d /etc/logrotate.d/nginx   # -d = debug: show what WOULD happen
sudo logrotate -f /etc/logrotate.d/nginx   # -f = force a rotation now
The postrotate block matters: an app that keeps its log file open by file descriptor will keep writing to the renamed old file after rotation unless it is told to reopen. That is why the nginx config reloads the service — so it opens the fresh access.log.

Exercises

  • Show the last 20 journal lines for the ssh (or sshd) service from the current boot only.
  • Follow a service's journal live and filter to warnings and errors in one command.
  • Count how many lines in a log contain the word error case-insensitively, then show three of them with surrounding context.
  • Check your journal's current disk usage and work out the command to trim it to the last 3 days.

Mini-project: a “what went wrong in the last hour” report

Write a one-shot script that gathers the recent errors across the system into a single readable report — the first thing you would run after an alert fires.

#!/usr/bin/env bash
set -uo pipefail
echo "=== Report generated $(date -Iseconds) ==="

echo; echo "--- systemd errors (last hour) ---"
journalctl --since "1 hour ago" -p err --no-pager | tail -30

echo; echo "--- failed/degraded units ---"
systemctl --failed --no-legend

echo; echo "--- nginx 5xx (last hour, if present) ---"
if [ -f /var/log/nginx/access.log ]; then
  awk -v t="$(date -d '1 hour ago' '+%d/%b/%Y:%H')" \
    '$0 ~ t && $9 ~ /^5/ {print}' /var/log/nginx/access.log | tail -20
fi

echo; echo "--- disk usage (is /var full?) ---"
df -h / /var 2>/dev/null
sudo ./incident-report.sh | tee /tmp/incident-$(date +%s).txt
# -> === Report generated 2026-10-08T10:05:00+00:00 ===
# -> --- systemd errors (last hour) ---
# -> Oct 08 09:51 web-01 myapp[5120]: ERROR db connection refused
# -> --- failed/degraded units ---
# -> myapp.service loaded failed failed Widget daemon
# -> ...

In one pass you get the systemd errors, any failed services, recent HTTP 5xx responses, and whether the disk is full — the four questions that explain the large majority of “the service is down” incidents, pulled straight from the logs that already recorded them.
