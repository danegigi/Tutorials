systemd is the init system and service manager on nearly every modern Linux distribution — PID 1, the first process the kernel starts, and the thing that boots the machine, supervises every service, collects logs, and schedules timers. This lesson goes past "start/stop a service" into writing robust unit files, understanding targets and ordering, journald, and locking a service down with its built-in sandboxing.

Units: everything is a unit

Beginner systemd models everything it manages as a unit, typed by file extension:

TypeManages
.servicea process (a daemon, a one-shot script)
.socketa socket that activates a service on first connection
.timera scheduled trigger (the cron replacement)
.targeta group of units (the runlevel replacement)
.mount / .automountfilesystem mounts
systemctl status nginx           # state, recent logs, PID, cgroup
systemctl start|stop|restart nginx
systemctl reload nginx           # SIGHUP — reload config without dropping connections
systemctl enable --now nginx     # start now AND on boot
systemctl list-units --type=service --state=running

Anatomy of a service unit

# /etc/systemd/system/myapp.service
[Unit]
Description=My App
After=network-online.target postgresql.service   # ORDER: start after these
Wants=network-online.target                       # WEAK dep: want it, don't fail without it

[Service]
Type=simple                 # the ExecStart process IS the service
ExecStart=/usr/local/bin/myapp --port 8080
Restart=on-failure          # auto-restart if it crashes
RestartSec=5
User=myapp                  # drop privileges — never run as root unless required
Environment=LOG_LEVEL=info
EnvironmentFile=/etc/myapp/env   # or load from a file

[Install]
WantedBy=multi-user.target  # enable = symlink into this target's .wants
systemctl daemon-reload          # ALWAYS run after editing a unit file
systemctl enable --now myapp
The two mistakes that make a service "not start after I edited it": (1) forgetting systemctl daemon-reload — systemd caches units and won't see your edit until you reload; (2) confusing After= (ordering) with Requires=/Wants= (dependency). After= only sequences; it does NOT pull the other unit in. You usually want both an ordering AND a dependency directive.

Service types

TypeMeaning
simpleExecStart is the main process (default)
execlike simple, but "started" only once exec() succeeds
forkingthe process daemonizes (old-style); set PIDFile=
oneshotruns to completion (a script); pair with RemainAfterExit=yes
notifythe service tells systemd when it's truly ready (sd_notify)
Prefer Type=notify or Type=exec for your own daemons over forking — systemd tracks the process directly instead of guessing via a PID file, so Restart= and dependency ordering actually work.

Targets: the runlevel replacement

Intermediate A target is a synchronization point / unit group. The old numeric runlevels map to targets:

systemctl get-default                 # graphical.target or multi-user.target
systemctl set-default multi-user.target   # boot to CLI (no GUI)
systemctl isolate rescue.target       # switch now (single-user-ish)
systemctl list-dependencies multi-user.target

multi-user.target ≈ old runlevel 3 (networked, no GUI); graphical.target ≈ runlevel 5. Your service's WantedBy=multi-user.target is what makes enable start it at boot.

Timers: cron, but observable

# backup.timer
[Timer]
OnCalendar=*-*-* 02:00:00    # daily at 02:00
Persistent=true              # if the machine was off, run on next boot
RandomizedDelaySec=300       # spread load
[Install]
WantedBy=timers.target
# backup.service (Type=oneshot) does the work; the timer triggers it.
systemctl enable --now backup.timer
systemctl list-timers            # next/last run for every timer
journalctl -u backup.service     # the run's output — this is why timers beat cron

Timers win over cron because the work is a normal service: you get logs in the journal, dependency ordering, resource limits, and Persistent= catch-up — none of which cron offers.

journald: the logs

journalctl -u myapp              # one service's logs
journalctl -u myapp -f           # follow (like tail -f)
journalctl -u myapp --since "1 hour ago" -p err   # time + priority filter
journalctl -b                    # this boot;  -b -1 = previous boot
journalctl --disk-usage
journalctl --vacuum-time=7d      # trim to 7 days

Anything your service writes to stdout/stderr lands in the journal automatically — you don't need to configure log files. For persistence across reboots, ensure /var/log/journal exists (Storage=persistent in journald.conf).

Hardening a service with sandboxing

Advanced systemd can confine a service using the kernel's own facilities — often more cheaply than containers:

[Service]
# ... ExecStart etc.
DynamicUser=yes              # ephemeral user, no account to manage
NoNewPrivileges=yes          # can't gain privileges via setuid
ProtectSystem=strict         # / is read-only to this service
ProtectHome=yes              # /home, /root hidden
PrivateTmp=yes               # private /tmp
ReadWritePaths=/var/lib/myapp
CapabilityBoundingSet=       # drop ALL capabilities
MemoryMax=512M               # cgroup resource limit
CPUQuota=50%
systemd-analyze security myapp.service    # scores your hardening, flags gaps
systemd-analyze security gives each service an exposure score and tells you exactly which directives would lock it down further — a concrete, prioritized hardening checklist generated for you.

Debugging a failed service

systemctl status myapp           # Active: failed (Result: exit-code) — and why
journalctl -u myapp -e           # jump to the end of its logs
systemd-analyze blame            # what slowed the boot
systemd-analyze verify myapp.service   # lint the unit file

Common mistakes

  • Editing a unit without daemon-reload — systemd keeps running the old definition.
  • Confusing After= with Requires= — ordering is not a dependency; you usually need both.
  • Running services as root when a dedicated User= (or DynamicUser=yes) would do.
  • Editing distro-shipped units in /lib/systemd — a package update overwrites them. Override with systemctl edit (drop-in in /etc/systemd/system/*.d/) instead.
  • Using Type=forking for a modern app that doesn't actually fork, so systemd thinks it died.
  • Reaching for cron for scheduled jobs when a timer gives you logs, ordering, and catch-up.

Exercises

  • Write a .service for a simple script, enable it, crash it on purpose, and confirm Restart=on-failure brings it back (watch with journalctl -f).
  • Create a .timer + oneshot service that runs every 2 minutes, then inspect it with systemctl list-timers and read a run's output in the journal.
  • Use systemctl edit to add a drop-in override that changes an environment variable on an existing service, without touching the original unit.
  • Harden your service with ProtectSystem, PrivateTmp, NoNewPrivileges, and a MemoryMax, then run systemd-analyze security and improve the score.
  • Change the default target to multi-user.target, reboot (in a VM), and confirm no GUI starts; then switch back.

Mini-project

Package a small web app as a production-grade systemd service: a .service with a dedicated DynamicUser, Restart=on-failure, an EnvironmentFile for config, full sandboxing (ProtectSystem=strict, PrivateTmp, dropped capabilities, ReadWritePaths for its data dir) and cgroup limits (MemoryMax, CPUQuota). Add a .timer + oneshot companion that backs up its data nightly with Persistent=true, verify everything through journalctl, score it with systemd-analyze security, and write the override as a drop-in so a package update can't clobber it.
