Everything running on a Linux box is a process, and the long-lived ones you care about — web servers, databases, your own app — are managed as services by systemd. This lesson covers inspecting what is running (ps, top, htop), sending signals to control or stop a process (kill, SIGTERM vs SIGKILL), keeping work running after you log off (jobs, bg, fg, nohup), and driving services with systemctl.

Seeing what is running

Beginner ps takes a one-time snapshot; top and htop refresh live. The aux flags to ps are the ones everyone memorises: all users, user-oriented columns, including processes with no controlling terminal (x).

ps aux | head -3
# -> USER   PID %CPU %MEM    VSZ   RSS TTY  STAT START TIME COMMAND
# -> root     1  0.0  0.1 168140 11236 ?    Ss   09:12 0:03 /sbin/init
# -> ada   3120  0.4  1.2 998220 50104 ?    Sl   10:55 0:11 node server.js

# Find a specific process (the grep -v drops the grep line itself)
ps aux | grep -v grep | grep nginx
# -> www-data 814 0.0 0.3 55200 13004 ? S 09:13 0:00 nginx: worker process

# Just the PID of a named process
pgrep -f "node server.js"
# -> 3120
ColumnMeaning
PIDProcess ID — the number you pass to kill.
%CPU / %MEMShare of CPU and physical RAM.
RSSResident set size — actual RAM used, in KB.
STATState: R running, S sleeping, Z zombie, D uninterruptible.

Live views: top and htop

top        # built in everywhere; press 'M' to sort by memory, 'P' by CPU, 'q' to quit
htop       # friendlier (install it): colour bars, scroll, F9 to send a signal
The load average in top's header (e.g. 0.52 0.40 0.33) is the 1/5/15-minute average number of processes wanting the CPU. As a rough rule, a sustained load above your core count means the machine is saturated — check with nproc.

Signals and kill

Intermediate You stop or control a process by sending it a signal. The two that matter most:

SignalNumberMeaning
SIGTERM15Default. “Please shut down.” The process can catch it, flush buffers, close connections, then exit cleanly.
SIGKILL9“Die now.” Cannot be caught or ignored — the kernel kills it instantly. No cleanup.
SIGHUP1Terminal hangup; many daemons treat it as “reload your config.”
SIGINT2What Ctrl-C sends — interrupt the foreground program.
 
kill 3120          # polite: send SIGTERM, let it clean up
kill -HUP 814      # ask nginx to reload its config
kill -9 3120       # last resort: SIGKILL, no cleanup
pkill -f "node server.js"   # by command pattern instead of PID
Common mistake: reaching for kill -9 first. SIGKILL gives the process zero chance to close files, finish writes, or release locks, which can corrupt data or leave stale lock files. Always try plain kill (SIGTERM) first and only escalate to -9 if it will not exit. And be careful with pkill -f: the pattern matches the whole command line, so pkill -f node can take down more Node processes than you meant. Scope it to a single PID (kill $(pgrep -f "node server.js")) when you can.

Jobs, background, and surviving logout

Intermediate A command you start normally runs in the foreground, tying up your terminal. You can suspend it, move it to the background, and bring it back.

./long-task.sh          # runs in foreground, blocks the prompt
^Z                      # Ctrl-Z suspends it -> "[1]+  Stopped"
bg                      # resume it in the background
jobs
# -> [1]+  Running    ./long-task.sh &
fg %1                   # bring job 1 back to the foreground

# Start something in the background directly
./long-task.sh &
# -> [1] 4210            (job number and PID)

But a backgrounded job still dies when you log out (it receives SIGHUP). To outlive your session use nohup, or better, a terminal multiplexer or a systemd service:

# nohup: ignore the hangup, redirect output to a file
nohup ./server > server.log 2>&1 &
# -> nohup: ignoring input and appending output to 'server.log'

# For anything long-lived in production, DON'T use nohup — make it a service (below).

Services with systemd

Intermediate On a modern server, long-running programs are units managed by systemd, controlled through systemctl. This gives you auto-restart on crash, start-on-boot, and unified logging via journalctl — everything nohup cannot do.

CommandWhat it does
systemctl status nginxIs it running? Show recent log lines and the main PID.
systemctl start nginxStart it now.
systemctl stop nginxStop it now.
systemctl restart nginxStop then start (picks up new config/binary).
systemctl reload nginxRe-read config without dropping connections (if supported).
systemctl enable nginxStart automatically on every boot.
systemctl disable nginxDo not start on boot.
systemctl enable --now nginxEnable AND start in one step.
 
sudo systemctl status nginx
# -> * nginx.service - A high performance web server
# ->      Loaded: loaded (/lib/systemd/system/nginx.service; enabled)
# ->      Active: active (running) since Thu 2026-10-08 09:13:02 UTC; 2h ago
# ->    Main PID: 812 (nginx)
# ->       Tasks: 3 (limit: 4631)

sudo systemctl restart nginx
systemctl is-active nginx
# -> active
systemctl is-enabled nginx
# -> enabled
restart vs reload: restart fully stops and starts the service (brief downtime, always picks up changes); reload sends a signal asking it to re-read config without dropping live connections, but only works for services that support it. When in doubt, restart.

Exercises

  • Use ps aux piped through sort to find the three processes using the most memory on your machine.
  • Start sleep 300 &, list it with jobs, then terminate it with a polite kill (not -9).
  • Run top, sort by CPU with P then by memory with M, and quit with q.
  • Check whether cron (or ssh) is active and enabled on your system using systemctl is-active and systemctl is-enabled.

Mini-project: run your app as a systemd service

Take a long-running program and turn it from a fragile nohup job into a real managed service that restarts on crash and starts on boot.

sudo tee /etc/systemd/system/widgetd.service >/dev/null <<'EOF'
[Unit]
Description=Widget daemon
After=network.target

[Service]
ExecStart=/opt/widgetd/widgetd --port 8080
User=widgetd
Restart=on-failure
RestartSec=2

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload          # re-read unit files after editing
sudo systemctl enable --now widgetd   # start now + on every boot
systemctl status widgetd
# -> Active: active (running) ... Main PID: 5120 (widgetd)

# Prove the auto-restart works: kill it and watch systemd bring it back
sudo kill $(systemctl show -p MainPID --value widgetd)
sleep 3; systemctl status widgetd | grep Active
# -> Active: active (running)   (restarted automatically)

The service now survives crashes and reboots, logs to the journal (journalctl -u widgetd -f), and runs as an unprivileged user — the production-grade replacement for backgrounding a process by hand.
