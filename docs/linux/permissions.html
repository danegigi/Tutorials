Every file on Linux carries an owner, a group, and three sets of read/write/execute bits that decide who may do what. Permissions are the first line of defence on a server and the most common cause of a “permission denied” that stops a deploy cold. This lesson teaches you to read ls -l fluently, set permissions in both octal and symbolic form, change ownership, and understand the special bits (setuid, setgid, sticky) that trip people up.

Reading ls -l

Beginner The first column of a long listing is a ten-character string that encodes everything:

ls -l deploy.sh
# -> -rwxr-xr-x 1 ada devs 2048 Oct  8 11:14 deploy.sh

Break the -rwxr-xr-x apart:

PositionCharsMeaning
1-File type: - regular, d directory, l symlink, c/b device.
2-4rwxOwner (user ada) may read, write, execute.
5-7r-xGroup (devs) may read and execute, not write.
8-10r-xOthers (everyone else) may read and execute.

So this script is owned by ada, grouped under devs, runnable by everyone and writable only by ada.

What read/write/execute mean for directories

The same three bits behave differently on a directory, which surprises people:

BitOn a fileOn a directory
rRead the contents.List the names inside (ls).
wModify the contents.Create/delete/rename entries inside.
xRun it as a program.Enter it (cd) and access files by name.
A directory needs x to be entered at all. A common puzzle: you can ls a directory (it has r) but cd into it fails — it is missing x. And deleting a file depends on write permission to its directory, not to the file itself.

Octal permissions

Beginner Each permission is a number: read=4, write=2, execute=1. Sum them per role to get one digit, three digits total (owner, group, others).

OctalSymbolicTypical use
644rw-r--r--A normal file: owner edits, everyone reads.
755rwxr-xr-xA script or a directory: owner full, others run/enter.
600rw-------A private file: owner only. SSH keys, cert stores.
700rwx------A private directory, e.g. ~/.ssh.
664rw-rw-r--Shared within a group: owner and group edit.
 
chmod 644 config.yaml
chmod 755 deploy.sh
chmod 600 ~/.ssh/id_ed25519
ls -l ~/.ssh/id_ed25519
# -> -rw------- 1 ada ada 411 Oct  8 11:20 /home/ada/.ssh/id_ed25519

Symbolic chmod

When you want to add or remove one bit without recalculating the whole number, use symbolic mode: user, group, others, all, with +/-/=.

chmod +x deploy.sh          # add execute for everyone
chmod u+x,go-w script.sh    # owner can run; group/others cannot write
chmod g=rx shared/          # group gets exactly r-x
chmod -R a-w release/       # recursively make a tree read-only

Changing ownership

Intermediate chown sets the owner (and optionally the group); chgrp sets just the group. Changing an owner you do not own needs sudo.

sudo chown ada file.txt            # owner only
sudo chown ada:devs file.txt       # owner and group
sudo chown -R www-data:www-data /var/www/site   # a whole tree
sudo chgrp devs report.csv         # group only
id ada
# -> uid=1001(ada) gid=1001(ada) groups=1001(ada),1005(devs),27(sudo)
Common mistake: running a web server as root and then being baffled that files it writes are owned by root and the app cannot clean them up later. Run services as a dedicated unprivileged user (www-data, app) and chown the data directory to that user once, rather than loosening permissions with chmod 777.

umask: the default for new files

New files do not start at 777. The umask is subtracted (masked off) from the base permissions. The common umask 022 turns the file base 666 into 644 and the directory base 777 into 755.

umask
# -> 0022

touch newfile; ls -l newfile
# -> -rw-r--r-- 1 ada ada 0 Oct  8 newfile      (666 - 022 = 644)

umask 077            # stricter: new files are private (600 / 700)
touch secret; ls -l secret
# -> -rw------- 1 ada ada 0 Oct  8 secret

The special bits

Advanced Beyond rwx there are three extra bits, shown as a fourth leading octal digit (4=setuid, 2=setgid, 1=sticky).

BitOctalEffect
setuid4000Run the program as its owner, not the caller. How passwd edits /etc/shadow as root. Shows as s in the owner-execute slot.
setgid2000On a directory, new files inherit the directory's group — ideal for shared project folders. Shows as s in the group-execute slot.
sticky1000On a world-writable directory, only a file's owner may delete it. Why /tmp is safe. Shows as t in the others-execute slot.
 
ls -ld /tmp
# -> drwxrwxrwt 10 root root 4096 Oct  8 /tmp       (note the trailing t)

ls -l /usr/bin/passwd
# -> -rwsr-xr-x 1 root root 68208 /usr/bin/passwd    (note the s)

# A shared, group-sticky project directory
sudo mkdir /srv/project
sudo chgrp devs /srv/project
sudo chmod 2775 /srv/project        # setgid + rwxrwxr-x
ls -ld /srv/project
# -> drwxrwsr-x 2 root devs 4096 /srv/project
chmod 777 grants write to everyone on the system and is almost always the wrong fix for a permissions error — it is a security hole, not a solution. Find the real owner/group the process runs as and chown to it instead. If you ever type chmod -R 777 on a system path, you have likely broken something that relied on tighter permissions (SSH refuses keys that are group/world-readable, for one).

Exercises

  • Create a file, give it 640, and translate that into the rwx string from memory before checking with ls -l.
  • Make a script executable with symbolic mode (chmod +x), then remove the execute bit for group and others only.
  • Set umask 077, create a file, and confirm it came out 600. Reset your umask afterward.
  • Create a directory, set its setgid bit (chmod g+s), create a file inside it as a user in a second group, and confirm the file inherited the directory's group.

Mini-project: lock down an SSH key directory correctly

SSH silently refuses to use keys with loose permissions, so getting this right is a real, daily task. Build a correctly-permissioned ~/.ssh from scratch and prove it.

mkdir -p ~/.ssh
chmod 700 ~/.ssh                       # only you may enter it
ssh-keygen -t ed25519 -f ~/.ssh/id_demo -N ""
chmod 600 ~/.ssh/id_demo               # private key: owner read/write only
chmod 644 ~/.ssh/id_demo.pub           # public key may be world-readable
touch ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys

ls -la ~/.ssh
# -> drwx------ 2 ada ada 4096 .
# -> -rw------- 1 ada ada  411 id_demo
# -> -rw-r--r-- 1 ada ada  101 id_demo.pub
# -> -rw------- 1 ada ada    0 authorized_keys

Now deliberately break it with chmod 644 ~/.ssh/id_demo and note that ssh -i ~/.ssh/id_demo ... prints “Permissions 0644 for id_demo are too open” and refuses the key. Restore 600 and it works again — a lesson you only need to learn once.
