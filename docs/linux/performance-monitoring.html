When a server is slow, you need to know which resource is the bottleneck — CPU, memory, disk, or network — before you can fix it. Linux ships a toolbox for exactly that, and the USE method gives you a system for pointing it at the right place.

The USE method

Intermediate For every resource, check three things: Utilization (how busy?), Saturation (is work queuing?), and Errors. Walk the resources — CPU, memory, disk, network — and the bottleneck reveals itself.

ResourceUtilizationSaturation
CPUtop %us+%syload average, run queue (vmstat r)
Memoryfree usedswap in/out (vmstat si/so)
Diskiostat %utilawait, queue depth
Networksar -n DEVdrops, retransmits

CPU: top, load average, vmstat

top                        # live; press 1 for per-core, P sort by CPU, M by memory
uptime
# load average: 2.15, 1.80, 1.50   (1 / 5 / 15 min)
Reading load average: compare it to your core count. On a 4-core box, a load of 4.0 means fully busy; 8.0 means twice as much work queued as the CPU can run (saturation). Load above the core count sustained = CPU-bound. (Note: on Linux, load also counts tasks blocked on disk I/O, so a high load with low CPU% often means disk, not CPU.)
vmstat 1 5                 # 5 samples, 1s apart
#  r  b   swpd   free   si  so    bi    bo   in   cs us sy id wa
#  r = runnable queue (CPU saturation)   wa = % waiting on I/O (disk pressure)
#  si/so = swapping (memory pressure — bad if nonzero sustained)

Memory: free and the cache trick

free -h
#               total   used   free   shared  buff/cache   available
# Mem:           16Gi  4.0Gi  1.0Gi    200Mi       11Gi        11Gi
The #1 memory misread: panicking that "free" is low. Linux deliberately uses spare RAM for disk cache (buff/cache) and reclaims it instantly when apps need it. The number that matters is available, not free. Real memory pressure shows up as swap activity (vmstat si/so > 0) and the OOM killer in dmesg, not a low "free".

Disk: iostat

iostat -xz 1               # extended, 1s (from the sysstat package)
# Device  r/s  w/s  rkB/s  wkB/s  await  %util
#   %util near 100% + high await = the disk is the bottleneck
#   await = avg ms per I/O; rising await under load = saturation

Network: ss and sar

ss -s                      # socket summary (established, time-wait…)
ss -tnp                    # per-connection, with the owning process
sar -n DEV 1               # per-interface throughput + errors/drops
sar -n TCP,ETCP 1          # TCP retransmits (retrans/s = trouble)

Per-process: what's eating it?

top -o %CPU                # or press P in top
ps aux --sort=-%mem | head # top memory consumers
pidstat 1                  # per-process CPU/IO over time
iotop                      # per-process disk I/O (needs root)

Historical data: sar

Live tools show now; sar (sysstat) records metrics on a schedule, so after an incident you can look back: sar -u -f /var/log/sysstat/sa15 shows CPU for the 15th. Install sysstat on servers so you're not blind to "what happened at 3am".

Exercises

  • Run vmstat 1 while compiling something; identify when the run queue (r) and I/O wait (wa) spike.
  • Explain to a colleague why free showing little "free" memory is usually fine (point at "available").
  • Use iostat -xz 1 under a disk-heavy task and read %util + await.

Mini-project: diagnose a slow server

On a test box, generate three different pressures — a CPU hog (yes >/dev/null &), a memory hog, and a disk hog (dd) — and for each, use the USE method to correctly identify the bottleneck resource from top/vmstat/free/iostat before you know which hog is running. Write the decision tree as a troubleshooting runbook; it's the hands-on complement to the DevOps Observability lesson.
