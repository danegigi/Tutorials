Disks fill up, mounts drop, and "no space left on device" takes down services. Learn to see what's using space, how block devices and filesystems fit together, how to mount things persistently via /etc/fstab, and the basics of LVM for flexible storage.

How full is it? df and du

df -h                      # free space per MOUNTED filesystem (human-readable)
# Filesystem   Size  Used Avail Use% Mounted on
# /dev/sda1     40G   32G  6.0G  85% /

du -sh /var/log            # total size of a directory
du -h --max-depth=1 /var | sort -rh | head   # biggest subdirectories
df -i                      # INODES — you can be "full" with free space (too many files)
Two "disk full" surprises: (1) df shows space free but writes still fail — you're out of inodes (df -i); millions of tiny files did it. (2) You delete a huge log but space doesn't come back — a process still holds the file open. Find it with lsof +L1 (or lsof | grep deleted) and restart/signal that process; the space frees when the last handle closes.

Block devices and partitions

lsblk                      # tree of disks → partitions → mountpoints
# NAME   SIZE TYPE MOUNTPOINT
# sda    50G  disk
# ├─sda1 40G  part /
# └─sda2 10G  part /home
sudo fdisk -l              # detailed partition tables
blkid                      # UUIDs + filesystem types (use UUIDs in fstab)

Filesystems and mounting

Intermediate

sudo mkfs.ext4 /dev/sdb1            # create an ext4 filesystem (ERASES the partition)
sudo mkdir /mnt/data
sudo mount /dev/sdb1 /mnt/data     # mount it (temporary — gone on reboot)
mount | grep sdb1                  # confirm
sudo umount /mnt/data              # unmount
mkfs destroys all data on the target — triple-check the device name (lsblk) before running it; formatting the wrong disk is unrecoverable. A manual mount does not survive a reboot — for that you need /etc/fstab.

Persistent mounts: /etc/fstab

# /etc/fstab — mounted automatically at boot
# <device>                              <mount>     <fs>  <options>        <dump> <pass>
UUID=1a2b-3c4d                           /mnt/data   ext4  defaults          0      2

sudo mount -a      # test fstab WITHOUT rebooting — mounts everything listed
Always use UUID=, not /dev/sdb1, in fstab — device names (sdb vs sdc) can change between boots, and a bad fstab entry can make the system fail to boot. After editing, run sudo mount -a to catch typos while you can still fix them.

Swap

free -h                    # see RAM and swap usage
swapon --show
# Add a swap file:
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
# Persist it in /etc/fstab:  /swapfile none swap sw 0 0

LVM: flexible volumes

Advanced LVM sits between disks and filesystems so you can resize and span volumes without repartitioning: physical volumes → volume groups → logical volumes.

sudo pvcreate /dev/sdb /dev/sdc           # mark disks as PVs
sudo vgcreate data-vg /dev/sdb /dev/sdc   # pool them into a VG
sudo lvcreate -L 20G -n app data-vg       # carve a 20G logical volume
sudo mkfs.ext4 /dev/data-vg/app
# Grow it later with no downtime:
sudo lvextend -L +10G /dev/data-vg/app && sudo resize2fs /dev/data-vg/app

Exercises

  • Find the three largest directories under /var with du --max-depth=1 | sort -rh.
  • Simulate "disk full with free space" reasoning: run df -i and explain what inodes are.
  • Add a persistent mount to /etc/fstab by UUID and verify it with sudo mount -a.

Mini-project: diagnose and fix a full disk

On a test VM, fill a disk (write a big file or many tiny ones), then play incident responder: use df -h/df -i to classify space-vs-inode exhaustion, du to find the culprit, and lsof | grep deleted to catch a held-open deleted file. Then add a second disk, format it, mount it persistently by UUID, and (bonus) put it under LVM so it can grow later. Write up the diagnosis as a runbook (ties to the DevOps incident lesson).
