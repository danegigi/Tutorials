The Generics Deep Dive covered the mechanics — constraints, the tilde, inference. This lesson is about shipping generic code: the small set of patterns that actually earn their keep in real codebases, the standard-library packages that already give you most of what you'd reach for generics to build, and the honest cases where a plain interface or even a little duplication is the better engineering call.

Start with the stdlib — most generic code is already written beginner

Before writing a generic function, check whether Go 1.21+ already ships it. The slices and maps packages replace a huge amount of hand-rolled generic plumbing:

import (
    "slices"
    "maps"
    "cmp"
)

nums := []int{3, 1, 2}
slices.Sort(nums)                      // [1 2 3]
i, ok := slices.BinarySearch(nums, 2)  // 1, true
slices.Contains(nums, 3)               // true
max := slices.Max(nums)                // 3

// Sort structs by a field without writing a Less func:
type User struct{ Name string; Age int }
users := []User{{"Ada", 36}, {"Linus", 25}}
slices.SortFunc(users, func(a, b User) int { return cmp.Compare(a.Age, b.Age) })

keys := slices.Collect(maps.Keys(m)) // iterator → slice (Go 1.23+)
Reach for slices, maps, and cmp first. Writing your own generic Contains or Map helper in 2026 is usually re-inventing something the stdlib already optimized and tested.

Constraints packages & type sets intermediate

A constraint is an interface describing which types are allowed. cmp.Ordered covers everything comparable with <; for arithmetic you define a type set with the ~ (tilde) operator so it also matches named types whose underlying type matches:

type Number interface {
    ~int | ~int64 | ~float64 // ~ ⇒ also matches `type Celsius float64`
}

func Sum[T Number](xs []T) T {
    var total T // zero value of whatever T is
    for _, x := range xs {
        total += x
    }
    return total
}

Sum([]int{1, 2, 3})          // 6
type Celsius float64
Sum([]Celsius{20.5, 21.0})   // works thanks to ~float64

Type inference means callers almost never write the type argument explicitly — Sum([]int{...}), not Sum[int]([]int{...}).

The three patterns that pay off intermediate

1. Generic containers — a type-safe stack/set/queue with no any boxing and no per-call type assertions:

type Set[T comparable] struct{ m map[T]struct{} }

func NewSet[T comparable]() *Set[T] { return &Set[T]{m: make(map[T]struct{})} }
func (s *Set[T]) Add(v T)           { s.m[v] = struct{}{} }
func (s *Set[T]) Has(v T) bool      { _, ok := s.m[v]; return ok }
func (s *Set[T]) Len() int          { return len(s.m) }

ints := NewSet[int]()
ints.Add(1); ints.Has(1) // true — fully type-checked, no interface{}

2. Transform helpers — Map/Filter/Reduce over slices (only when the stdlib doesn't already have it):

func Map[T, U any](in []T, f func(T) U) []U {
    out := make([]U, len(in))
    for i, v := range in { out[i] = f(v) }
    return out
}
names := Map(users, func(u User) string { return u.Name })

3. Removing "copy-paste for each type" code — the single best reason to use generics. If you have Int64Ptr, StringPtr, BoolPtr helpers, collapse them:

func Ptr[T any](v T) *T { return &v } // one func replaces N

When NOT to use generics advanced

Generics are a tool, not a goal. Prefer a plain interface when behavior — not the concrete type — is what varies:

// Generics: WRONG tool. You only call a method; the type doesn't matter.
func WriteAll[T io.Writer](ws []T, p []byte) { for _, w := range ws { w.Write(p) } }

// Interface: RIGHT. Simpler, and accepts a heterogeneous slice.
func WriteAll(ws []io.Writer, p []byte) { for _, w := range ws { w.Write(p) } }

Rules of thumb from the Go team's own guidance:

  • Use generics when the function body is identical across types and only the type differs (containers, Map, numeric helpers).
  • Use an interface when different types need different behavior for the same operation.
  • If you'd write a generic function with a single type parameter used only as a method receiver — you want an interface.
  • A little duplication is cheaper than a confusing generic signature. Don't make callers read func F[T C1, U C2, V comparable](...) to save three lines.
You cannot write generic methods with their own type parameters (only the receiver type can be parameterized), and generics do not give you specialization/overloading. If you find yourself fighting the type system to express "this but faster for ints", stop — that's a sign generics is the wrong fit.

Common mistakes

  • Re-implementing slices/maps. Your hand-rolled Contains[T] is slower to maintain and no faster than slices.Contains.
  • Forgetting the tilde. int | float64 rejects type Celsius float64; ~int | ~float64 accepts it. Named types are common in real code.
  • Using generics where an interface is clearer. If the body only calls methods, you wanted an interface all along.
  • Over-parameterizing. Three type parameters with three constraints is usually a design smell; split the function or accept a small amount of duplication.
  • Assuming zero-value equals "empty". var zero T is the zero value, which for pointers is nil and for structs is all-fields-zero — handle it explicitly if "unset" matters.

Exercises

  1. Rewrite a set of FooPtr/BarPtr helpers in a codebase (or invent three) into a single generic Ptr[T].
  2. Implement Filter[T any](in []T, keep func(T) bool) []T and a Reduce[T, U any]. Then find out how many of your use cases slices already covers.
  3. Build a generic OrderedMap[K cmp.Ordered, V any] that iterates keys in sorted order. Decide where generics help and where a plain map + slices.Sort on the keys is simpler.
  4. Take a generic function you wrote and argue, in two sentences, whether an interface would have been clearer. Rewrite it if the answer is yes.

Mini-project: a type-safe in-memory cache

Build Cache[K comparable, V any] with Get(k) (V, bool), Set(k, v), Delete(k), and a GetOrCompute(k, func() V) V that fills misses atomically (guard with a sync.Mutex). Make it work for Cache[string, User] and Cache[int, []byte] with no changes. Then write a short note: which parts genuinely needed generics (the typed V return with no assertion) and which could have been a plain map[string]any — and why the generic version is worth it here.
