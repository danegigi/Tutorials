The modules lesson covered go.mod and adding dependencies. This one handles the situations that trip up real projects: pointing a dependency at a fork or local copy, vendoring for reproducible builds, pulling private modules through auth, understanding how Go picks versions, the major-version suffix rule, and publishing your own module.

How Go actually selects versions

Intermediate Go uses Minimal Version Selection (MVS): for each dependency, it picks the highest version required by anything in the build graph — not the newest that exists. This makes builds reproducible: adding a new dependency can't silently upgrade an unrelated one. go.sum records cryptographic hashes so a tampered or changed module is rejected.

go list -m all              # the full resolved build list (what MVS chose)
go mod graph                # the dependency graph (who requires what)
go mod why golang.org/x/text   # why is this module in my build?
go.sum is not a lockfile in the npm sense — go.mod's require lines + MVS already make the build deterministic. go.sum is an integrity record. Commit both; never hand-edit go.sum.

replace: fork, fix, or go local

// go.mod
require github.com/some/lib v1.4.0

replace github.com/some/lib => github.com/myfork/lib v1.4.1-patch
replace github.com/some/lib => ../lib          // a local checkout, for development
replace github.com/some/lib => github.com/some/lib v1.3.0  // pin DOWN a transitive dep

Use replace to test a fix in a dependency before it's released, develop two modules side by side, or force a transitive dependency to a specific version. exclude blocks a specific bad version from selection.

A replace pointing at a local path does not travel — anyone who imports your module gets no benefit and a path that doesn't exist on their machine. replace is for your builds; remove local-path replaces before tagging a release. For side-by-side local dev, prefer a go.work workspace (see the Modules & Packages lesson) which keeps the replaces out of go.mod entirely.

Vendoring

go mod vendor      # copies all deps into ./vendor
go build           # auto-uses ./vendor when it exists (or -mod=vendor)
go mod verify      # confirm vendored copies match go.sum

Vendoring commits your dependencies' source into the repo. Trade-off: builds work with zero network and you can audit exactly what ships, at the cost of a larger repo and manual go mod vendor after dependency changes. Common in regulated/air-gapped environments and some monorepos; many teams skip it and rely on the module proxy + go.sum.

Private modules

Advanced By default Go fetches modules through the public proxy (proxy.golang.org) and checks them against the checksum database (sum.golang.org). Private repos must bypass both:

# Tell Go these paths are private: skip proxy AND sumdb
go env -w GOPRIVATE=github.com/mycompany/*,gitlab.internal/*

# Make git use SSH / a token for the fetch
git config --global url."git@github.com:".insteadOf "https://github.com/"
# or a token:  ~/.netrc  with machine github.com login x password <TOKEN>

Related knobs: GONOPROXY (fetch directly, not via proxy), GONOSUMCHECK/GONOSUMDB via GONOSUMCHECK→GONOSUMDB→GOFLAGS; in practice GOPRIVATE sets sensible defaults for both GONOPROXY and GONOSUMDB.

The classic private-module failure is a 410 Gone or verifying module: ... checksum database error — Go tried the public proxy/sumdb for your private repo. Setting GOPRIVATE is what fixes it, plus git auth for the actual clone.

Major versions: the v2+ rule

Go's "import compatibility rule": a breaking change means a new major version, and v2+ carries the major in both the module path and the import path.

// go.mod of the LIBRARY, at v2+
module github.com/me/lib/v2

// consumers import it WITH the suffix
import "github.com/me/lib/v2"
require github.com/me/lib/v2 v2.1.0
This is why you'll see /v2, /v3 in import paths. v0 and v1 use no suffix. The suffix lets a build depend on v1 and v2 of the same library simultaneously (they're different module paths), which is how large upgrades happen incrementally.

Publishing a module

# 1. Make the module path match the repo URL
module github.com/me/greet

# 2. Tag a semver release and push the tag
git tag v1.0.0
git push origin v1.0.0

# 3. Consumers just: go get github.com/me/greet@v1.0.0
# 4. (optional) warm the proxy / docs:
GOPROXY=proxy.golang.org go list -m github.com/me/greet@v1.0.0

No registry upload step — Go modules are fetched straight from your tagged VCS repo (via the proxy's cache). The tag is the release. Follow semver strictly: breaking change → new major (with the path suffix).

Common mistakes

  • Leaving a local-path replace in a tagged release — it breaks every consumer. Use go.work for local dev instead.
  • Forgetting the /v2 suffix on both the module path and imports when releasing v2 — consumers can't get the new major, or get v1 forever.
  • Not setting GOPRIVATE for internal modules, then fighting proxy/sumdb 410 errors.
  • Hand-editing go.mod/go.sum instead of letting go get/go mod tidy manage them.
  • Expecting go get -u to behave like npm — MVS picks minimal versions; -u is an explicit opt-in to upgrade.
  • A module path that doesn't match the repo — then go get can't find it.

Exercises

  • Add a dependency, then run go mod why and go mod graph to trace why a transitive dependency is in your build.
  • Fork a small library, make a one-line fix, and use a replace to build your program against the fork; then switch the replace to a local path.
  • Run go mod vendor, delete your module cache, disconnect from the network, and confirm the build still works from ./vendor.
  • Create a private repo, set GOPRIVATE + git auth, and successfully go get it from another module.
  • Publish a trivial module: tag v1.0.0, consume it from a second module, then make a breaking change and release it correctly as v2 with the path suffix.

Mini-project

Create and publish a small reusable library module (e.g. a greet package) to a public repo: write it, document it, tag v1.0.0, and consume it from a separate program via go get. Then evolve it: ship a backward-compatible v1.1.0, and a breaking v2.0.0 done correctly (module path /v2, import path updated), proving a single consumer can depend on both majors at once. Finally, set up a private variant: a second module in a private repo reachable only with GOPRIVATE + git auth, and document the exact env/config a teammate needs to build it.
