The Structs lesson introduced generics; this goes deeper: writing real constraints, generic data structures, how type inference actually works, the limits of Go generics, and — most importantly — when a plain interface or function is the better choice.

Type parameters and constraints

// A constraint is an interface describing a SET of types.
type Ordered interface {
	~int | ~int8 | ~int16 | ~int32 | ~int64 |
	~uint | ~uint8 | ~uint16 | ~uint32 | ~uint64 |
	~float32 | ~float64 | ~string
}

func Max[T Ordered](a, b T) T {
	if a > b { return a }
	return b
}
Max(3, 7)        // T inferred: int → 7
Max("a", "b")    // T inferred: string → "b"

Intermediate The ~int syntax means "any type whose underlying type is int" — so a type Celsius float64 satisfies ~float64. Without the tilde, only the exact type matches. Most useful constraints already exist in golang.org/x/exp/constraints (Ordered, Integer, Signed…).

The two built-in constraints

any          // alias for interface{} — matches every type
comparable   // types usable with == and != (map keys, set elements)

func Contains[T comparable](s []T, x T) bool {
	for _, v := range s { if v == x { return true } }
	return false
}

Generic data structures

type Stack[T any] struct { items []T }

func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }
func (s *Stack[T]) Pop() (T, bool) {
	var zero T
	if len(s.items) == 0 { return zero, false }
	v := s.items[len(s.items)-1]
	s.items = s.items[:len(s.items)-1]
	return v, true
}

var s Stack[string]
s.Push("a"); v, ok := s.Pop()   // "a", true
Note var zero T — the generic way to produce "the zero value of whatever T is" (0, "", nil, or the zero struct). You can't write a literal because you don't know the type, so var zero T is the idiom for a generic default/not-found return.

Generic functional helpers

func Map[T, U any](s []T, f func(T) U) []U {
	out := make([]U, len(s))
	for i, v := range s { out[i] = f(v) }
	return out
}
func Filter[T any](s []T, keep func(T) bool) []T {
	var out []T
	for _, v := range s { if keep(v) { out = append(out, v) } }
	return out
}
nums := []int{1, 2, 3, 4}
evens := Filter(nums, func(n int) bool { return n%2 == 0 }) // [2 4]
strs := Map(evens, func(n int) string { return fmt.Sprint(n) }) // ["2" "4"]

Type inference and its limits

Advanced Go infers type parameters from the arguments, not from the return type. When it can't, specify them explicitly:

// Can't infer U from args alone (it's only in the return position sometimes):
result := Map[int, string](nums, strconv.Itoa)   // explicit when needed

// Methods cannot have their OWN type parameters — only the type can.
// func (s Stack[T]) MapTo[U any]() ...  // ← NOT allowed in Go
Known limits: (1) methods can't introduce new type parameters (put them on package-level functions instead). (2) No generic specialization/overloading. (3) A constraint union can't mix types with different method sets freely. These catch people coming from C++/Rust/TypeScript generics.

When NOT to use generics

The official guidance: if you'd write the same code regardless of type (collections, map/filter), generics help. If the behavior differs per type, you want an interface, not a type parameter. And if you're writing it once for one type, just write it concretely — generics add cognitive cost. "Write code, not types"; reach for generics when you see yourself copy-pasting a function that differs only in a type.
// Interface is RIGHT here — behavior differs per implementation
type Shape interface { Area() float64 }

// Generics would be WRONG — you'd just be hiding a type switch

Exercises

  • Write a generic Keys[K comparable, V any](m map[K]V) []K and a Values counterpart.
  • Implement a generic Set[T comparable] with Add, Has, and Len backed by a map.
  • Take a function you've duplicated for int and float64 and unify it with an Ordered constraint — then argue whether it was worth it.
